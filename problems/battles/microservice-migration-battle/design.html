問題の物理構成

EC2 1 台 (t3.small / Amazon Linux 2023) に docker compose で 4 コンテナ:

コンテナimage役割port
nginxnginx:1.27-alpine frontend (= 唯一の外部公開)、3 サービスへの reverse proxy80
usersbuild (Python 3.12) FastAPI、score/meta/health endpoint8000 (内部)
ordersbuild (Python 3.12) 同上、ただし legacy は N+1 風 sleep8000 (内部)
catalogbuild (Python 3.12) 同上、legacy は cache 同期 sleep8000 (内部)

nginx が /users/ /orders/ /catalog/ を各サービス (http://<name>:8000/) に proxy。EC2 SG は port 80 のみ ingress。

VPC は per-team で新規作成 (= 10.99.0.0/16)、Subnet 1 つ + IGW + Route Table。 SSM Session Manager 用 IAM Role はあり (= 運営デバッグ用)、competitor 側からは触れない。

仕掛け (= "答え" の中身)

① 各サービスに仕込んだ legacy endpoint

3 サービス共通インターフェイス:

  • GET /score — 高速経路。即座にレスポンス。
  • GET /score?legacy=true — 意図的な遅延経路。スコアエンジンが切替フェーズで叩きにくる。
サービス遅延の仕組み修正方針 (= 答え)file
users time.sleep(2.0) 単発 _legacy_score() 内の time.sleep を削除して _fast_score() と統合 services/users/main.py:64
orders 5 回ループで time.sleep(0.45) = 合計 2.25 秒 (= N+1 風) ループ自体を削除し random ベースの集計を 1 回にまとめる services/orders/main.py:65-72
catalog 「外部キャッシュ更新」のフリをする time.sleep(2.2) cache を non-blocking にする (= sleep を削除、async タスクへ) services/catalog/main.py:64

3 つとも legacy 関数の 戻り値は fast 関数と等価 (= 機能的には同じ)。 唯一の違いは応答時間。これにより「スコアエンジンが切り替えても返る値の妥当性チェックは 通る、ただし応答時間からスコアが下がる」という設計になる。

② プラットフォーム自己申告

GET /meta が {"service": "...", "platform": "ec2|lambda|ecs|apprunner", "version": "..."} を返す。platform は環境変数 TC_PLATFORM で制御。

初期値 (= EC2 docker compose) では TC_PLATFORM=ec2。競技者が Lambda に 移植したら TC_PLATFORM=lambda を設定すれば /meta が変わり、 スコアエンジンが「Lambda にマイクロサービス化された」と判定して大幅加点に切り替わる。

cross-validate (= DNS pattern や response header) は MVP ではしない。Battle は チーム間で互いを攻撃しないので緩めで良いと判断 (ADR-008 v2 D6 と整合)。

スコアリング仕様

スコアエンジンは 1 分毎に各登録 endpoint を polling し、以下のルールで加減算する。

状態判定1 check (1分) あたり
endpoint 未登録 / 200 以外 / timeout HTTP status != 200 or no response in 5s -100
EC2 上 (劣化前) /meta.platform == "ec2" and 応答 < 500ms +100
EC2 上 (劣化後 = degradationMinutes 経過) 同上、ただしフェーズ判定で adjust +10
Lambda + API GW にマイグレ済 /meta.platform == "lambda" +1,000
ECS Fargate にマイグレ済 /meta.platform == "ecs" +1,000
App Runner にマイグレ済 /meta.platform == "apprunner" +1,000
3 サービス全分離達成 (= 一括ボーナス) 3 endpoint の platform が全て ec2 以外 +5,000 (1 回限り)
遅延 endpoint (応答 > 1.5s) を返した 切替フェーズ後の /score?legacy=true に対して +10

劣化前 1 時間放置 (3 endpoint 登録済): 60 × 100 × 3 = 18,000 / h
劣化後 1 時間放置: 60 × 10 × 3 = 1,800 / h (= 10 分の 1)
30 分で 1 サービスを Lambda に移行: 30 × 100 × 3 + 30 × (100 × 2 + 1000 × 1) = 9,000 + 36,000 = 45,000 / 1h

→ 1 サービスでも分離すれば EC2 滞在を大きく上回る = 強い移行インセンティブ。

競技タイムライン (= デフォルト値)

T+0 min — 競技開始

deploy 完了直後

3 サービスが EC2 で稼働中。endpoint URL が払い出され、競技者が participant-portal で 3 endpoint を登録する。
登録しないと -100/min の出血。

T+0〜60 min — EC2 通常フェーズ

degradationMinutes まで

EC2 のままでも +100/min × 3 = 18,000/h の高加点。ただしマイクロサービス化すれば +1,000/min × 3 = 180,000/h で 10 倍差。
最初の 1 サービス分離を 30 分以内に終わらせるのが目安。

T+60 min — EC2 劣化フェーズ開始

degradationMinutes 到達

スコアエンジンが「EC2 上の endpoint」を発見すると加点を +10/min に下げる (= 90% 減)。EC2 残留チームのスコア急減。Battle Portal の timeline で「EC2 劣化フェーズに入りました」と通知。

T+87 min — 遅延切替の 3 分前告知

legacySwitchMinutes - 3

「3 分後に legacy endpoint への切替が起きます」と Battle Portal に告知。

T+90 min — 遅延 endpoint 切替フェーズ

legacySwitchMinutes 到達

スコアエンジンが polling 対象を /score → /score?legacy=true に切り替える。事前にコード修正していないと、応答 > 1.5s 判定で +10/min まで落ちる。
修正方針: コード読み → time.sleep / N+1 ループを取り除き → 再デプロイ。Lambda / ECS / App Runner どこに乗っていても作業は同じ (= ソース修正 + redeploy)。

T+120 min — 競技終了

合計 2 時間

累積スコアでランキング。3 サービスを早期に異なる 3 ホスティングに分離 + 遅延修正完了したチームが上位。

期待される攻略順序 (= 想定解の 1 つ)

  1. T+0〜10 min: deploy 完了確認 / 3 endpoint を participant-portal に登録 / コードを cat (= 仕掛けの存在に気づく)
  2. T+10〜30 min: 最も簡単な users サービスを AWS App Runner に乗せる (= source-deploy 1 発で公開可、最短)
  3. T+30〜55 min: orders を Lambda + API Gateway に乗せる (= FastAPI を Mangum でラップして lambda handler 化)
  4. T+55〜80 min: catalog を ECS Fargate に乗せる (= 一番設定が重いが、長時間稼働 / VPC 統合の練習になる)。3 サービス全分離ボーナス +5,000 を取りに行く
  5. T+80〜90 min: 各サービスのコードから legacy 遅延処理を取り除く → 再デプロイ。切替前に間に合わせる
  6. T+90〜120 min: 残時間で安定運用。失敗 endpoint があれば修正

もちろん別解も可能 (= 全部 Lambda、全部 App Runner 等)。ホスティング多様性ボーナスは ない (= ADR レベルで「学習目的」に多様性を強く要請しているが、スコアでは強制しない)。

運営側スコアエンジン (= 別 PR、現時点未実装)

本 PR では 問題テンプレート部分のみ 実装。スコアエンジン (= 1 分毎 polling Lambda + endpoint 登録 UI) は次 PR に分離する。理由:

  • endpoint 登録 → polling → スコア event 配信は 他 Battle でも使い回せる共通基盤 になりうる (= microservice-migration-battle 専用にしない)
  • 本 PR の INVARIANT_PR_SHIPS_WORKING_INCREMENT は「3 サービスが立ち上がって /score が叩ける」で満たせる (= スコアエンジン無しでも観察可能)
  • スコアエンジンの実装は ADR-008 v2 Phase 4 (= 検証パイプライン) と同じく独立した複雑性

次 PR で作るスコアエンジン (= 設計案)

  • EventBridge Scheduler で 1 分毎に Polling Lambda を起動
  • DDB EndpointRegistry table (PK: TenantId#TeamId, SK: SLOT#1|2|3)
  • Polling Lambda が各 endpoint を fetch → ScoreEvent 発行 → 既存 score stream に乗せる
  • participant-portal に endpoint 登録 UI (3 slot)
  • Battle Portal の timeline card に「次フェーズまでの残り時間」を表示

microservice-migration-battle 以外の今後の Battle (= 「N 個の endpoint を polling してスコアを増減」型) でも同じ仕組みを使えるよう、generic な polling 基盤 として切り出す。

ホスティング移植のヒント (= 競技者向けには公開しない)

users → AWS App Runner

$ apprunner create-service \
    --service-name tc-users \
    --source-configuration '{
      "AutoDeploymentsEnabled": false,
      "ImageRepository": {
        "ImageIdentifier": "<your-ecr>/users:latest",
        "ImageRepositoryType": "ECR",
        "ImageConfiguration": {
          "Port": "8000",
          "RuntimeEnvironmentVariables": { "TC_PLATFORM": "apprunner" }
        }
      }
    }'

App Runner は ECR から自動 pull → URL 即発行。所要 5〜10 分。

orders → Lambda + API Gateway

FastAPI を Lambda で動かすために mangum を入れる:

# requirements.txt に追加
mangum==0.17.0

# main.py に追加
from mangum import Mangum
handler = Mangum(app)

Lambda は container image で deploy (Python 3.12 base image + uvicorn は不要、mangum が ASGI を Lambda event に変換)。

catalog → ECS Fargate

標準的な手順 (Task Definition + Service + ALB)。VPC / ENI / Target Group が必要な分、3 つの中で最も config が重い。

Open Questions

  1. 遅延の閾値 1.5s が妥当か: orders の N+1 ループは合計 2.25s なので 1.5s 閾値で正しく検出される。users / catalog の 2.0s / 2.2s も同様。閾値を 1.0s に 下げると network jitter で false positive のリスクあり
  2. EC2 劣化の実装方法: tc qdisc で latency 注入 vs サービス 側で「/var/run/tc-degraded flag が存在したら sleep」分岐。後者は プラットフォーム移植性が高い (= Lambda / ECS でも動く) が、移植したら劣化の影響を 受けないので「マイグレーションのインセンティブ」としては正しい
  3. 3 サービスの 1 つだけ移行した時のスコアバランス: 例の試算は妥当か microservicePoints を 800 に下げる / EC2 通常を 80 に下げる等で調整可
  4. scoring engine を本問題に inline するか generic 基盤として切り出すか: 本ドキュメントでは後者を推奨 (= 別 PR)。ただし microservice-migration-battle 専用の 仕様 (= platform 判定 / フェーズ進行) もあるので、「generic polling + 問題ごとの scoring config」 の分離設計が必要
  5. 競技者がコードを書き換える前提なので、本体 repo の services/ を直接書き換えると 他チームに影響: 各チームは 自分の AWS account 内で 編集 (= EC2 上の /opt/tenkacloud/repo/.../services/ を vim) するので影響なし。 ただし git fetch がレースする可能性 → UserData は初回 clone 時のみ実行、再起動しても git pull しない設計にする

Vibe Coding 時代の壁

AI で“動くもの”はもう作れる。
詰まるのは、その先だ。

Claude でアプリは 1 時間で立つ。だが本番に出す瞬間、全員が同じ壁にぶつかる:

🔐 認証 / 認可

とりあえず Basic 認証。SSO も権限分離も後回しのまま公開できない。

🛡️ セキュリティ

公開 S3、ワイルドカード IAM、秘密鍵の commit、レート制限なし。

📊 運用 / 監査

ログは標準出力だけ。落ちても気づけない。監査に出せない。

「AI が書く速さに、“安全に公開する”側が追いつけていない。」
— これは個人開発者も、社内 Platform チームも、まったく同じ構図。
03

TenkaCloud とは

その壁の越え方を、
採点付きの演習にする OSS。

スライドでも野放しのサンドボックスでもない。本物の AWS に問題を deploy し、毎分採点し、順位を出す。

⚔️ Battle

リアルタイム対戦。ヘルスプローブが全チームを毎分叩く。生き残った Platform チームが勝つ。

🎯 Challenge

自分のペースで 1 サービスずつ深掘り。flag 提出で採点。

moat = 問題はプラグイン

1 問題 = metadata.json + template.yaml（CFn ペライチ）+ 任意の portal 部品。 platform は host、問題は plugin（ADR-012）。一度書いた問題は、再利用できる資産になり、コミュニティで育つ。

旗艦シナリオ — BootCamp で検証する本体

StackStack — AI → Production ラストワンマイル

あなたは Platform チーム。AI Builder 100 人が量産したアプリが、5 つの統制軸すべて未整備・EC2 1 台同居で積まれている。 90–120 分で“公開していい状態”に持っていけ。

slot統制軸初期（EC2）hardened（managed）
auth認証 / 認可naive Basic 認証Cognito / SSO
networkS3 / WAF / IAM公開 S3 + ワイルドカード IAMOAC + 絞った IAM
rateレート制限 / DoS無制限 FlaskAPI GW throttle
auditログ / 監査標準出力のみCloudTrail + Athena + WORM
ux可用性EC2 1 台Multi-AZ + ALB + Auto Scaling

EC2 = 100pt/分 → managed runtime に切り出すと 1,000pt/分。 5 slot 全部 managed で +30,000pt（“production-ready” 認定、1 回）。 30 / 60 / 90 分で「公開期限」「PII 監査」「障害対応」フェーズが襲ってくる。

06

赤チーム / 障害注入 — 実態（誇張なし）

「混乱を注入する」 仕組みは、もう動いている。

実証済 hello-world-battle の frontend-down

operator が fire → EventBridge → executor Lambda が SSM SendCommand で nginx を停止 → failurePenalty -100 がスコア履歴に “谷” として現れる → 既定時間で 自動復帰。 fire → 減点 → 復帰を実機で確認済み。ゲームが詰まることはない（idempotent な auto-revert）。

実装済 StackStack の組織イベント — 5 件すべて実体化

注入 2 件（.env 流出 / AI が秘密鍵を commit）は実 SSM action で該当 slot を停止し強制 revert（ADR-031）。 減点 3 件（CEO 5000 人デモ / MFA 必須化 / Legal PII）は採点 tick で実減点し、window 経過で自動失効（ADR-033、#1668 出荷済）。 残るは 本番イベントでの通し検証のみ。

  • 実装中 inter-team coordination plugin（問題側 plugin として dispatch）

08

BootCamp で検証したいこと

この場を、Vibe Coding の“詰まり”の実験場にしたい。

いま AI でアプリを作っている参加者に、StackStack を実際に解いてもらう。知りたいのは 3 つ:

① どこで詰まるか

auth / 公開 S3 / 秘密情報 / レート制限 / 監視 — “公開の壁” のどれが一番きついか、実データで観たい。

② どの体験が刺さるか

毎分加点・順位・障害注入・“production-ready 認定” — どれが学びと熱量を生むか。

③ 初見で問題を作れるか

/new-problem と AUTHORING で、参加者自身が自分の“詰まり”を問題として投稿できるか。

作って終わりにしない。参加者の詰まりが、そのまま次の問題カタログになる。
09

次の一手

赤チームは実装済み。残るは本番での通し検証。

  • 本番 StackStack イベントの通し検証 — 実 AWS で 5 slot を deploy → 組織イベントを fire → 注入（slot 停止→復帰）と減点（window 失効）を 1 イベント通して観測する。本番検証
  • 初見で問題を作れるオーサリング — プロンプト / プラグインを足し、参加者が「自分が詰まった所」を 1 問にできる導線を太くする。
  • このデッキ自体が最新を映す — /pitchdeck スキルでリポジトリの実態（件数・実証ラベル）から再生成。聞かれたら常に今の状態で話せる。

1. 問題とは何か (= 3-asset model)

TenkaCloud の 1 問題は 3 種類の asset で構成される。 platform は 3 つを plugin として扱い、 問題側のロジックを platform に書き込まない (ADR-012)。

Asset役割必須?
metadata.json catalog 表示 + scoring engine 配線 + portal plugin 配線の正本 ○
template.yaml CFn ペライチ (deploy 本体)。 競技者 account に直接 deploy される ○
portal/<Slot>.tsx 問題固有 portal UI plugin。 metadata.dashboard.slots で宣言、 portal が React.lazy で chunk 分割 load —

ディレクトリレイアウト:

problems/<category>/<id>/
├── metadata.json            # 必須
├── template.yaml            # 必須
├── README.md                # 任意 (= 作者向け notes、 競技者には見せない)
├── portal/                  # 任意 (= ADR-012 Phase 5 plugin)
│   ├── StatusPanel.tsx
│   └── RegistrationPanel.tsx
├── services/                # 任意 (= container-based、 docker-compose 等)
├── api/                     # 任意 (= server-side コード)
├── frontend/                # 任意 (= 静的サイト)
└── local/                   # 任意 (= local dev assets)

<category> は battles または challenges。 metadata.json 内の category field (Battle / Challenge) が catalog / pipeline の正本。

2. Step 0 — 採点 kind を決める

scoring engine (= ADR-012 Phase 3 の generic scoring Lambda) は 6 種の builtin kind をサポートする。 1 問題 1 kind。 最初に「この問題はどう採点するか」 を決めると後の選択肢が全部決まる。

Kindカテゴリ採点ルール典型例
flag Challenge 1 deploy で 1 回 flag 提出。 CFn Output 値と submitted flag が一致したら points 加算 CTF 風 (= AWS Console で値を発見する Challenge)
multi-flag Challenge 1 問題に N 個の独立 flag を持ち、 各 flag を個別提出して部分点を与える。 flags[].points の合計が満点 ストーリー連作 Challenge を 1 問に統合 (= 単一 flag で足りるなら flag を使う)
uptime-flat (旧 uptime) Battle endpoint を 1 分毎に probe。 全 ok で pointsPerSuccess 加算 最低限 1 service の稼働維持
uptime-multi Battle N slot probe。 全 slot 同時 ok で pointsAllOk 加算、 1 fail で failurePenalty 複数 service の同時稼働 (= 3-tier app 等)
phased-polling Battle 時間経過 (phases[]) で rule が変わる。 platform 自己申告 (/meta) で platform 分類加点 マイクロサービス移行レース、 段階的負荷試験
attack-detection Battle CFn Output 内 counter の差分 current - prev × pointsPerAttack WAF 防御 / SOC monitoring / IDS 評価
決定木:
  • 1 回提出で終わるか? → flag
  • 1 問で複数の独立 flag を部分点採点するか? → multi-flag
  • endpoint が常に生きていることが採点軸か? → 1 endpoint なら uptime-flat、 N endpoint で「全部生きている」 を求めるなら uptime-multi
  • 途中で rule が変わるか? → phased-polling
  • 攻撃検知数で勝敗が決まるか? → attack-detection

3. Step 1 — CLI で雛形生成

CLI が .claude/templates/problems/<kind>/ から雛形 (= metadata.json + template.yaml) を copy し、 placeholder (__PROBLEM_ID__ / __PROBLEM_NAME__) を置換する。

bun run scripts/tenkacloud-problem.ts create <id> --kind <kind> [--category Battle|Challenge]

例:

# Challenge (flag-kind) を作る
bun run scripts/tenkacloud-problem.ts create my-flag-challenge --kind flag

# Battle (uptime-multi) を作る
bun run scripts/tenkacloud-problem.ts create my-battle --kind uptime-multi

# 利用可能 kind 一覧
bun run scripts/tenkacloud-problem.ts list-kinds

# template.yaml 編集後の cost-risk estimate
bun run scripts/tenkacloud-problem.ts cost my-battle

出力先は problems/<category>/<id>/。 category は kind から自動決定 (flag → Challenge、 残りは Battle)、 --category で上書き可能。

AI agent (Claude Code) で作る場合: /create-problem skill が同 CLI を起動して要件ヒアリング → 雛形生成 → 細部入力までを誘導する。 手動 CLI と同等の出力。

4. Step 2 — metadata.json を埋める

CLI が出力した metadata.json には placeholder (__PROBLEM_NAME__ / __TAG__ / __LEARNING_GOAL_1__) が残っている。 これを正しい値に書き換える。

言い回し (voice) は .claude/skills/create-problem/references/writing-style.md に従う。 競技者が読む name / shortDescription / instructions / hints は、 天下クラウド株式会社の cold-open シナリオ + 二人称 + 命令形 (= 本家 AWS GameDay と同型)。 個人名 (苗字) は使わず役職・役割 (CTO / 運営 / 前任の SRE) で書き、 実在の誰かを想起させない・前任者を無能扱いしない。 「本問題では〜を学びます」 等の AI 臭い前置きや空虚な形容 (堅牢 / 包括的 / シームレス / 活用 …) は禁止。 採点の数字・正解は shortDescription でなく description へ。

Field必須説明
id○kebab-case 3-32 文字。 dir 名と完全一致
name○UI 表示名 (日本語可、 80 字以内)
category○Battle / Challenge
status○draft で作成、 review 後 ready
difficulty○1=入門 / 2=初級 / 3=中級 / 4=上級 / 5=エキスパート
estimatedDuration○自由文字列 (例: 60〜90 分)
shortDescription○カード用 1 行 (200 字以内)
description○詳細ページ用の長文 (改行可)
tags○kebab-case の array
exposedPorts○deploy 後に競技者へ払い出す port
learningGoals○想定学習目的 (非空 array)
cfnTemplate○"template.yaml" など
runtime—[ADR-023] {provider, engine, entry}。 推奨だが省略可 (= legacy cfnTemplate から自動推論)。 後述
scoring—1 kind 1 設定 (Step 0 参照)。 省略で採点無効
endpoints[]—Battle で endpoint を持つなら宣言 (= 後述)
phases[]—phased-polling 系で時間経過 rule を入れるなら宣言
disruptions[]—Phase 4 self-triggered Scheduler を bake するなら宣言
dashboard.slots—portal plugin を持たせるなら宣言

endpoints[] (Battle 用)

1 endpoint しか無くても slot 名を付ける (= 後で多 slot 拡張しやすい)。 default.key は template.yaml の Outputs: に同名 key が存在することが validate で確認される。

"endpoints": [
  {
    "slot": "frontend",
    "default": { "from": "cfn-output", "key": "FrontendUrl" },
    "overridable": true,
    "label": "Frontend (nginx)",
    "description": "競技者が公開する商品ページ。 WAF / CDN を被せて override 可。"
  }
]

phases[] (= phased-polling 系)

時間経過で rule が変わる場合のみ。 each phase は afterMinutes で発火 offset を持ち、 effect で scoring engine への指示を表す。

"phases": [
  { "name": "degraded", "afterMinutes": 60, "effect": { "switchPlatformToDegraded": ["ec2"] } },
  { "name": "legacy",   "afterMinutes": 90, "effect": { "scorePathOverride": "/score?legacy=true" } }
]

disruptions[] (= ADR-012 Phase 4)

template.yaml 側に EventBridge Scheduler + Disruption Lambda を bake した場合、 portal 予告のために metadata 側でも宣言する (= portal predict 表示 + Phase 2 future-facing trigger)。

"disruptions": [
  {
    "id": "ec2-latency-injection",
    "name": "EC2 ネットワーク遅延注入",
    "eventDetailType": "DegradedDisruptionFired",
    "defaultAfterMinutes": 60,
    "operatorEditable": ["afterMinutes"],
    "parameters": { "delayMs": 200 }
  }
]

runtime (= ADR-023)

optional metadata field。 問題が deploy される対象 cloud と engine を明示宣言する。 推奨形式:

"runtime": {
  "provider": "aws",
  "engine": "cloudformation",
  "entry": "template.yaml"
}
現状 executable な組み合わせは provider=aws + engine=cloudformation のみ。 schema は将来の provider 値 (azure / kubernetes / gcp) を reservation として受理するが、 CLI validator (scripts/tenkacloud-problem.ts validate) と deploy worker は今 reject する。 詳細と migration plan は ADR-023 参照。

後方互換: runtime を省略すると validator が legacy cfnTemplate から {provider:'aws', engine:'cloudformation', entry:cfnTemplate} に正規化する。 既存 catalog 問題はそのまま valid。 両方宣言する場合は runtime.entry === cfnTemplate でなければ validator が reject する (= 互換期間の整合性制約)。

5. Step 3 — template.yaml を書く

CFn ペライチ。 deploy pipeline がこの 1 file を競技者 account の CFn にアップロードする。 同一 (Account, Region) に複数 team の stack が共存するため、 全リソース名 / タグ / Group 名は ${NamePrefix} を冠する。

Cost-risk check: template.yaml を編集したら bun run scripts/tenkacloud-problem.ts cost <id> を実行する。 CLI は template の Resources から resource type / rough hourly USD / typical-session cost / left-running day cost / always-on warning を offline に算出する。 NAT Gateway、 RDS、 Load Balancer、 EC2、 EIP、 WAF などは idle でも cost が残るため、 PR body で根拠を説明する。

必須 Parameters

Parameters:
  NamePrefix:
    Type: String
    MinLength: 5
    MaxLength: 80
    AllowedPattern: "^tc-[a-z0-9]+(-[a-z0-9]+)+$"
    Description: "tc-{problemSlug}-{teamSlug} 形式の共通 prefix"
  AllowedCidr:                              # 任意 (= 公開 service で使う)
    Type: String
    Default: "0.0.0.0/0"

必須 Outputs (kind 別)

Kind必須 Output
すべてNamePrefix (echo)、 metadata endpoints[].default.key で参照する key
flag+ FlagValue (= scoring.flagOutputKey で参照)
attack-detection+ AttackCount (= scoring.statsOutputKey で参照、 数値文字列)
phased-polling + disruption+ Disruption Lambda + Scheduler の AWS::Scheduler::Schedule
disruption pattern reference (= ADR-012 Phase 4) 
DisruptionFunctionRole:    # Lambda 実行 Role (= SSM RunCommand 等の権限)
  Type: AWS::IAM::Role
  ...

DegradedDisruptionFunction:    # idempotent な disruption Lambda
  Type: AWS::Lambda::Function
  Properties:
    Runtime: python3.12
    Handler: index.handler
    Code:
      ZipFile: |
        def handler(event, context):
            # tc qdisc add / S3 swap / IAM 剥奪 等
            return {"ok": True}

SchedulerInvokeRole:    # EventBridge Scheduler が Lambda invoke する権限
  Type: AWS::IAM::Role
  ...

DegradedDisruptionSchedule:
  Type: AWS::Scheduler::Schedule
  Properties:
    ScheduleExpression: !Sub "rate(${DegradedAfterMinutes} minutes)"
    Target:
      Arn: !GetAtt DegradedDisruptionFunction.Arn
      RoleArn: !GetAtt SchedulerInvokeRole.Arn
実例: microservice-migration-battle/template.yaml

6. Step 4 — portal plugin (任意)

問題固有 portal UI を持たせるなら portal/<Slot>.tsx を実装し、 metadata.json で配線する。 plugin は plain HTML + inline style で書く (= Cloudscape は portal 本体側にあり、 plugin bundle には乗せない)。

// problems/battles/<id>/portal/StatusPanel.tsx
import type { PortalSlotProps } from "@tenkacloud/portal-plugin-sdk";

export default function StatusPanel({ endpoints, phases, disruptions }: PortalSlotProps) {
  return (
    <section style={{ padding: "16px" }}>
      <h3>Custom Status Panel</h3>
      <ul>{endpoints.map((e) => <li key={e.slot}>{e.label}: {e.effectiveUrl}</li>)}</ul>
    </section>
  );
}

metadata.json で配線:

"dashboard": {
  "slots": {
    "StatusPanel": "portal/StatusPanel.tsx",
    "RegistrationPanel": "portal/RegistrationPanel.tsx"
  }
}

portal 予約 slot: StatusPanel / RegistrationPanel / HelpDrawer。 詳細は ADR-012 + SDK の型定義 (packages/portal-plugin-sdk/src/index.ts) を参照。

7. Step 5 — 検証 + PR

# 1. JSON Schema 適合 (= problems/SCHEMA.json)
make validate-problems

# 2. CLI による追加 check (= endpoints.default.key が template.yaml Outputs にあるか、
#    flag.flagOutputKey が存在するか、 dashboard.slots の portal/.tsx が物理 file としてあるか)
bun run scripts/tenkacloud-problem.ts validate <id>

# 3. Offline cost-risk estimate (= AWS creds / network 不要)
bun run scripts/tenkacloud-problem.ts cost <id>

# 4. ローカル CFn dry-run (= 競技者 account で aws cli)
aws cloudformation deploy \
  --template-file problems/<category>/<id>/template.yaml \
  --stack-name tc-<id>-test \
  --parameter-overrides NamePrefix=tc-<id>-test \
  --capabilities CAPABILITY_NAMED_IAM

PR を出す前に make before-commit で全 lint / typecheck / test を通す。 PR body には:

  • Summary: 何の問題を追加 / 修正したか
  • Test plan: validate-problems / CLI validate / 実 deploy の確認状況
  • 物理影響: 新 CFn リソース、 metadata 変更
  • Regression 分析: 既存問題への影響

8. チェックリスト

  • ☐ metadata.json の id が dir 名と完全一致
  • ☐ category が Battle / Challenge (大文字始まり)
  • ☐ scoring.kind が 6 種のいずれか
  • ☐ cfnTemplate で参照する template.yaml が同 dir にある
  • ☐ template.yaml の Parameters に NamePrefix を含む
  • ☐ 全リソース名 / タグに ${NamePrefix} が冠されている
  • ☐ Outputs に competitor 向け URL + NamePrefix echo + scoring 用 key (flag / counter) がある
  • ☐ endpoints[].default.key が template.yaml の Outputs に存在する
  • ☐ dashboard.slots[name] の portal tsx が物理 file としてある
  • ☐ bun run scripts/tenkacloud-problem.ts cost <id> を確認し、 always-on warning を PR body に記載
  • ☐ make validate-problems 通過
  • ☐ bun run scripts/tenkacloud-problem.ts validate <id> 通過
  • ☐ status は draft (= ready は別 PR で review 後)

10. よくある落とし穴

placeholder の置換忘れ

CLI が生成する metadata.json には __TAG__ / __LEARNING_GOAL_1__ / __HINT_1__ 等の placeholder が残っている。 これらを書き換えずに validate すると schema は通る (= placeholder も string なので形は valid) が、 catalog 表示 / scoring engine の挙動は不正。 すべての __ を grep して残っていないか確認する。

endpoints[].default.key と template Outputs の不整合

metadata で "key": "FrontendUrl" と宣言したのに template.yaml に FrontendUrl: Output が無い場合、 scoring engine は default URL を解決できず採点不能。 scripts/tenkacloud-problem.ts validate <id> でこの不整合を catch する。

NamePrefix を冠していないリソース名

同一 (Account, Region) で複数 team の stack が並走する。 リソース名がハードコードだと衝突する (= 2 team 目の deploy が CFn 失敗)。 全リソース名 / タグ / Group 名に !Sub "${NamePrefix}-..." を入れる。

tc qdisc add 等の disruption は idempotent に

EventBridge Scheduler は rate(N minutes) で N 分毎に再発火する。 disruption Lambda は 2 回目以降の発火を no-op にする (= tc qdisc add ... || true で EEXIST を握る等)。

portal plugin に Cloudscape を import しない

plugin bundle が peer-dep free を維持するための制約。 plain HTML + inline style で書く。 Cloudscape は portal 本体側で持っている (= ADR-012 Phase 7 で peer-dep externalization する予定)。

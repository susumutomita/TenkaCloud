Problem Review Checklist

Reviewer rubric for Challenge and Battle problem PRs. Use it as PR review comments — one check per rubric item.

For: Scenario Reviewer role (see ONBOARDING.html)
Goal: Block problems that are unfair, unrealistic, unsafe, or fundamentally broken. Approve problems that meet a credible event bar.
Cross-references: ADR-012 (problem = plugin), #1353 (security hardening)

1. How to use this checklist

Open the problem PR in TenkaCloudChallenge. For each of the six rubric sections below:

  1. Read the relevant files (metadata.json, template.yaml, problem statement, hints, optional portal/ components).
  2. Walk the checklist. Each item is a yes/no — if no, leave a PR review comment with the rubric ID.
  3. At the end, summarize using the reviewer summary template.

Decision rule:

  • Approve — every checklist item passes, optional items are noted as suggestions, no blockers.
  • Request changes — one or more checklist items fail. Comment which.
  • Block (security) — section 7 (template security) finds a critical issue. Use the "Block" review on GitHub and cross-link #1353.
Reviewers are not required to playtest. If you want to playtest as part of your review, follow PLAYTEST-CHECKLIST.html instead. A pure-review pass (no deploy) takes 30-60 min; a playtest-plus-review takes 90+ min.

2. Scoring fairness

A problem must reward the work it claims to test. Misaligned scoring is the #1 way an event loses participant trust.

  • The scoring kind in metadata.json matches what the problem actually tests (e.g., uptime problems use uptime-flat or uptime-multi, not flag).
  • Point values are proportional to effort. A 10-minute task does not award the same as a 60-minute task within the same event.
  • Negative scoring (Battle) only penalizes actions the participant could have controlled — no "the platform failed, you lost points".
  • For phased-polling: each phase requires new work, not the same work re-scored.
  • For attack-detection: detection signal is genuinely detectable from the data given to the participant — no insider information needed.
  • The scoring window (start / end time) is documented. Late submissions are handled deterministically (accepted partial credit or rejected).

3. Hint progression

Hints exist so the median participant finishes within the advertised time. They must escalate without giving away the answer for free.

  • Hints are tiered (e.g., 3 levels: nudge → direction → near-solution). Reading hint 1 should not reveal the answer.
  • Each hint has a point cost or unlock condition declared in metadata.json.
  • The final hint does not contain the full answer. The participant still has to apply it.
  • Hints are useful — they actually move a stuck participant forward, not paraphrase the problem statement.
  • If the problem has no hints, the difficulty is "intro" / "beginner" (= self-evident enough not to need them) and that is declared in metadata.json.

4. No skip-by-luck

A participant must not be able to "score" without understanding the underlying issue. Lucky flag guesses, wildcard health checks, or copy-paste solutions that bypass learning all fail this bar.

  • Flags are not enumerable / brute-forceable in a reasonable time. (Avoid 4-digit numeric flags, short string flags.)
  • The flag is not present in template.yaml in plain text. It is generated at deploy time, or derived from a per-team seed.
  • Battle health checks cannot pass by accident — e.g., a returning-200-on-everything proxy would not score.
  • Copy-pasting another team's submitted flag does not score (per-team flag derivation).
  • Searching the public internet (incl. GitHub) for the flag does not find it. (Reviewers should briefly Google a representative substring.)
  • The "obvious wrong answer" does not earn partial credit (e.g., creating any S3 bucket should not earn points if the problem is about a specific bucket policy).

5. Time-to-solve estimate

Mis-stated difficulty wastes facilitator time. An "easy" 2-hour problem destroys event scheduling; an "advanced" 10-minute problem feels insulting.

  • metadata.json declares difficulty (intro / beginner / intermediate / advanced / expert) and an estimated time range (e.g., 30-60 min).
  • The reviewer's gut estimate matches the declared difficulty within one tier.
  • The time range is wide enough (e.g., 30-60 min, not "45 min exactly") — real participants vary a lot.
  • Prerequisites are declared (e.g., "familiar with IAM policies", "has used CloudFormation before"). The problem does not assume tribal knowledge.
  • If two reviewers disagree by more than one tier on difficulty, request a playtest (per PLAYTEST-CHECKLIST.html) before approving.

6. Scenario realism

TenkaCloud's reason to exist is "real cloud drills". A problem that does not feel like a real incident / migration / hardening task fails the brand.

  • The scenario maps to something a real cloud team encounters (incident response, security finding, migration step, cost optimization, etc.). "Solve this puzzle that has no real-world analogue" is not the goal.
  • The AWS services chosen are the services a real team would use for this scenario, not a less common alternative chosen for novelty.
  • The problem statement is written in the voice of a realistic stakeholder ("Your on-call paged you because...", "Security found...", "Migration deadline is..."). Not "Solve this CTF challenge".
  • The "solution" reflects a real best practice — not an artificial path required only by the scoring logic. If reviewers think "I would never do this in production", that is a finding.
  • If the problem simulates an attack (Red Team / Blue Team), the attack vector is one that has actually been observed in the wild.

7. Template security

Problem templates run in real participant AWS accounts. A reckless template can leak data, get an account flagged, or cost real money. This is the strongest gate; section 7 failures can block a PR even when sections 2-6 pass.

Cross-reference: #1353 commercial security hardening checklist.

  • No resource is granted "Principal": "*" with no condition (e.g., a public S3 bucket policy, an open SNS topic). If intentional (the scenario is literally about public exposure), the blast radius is constrained (per-team bucket, unique random name, scheduled cleanup).
  • Security Groups do not include 0.0.0.0/0 ingress on all ports. Specific port + protocol + intentional within scenario only.
  • IAM Roles created in the template have least-privilege policies — no "Action": "*" + "Resource": "*".
  • No long-lived AWS access keys are created (use IAM Roles for everything; AssumeRole via the federation pattern).
  • Secrets / API keys are not committed to the template. Generate at deploy time (CloudFormation custom resource, SSM Parameter Store SecureString).
  • DynamoDB tables are PROVISIONED, not PAY_PER_REQUEST (the platform's DynamoDbLowCapacity Aspect enforces this — confirm the template does not try to opt out).
  • Any data the template seeds is synthetic. No real PII, no realistic-looking customer data.
  • The template's teardown removes every resource it creates (no orphaned S3 buckets, no leaked KMS keys, no zombie Lambda functions).
  • Outbound network calls from any Lambda / EC2 in the template go to documented, owned-by-the-author endpoints. No unexplained curl to third-party domains.
  • If the template uses a Lambda layer or container image, the source of the image is documented and pinned to a specific digest (not :latest).
Block-not-comment items: Any of these warrant a "Block" review, not "Request changes":
  • A real AWS access key in the template / metadata / docs.
  • An iam:* + Resource: * grant with no constraint.
  • Outbound network calls to a domain the author cannot identify.
  • Any executable code fetched at runtime from a non-pinned source.
When you block, also email the maintainer privately (do not disclose the specific finding in a public comment if it could be weaponized).

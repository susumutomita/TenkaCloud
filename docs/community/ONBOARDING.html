TenkaCloud Community Onboarding

Pick one of five roles. Each role has a 15-30 minute first task and a clear recognition path. You do not need to be personally onboarded by the maintainer.

For: CCoE practitioners, AWS / JAWS-UG members, cloud security & SRE engineers, training facilitators, problem authors, testers
Coordination: GitHub Discussions (source of truth) + Discord (live coordination, optional)
Related: ADR-024 (community voting), CONTRIBUTOR_MAP.md (task recipes)

1. How this works

TenkaCloud's moat is the community problem catalog, not only the deploy runtime. For that catalog to grow, external people must be able to contribute without being personally onboarded by the maintainer.

This guide gives you a self-serve onboarding path: choose a role, follow its first task, ship one PR. After your first merged contribution you become a recognized community member (see recognition).

The operating model follows the Option B recommendation from the design issue (#1364):

  • GitHub is the durable source of truth. Every decision, bug, and contribution lives in an issue or a PR.
  • Discord is for live coordination. Problem testing sessions, dry runs, and squad chat. Anything decided there must be summarized back into a GitHub issue.

You do not need a Discord account to contribute. GitHub-only contributors are first-class.

2. Role chooser

Pick the role that matches what you want to spend your time on. You can hold multiple roles over time; most active contributors end up doing two.

Role 1

Tester low barrier

Expected contribution
Run existing problems, report unclear instructions, broken deploys, scoring bugs. Estimate difficulty and time-to-solve.
Required skill level
Comfortable with AWS Console & CLI. No CDK / TypeScript knowledge needed.
First task
Run one starter problem and file feedback using PLAYTEST-CHECKLIST.html (30 min).
Where to communicate
Open a problem-feedback issue on GitHub. Discord #tester-squad for live sessions.
Time commitment
30-60 minutes per problem. Ad-hoc, no schedule.
Role 2

Problem Author creative

Expected contribution
Create new Challenge or Battle problems. Turn real incidents or training goals into drill scenarios.
Required skill level
One AWS service deeply (e.g., S3, IAM, Lambda). Basic CloudFormation. No platform internals required.
First task
Scaffold a small Challenge with the /new-problem skill or scripts/tenkacloud-problem.ts create. Walkthrough: docs/problems/AUTHORING.html (30 min onboarding).
Where to communicate
PR to the TenkaCloudChallenge catalog repo. Discord #problem-authors.
Time commitment
2-6 hours per problem (faster with AI agent help).
Role 3

Event Facilitator operational

Expected contribution
Run small community / internal events. Test the runbooks. Report event ops feedback (what the docs miss, what felt slow on the day).
Required skill level
Have run a workshop / study group before. Comfortable being on-call for 2-3 hours.
First task
Join or run a mini dry-run with the starter-event bundle (1 Challenge + 2 Battles, 60-90 min). Report observations as an issue.
Where to communicate
Discord #facilitators for dry-run scheduling. GitHub issue with the facilitator-feedback label for durable findings.
Time commitment
2-4 hours per dry-run. 1 dry-run per month sustains the squad.
Role 4

Platform Contributor deep

Expected contribution
Fix Lambda bugs, build admin UI features, extend CDK, add Aspects, write ADRs. The "platform engineer of the platform" role.
Required skill level
TypeScript + Vitest + AWS CDK. Read docs/architecture/OVERVIEW.md first.
First task
Pick a good first issue from GitHub, follow the matching recipe in CONTRIBUTOR_MAP.md.
Where to communicate
GitHub PR + issue. Discord #platform-dev for design questions.
Time commitment
1-2 evenings per PR. Variable.
Role 5

Sponsor / Requester demand

Expected contribution
Request problem themes you want to see. Signal enterprise / community demand. Optionally sponsor problem development.
Required skill level
Know what training problem your org actually needs. No engineering required.
First task
Open a problem request issue using the problem-request template, including desired learning outcomes and difficulty. Private / anonymous path available — see FAQ.
Where to communicate
GitHub issue (public requests) or the contact form on the landing page (private / enterprise).
Time commitment
15-30 minutes per request.

3. Role-specific first PR / contribution

Each role has a single concrete starter task. Doing one of these makes you a community member; you do not need a follow-up.

Tester — Run a starter problem and file feedback (30 min)

  1. Clone TenkaCloud, run make install + make deploy (Lite mode, ~10 min).
  2. Pick one problem from the catalog (start with hello-world).
  3. Register as a participant, solve it, score it.
  4. Fill the playtest report template in PLAYTEST-CHECKLIST.html.
  5. Open an issue with the problem-feedback label.

Problem Author — Ship a small Challenge

  1. Read docs/problems/AUTHORING.html (30 min onboarding).
  2. Decide which of the 6 scoring kinds your problem uses (flag / multi-flag / uptime-flat / uptime-multi / phased-polling / attack-detection).
  3. Scaffold: bun run scripts/tenkacloud-problem.ts create <id> --kind <kind> (or use the /new-problem Claude Code skill).
  4. Fill metadata.json and template.yaml. Validate locally: bun run scripts/tenkacloud-problem.ts validate <id>.
  5. Open a PR in the TenkaCloudChallenge catalog repo.

Event Facilitator — Run a mini dry-run

  1. Schedule a 60-90 min slot with 2-4 testers (Discord #facilitators).
  2. Deploy the starter-event bundle (1 Challenge + 2 Battles).
  3. Run the event: register teams, deploy problems, watch the scoreboard, debrief.
  4. Open a GitHub issue with the facilitator-feedback label: what went well, what slowed the day, what the docs miss.

Platform Contributor — Pick a good first issue

  1. Browse good first issue labels.
  2. Map the issue to the right recipe in CONTRIBUTOR_MAP.md (Lambda bug / admin UI / Aspect / etc.).
  3. Write tests first (should ... pattern), implement, run make harness + make before-commit, open a PR.
  4. The PR body must include ## Regression analysis and ## Physical impact sections (see harness invariants).

Sponsor / Requester — Open a problem request

  1. Use the problem-request issue template.
  2. Describe: target audience, desired learning outcome, AWS services involved, expected difficulty, whether it should be Battle or Challenge.
  3. If your scenario is company-specific or sensitive, use the private contact form instead. Maintainers can take it on as a paid problem development engagement.

4. How contribution gets recognized

Doing the first task does not make you invisible. Every community role has a public credit path.

RoleRecognition pathWhere it appears
Tester Issue you filed is linked from the fixing PR's commit (Closes #N) — your handle stays in the GitHub history. Frequent testers are listed in CONTRIBUTORS.md under "Tester squad". GitHub commit log + CONTRIBUTORS.md + Discord role badge
Problem Author Your handle is the author field in metadata.json. The catalog UI shows the byline on every problem card. problems/<id>/metadata.json author field + catalog UI + CONTRIBUTORS.md "Problem authors"
Event Facilitator Dry-run reports get credited Co-Authored-By trailers on any docs/runbook PR they trigger. Frequent facilitators land in CONTRIBUTORS.md. Git commit trailer + CONTRIBUTORS.md "Facilitators" + Discord role
Platform Contributor Standard GitHub PR authorship. Significant changes get a callout in release notes. GitHub author history + release notes + CONTRIBUTORS.md "Contributors"
Sponsor / Requester Public requesters are mentioned in the resulting problem's metadata.json sponsored_by field (opt-in). Private sponsors get an off-list credit unless they opt in. Problem metadata.sponsored_by + landing page sponsor wall (opt-in)

The deeper recognition story (community voting, on-chain registry, reputation tokens) is designed in ADR-024. The Web3 layer is optional; nothing in this onboarding requires a wallet.

Bottom line: Every contribution is publicly creditable. You decide whether to be public or private; both are first-class.

5. Where to communicate

The rule is simple: decisions live on GitHub, energy lives on Discord.

ChannelBest forNot for
GitHub Issues Bugs, problem feedback, problem requests, feature requests, architecture proposals Real-time Q&A, scheduling
GitHub Discussions Open-ended questions, "how does X work?", design exploration Tracking actionable work (use Issues)
Discord #tester-squad Live playtest sessions, "is anyone testing X right now?" Bug reports (move to GitHub Issue)
Discord #problem-authors Brainstorming new problems, getting feedback on a scenario idea Final review (use PR)
Discord #facilitators Scheduling dry-runs, debriefing in real time Permanent runbook updates (open a docs PR)
Discord #platform-dev Design questions on a draft PR, pairing Decisions (write an ADR)
Discord #announcements Release notes, dry-run schedules, new problem ships Discussion (open a thread on the announcement)

Anything decided on Discord must be summarized back into a GitHub issue or PR comment — Discord history is not durable enough to be the source of truth.

6. FAQ

I do not have a Discord account. Can I still contribute?

Yes. Discord is optional. Every role has a GitHub-only path. Open issues, file PRs, leave PR reviews — that is enough. Discord is for momentum, not gatekeeping.

My problem request is sensitive (company-specific incident, real customer data shapes). What do I do?

Use the contact form on the landing page instead of opening a public issue. Maintainers can engage privately, sign NDA, or develop a closed-source problem on commission. The public OSS catalog only receives problems you have explicitly cleared for publication.

I want to do the Tester role, but Lite mode make deploy needs an AWS account. I do not have one.

Two options. (1) Use the AWS Free Tier — TenkaCloud's DynamoDbLowCapacity Aspect forces every table to 1/1 RCU/WCU, so the platform itself fits inside Free Tier. The problem you deploy may consume a few cents per session. (2) Coordinate a Discord dry-run with a facilitator who has their own account; you join as a participant, not as an operator.

Can I become a Problem Author without AWS deep knowledge?

You need one AWS service you understand well — the problem typically only exercises a small subset of AWS. Use the /new-problem Claude Code skill if you want AI help with the CloudFormation. A Tester or Reviewer can pair with you to vet realism.

How do I become a maintainer?

Ship across two roles consistently for a quarter (e.g., Reviewer + Platform Contributor) and we will offer write access on either the platform repo or the catalog repo. We do not have a formal "vote you in" ceremony; it is a maintainer's invitation based on observed contribution quality.

What if my role does not appear in this list?

Open a Discussion. The 5-role split was designed to cover the typical OSS contributor surface; new roles are welcome if they fill a real gap.

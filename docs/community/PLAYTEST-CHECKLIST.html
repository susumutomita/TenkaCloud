Playtest Checklist

30-minute protocol for the Tester squad. Run one problem end-to-end, fill the report template, file an issue.

For: Tester role (see ONBOARDING.html)
Goal: Catch unclear instructions, broken deploys, scoring bugs, and unrealistic time estimates before they reach paid events
Output: One GitHub issue with the problem-feedback label

Contents

  • 1. Prep (5 min)
  • 2. Deploy in Lite mode (10 min)
  • 3. Register, solve, score (10 min)
  • 4. Report findings (5 min)
  • 5. Report template (copy-paste)
  • 6. Heuristics: what to look for

1. Prep (5 min)

5 min

1Pick a problem and clone the repo

  • Pick one problem from the TenkaCloudChallenge catalog. For your first playtest, start with hello-world (Challenge, ~15 min) or microservice-migration-battle (Battle, ~30 min).
  • Clone TenkaCloud locally if you have not already.
git clone --recurse-submodules https://github.com/susumutomita/TenkaCloud
cd TenkaCloud
make install
  • Have AWS credentials available for an account you can deploy into (Free Tier is fine).
  • Open the problem's metadata.json + template.yaml and skim them. You are about to be a participant; do not memorize the answer, but understand what is being deployed.

2. Deploy in Lite mode (10 min)

10 min

2Run make deploy (Lite mode)

Lite mode (= default since #955) deploys two stacks and is the shortest path to a single-organizer event.

make deploy ENV=development
  • Note the time from make deploy start to the Participant Portal URL being printed. If it exceeds 15 min, that is itself a finding.
  • Capture any error or warning that scrolls by — even one that recovers. Tester eyes catch what CI ignores.
  • Confirm the Participant Portal opens in a browser.
If deploy fails: Stop and file the issue now. A broken make deploy is the single most valuable bug class. Do not "skip past" it.

3. Register, solve, score (10 min)

5 min

3Register as a team and deploy the problem

  • Open the Participant Portal. Register your team with a login key. Note any UX friction (unclear copy, unexplained fields, browser warnings).
  • Deploy the problem you picked into your team account.
  • Note the time from "Deploy" click to "endpoint visible" — this is the time-to-first-attempt that real participants will see.
5 min

4Solve and submit

  • Read the problem statement. Are the instructions clear enough that a competent AWS engineer can attempt the problem without external help?
  • Solve the problem (or attempt to solve it). Do not look at the answer in template.yaml on purpose — try the participant path first.
  • Submit the flag (Challenge) or wait for an uptime / phased-polling tick (Battle).
  • Verify the score reflects on the scoreboard within the documented polling interval.
If you cannot solve it in the time the problem promises: That is a finding too. Difficulty mismatch is the #2 cause of bad events. Capture how far you got and what blocked you.

4. Report findings (5 min)

5 min

5File a GitHub issue

  • Open the problem-feedback issue template on the catalog repo (or platform repo for platform-side findings).
  • Paste in the report template below, filled out.
  • Attach screenshots if you have them (Cloudscape UI, scoreboard, error toast). Redact any AWS account number.
  • Add the problem-feedback label.
You are done. Maintainers triage problem-feedback within a week. Your handle stays in the GitHub history — see Recognition.

6. Heuristics: what to look for

Instruction quality

  • Can someone start the problem within 60 seconds of opening the page? If not, the opening paragraph is buried.
  • Is there exactly one "what you must do" sentence? If multiple, the success criterion is fuzzy.
  • Are AWS service names spelled out at first mention (e.g., "Amazon S3 (S3)")? Critical for non-native English readers.

Scoring fairness

  • Could a participant score without solving the underlying issue (e.g., a Battle where one health check accidentally passes)?
  • Are negative-score events tied to actions the participant could have controlled? Penalties for nothing they did are unfair.
  • For phased-polling problems: does each phase actually require new work, or is it the same work re-scored?

Time-to-solve estimate

  • Your time + 30% buffer is roughly the time a target-audience participant will take. Capture both.
  • If you used external tools (Claude, ChatGPT, AWS Docs), note it. The metadata's difficulty assumes no AI assist by default.

Deploy / teardown reliability

  • Did make deploy need a retry? Each retry adds operational pain at events.
  • Did teardown clean up everything? Leftover resources cost real money for facilitators.

Security & safety

  • Does the template create any resource with broad public access (e.g., a wildcard S3 bucket policy, an open security group)? If so, flag it — cross-reference #1353 hardening checklist.
  • Are secrets / API keys printed to logs?

UX micro-friction

  • Loading spinners that never resolve.
  • Buttons that fire but give no feedback.
  • Toast notifications that disappear before they are readable.
  • Text that overflows on narrow screens.
Big bugs are obvious. The tester squad's real value is catching the small papercuts that compound into a bad event experience.

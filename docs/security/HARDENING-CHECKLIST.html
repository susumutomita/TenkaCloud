TenkaCloud Commercial Hosted Event Security Hardening Checklist

The minimum credible security baseline for running paid TenkaCloud cloud-competition events. Not a SOC2 certification.

Status: Living document
Tracks: #1353 (parent: #1336)
Audience: Hosted-event operators, enterprise evaluators, security reviewers
Last reviewed: 2026-05-26

What this document is

An item-by-item posture statement for every control we promise to commercial buyers, with a direct evidence link (file path / harness rule ID / ADR / runbook) or an explicit acknowledged gap. Owners and statuses are tracked so that one glance tells a reviewer what is enforced, what is documented but manual, and what is on the roadmap.

Verification commands are in the companion docs/security/README.md. Operators should run them before every paid event.

What this document is NOT

  • A SOC2 / ISO 27001 certification (those require external audit and continuous evidence collection).
  • A pen-test report (commission one separately for high-value events).
  • A guarantee. Competitor AWS accounts host real workloads under operator supervision; problem templates can intentionally expose insecure resources by design (see allowIntentionallyVulnerable).

1. Identity & access

Every request crosses a Cognito JWT boundary. No bypass exists in app code. Cross-account access into competitor AWS uses the IAM Confused-Deputy mitigation (account-id + ExternalId) by construction.

4. Data & log handling

We use SSM SecureString for secrets (cost-zero principle) and field-level redaction before audit records are written. Long-retention immutable archive (S3 Object Lock) is intentionally NOT used — TenkaCloud is a competition platform, not a regulated-data workload, so the cost / lock-in trade-off does not pay off.

Acknowledged gaps and roadmap

Known gaps to disclose to commercial buyers
  • OPS-01..04 (operator account hygiene) — Operator owns AWS Organizations, SCPs, break-glass IAM, CloudTrail enablement. We document the expectation but cannot ship the control because TenkaCloud CDK does not deploy into the customer's management account.
  • TPL-06 (expensive-resource detection) — No automated scan for large EC2 / RDS / NAT Gateway. Operator dry-run review catches it today.
  • TPL-07 (teardown-coverage scan) — Convention-only; reviewer must confirm every resource is destroyable. Roadmap: add a retain-without-justify harness rule.
  • DAT-05 (no-credential-in-logs lint rule) — Reviewer-enforced; no machine check. Roadmap: a structured-log linter that bans known-sensitive field names.
  • IAM-05 (participant least-privilege baseline) — Competitor bootstrap template grants AdministratorAccess in the competitor account because problems span unpredictable services. Documented trade-off; mitigated by the 2-factor trust (account-id + ExternalId) and short-lived event windows.
  • TDN-04 (leftover-resource sweep CLI) — Manual tag-editor sweep today. Roadmap: CLI subcommand tenkacloud event leftovers --event-id <id>.
  • TDN-05 (default budget) — Operator must set AWS Budgets manually. Roadmap: CDK construct that ships a default $50 monthly alarm.

Maintenance & review cadence

  • This document is reviewed at every commercial pilot kick-off and after every security-relevant ADR (IAM, audit, cross-account).
  • New harness rules that close a gap should add their rule ID to the relevant evidence cell and flip the status badge.
  • Operators run the verification commands in docs/security/README.md as part of the pre-event checklist.
  • Vulnerability reports follow SECURITY.md private-disclosure channel (not public issues).

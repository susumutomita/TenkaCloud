TenkaCloud Data Classification & Handling Policy

Status Living document Scope Data the platform itself collects, stores and processes Audit ref items 10 & 11 Related Hardening checklist · Privacy policy

This document inventories every data item TenkaCloud collects, classifies it, and records where it is stored, how long it is kept, and how it is protected. It is the source of truth that the public privacy policy must stay consistent with. The inventory is grounded in the code: each row links to the module that writes or stores the data.

Design principle: minimize the PII the operator has to carry

TenkaCloud does not create an individual account per competitor. Each team authenticates with a short-lived, per-team bearer key (teamLoginKey), so the platform never asks competitors for an email, name, or any personal identifier. The personal data the platform does hold is therefore limited to operator / admin identities (who sign in via Cognito) and audit trails of their actions. We are honest about that: we collect operator email and the audit IP address, and we say so below and in the privacy policy.

Classification levels

PII Personal data that can identify a natural person (email, IP address). Secret A credential or value that grants access; disclosure is a security incident. Operational Competition / platform state with no direct personal identifier.

Handling rules

  • Secrets never go in source or in client bundles. The ExternalId is a KMS-encrypted SSM SecureString; @aws-sdk/client-secrets-manager is forbidden by the architecture harness (secrets-manager-forbidden) to keep the cost-zero, SSM-only posture explicit.
  • Credentials are not logged or returned. The teamLoginKey is projection-stripped out of list responses and collapsed to undefined at the handler layer before any tenant-summary surface can read it.
  • Audit access is metadata-only. Admin read endpoints log who looked and when (actor sub + path), not the contents that were viewed.
  • API responses are not cached. Authenticated JSON carries Cache-Control: no-store and X-Content-Type-Options: nosniff (#1694).
  • Tenant isolation is enforced at the infra layer. Every table is partitioned by TenantId (or separated by stack); no request can read another tenant's rows.
  • Deletion is real, not TTL-only. Event data is auto-expired at event end + 7 days, and tenant deprovisioning explicitly removes DynamoDB rows and the SSM SecureString rather than waiting for TTL.

Subject rights

Operators can export and erase their own tenant's data; competitor-facing personal data stays minimal by design (team key, not personal accounts). The export / self-service deletion flow is tracked under the data-rights work and surfaced in the application admin console.

Keeping this in sync

When a change adds a new field that stores personal data or a credential, add a row here in the same PR and confirm the public privacy policy still matches. The classification table is the contract; the privacy policy is its public-facing summary.

# Google Gruyere: Web Application Exploits and Defenses

## 調査メタデータ

- 公式 URL: <https://google-gruyere.appspot.com/>
- 公式情報の確認日: 2026-07-13
- 受講・プレー日: 2026-07-13
- 観察範囲: Setup、XSS の導入、Reflected XSS の課題 1 件
- 所要時間: 約 15 分
- アクセス条件: 公開 codelab と払い出された一時 Gruyere インスタンス
- 認証・課金: 外部アカウント登録なし、課金なし
- 記録者: Codex の制限付きブラウザーセッション
- 証拠境界: 下記の「実操作記録」に実操作と公式説明を分離して記載

## 実操作記録

`tenkacloud-2603-gruyere` という名前付きセッションを使用した。
ページ由来の出力には content boundaries を有効化し、通信先を
`google-gruyere.appspot.com` だけに制限した。codelab の利用条件を確認し、
説明された課題以外の操作、基盤探索、可用性へ影響する操作は行っていない。

公開の Setup から一時インスタンスを開始し、XSS の説明と課題文を読んだ。
最初は無効なパスがどのように表示されるかを確認した。次に Hint 1、Hint 2
を順に開き、パスへ渡した入力がエラーページへ反映されることを確認した。
最後に、スクリプトを含む URL で `document.domain` を表示する alert が
発火することをブラウザーの dialog 状態で確認した。完全な payload、
一時インスタンス ID、画面の複製は保存していない。

この記録が証明するのは、Reflected XSS 課題 1 件の実プレーです。
codelab 全体の修了や、ほかの脆弱性課題の達成は主張しない。

## 概要

Gruyere は、意図的に脆弱な小規模 Web アプリケーションと解説を組み合わせた
Google の codelab です。学習者は許可された隔離環境で脆弱性を見つけ、
攻撃の成立条件と修正方法を対で学ぶ。公式ページは XSS、XSRF、
パストラバーサル、情報漏えい、サービス妨害、コード実行などを扱う。

## 対象者・前提知識

公式説明では、Web アプリケーション、HTML、テンプレート、Cookie、AJAX
に関する基礎知識を想定している。今回の課題には、URL エンコード、
HTTP の要求と応答、ブラウザーでの JavaScript 実行の基礎も必要だった。

初学者向けに使う場合は、HTTP、HTML のエスケープ、ブラウザーの
same-origin model を短い準備モジュールとして先に置く必要がある。

## 学習目標

- 入力が HTML 応答へ入るまでのデータフローを追跡できる。
- Reflected XSS の成立を、入力、出力コンテキスト、実行結果で説明できる。
- 攻撃の再現だけで終わらず、出力時エスケープとテンプレート利用の
  修正方針を説明できる。
- 許可された演習環境と、それ以外のシステムの境界を守れる。

## モジュール構成

全体は Setup で一時環境とコードの見方を説明した後、脆弱性の種類ごとに
説明、課題、段階的な Hint、Exploit and Fix を配置している。
XSS 節の中でも、ファイル、反射、保存、HTML 属性、AJAX と入力経路を
分けているため、同じ脆弱性名を異なるコンテキストで反復できる。

## 演習一覧

今回プレーした Reflected XSS は、無効な URL から始めて、入力が応答へ
反映される経路を発見する課題だった。正解の URL は複数作れるため、
単一の文字列を覚えるより、実行コンテキストを理解する余地がある。

課題本体は短い。解説と一時アプリケーションを往復しながら、観察、仮説、
試行、ブラウザー上の結果を確認する。失敗してもインスタンスを再作成せず
同じ URL を修正して再試行できる。

## 難易度設計

難易度は、最初から解答を見せず、Hint 1 で観察対象、Hint 2 で危険な文字と
符号化の観点を示す段階式です。課題後には exploit と fix の説明を開けます。
これは「対象の発見」「表現方法の発見」「一般化」の順に支援する設計です。

一方、ヒントを開いたことによる減点や、ヒント前後の到達度の区別はない。
学習者がどこで詰まったかは codelab だけでは記録できない。

## 評価方法

課題ページには、TenkaCloud の flag や checkpoint に相当する明示的な
完了通知がない。今回の成功判定は、指定した JavaScript alert が対象の
オリジンで実行されたことを学習者自身が観察する方式だった。

自動評価に移す場合は、ブラウザー側の任意コード実行を直接採点せず、
隔離された verifier が固有 nonce の反映と実行イベントを受け取り、
対象インスタンス、課題 ID、期限を照合する必要がある。修正案の妥当性は、
回帰テストの自動評価と説明 rubric の人手評価を組み合わせる。

## 良かった点

- 説明の直後に同じ概念を試せるため、読むことと操作が分断されにくい。
- Hint を段階的に開けるため、完全な解答を見る前に再試行できる。
- exploit と fix を対にし、攻撃成功を学習の終点にしていない。
- 一時インスタンスにより、許可範囲を具体的に示している。
- 同じ XSS を複数の出力コンテキストで反復する構造がある。

## 改善できる点

- codelab の一部には、現在のブラウザーでは廃止された XSS Auditor を前提に
  した古い説明が残っている。更新日と対象ブラウザーの明示が必要である。
- 説明ページと演習インスタンスが別の場所にあり、初学者は対象 URL を
  取り違えやすい。
- 課題の成功条件が画面上で明示されず、正しく実行できたかを自己判断する。
- 失敗履歴、Hint 利用、所要時間、再試行回数を使った形成的評価がない。
- 攻撃後に修正を実装し、回帰テストまで通す一連の提出経路はない。

## TenkaCloudへ取り込める要素

- 「説明、隔離環境、観察、実行、修正、再検証」を 1 つの演習単位にする。
- Hint を観察対象、診断方法、設計原則の順で段階公開する。
- 同一概念を別のコンテキストで反復し、暗記ではなく転移を確認する。
- 攻撃成功と防御成功を別 checkpoint にして、修正前後を比較する。
- 許可範囲、禁止操作、環境の破棄時刻を演習開始時に明示する。

## TenkaCloudでは採用しない要素

- ブラウザーの alert 発火だけを最終的な合否判定にしない。
- 解答文字列をそのまま verifier の正解として保存しない。
- 古いブラウザー固有機能へ依存する説明を無期限に残さない。
- 攻撃の成功だけで満点にせず、安全な修正と回帰防止まで評価する。

## 新たに追加すべき要素

- checkpoint ごとの attempt、Hint 利用、経過時間を記録するイベント。
- 成功条件を学習者へ説明する状態表示と、理由を返す verifier 契約。
- 修正後に正常系と悪用系を両方確認する自動回帰テスト。
- 責任境界と設計判断を説明する短い人手評価 rubric。
- 教材、ブラウザー、依存サービスの最終確認日を持つ鮮度メタデータ。

## 初学者の詰まりポイント

- codelab と一時インスタンスのどちらを操作するか分かりにくい。
- URL エンコードと HTML エスケープの違いを同時に理解する必要がある。
- alert が出ればなぜ脆弱なのか、実害へどうつながるかの説明が必要である。
- 自動の完了表示がないため、正しい失敗と操作ミスを区別しにくい。
- Hint 2 は多くの表現を一度に示すため、初学者には情報量が多い。

## 運営依存性

教員や TA の常駐なしでも、公開説明と Hint で短い課題は進められる。
ただし、説明の鮮度確認、一時サービスの可用性、成功判定の自己判断は
外部運営に依存する。組織へ移植する場合は、ローカルで再現できる環境、
自動 verifier、教材の定期レビュー担当が必要です。

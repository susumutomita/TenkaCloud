ADR-029: Attack resilience — the competition always ends

Once disruptions and inter-team attacks actually land in a competitor's account, the platform must guarantee that no team is permanently knocked out and every round reaches a terminal state.

Status: Proposed 2026-05-30
Tracking: #1421 (program: #1417)
Related: ADR-012 (problem = plugin), ADR-013 (condition-triggered disruptions), ADR-014 (reconciliation), ADR-028 (inter-team coordination)

Context

Battle is gaining two capabilities that, for the first time, let one actor degrade another team's running environment:

  • Operator-fired disruptions that reach the competitor account (cross-account dispatch, #1419) — a referee injects a fault (latency, a killed instance, a flipped security group) into a team's deployed problem.
  • Inter-team interaction (ADR-028) — a problem plugin lets teams attack, ally, or contend for a shared resource.

Today neither attacks nor any recovery mechanism exists, so the two must be designed together: shipping attacks without a resilience contract would let a single fault or a coordinated attack put a victim team into a state from which they cannot score, and let a round run past its intended end with no terminal condition. For a timed, scored competition that is a correctness failure, not just a balance problem — a paying operator cannot run an event where a team can be eliminated for good or where the leaderboard never finalizes.

The requirement is therefore a hard invariant, not a tuning knob: an attack must never make the game un-finishable. This ADR defines what "resilient" means as a set of platform-enforced invariants and the mechanisms that uphold them, so that every problem author and every operator inherits the guarantee by construction rather than by discipline.

Decision

Three platform invariants, enforced for every Battle round

I1 — No permanent fault. Every disruption is time-boxed and auto-reverting. A fault carries a bounded maxDurationMinutes and a guaranteed revert path; the platform never leaves an injected fault open-ended, and a fault can never outlive its window or the round.
I2 — Bounded victim recovery. A team can always return to a scoreable state within a bounded recoveryBudgetMinutes: faults revert automatically (I1), and a team may trigger an idempotent re-deploy / reset of its own problem stack subject to a cooldown. Recovery never depends on operator intervention.
I3 — Guaranteed termination, disruption-aware scoring. Every round reaches a terminal state at its endTime (scoreboard freezes), and scoring is disruption-aware: by default an active fault pauses a victim's penalty rather than sinking their score, so a team cannot be driven below their pre-attack baseline by something outside their control. A round's terminal transition is guaranteed even if a poll is missed.

These invariants are platform guarantees. Problem plugins declare disruptions and inter-team primitives; they cannot opt out of time-boxing, recovery, or termination — only configure them within platform-enforced bounds.

Mechanisms

MechanismHow it upholds the invariant
maxDurationMinutes (per disruption) I1. Required field on each disruptions[] entry, bounded to ≤ the round length. The validator rejects an out-of-bounds value at authoring time; the disruption-fire handler rejects a fire request that would exceed it at runtime.
Auto-revert contract I1 / I2. Every disruption ships its undo. The competitor-side mechanism (the CFn-deployed disruption Lambda / SSM document) schedules its own revert at maxDurationMinutes, and the platform also emits a DisruptionExpired event the mechanism consumes — belt-and-suspenders so a fault reverts even if the in-account timer is lost. Reverts are idempotent.
Self-reset (idempotent re-deploy) I2. A team can re-trigger the deploy of its own problem stack (the existing idempotent DeployRequested path keyed by (tenantId, eventId, teamId, problemId)) behind a cooldown, returning to a clean scoreable baseline without a referee.
Round terminator I3. At endTime the round transitions to ENDED and the scoreboard freezes (the freeze already exists). The transition is driven by EventBridge reconciliation (ADR-014) so a missed poll cannot leave a round hanging.
scoreImpact policy (per disruption) I3. Enum pause | count. pause (default) means uptime/availability scoring is not penalized for the duration of the fault — the team is held at their pre-fault value, never sunk below baseline. count means the fault is the challenge (e.g. the attack-detection scoring kind) and the team is expected to respond; even then the round still terminates (I3) and the fault still reverts (I1).

Schema changes (problems/SCHEMA.json)

The disruptions[] entries gain three fields:

"disruptions": [
  {
    "id": "availability-flood",
    "name": "Availability flood",
    "maxDurationMinutes": 10,        // required, ≤ round length (I1)
    "autoRevert": true,              // required true; the disruption must ship its undo (I1/I2)
    "scoreImpact": "pause"           // "pause" (default) | "count"            (I3)
    // ... existing fields (eventDetailType, parameters, triggers, ...)
  }
]

The validator (extending the existing scripts/problem-cli/validate.ts + problems/SCHEMA.json) enforces: maxDurationMinutes present and within bounds, autoRevert: true present, and scoreImpact one of the enum. A problem that declares a disruption without a bounded duration or a revert fails validation — it cannot be shipped.

Alternatives considered

AlternativeWhy rejected
No time-box — faults persist until an operator manually reverts. Operator error or absence leaves the game hung. Directly violates "the game always ends." Manual revert is a recovery path, not a guarantee.
Platform owns recovery by auto-redeploying victim stacks on every fault. Heavy, cross-account, and problem-specific; redeploying mid-round can itself destroy legitimate progress. Recovery is instead delivered by making faults reversible (I1) plus a team-initiated, cooldown-gated self-reset (I2).
Scoring ignores disruptions entirely (faults never affect score). Some problems intentionally make the disruption the challenge (attack-detection). A blanket ignore removes that design space. The per-disruption scoreImpact policy keeps both modes while still guaranteeing termination and revert.
Cap total attacks per team instead of bounding each fault. A cap limits frequency but not the duration or reversibility of any single fault — a team could still be stuck by one open-ended attack. Bounding each fault (I1) is the property that actually guarantees recovery.

Migration

Phased so the app-layer guarantees land before any cross-account injection is enabled (the resilience contract must exist before attacks do):

  1. Phase 1 — schema + validator (app). Add maxDurationMinutes / autoRevert / scoreImpact to SCHEMA.json and enforce them in the CLI validator. No problem can declare a non-conforming disruption.
  2. Phase 2 — fire-time enforcement (app). The disruption-fire handler rejects any fire whose effective duration would exceed maxDurationMinutes or the remaining round time, and stamps an expiry on the dispatched event.
  3. Phase 3 — auto-revert contract (infra + problem-side). The cross-account dispatch (#1419) carries the expiry; the competitor-side mechanism self-reverts and also honors a platform DisruptionExpired event. Reverts are idempotent.
  4. Phase 4 — termination + disruption-aware scoring (infra + scoring). The round terminator (ADR-014 reconciliation) finalizes every round at endTime; the generic scoring path applies the scoreImpact policy so a pause fault holds the victim at baseline.

Infrastructure-touching phases (3–4: cross-account, IAM, scoring Lambda) are owned by the platform maintainer; the schema/validator and the scoring-policy logic are app-layer.

Consequences

  • Every disruption is bounded and reversible by construction — the validator refuses to ship anything else, so resilience is not a per-event operator checklist item.
  • Two testable platform invariants emerge that can be pinned in CI: "no disruption duration exceeds the round length" and "every round reaches a terminal state." These become harness-style guarantees rather than prose.
  • Problem authors gain a small, explicit vocabulary (maxDurationMinutes / autoRevert / scoreImpact) instead of an implicit, unsafe default.
  • The count policy preserves the adversarial problem genre (attack-detection) while the platform still guarantees the round ends and the fault reverts.
  • This ADR constrains, but does not implement, #1419 (cross-account dispatch) and ADR-028 (inter-team) — both must satisfy I1–I3.

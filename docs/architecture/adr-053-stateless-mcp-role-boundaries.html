ADR-053 — Stateless MCP 2026-07-28 with role-bound endpoints

Status: Accepted Date: 2026-07-31 Issue: #2819 Relates: ADR-049, ADR-050

TenkaCloud exposes a strict, sessionless MCP 2026-07-28 surface from its Always-On Cloudflare control plane. Developer, organizer, participant, and problem-author authority are separated by endpoint and by the existing authentication middleware. The initial surface is read-only. It never trusts a client-supplied role, never sends a raw credential into the MCP SDK, and never exposes a flag, team key, another team's private data, or another tenant's event.

1. Context

MCP revision 2026-07-28 removes the mandatory initialize handshake and protocol session. Each request carries the protocol version, client identity, and client capabilities in its _meta envelope. HTTP requests also carry MCP-Protocol-Version, Mcp-Method, and, where applicable, Mcp-Name. Servers advertise support through server/discover.

TenkaCloud has four distinct users. A single endpoint that accepts {"role":"organizer"} from an MCP client would make untrusted input an authorization decision. A process-local MCP session would also be a poor fit for the Always-On Worker, where successive requests can land on different instances. The design must therefore make every request independently authenticatable and independently executable.

2. Decision

  1. Use @modelcontextprotocol/server version 2, which implements protocol revision 2026-07-28, rather than a local JSON-RPC interpretation.
  2. Mount four distinct HTTP POST endpoints in apps/always-on-control-plane. Endpoint selection narrows authority; no tool argument can select or expand a role.
  3. Construct and close a fresh MCP handler/server for every HTTP exchange. Configure the SDK with legacy: "reject" and JSON responses. Do not create or return Mcp-Session-Id, and do not require sticky routing.
  4. Reuse the existing Auth0 organizer and team-key participant middleware before MCP dispatch. After authentication, remove Authorization, Proxy-Authorization, and Cookie from the Request passed into the SDK. The server factory receives only the projected organizer or team identity.
  5. Publish RFC 9728 Protected Resource Metadata for the organizer endpoint and reference it from the 401 bearer challenge. Use Auth0 clients registered in advance. Do not expose Dynamic Client Registration. Use Client ID Metadata Documents only when the configured authorization server explicitly advertises support; the configured issuer by itself is not evidence of CIMD support.
  6. Validate Host and Origin before dispatch. Let the official SDK validate the modern protocol envelope, supported version, Mcp-Method, Mcp-Name, and request schema.
  7. Keep the first release read-only. Do not expose deploy, teardown, setting changes, flag submission, hint reveal, or any other mutation as a synchronous tool.
  8. Require the MCP host to show the tool name and arguments and obtain the user's approval before each tool call. Tool annotations identify every current tool as read-only, non-destructive, and idempotent. Because an HTTP server cannot verify that a remote client's local approval UI was actually shown, a client that cannot provide this approval step is not a supported connection path.

4. Stateless request flow

5. Protocol and cache contract

  • The only supported modern revision is 2026-07-28. server/discover advertises it. Legacy initialize traffic is rejected.
  • Each request must carry protocol version, client info, and client capabilities under the standard _meta keys.
  • The HTTP headers and JSON body must agree. Missing or mismatched Mcp-Method/Mcp-Name is an error before dispatch.
  • The control plane's shared 32 KiB request-body limit also applies to MCP. A larger body is rejected with HTTP 413 before tool dispatch.
  • Public developer/author discovery and list/read results use ttlMs=300000 and cacheScope=public. Organizer and participant results use ttlMs=0 and cacheScope=private.
  • Tools and resources are registered in deterministic lexical order. Every modern result is encoded by the SDK with resultType=complete.

6. Mutation and extension policy

Long-running platform actions are not added until they can use the MCP Tasks extension. A future deploy or teardown operation must provide a durable task handle, idempotency, status retrieval, cancellation, and crash-safe persistence. When additional approval or input is needed, it must use the multi-round-trip request mechanism; a Boolean confirm argument in the first tool call is not sufficient consent.

MCP Apps, Tasks, and other extensions are versioned and reviewed independently. Core protocol support does not imply that an extension is enabled.

7. Security verification

The repository's deterministic tests must prove all of the following:

  • unsupported, legacy, missing-header, and header/body-mismatch requests fail;
  • two fresh app/Worker instances return the same discovery and list results;
  • no response contains Mcp-Session-Id;
  • organizer reads are tenant-scoped and participant reads select only one team row;
  • organizer and participant credentials cannot be interchanged;
  • flags, checkpoint identifiers, login-key hashes, other teams, and other tenants do not leak;
  • bearer/cookie credentials are absent from the Request handed to the SDK;
  • oversized request bodies fail before a tool can run;
  • structured audit logs include role, principal, method, name, and status but no request arguments or credentials.

8. Consequences and alternatives

ChoiceConsequence
One endpoint per role Authorization is visible in routing and middleware; client input cannot promote a role.
Fresh server per request Round-robin Workers need no session affinity. Construction work repeats, which is acceptable for the small read-only registry.
Official v2 SDK Protocol headers, discovery, result discrimination, and cache fields follow the specification instead of a local approximation.
Read-only first release MCP cannot yet operate an event, reveal a hint, submit a flag, deploy, or teardown. Existing Portal and operating flows remain authoritative.
Single endpoint plus a role argument Rejected: it turns untrusted model/client output into an authorization selector.
Sessionful MCP on Durable Objects Rejected for core requests: it adds state, affinity, lifecycle, and cost where revision 2026-07-28 requires none.
Hand-written JSON-RPC subset Rejected: protocol drift would be likely around discovery, headers, result types, cache hints, and future extensions.

9. Scope and rollout

The endpoints ship with the Always-On control plane and do not silently appear in the Lite deployment pipeline. Lite organizers continue to use the Application Admin Console. The developer and problem-author endpoints contain public, deterministic information; organizer and participant endpoints require their existing Always-On credentials.

The role manuals are the operator-facing source of truth. The upstream protocol sources are the MCP 2026-07-28 specification and the official TypeScript SDK.

Accepted for TenkaCloud's initial MCP 2026-07-28 surface. Any mutation or additional role capability requires a separately reviewed expansion of this matrix.

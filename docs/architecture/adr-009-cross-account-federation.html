ADR-009: Cross-account federation Phase 2.1 — CompetitorAccounts + ExternalId Onboarding 実装

Status:Accepted 2026-05-11 — Issue 459 の Phase 2.1 (= ADR-002 で確定した設計判断の実装) を確定。
Related issues: Issue 459 (cross-account federation 設計)
Related ADR: ADR-002 (設計判断 A2 + B2/B3 + C + D の原本)

Context

ADR-002 で「ExternalId は tenant 単位 (A2)」「メタデータは 新 DDB CompetitorAccounts (B2) + ExternalId は SSM SecureString (B3)」「Onboarding は 5-step (C)」「legacy env は dev fallback として残す (D)」を確定した。本 ADR は ADR-002 の Phase 2.1 に該当する 実装 PR の決定事項 を残す。

Issue 459 のオリジナル要求では「やること」が backend / frontend / infra の三方に跨り 1 PR で消化するには重い。本 ADR は分割スコープの境界を明確化し、Phase 2.1 / 2.2 / 3 をそれぞれ独立して観察可能にする。

Decision

1. Phase 2.1 = 本 PR で扱う scope

  • backend:
    • CompetitorAccountsTable CDK construct (PROVISIONED 1/1)
    • CompetitorAccountsApiLambda CDK construct + IAM (SSM / STS / KMS)
    • SSM SecureString helper (handlers/shared/external-id-store.ts)
    • Hono handler 一式 (POST / GET / POST .../verify / DELETE)
    • tenant API GW route の配線 (/admin/competitor-accounts*) + Cognito JWT authorizer 共通化
  • frontend:
    • 新 API client (api/competitor-accounts-client.ts)
    • 新 page CompetitorAccountsPage (一覧 / Add modal / Verify / Delete)
    • AppLayout SideNavigation への link 追加
    • 「Add account」直後の 1 度きり Reveal modal (ExternalId 表示)
  • tests:
    • backend: store / verify / handler routes / stack synth (4 ファイル、計 17 テスト)
    • frontend: API client (4 テスト)
    • 「ExternalId 付き STS AssumeRole」が常に発行されることを pin (= Confused Deputy 対策が剥がれないように)

2. Phase 2.2 = 別 PR / 別 Issue

本 PR で 同梱しない:

  • EventCreate の AWS Account ID 自由入力 → verified-account drop-down 移行
  • Worker Lambda (= 実 deploy 経路) の ExternalId injection (現状の Worker は same-account のみで cross-account を呼ばないため、Phase 2.2 で Worker を cross-account 化するときに同時に実装する)
  • CDK_PARAM_DEPLOY_EXTERNAL_ID 撤去 / rename (Worker が cross-account になるまで触らない)
  • migration script (旧 deployment 行への externalId 補填) — 現状 cross-account deploy が稼働していないため migration 対象が 0 件

これらは新 Issue として切り出し、Phase 2.1 が user により本番 deploy + 動作確認された後に着手する。

3. Onboarding (実装)

stepactor動作
1operatorapplication-admin-console / Competitor Accounts 画面で「アカウントを追加」
2backendSSM /{env}/tenants/{tenantId}/external-id が無ければ 64 char hex を生成 + Put。DDB CompetitorAccounts に verified=false の row。
3operatorReveal modal に表示された { tenkaCloudAccountId, externalId, competitorRoleName } を競技者にコピペで渡す
4競技者competitor-bootstrap.yaml を Parameter (= ExternalId / TrustedAccountId) 付きで自分の AWS account へ deploy
5operator画面で「Verify」 button → backend が STS AssumeRole sanity check → 成功で verified=true

4. IAM 最小権限

CompetitorAccountsApiLambda の execution role に付与する権限:

  • DDB CompetitorAccounts の RW (table-scoped)
  • SSM arn:aws:ssm:{region}:{account}:parameter/{env}/tenants/*/external-id の GetParameter / PutParameter / DeleteParameter
  • KMS Decrypt / Encrypt (= AWS managed key alias/aws/ssm 用、Condition で kms:EncryptionContext:PARAMETER_ARN を SSM path に絞る)
  • STS AssumeRole on arn:aws:iam::*:role/TenkaCloud-* (= account 全体ではなく Role 名 pattern で絞る、IAM 越境攻撃の余地を最小化)

本 ADR では tenant 単位の SSM path 絞り込みを session tag injection 無しで 開始する (= Phase 2.1 では Lambda の IAM が tenant 全体の parameter/{env}/tenants/*/external-id を許可する)。理由は ADR-002 §2.2 と同じ: Cognito identity propagation で per-tenant session tag を inject する経路は Phase 3 で実装する。

5. API 形状

すべて tenant API GW + Cognito JWT authorizer 経由。tenantId は JWT custom:tenantId claim から backend が解決し、request body の tenantId は信頼しない。

POST /admin/competitor-accounts — register

Body (Zod validated): { awsAccountId, region?, competitorRoleName?, alias? }

動作: SSM に ExternalId を冪等に確保 (既存ならそのまま) → DDB に row を verified=false で Put → response に { ..., externalId, tenkaCloudAccountId }。

失敗:

  • validation_failed (400) — Zod の issue を返す
  • duplicate_account (409) — 同 (tenantId, awsAccountId) が既存
GET /admin/competitor-accounts — list

Response: { items: CompetitorAccountSummary[] }。externalId は含めない (= SecureString は POST 直後の 1 度きり露出)。

POST /admin/competitor-accounts/{awsAccountId}/verify — sanity check

動作: DDB.Get で row 取得 → SSM.Get で ExternalId 取得 → STS.AssumeRole 発行 (= RoleArn, ExternalId, DurationSeconds=900) → 成功なら DDB に verified=true / verifiedAt を Update。

失敗:

  • not_found (404)
  • external_id_missing (409) — SSM が空 (= 整合性違反)
  • assume_role_failed (422) — STS Error name を underlyingErrorName として operator に返す (AccessDenied / ExternalIdMismatch 等を画面で識別可能)
DELETE /admin/competitor-accounts/{awsAccountId} — remove

動作: 存在確認 (Get) → 無ければ 404 → DeleteCommand 発行 → 残行 0 件なら SSM の ExternalId も同時に削除 (= 鍵漏洩リスク削減)。

Consequences

Positive

  • ADR-002 で確定した tenant 単位 ExternalId が実装され、漏洩時の blast RADIUS が 1 tenant に閉じる
  • operator が画面上で competitor account を一覧 / 追加 / verify / 削除できる (= 「どの account が deploy 可能か」を画面で可視化)
  • Phase 2.1 はテストで STS AssumeRole が ExternalId 付きで発行される ことを pin (= Confused Deputy 対策の regression を防ぐ)
  • Phase 2.2 (= DeployForm migration / Worker cross-account 化) は別 PR で扱う前提に整理されており、PR の review burden が下がる

Negative / 未解決

  • Phase 2.1 単独では「verified=true の account を強制する」 backend 制約が無い (= 実 deploy 経路がまだ same-account 前提)。Phase 2.2 で Worker を cross-account 化する際に同時に立てる
  • session tag による per-tenant SSM 絞り込みは Phase 3 待ち
  • EventCreate 画面の awsAccountId 自由入力は本 PR では撤廃せず、互換のため残す

Migration / 互換性

  • 本 PR 単独では既存 deploy 経路に影響無し (= 既存 EventCreate / DeployForm はそのまま動く)
  • 新 Lambda + DDB は Phase 2.1 で deploy するが、誰も呼ばなければ無料 (DDB 1/1 PROVISIONED = ~$0.60/月、SSM SecureString は無料の標準 tier 内)
  • Worker が cross-account 化されたら、本 ADR 5 章の verify endpoint が事前要件になる (= verified=false の account では deploy が拒否される、Phase 2.2 で実装)

ADR-043: Tenant self-service signup is not the OSS trial path

OSS の「触ってみる」導線は Lite mode、SaaS tenant 作成は System Admin 管理下に残す

Status: Accepted 2026-06-18
Decision: Reject public tenant signup
Related: ADR-016, Architecture harness, 5-minute quickstart
Tracking: #1774

Context

TenkaCloud has two operating modes. SaaS mode is the full SBT-backed multi-tenant control plane: System Admins create tenants, SBT emits an onboarding request, and the tenant pipeline provisions the tenant application plane. Lite mode is the OSS and demo path: make deploy creates a single local tenant, application admin console, problem deploy backend, and participant portal without requiring SBT tenant onboarding.

Issue #1774 proposed a public tenant self-service signup flow to reduce the distance between a visitor and a running tenant. The proposed scope included a public signup form, email confirmation, a System Admin approval queue, rate limiting, and a connection to the SBT onboardingRequest event. That is not a small frontend addition. It creates a public unauthenticated control-plane edge that can request AWS-backed tenant provisioning.

The product problem is real: first-time users should be able to try TenkaCloud quickly. ADR-016 already resolved that with Lite mode. The public quickstart asks users to clone the repository and run make deploy; it does not require Cognito setup, SBT, a hosted SaaS account, or a pre-configured tenant.

Decision

TenkaCloud will not add public tenant self-service signup to the SaaS control plane. Tenant creation in SaaS mode remains an authenticated System Admin action. The OSS trial and public demo path is Lite mode, not a hosted self-service tenant request queue.

Try TenkaCloud Use Lite mode: clone, make install, make deploy, then run one event in a single AWS account.
Operate SaaS Tenants Use SaaS mode: System Admin creates or rejects tenants through the authenticated admin console.
Collect Interest Use docs, a contact form, or GitHub Discussions. Do not connect unauthenticated public forms to SBT onboarding.

Rationale

ConcernReason
Control-plane exposure Self-service signup would add an unauthenticated public edge that can create tenant provisioning requests. Even with approval, it must handle abuse, replay, enumeration, and request flooding before any user has authenticated.
AWS resource blast radius A tenant approval can launch Cognito, API Gateway, DynamoDB, CloudFront, CodeBuild, and tier-specific stacks. That is a materially different risk from Lite mode, where the operator deploys into their own account intentionally.
Existing trial path ADR-016 made Lite mode the fast path for OSS, meetup, and demo usage. Adding a hosted signup queue would duplicate the "try it" job while making the control plane more complex.
SBT ownership Tenants are a System Admin concept in the SBT control plane. Keeping creation behind authenticated System Admin actions preserves the current audit and approval boundary.
Operational readiness A public signup surface needs email verification, CAPTCHA or equivalent throttling, moderation queues, retention policy, spam handling, and abuse response. Those are not present operating commitments for TenkaCloud.

Allowed Future Work

The decision does not block lower-risk onboarding improvements:

  • Improve the Lite mode quickstart and demo runbooks.
  • Add a static interest form or documentation link that sends people to maintainers without touching the control-plane API.
  • Improve the authenticated System Admin tenant creation wizard, validation, and provisioning status visibility.
  • Add import/export helpers for tenant request data when a human System Admin is still the approving actor.

A future public signup proposal must arrive as a separate ADR and include abuse prevention, identity proofing, rate limits, approval audit semantics, retention/deletion policy, and a clear AWS cost-control model before it can connect to SBT onboarding.

Consequences

Positive

  • No unauthenticated control-plane API surface is introduced.
  • The fastest public trial path remains the already-shipped Lite mode.
  • SaaS tenant creation keeps its current System Admin audit boundary.
  • No new Cognito app client, confirmation workflow, request table, queue, approval API, or public rate limiter is required.

Negative

  • People cannot request a hosted SaaS tenant directly from a public signup page.
  • Hosted SaaS adoption remains a human-mediated motion until a future ADR changes that boundary.

Implementation Status

No runtime implementation is required for this ADR. Issue #1774 is resolved by this decision: public tenant self-service signup is not the onboarding path. Lite mode remains the public trial path, and SaaS tenant creation remains an authenticated System Admin workflow.

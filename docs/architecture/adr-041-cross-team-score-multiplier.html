ADR-041: Cross-team health score multiplier is not a generic platform primitive

他チームの RegisteredUrl health を自チーム得点の倍率にする案の採否と境界

Status: Accepted 2026-06-18
Decision: Reject as generic scoring primitive
Related: ADR-012, ADR-028, ADR-033, ADR-040
Tracking: #1794

Context

Issue #1794 proposed a cooperative Battle mechanic: a team registers another team's service as a dependency, and if that other team's registered URL is healthy, the current team's per-minute uptime score is multiplied, for example from 500 points per minute to 1000 points per minute. The game-design intent is useful: contestants should care about adjacent teams, not only their own service.

The proposed implementation crosses a platform boundary. ADR-012 deliberately makes each scoring kind evaluate one deployment row and its declared endpoint slots. ADR-028 puts inter-team coordination into problem-declared plugins rather than hardcoded platform primitives. ADR-033 lets disruptions affect scoring only through declared, bounded effects. A global cross-team multiplier would introduce an implicit trust channel between teams and would make generic scoring depend on another team's latest health state.

Decision

TenkaCloud will not implement "register another team's raw URL and multiply my score when it is healthy" as a generic platform feature. Generic scoring remains local to the current deployment, event, team, problem, and declared endpoint slots.

If a future Battle needs cooperative scoring, it must be expressed as a problem-specific, metadata-declared mechanic. The first acceptable shape is a team-id based dependency, not a raw URL: 

{
  "interTeamCoordination": {
    "plugin": "coordination/cooperative-health.ts",
    "name": "Cooperative health dependency",
    "publicHint": true
  },
  "scoringExtensions": {
    "kind": "declared-team-health-bonus",
    "source": "coordination-plugin",
    "targetSlots": ["main"],
    "multiplier": 2,
    "maxBonusPerTick": 500
  }
}

This example is illustrative. It is not an accepted schema. A future implementation would require a separate ADR, schema migration, handler tests, and a catalog problem that proves the mechanic is fair and safe.

Rationale

ConcernWhy the generic multiplier is rejected
Identity and spoofing Raw URL registration lets a team claim an unrelated always-healthy endpoint, its own endpoint, or a URL outside the event. Validating URL ownership is more complex than the game mechanic warrants.
Scoring determinism Current polling kinds can explain a tick from the current deployment, metadata, endpoint overrides, and active effects. A cross-team multiplier makes score depend on another row's timing, last probe result, and possible page-scan ordering.
Game balance A multiplier amplifies score inflation and can reward or punish a team for another team's outage. That can be fun in a specific Battle, but it should not become a platform default.
Operational blast radius Generic scoring is a shared platform path. Adding cross-team reads, registration state, and fallback rules there affects every Battle even when only one problem wants the mechanic.
Existing architecture ADR-028 already provides the right extension point: a problem declares its inter-team primitive and the platform dispatches it. The multiplier should be a declared problem behavior if it is ever implemented.

Allowed Future Shape

The following constraints are mandatory for any future cooperative-health implementation:

  • Participants register a target teamId within the same event, never an arbitrary URL.
  • The registration API rejects the caller's own team, unknown teams, teams outside the event, and problems that did not declare the mechanic.
  • URL resolution is performed by the platform from the target team's declared endpoint slot or endpoint override. Participants cannot supply the target URL directly.
  • The effect is bounded per tick with an explicit maximum bonus. Penalties remain separate from bonuses unless the problem metadata states otherwise.
  • Score events include enough source detail to explain whether the normal base score, the cooperative bonus, or neither was applied.
  • If the target team's health is stale, missing, or unreadable, the bonus fails closed to multiplier 1 with no extra penalty.
  • The behavior has unit tests for self-team rejection, event-scope rejection, stale-health fallback, page-order independence, and unchanged existing scoring kinds.

Consequences

Positive

  • Generic scoring keeps its local, per-deployment invariant.
  • Raw URL spoofing and unrelated always-healthy endpoints are structurally excluded.
  • Problem authors still have a path for cooperative mechanics through ADR-028-style coordination plugins and explicit metadata.
  • No new DynamoDB table, Lambda, IAM policy, scheduler, or polling load is introduced for this proposal.

Negative

  • The specific "health of another team doubles my score" idea is not available as a platform toggle.
  • A future Battle that wants this behavior must do design work before implementation instead of reusing a ready-made multiplier.

Implementation Status

No runtime implementation is required for this ADR. The issue is resolved by the decision: cross-team score multipliers are not a platform-global scoring primitive. Any future proposal must arrive as a new, explicit problem-scoped design rather than as a direct generic-scoring patch.

ADR-026: Sakura Cloud as a problem-target provider (AppRun runtime)

How TenkaCloud runs competition problems on さくらのクラウド (Sakura Cloud) as the first non-AWS target — which engine satisfies the ADR-023 runtime contract, why the Trust Bridge federation model does not apply, and how the AWS control plane stays unchanged.

Status: Proposed 2026-05-29
Builds on: ADR-012, ADR-017, ADR-023
Scope: problem runtime + credential path only — not the platform itself

Context

ADR-023 defined the multi-cloud expansion path: a problem declares runtime: { provider, engine, entry }, the deploy dispatcher selects the execution path, and the first non-AWS step is provider-specific problems (not a cloud-agnostic compiler). Two of its decisions constrain any new provider:

  • ADR-023 D3 — a first-class engine must let the cloud own the runtime, the state, and the teardown. The platform stores deploy metadata (id, status, outputs) but is never the source of truth of cloud state: no state file, no lock backend.
  • ADR-023 D5 — Terraform is explicitly not the default multi-cloud runtime, precisely because it would force the platform to own state, locking, and partial-failure cleanup.

Today the only executable combination is aws + cloudformation: the deploy worker AssumeRoles into a team's isolated AWS account with a tenant ExternalId and runs CloudFormation CreateStack. ADR-017 (Trust Bridge) abstracts cross-cloud authority transfer as "verified intent → short-lived provider-native credential", with adapters for federation-capable providers (AWS STS AssumeRole, GCP Workload Identity, Azure Federated Credential).

This ADR adds Sakura Cloud (さくらのクラウド) as the first non-AWS problem target. The motivation is concrete: a drill that runs on a Japanese public cloud ("a Sakura Cloud GameDay") is a differentiated, market-relevant offering and the first real exercise of the multi-cloud runtime contract. Sakura's service shape differs from AWS in two ways that this ADR must resolve before any code is written:

DimensionAWS (today)Sakura CloudConsequence
Cloud-native IaC that owns its own state CloudFormation (a Stack owns the resource graph, teardown = DeleteStack) None. No CloudFormation-equivalent; no managed Kubernetes-as-a-Service. IaC is the community Terraform provider, or direct API calls. A naïve "Terraform / API" engine would make the platform own state → violates ADR-023 D3 / D5.

Decision

D1: The first (and only) Sakura engine is apprun

A Sakura problem is a container image run on AppRun. The deploy worker creates an AppRun application from the image, passes parameters as environment variables, and reads back the application's public URL as the deploy output. AppRun — being Knative on managed Kubernetes — owns the running application, its scaling, and its teardown (delete the application). This satisfies ADR-023 D3 without the platform holding any state file or lock backend.

Container-shaped problems cover the bulk of TenkaCloud's scoring kinds — keep a service up (uptime-flat / uptime-multi), reach a deployment milestone (phased-polling), or serve a flag from an endpoint (flag via the app's HTTP surface). They do not cover AWS-infrastructure-shaped drills (VPC / IAM misconfiguration), which are AWS-specific by nature and stay on the aws + cloudformation path.

D2: Runtime metadata and the executable set

Per ADR-023 D2 the schema already accepts an arbitrary runtime shape. A Sakura problem declares:

"runtime": { "provider": "sakura", "engine": "apprun", "entry": "<container-image-reference>" }

The validator's executable set — enforced at the CLI / validator layer with a descriptive error — grows from one to two combinations:

providerengineentryExecutable
awscloudformationtemplate pathyes (today)
sakuraappruncontainer image referenceyes (this ADR)
anything else——reserved, not executable

Every existing problem keeps validating unchanged: absent runtime with a cfnTemplate still normalizes to { aws, cloudformation } (ADR-023 D2).

D3: Credential model — stored scoped API key, not Trust Bridge federation

Sakura has no OIDC / STS federation, so the Trust Bridge exchange (verified intent → short-lived federated credential, ADR-017) cannot produce a Sakura credential. Sakura is therefore the first provider on a stored-credential path:

  • The team registers a least-scope Sakura API key (Access Token + Secret) for an isolated Sakura account / project.
  • The platform stores it as an SSM SecureString, one per team, mirroring how the AWS ExternalId is stored (per infrastructure/lib/problem-deploy/handlers/shared/external-id-store.ts; never returned in plaintext, encrypted with a condition-scoped key).
  • The deploy worker reads it at deploy time and calls the Sakura API to create / update / delete the AppRun application.
Security note — weaker isolation than AWS. A Sakura API key is long-lived, whereas the AWS path uses a 15-minute AssumeRole session. This is a strictly weaker property and must be compensated: scope the key to the minimum AppRun operations, store it only as SSM SecureString, support rotation (re-register), and prefer a dedicated per-team Sakura account so the key's blast radius is one team's project. The Trust Bridge stays AWS/GCP/Azure-only until Sakura offers a federation primitive.

D4: Full Sakura IaC (Terraform / direct API multi-resource) is out of scope

Deploying arbitrary multi-resource Sakura infrastructure (servers, switches, managed DB) has no cloud-native owner of state on Sakura — it would force the platform to run a Terraform backend or track created resource IDs, which ADR-023 D3 forbids and D5 explicitly rejects. It is deliberately excluded from the first engine and reserved, consistent with ADR-023's "provider-specific, cloud-owns-state first" stance.

D6: Scoring is already provider-agnostic

The generic scoring engine (ADR-012 Phase 3.B) probes an HTTP endpoint. For a Sakura problem it probes the AppRun application URL exactly as it probes an AWS endpoint — uptime-flat, uptime-multi, phased-polling, and endpoint-served flag work unchanged. attack-detection, which reads a CloudFormation Output, is AWS-specific and not available for Sakura problems.

D7: The control plane stays on AWS

Only the deploy engine, the credential adapter, and the scoring target become provider-aware. The Control Plane (SBT Cognito + EventBridge + tenant CRUD), the Application Plane, the deploy worker host, and the participant portal remain on AWS exactly as today. This is a bounded addition to the dispatcher, not a platform migration.

Options considered

OptionVerdictWhy
AppRun as the Sakura engine Accepted GA managed container runtime; AppRun owns runtime / scaling / teardown, satisfying ADR-023 D3 with no platform-side state. Matches the HTTP-probe scoring model.
Self-managed Kubernetes on Sakura VMs Rejected Sakura has no managed Kubernetes-as-a-Service; a self-built cluster makes the platform or team own cluster ops, networking, and lifecycle — the opposite of "cloud owns the runtime".
Terraform / direct Sakura API (full IaC) as the first engine Rejected No cloud-native state owner on Sakura ⇒ platform owns state / locking / cleanup ⇒ violates ADR-023 D3 and D5. Reserved for later, not first.
A federated Trust Bridge adapter for Sakura N/A Sakura exposes no OIDC / STS federation to exchange a verified intent into. A stored scoped API key (D3) is the only available model.
Port the whole platform (control + app plane) to Sakura Rejected The control plane is AWS-by-design (SBT, Cognito, EventBridge, Step Functions). Replacing them is a multi-month rebuild that contradicts the architecture and is unnecessary to run drills on Sakura.

Rollout

  1. Schema + sample (no execution). Extend the validator's executable set and add a sample Sakura problem (runtime: { sakura, apprun }). The AWS path is untouched; the new combination validates.
  2. AppRun engine + credential. Implement the AppRun dispatch branch in the deploy worker and the Sakura API-key SecureString store. Behind the dispatcher, so AWS problems are unaffected.
  3. Catalog provider badges. Surface the provider in the catalog and portal so a Sakura drill is discoverable next to AWS drills.

Open questions

  • AppRun control surface. Confirm the AppRun API (and whether the Sakura Terraform provider covers AppRun yet) for application create / update / delete and public-URL retrieval, and pin the exact call sequence the deploy worker uses.
  • Isolation tier. Whether AppRun's 専有型 (dedicated) is required for cross-team isolation, or 共用型 (shared) with per-team accounts suffices.
  • Key lifecycle. Per-team Sakura API-key provisioning, rotation, and revocation flow — the long-lived-key risk (D3) needs an operational answer.
  • Problem payload delivery. Whether private container images use a Sakura container registry, and how that maps to the private-payload model (ADR-012 / the S3 presigned-URL analog).

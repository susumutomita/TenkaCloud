ADR-011: admin-console per-tenant ドリルダウン — System Admin が cross-tenant に deploy 進捗を見る経路

Status:Proposed 2026-05-11
Issue: #590
Related ADR: ADR-001、 ADR-004

Context

PR-585 (#532) で admin-console (System Admin) の tenant 一覧に provisioning 状態 badge + CodeBuild log link を追加。 PR-588 (#534) で application-admin-console (Tenant Admin) の deploy job 詳細に CFn StackEvents / Resources / Console link を追加。

ただし System Admin から各 tenant の deploy job 進捗を横断的に見る経路は存在しない。System Admin が「どの tenant のどの問題が今 deploy 中か」「失敗してる tenant はどれか」を確認するには、tenant ごとに application-admin-console に切り替えて再ログインする必要がある。

制約由来本 ADR への影響
テナント分離はインフラ層でINVARIANT_TENANT_ISOLATION_AT_INFRA_LAYER System Admin だけが超える正規経路を本 ADR で設計
cost 最小化repo 経済設計 新 Lambda 1 個 + 既存 DDB read で完結、新 table は追加しない
polling over SSELambda は long-lived connection を持てないため real-time は polling で実装する設計原則 tenant 一覧の auto-refresh は 60s polling
HTTP status は enumrepo 規約: 数値リテラル直書き禁止、 http-status-codes ライブラリの StatusCodes.* を使う 新 endpoint も StatusCodes.* 規約遵守
SystemAdmin group は SBT 標準SBT 0.3.9 Cognito authorizer は SystemAdmin group のみ受理

現状

  • admin-console は SBT ControlPlane API のみ叩く (= tenant CRUD)
  • tenant 一覧の provisioning status は provision-tenant.sh の最終出力 (= bootstrap 完了 / 失敗) 粒度のみ
  • Application Plane の Events / Deployments table を read する経路は tenant API GW (Cognito JWT、custom:tenantId claim) のみ
  • System Admin が他 tenant の Events を見るには (a) tenant Admin に invite してもらう、(b) AWS Console で DDB を直接叩く、のどちらか — どちらも運用上厳しい

D1. Read 経路

案採否内容欠点
D1-A採用 新 backend Lambda + 新 API (`AdminInsightApiLambda`)。SystemAdmin Cognito JWT で認可、Application Plane DDB (Events / Teams / Deployments) を read-only (cross-tenant) で query する。新 stack `AdminConsoleHostingStack` か既存 ControlPlane に同居する 新 Lambda 1 個増 (~$0 idle、Free Tier 内)
D1-B却下 既存 tenant API を SystemAdmin claim で bypass tenant authorizer に SystemAdmin 例外を埋め込むのは 分離の境界を破る。tenant 側 Lambda が cross-tenant の責務を持ってしまう
D1-C却下 iframe / new window で application-admin-console をログインせず開く OAuth Code + PKCE が各 tenant Cognito に別々ログインを要求するので結局再ログインが要る、UX 不一致

D2. 認可境界

案採否内容
D2-A採用 SBT 標準 SystemAdmin group (= ControlPlane の Cognito UserPool に既存)。新 Lambda の authorizer で cognito:groups claim に SystemAdmin が含まれることを必須化
D2-B却下 新 Cognito group (例: SystemAdminReadOnly) を追加
D2-C却下 IAM-based authorizer (= SigV4)

D3. drill-down 段階

段階表示API
L1 tenant 一覧 (= 既存 admin-console) tenant 一覧 + active deploy / failed / total の集計 column 追加 GET /admin/insight/tenants/summary (= per-tenant 集計)
L2 tenant 詳細 tenant の Events 一覧 (= application-admin-console EventList と同等) GET /admin/insight/tenants/{tenantId}/events
L3 event 詳細 event の deploy 進捗 (= EventDetail の問題セット / チーム を read-only) GET /admin/insight/tenants/{tenantId}/events/{eventId}
L4 deploy job 詳細 CFn StackEvents / Resources / Console link (= PR-588 DeploymentDetail と同等) GET /admin/insight/tenants/{tenantId}/deployments/{jobId}
GET /admin/insight/tenants/{tenantId}/deployments/{jobId}/stack-progress

D4. CFn StackEvents 経路

same-account 前提 (= MVP-1 と同じ)。Application Plane の各 tenant 用 stack は同 AWS account 内に存在するので、新 Lambda の IAM role に cloudformation:DescribeStackEvents / cloudformation:DescribeStackResources を Resource:* で grant する (PR-588 と同設計)。

Phase 2 (= 競技者 cross-account に Lambda が直接見にいく時) は #459 ADR-009 の cross-account federation を流用する (= deployment 行から (awsAccountId, externalId, competitorRoleName) を読んで AssumeRole)。

D5. 監査ログ

案採否内容
D5-A採用 CloudWatch Logs structured log。各 read API に console.log({ event: "admin.insight.read", admin: sub, target: tenantId, path }) を入れて Logs Insights で query 可能に
D5-B却下 専用 DDB AdminAuditLog table 1 table 増 + WCU 課金、現フェーズ過剰
D5-C却下 監査ログ無し compliance / 信頼性で不可

D6. read-only スコープ

Phase 1 は read-only に限定。SystemAdmin が他 tenant の deploy を中止 / lock-scoring / 再 deploy する操作経路は本 ADR では作らない (= 別 ADR で要件確定後)。

理由:

  • SystemAdmin が誤って他 tenant の競技中 event を止めると blast radius が大きい (= 全 team の競技体験を破壊)
  • read-only に閉じることで 境界の正当性 (= tenant 分離違反は「読むだけ」) が明確になる
  • Phase 2 で write 経路を作るなら「明示 ack ボタン + 監査 log 強化 + 競技者通知」が要る (= 別 ADR)

Phase 1 Acceptance Criteria

  • System Admin が admin-console から tenant 一覧 → tenant 行 click → Events 一覧 → Event 行 click → deploy 詳細 へ 1 度もログインし直さず ドリルダウンできる
  • failed な deploy が存在する tenant が tenant 一覧で識別できる (= 失敗件数 badge)
  • CFn StackEvent reason が System Admin 画面で直接読める
  • Tenant Admin (= non-SystemAdmin) は同じ API を叩いて 403 を返される
  • 各 read action が CloudWatch Logs に structured log として残る

API 設計 (Phase 1)

methodpathresponse
GET/admin/insight/tenants/summary { items: [{ tenantId, name, tier, activeDeploys, failedDeploys, totalEvents }] }
GET/admin/insight/tenants/{tenantId}/events { items: [EventSummary], nextCursor? } (= 既存 EventSummary 型を流用)
GET/admin/insight/tenants/{tenantId}/events/{eventId} EventDetail (= 既存型、ただし teamLoginKey は黒塗り)
GET/admin/insight/tenants/{tenantId}/deployments/{jobId} DeploymentDetail (= 既存型)
GET/admin/insight/tenants/{tenantId}/deployments/{jobId}/stack-progress { stackEvents, resources, consoleUrl } (= PR-588 同型)

セキュリティ要件:

  • teamLoginKey は detail response から 除外 (= System Admin 経路で漏洩しない、Tenant Admin の領域)
  • path の tenantId は実在チェック (= tenant 存在しないなら 404)。tenantId を typo して別 tenant の data を見ない保証
  • tenant 削除済の場合は historical data の read を許可 (= archive view)

Consequences

positive

  • System Admin が 全 tenant 横断で deploy 状態を観察 できる (= 運営判断のため必須)
  • tenant 分離原則を 1 つの正規経路 (= AdminInsightApiLambda) に閉じ込め、tenant Lambda 側に admin 例外を漏らさない
  • 監査ログ (CloudWatch) で誰がいつ覗いたか追える
  • Phase 2 で #459 ADR-009 と統合すれば cross-account の StackEvents まで System Admin が直接見える

negative

  • 新 Lambda 1 個 + Cognito group 配線 + IAM の追加
  • SystemAdmin の権限が「全 tenant の Event / Deployment 内容を read 可能」に拡大 (= 既存は tenant CRUD のみだった)
  • admin-console SPA に 3 新 page (Events 一覧 / Event 詳細 / Deploy 詳細) が必要、bundle size +

open questions (= follow-up issue)

  • tenant 一覧の activeDeploys / failedDeploys 集計は per-tenant Scan が必要。tenant 数 × per-tenant Deployments 行数 で RCU 消費が問題化する境界はどこか
  • 監査ログのリテンション (CloudWatch Logs default 30 日で良いか)
  • Phase 4 (write 操作) の正当な ADR 要件 — どこまでが SystemAdmin の責務か
  • tenant 削除済の historical data はどこまで残すか (TTL との関係)

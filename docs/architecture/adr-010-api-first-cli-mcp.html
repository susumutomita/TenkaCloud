ADR-010: API-first / CLI / MCP — operator 経路を AI native 化する

Status:Proposed 2026-05-11
Issue: #578
Related ADR: ADR-001、 ADR-004、 ADR-007

Context

TenkaCloud の operator 操作 (event 作成 / bulk deploy / schedule / notify) は web UI (application-admin-console) 経由のみ 提供されている。認証は Cognito Hosted UI による OAuth Code + PKCE フローで browser 必須。これにより CLI / AI agent (Claude Code / Cursor / Codex 等) が operator API を直接呼べない。

「AI 対応がなければレガシー」(= 2026 年時点の SaaS 評価軸)。本 ADR で API-first 化を段階的にロールアウト し、operator 操作を browser から CLI / AI に解放する。

D1. M2M 認証方式

案採否内容欠点
D1-A採用 Cognito Client Credentials grant。既存 tenant Cognito UserPool に App Client (no secret) ではなく Client Credentials 対応の app client を新設。POST /oauth2/token で client_id + client_secret から JWT を取得 tenant 単位で app client を払い出す運用必要 (= operator が CLI 用 token を生成する画面が要る)
D1-B却下 独自 API Key (DDB に保存 + hash 比較) Cognito JWT 経路と二重管理。既存 authorizer の置換が大きい
D1-C却下 mTLS / IAM SigV4 operator 体験が劣る (鍵 / 証明書管理が複雑)、Cognito 既存資産が無駄になる
D1-A の運用フロー
  1. operator が application-admin-console で「CLI トークン発行」 ボタンを押す
  2. backend が Cognito CreateUserPoolClient で新 client (generateSecret=true) を tenant scope に作成
  3. client_id + client_secret を画面に 1 度だけ表示 (= operator が CLI 環境変数 / config に保存)
  4. DDB の CliTokens table に発行履歴を記録 (id / createdAt / createdBy / lastUsedAt)、revoke 可能に
  5. operator は CLI で tenkacloud auth login --client-id ... --client-secret ... 実行 → access_token を ~/.tenkacloud/credentials に保存

D2. OpenAPI 生成方式

案採否内容欠点
D2-A採用 @hono/zod-openapi。既存 Hono routers + 既存 zod schemas (= types.ts の CreateEventRequestSchema 等) を OpenAPIHono に書き換えるだけで自動生成。生成された OpenAPI 3.x spec を CI で artifact 化 既存 routers 全て (= event / deploy / participant / notification) の置換が必要。1 router あたり ~50 行の書き換え
D2-B却下 手書き openapi.yaml handler と spec の drift が即発生。type 安全性なし
D2-C却下 tsoa (TypeScript controllers + decorator) Hono と相反するパラダイム (= controllers vs functional router)、既存実装の置換コスト最大

D3. CLI runtime

案採否内容欠点
D3-A採用 Node + bun (npm package @tenkacloud/cli)。repo の他 package と同じ TypeScript / vitest stack を流用。bunx @tenkacloud/cli で 1 回実行可能 operator 環境に Node 22+ / bun が必要 (= AWS CloudShell には bun が未デフォルト、curl install が要る)
D3-B却下 Go binary (single static binary) repo の言語 stack が分裂。OpenAPI client 生成は Go でも可能だが、tenkacloud のドメインモデルが TS で書かれている
D3-C却下 Rust binary 同上 + 開発速度の問題
D3-A の package 構造 
packages/cli/
├── package.json              # name: "@tenkacloud/cli", bin: "tenkacloud"
├── src/
│   ├── index.ts              # CLI entry (commander.js or yargs)

│   │   ├── login.ts          # Client Credentials → ~/.tenkacloud/credentials

D4. 宣言的 spec 形式

案採否内容欠点
D4-A採用 YAML (kubectl 風)。tenkacloud apply event.yaml で event spec を冪等適用。apiVersion: tenkacloud.io/v1 / kind: Event / spec: {...} の慣用フォーマット operator が YAML を書く必要 (= UI と比べて初見障壁高い、CLI/AI 経路のみ)
D4-B却下 HCL (Terraform 風) operator に追加文法。生態系が AWS-IaC に偏っており competition spec には過剰
D4-C却下 TypeScript (CDK 風 imperative) 「宣言的」が崩れる、apply の冪等性が手書きロジック依存になる
D4-A の event.yaml 例 
apiVersion: tenkacloud.io/v1
kind: Event
metadata:
  name: jaws-ug-spring-2026
spec:
  teams:
    - internalSlug: team-alpha
      awsAccountId: "111111111111"
    - internalSlug: team-beta
      awsAccountId: "222222222222"
  problems:
    - problemId: hello-world-battle
      defaultRegion: ap-northeast-1
  schedule:
    startsAt: 2026-05-11T14:00:00+09:00
    endsAt:   2026-05-11T17:00:00+09:00
tenkacloud apply -f event.yaml で:
  1. name で既存 event を検索 (= label selector)、なければ create
  2. teams / problems の diff を計算、必要なら patch / bulk deploy enqueue
  3. schedule の startsAt / endsAt を patch
  4. dry-run mode: 上記 diff を表示のみで apply しない

D5. MCP server 配置

案採否内容欠点
D5-A採用 local subprocess (= Claude Code が npx @tenkacloud/mcp-server を起動)。MCP server は M2M token を CLI と同じ ~/.tenkacloud/credentials から読む operator のローカル環境に bun / node が必要
D5-B却下 remote Lambda (= MCP 経路を HTTP で expose) 1st-party MCP の現行仕様 (stdio / SSE) と整合しない、追加 Lambda + IAM のコスト
D5-C却下 local + remote 両モード MVP には過剰、Phase 5+ で remote が要りそうになったら別 ADR で扱う

D6. 段階的ロールアウトの順序

Phasescope依存並列可
0 M2M auth (Cognito Client Credentials app client + ADR) なし—
1 OpenAPI 生成 (zod-openapi 全 routers 置換 + CI artifact) なしPhase 0 と並列
2 CLI scaffold (packages/cli/ + 主要 subcommands) Phase 0 + 1—
3 宣言的 apply (tenkacloud apply event.yaml + reconciler) Phase 2Phase 4 と並列
4 MCP server (packages/mcp-server/ + Claude Code 向け manifest) Phase 2Phase 3 と並列

採用順: 0 → 1 (並列) → 2 → 3 / 4 (並列)。Phase 0 と 1 は独立に開発できるので 2 並列で開始する。Phase 2 が完了したら Phase 3 と 4 を 2 並列でロールアウト可能。

D7. 既存 web UI との関係

並存。CLI / MCP は web UI を置き換えない。理由:

  • operator の onboarding は web UI の方が compelling (= Cloudscape の UX、ドキュメント不要)
  • 競技中の 1 件だけ手動操作 (= 特定 team の問題 status を確認、通知 1 件送信) は CLI より UI の方が早い
  • CLI は 自動化 + AI 経路 の専用、bulk 操作 / repeat-able 操作に強い
  • 両者は同じ HTTP API を share するので、片方で起きた変更は他方からも観察可能 (= ADR-007 outside-in scenario との整合)

Phase 別 Acceptance Criteria

Phase 0 (M2M auth、本 ADR 採択直後の次 PR)

  • aws cognito-idp admin-initiate-auth 経路で operator JWT を取得できる
  • その JWT で POST /events が 200 を返す
  • 既存 web UI (admin-console) OAuth Code + PKCE は無変更で動く (= regression なし)
  • integration test: M2M で event create → list → delete の full cycle が pass

Phase 1 (OpenAPI)

  • infrastructure/openapi.json が CI で出力される
  • 主要 routers (event-handler / deploy-handler / participant-handler) すべて OpenAPIHono 形式
  • diff 検出: 既存 API の breaking change が PR review で見える

Phase 2 (CLI)

  • tenkacloud event create / list / delete / deploy / schedule / end / notify が動く
  • tenkacloud --help が subcommand を一覧
  • tenkacloud auth login で M2M token を ~/.tenkacloud/credentials に保存

Phase 3 (宣言的 apply)

  • tenkacloud apply -f event.yaml で event spec を冪等適用
  • tenkacloud apply -f event.yaml --dry-run で diff のみ表示
  • spec 削除 (= kubectl delete 相当) は明示コマンド (tenkacloud delete -f event.yaml)、apply では暗黙削除しない

Phase 4 (MCP server)

  • Claude Code から 「event を作って全 team に deploy して 14:00 開始」 を 1 文で実行できる
  • MCP tools: event_create / event_list / event_deploy / event_schedule / notify_send
  • MCP resources: tenkacloud://events で event 一覧を read

Consequences

positive

  • AI agent (Claude Code / Cursor / Codex) から operator 操作可能。 自己使用検証 (= 開発者自身が運用) でも CLI 経路を経由できる
  • OpenAPI 化で typed client / SDK 自動生成。CLI / MCP / 他言語 client が同一 spec から再現可能
  • 競技運営の自動化 (= event を YAML で declare、git で版数管理、CI で apply)
  • 新 operator のオンボード時間短縮 (= CLI --help + OpenAPI spec で API 表面を発見可能)
  • ADR-007 outside-in scenario との相補性: Playwright scenario と同じ操作を CLI でも記述できる (= dual surface validation)

negative

  • Phase 0-4 で 5 つの大型 PR が必要。完成まで数週間以上
  • OpenAPI 化 (Phase 1) は既存 routers 全置換、regression risk あり (= 慎重に段階移行)
  • CLI package のメンテナンス cost (= 新規 endpoint 追加時に CLI subcommand も追加が要る、CI で自動生成しない限り)
  • MCP server の AI 経路は 誤操作リスク (= 自然言語が compile されて bulk delete されるシナリオ) — Phase 4 で MCP tools に dry-run + confirm mode 設計が要る

open questions (= follow-up issue)

  • Phase 0 で発行する Client Credentials の scope 細分化 (= read-only / event-write / deploy-write の分離)
  • CLI の multi-tenant 切替 UX (= ~/.tenkacloud/credentials に複数 profile or env 変数で切替)
  • CLI の backward-compat policy (= API breaking change に CLI でどう対応するか)
  • MCP tools の dry-run / confirm 設計 (= 破壊的操作の事前確認)
  • participant 経路の CLI 化 (= 競技者用 tenkacloud-participant 別 binary を立てるか、operator CLI と同居か)

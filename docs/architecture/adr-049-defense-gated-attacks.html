ADR-049: Defense-gated attacks

正しく守れたチームは攻撃をブロックし、 報われる。 disruption が防御条件を宣言し、 platform は チームの posture を評価して「ブロック (= 注入も減点もせず防御ボーナス)」 か 「成立 (= 注入 + 減点)」 を 分岐する。 防御の中身は問題が所有し、 platform は条件を dispatch するだけ。

Status: Proposed 2026-06-19
Related: ADR-034 (攻撃の 2 実現パターン / 防御の self-report), ADR-033 (採点上の disruption 効果 = 減点), ADR-037 (disruption の予約 / 定期 / 条件発火), ADR-038 (always-ends), ADR-012 (problem = plugin, platform = host)

Context

運用フィードバック (live event): red-team の攻撃が 100% 成立してしまい、 サイトを正しく構築・防御 しても結果が変わらない。 防御ゲームの肝が死に、 つまらない。 「正しく守れていれば攻撃をブロックし、 守れたチームが報われる」 のが望ましい。

ADR-034 は攻撃の実現を 2 パターンに分けている:

パターン防御の効き方現状の問題
A. 可用性劣化型 (attack → uptime が下がる) 防御非依存。 負荷/飽和でアプリが劣化すれば、 ハードニングの度合いに関係なく uptime が落ちて減点。 StackStack の availability-flood 等がこれ。 = 観測された「100% 成立」 そのもの。
B. 防御テスト型 (attack probe → アプリが self-report → attack-detection 採点) 防御を評価する。 ブロックしたチームを加点、 突破は減点しない。 「防御が報われる」 mechanic は既にあるが、 問題が self-report (CFn Output counter) を実装し attack-detection kind を使う前提。 可用性型には効かない。

さらに platform 側の減点 (ADR-033 の disruption effect) と注入 (ADR-031 executor / ADR-037 timing) は 無条件に適用される — チームの防御 posture を一切参照しない。 結果、 パターン A の攻撃も、 ADR-033 の penalty window も、 守っていようがいまいが同じだけ刺さる。

Decision

disruption に 宣言的な防御ゲートを追加する。 攻撃発火時に platform が対象チームの posture (= 防御状態) を評価し、 条件を満たしていれば攻撃をブロックする:

項目意味
defense.blockedWhenこのチームが満たしていれば攻撃をブロックする posture 条件 (= 問題の posture key を参照)。
defense.bonus (任意)ブロック成功時に守備側へ与える加点 (= 防御が報われる)。

発火時の分岐:

disruption 発火 (operator / 条件 / 定期、 ADR-037) │ ├─ defense.blockedWhen を宣言? ──no──▶ 従来どおり: 注入 (executor) + 減点 (ADR-033 effect) │ │yes │ ▼ │ 対象チームの posture を解決 (問題所有の防御信号) │ │ │ 満たす (= 防御済) ──▶ BLOCKED: 注入を skip / ADR-033 減点を waive / defense.bonus を加点 │ │ │ 満たさない (= 無防備) ──▶ LANDED: 従来どおり 注入 + 減点 ▼ score event に結果を残す ("attack blocked — defense bonus" / "breached — penalty")

防御信号は問題が所有する (ADR-012)

「守れている」 の判定 (= posture) は 問題の所有物であり、 platform は中身を知らない。 platform は disruption が宣言した posture key を、 問題が公開する posture 信号 (= StackStack の /posture gate — rate_limited / ssh_closed / auth_enabled 等、 ADR-034 の attackProbe / dashboard posture と同じ source) から解決し、 条件の真偽を評価するだけ。 防御ロジックを platform に hardcode しない。 例: availability-flood の blockedWhen: rate_limited = 「WAF レート制限を入れたチームには洪水攻撃が通らない」。

パターン A / B との関係

  • パターン B (self-report) は問題側で「防御を加点」 する既存路として残る (= 攻撃検知をアプリが実装する問題向け)。
  • 本 ADR は platform 側のゲートを足し、 パターン A (可用性型) でも防御を効かせる。 問題は self-report を実装せず、 既に公開している posture を blockedWhen で参照するだけでよい。 = 「防御が報われる」 を可用性攻撃にも一般化する。

always-ends (ADR-029 / ADR-038) との結線

ブロックは liveness を壊さない: ラウンドは必ず終わる。 攻撃が成立した場合も、 ADR-037/031 の revert は 従来どおり予約され、 障害は永続しない。 ブロック時は注入しないので revert も不要。

Alternatives considered

案評価却下理由
現状維持 (攻撃 100% 成立)却下防御ゲームが成立しない (= 本 ADR の動機)。
パターン B (self-report) のみ併存 問題ごとに self-report 実装 + attack-detection kind が要り、 可用性型には効かない。 本 ADR の platform ゲートは self-report 無しで防御を効かせ、 B を置き換えず補完する。
platform が防御判定を hardcode却下 ADR-012 違反 (= 防御の中身は問題所有)。 platform は宣言条件を dispatch するだけにする。
「何か防御していれば全攻撃ブロック」 の粗い gate却下 攻撃と防御の対応 (= flood ↔ rate-limit) が表現できず、 ゲーム性が落ちる。 per-disruption の blockedWhen で「この攻撃はこの防御で止まる」 を宣言できるようにする。

Consequences

  • 防御が結果を変える → 競技として成立し、 ハードニングの努力が報われる (= 100% 成立の解消)。
  • 可用性型攻撃にも防御を効かせられる (= self-report 不要、 既存 posture を参照)。
  • 防御の中身は問題所有のまま (ADR-012)。 platform は条件評価のみ。
  • posture 信号の信頼性とtenant/team scope が前提 (= 誤判定で誤ブロック/誤減点しない)。 posture source の解決と鮮度を慎重に設計する。
  • 結果の可視化が要る (= なぜブロック/被弾したか)。 #1917 (participant service-status) / #1916 (operator team-status) と一体で初めて意味を持つ。

Migration

追加 (additive) であり破壊的変更はない。 defense 未宣言の disruption は従来どおり無条件に成立する。

  1. SCHEMA (TenkaCloudChallenge submodule): disruptions[].defense = { blockedWhen, bonus? } と、 問題が公開する posture source の宣言を追加する。
  2. platform 評価: executor (注入) / ADR-033 effect (減点) の発火直前に、 宣言された posture を解決して blockedWhen を評価し、 満たせば注入 skip + 減点 waive + bonus 加点 (= BLOCKED outcome)。
  3. 採点透明性: BLOCKED / LANDED を score event の理由として残す (= #1917 と接続)。
  4. 後方互換: 既存 disruption は defense 無し = 従来挙動。 問題作者が攻撃ごとに 「この防御で止まる」 を宣言したものから順に防御可能になる。

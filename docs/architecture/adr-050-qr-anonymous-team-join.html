ADR-050: QR anonymous team join

初対面・ミートアップの参加者に、 個人情報を一切もらわずチームの login key を渡す。 QR を 「これ読んで」 で配り、 スキャン → portal がキー入りで開く → ワンタップ参加。

Status: Proposed 2026-06-19
Related: ADR-042 (email 招待 = 既知の相手向け / revocable), ADR-047 (deploy 窓 = 触れる時間の有界化), ADR-012 (apps/* は共有 dist + runtime-config)

Context

participant-portal のログインは チーム単位の login key で行う (team ごとに払い出される秘密鍵を portal に入力 → セッション確立)。 鍵を相手に渡す手段は今のところ 2 つしかない:

手段前提初見の人への適性
メッセージ / チャットで鍵を送る連絡先を既に知っている不可 — 連絡先交換が要る
email 招待 (ADR-042)相手の email を入力する重い — 個人情報 (email) をもらう必要がある

ミートアップや展示ブースで「その場で初見の人に触ってもらう」 とき、 上記はどちらも摩擦が大きい。 連絡先も email も取らずに、 その場で見せて読ませるだけで参加させたい。 物理的に同席している 相手に短時間で渡す用途には QR が最適である。

Decision

team ごとに join URL を符号化した QR コードを出す。 join URL は participant-portal の 起点 URL に login key を fragment で載せた形にする: 

https://<portal-origin>/join#k=<teamLoginKey>

スキャンした端末のブラウザが portal を開き、 portal は fragment の k を読んで ログインフォームに自動投入 → ワンタップ (または自動) で参加する。 鍵を手入力させない。

operator 画面 (team ごと) 初見の参加者 ┌─────────────┐ │ ▓▓ QR ▓▓ │ ── 「これ読んで」 ──▶ カメラでスキャン │ Team Alpha │ │ └─────────────┘ ▼ ▲ portal /join#k=… が開く │ │ 「投影」 表示モード ▼ fragment の鍵を自動投入 (ミートアップで大きく出す) チーム参加 (個人情報の入力なし)

fragment を使う理由 (鍵をサーバに送らない)

login key を query (?k=) ではなく URL fragment (#k=) に置く。 fragment は HTTP リクエストに含まれず、 サーバ・CloudFront・アクセスログ・Referer に 送信されない。 鍵はスキャンした端末のブラウザ内だけに留まり、 portal の client JS が読んで使う。 これにより 「QR 経由の参加」 が中間ログに鍵を残さない。

QR の生成 (依存を増やさない)

QR の符号化は 依存を追加せず、 小さな自前エンコーダ (SVG 出力) を @tenkacloud/web-kit に同梱して実現する。 これは本リポジトリの supply-chain 方針 (trustedDependencies を空に保ち、 lifecycle script を持つ新規 npm を増やさない) に沿う。 QR は client 側で SVG として描くため、 鍵がサーバや画像生成サービスに渡らない (= fragment 方針と一貫)。

セキュリティモデル

join URL / QR は bearer credential である — 見えた人は誰でもそのチームに入れる。 これは 「その場で配って即参加」 という目的そのものであり、 email 招待 (1:1 / revocable, ADR-042) とは 別レーンとして共存させる。 リスクは次で抑える:

  • 鍵は fragment に置き、 中間ログ・Referer に残さない (上記)。
  • QR は その場限りの提示を前提とし、 公開ページや indexable な場所に貼らない (= 運用ガイドに明記)。
  • operator は team の login key を rotate できる (= QR を配った会が終わったら鍵を回し、 以後の参加を断つ)。 ADR-047 の deploy 窓と併用すれば、 そもそも触れる時間が有界化される。
  • scope は単一 team に閉じる (= 1 つの QR は 1 team にしか入れない。 tenant / 他 team を跨がない)。
  • QR は client 描画。 鍵を画像化するために外部サービスへ送らない。

Alternatives considered

案評価却下理由
email 招待のみ (ADR-042) 併存 既知の相手・revocable な配布には最適だが、 初見の人から email をもらう摩擦が大きい。 QR は これを置き換えず、 anonymous-join レーンとして補完する。
QR に raw login key だけを符号化 却下 スキャン後に参加者が鍵を読み取って手入力する必要があり摩擦が残る。 join URL なら スキャン → 自動で portal が開きキーが入る。
鍵を query (?k=) に載せる 却下 query はサーバ・CDN・アクセスログ・Referer に送信され、 鍵が中間に残る。 fragment なら残らない。
QR ライブラリを npm 追加 却下 lifecycle script を持つ新規依存は supply-chain 面を広げる。 QR は枯れた仕様で、 小さな自前 SVG エンコーダで十分。
ワンタイム / 短命トークンで参加 将来 より厳密だが token 発行・失効の基盤が要る。 まず鍵 rotate + deploy 窓 (ADR-047) で 実用的な失効性を確保し、 必要が顕在化したら別 ADR で追加する。

Consequences

  • 初見の人に個人情報なしで「読ませるだけ」 で参加させられる (= ミートアップ / ブースの摩擦が消える)。
  • 鍵が中間ログに残らない (fragment + client 描画)。
  • 新規 npm 依存ゼロ (自前 QR エンコーダを web-kit に同梱)。
  • 既存の鍵ログインは不変 (= 後方互換)。 email 招待 (ADR-042) と独立に共存。
  • join URL は bearer。 「その場限り提示」 「鍵 rotate」 「deploy 窓」 で運用的に抑える前提を ガイドに明記する。

Migration

追加 (additive) であり破壊的変更はない。

  1. @tenkacloud/web-kit に no-dep の QR エンコーダ (SVG 出力) と、 join URL を組む helper を加える。
  2. participant-portal に /join ルートを追加し、 fragment の k を読んで ログインに自動投入する (鍵が無ければ通常のログイン画面)。
  3. application-admin-console の team 一覧 / 詳細に「QR で共有」 を出す: team ごとの QR と、 ミートアップ用の投影 (大画面) モード。 鍵 rotate 操作も同画面に置く。
  4. 運用ガイド (community / facilitator docs) に bearer の注意と rotate 手順を追記。 i18n は ja / en。
  5. 既存 team は変更なし。 operator が QR を使いたい team でだけ表示する。

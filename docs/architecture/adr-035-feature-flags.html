ADR-035: Feature flags — typed registries with runtime-config overrides

Accepted Delivery gap open   Scope: SPA feature gating; explicitly not infrastructure toggles

Context

Experimental surfaces (per-tenant SAML SSO, non-AWS runtime management, red-team disruption tooling) need to ship dark: merged and deployed, but hidden until an installation opts in. Requirements that shaped the mechanism:

  • Flags must be typed and enumerable per app — a flag that nothing reads, or a typo'd override key, should be impossible to introduce silently.
  • Overrides must not require rebuilding the SPA. The built dist/ is shared across tenants (architecture invariant: per-tenant differences flow only through runtime-config.json).
  • Flipping a flag must never create or destroy cloud resources — flags gate UI and behaviour, not infrastructure shape.

Decision

  • Registry per app. Each SPA declares its flags in src/features.ts as a FEATURE_REGISTRY entry: key, human description, stability (experimental | …), and defaultEnabled. The registry is the complete flag universe for that app.
  • One resolver. resolveFeatureFlags(registry, overrides) in @tenkacloud/web-kit merges registry defaults with an override object. Unknown keys and non-boolean values are ignored — an override can only flip flags the registry declares.
  • Overrides travel in runtime-config.json under a features object. Runtime config is served with no-store/no-cache, so an override change is visible on the next page load without rebuilding or invalidating the SPA bundle. During local development, VITE_FEATURES provides the same override map.
  • Deploy-time infrastructure toggles are out of scope. Settings that change synthesized resources (e.g. whether the participant portal stack exists, SAML IdP provisioning, quota limits) are CDK parameters (CDK_PARAM_*), not feature flags: they require a deploy by nature and must not be presented as runtime-flippable.
// resolution (conceptual)
config.features = resolveFeatureFlags(FEATURE_REGISTRY, runtimeConfig.features)
// component gate
if (config.features.samlSso) { /* render IdP management */ }

Delivery status and target state

The resolver, registries, and component gates are in place. Two delivery pieces are not yet implemented, and until they land every flag rests at its registry default (the only workaround being manual edits to the deployed runtime-config.json object in S3):

PieceTarget behaviourTracked by
Deploy-time override emission The CDK runtime-config writers accept a features map from environment configuration and emit it into runtime-config.json, making flag values a reviewed, versioned deploy input. Issue #2230
Per-tenant runtime toggles A tenant-admin settings surface (role-gated API + audited writes + console UI, following the same storage pattern as the event scoringLocked toggle) lets a TenantAdmin flip that tenant's flags at runtime; the resolved order is registry default → deploy-time override → tenant override. Issue #2231

Consequences

  • Every flag is discoverable in one file per app, with a description and stability level a settings UI can render directly.
  • Flag changes are UI-safe by construction: the override channel cannot reach infrastructure.
  • A flag whose gated code is removed should be deleted from the registry in the same change; the resolver's unknown-key rule means stale overrides degrade harmlessly.
  • Because overrides are ignored unless boolean, operators cannot smuggle configuration values through the flag channel — non-flag configuration belongs to the typed runtime-config fields.

Alternatives considered

AlternativeWhy rejected
Build-time flags (import.meta.env only) Would fork the shared dist/ per tenant, violating the unmodified-app invariant.
A third-party flag service External dependency and cost for a platform whose budget target is the AWS Free Tier; overkill for boolean gates.
Free-form features bag without a registry Unreadable flag universe, silent typos, and no metadata to drive a future settings screen.

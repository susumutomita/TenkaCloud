ADR-051: Sunset-service requiem problems

サービス終了 (サ終) した AWS サービスは新規作成できない。 そのサービスは 「動かして偲ぶ」 ことができないため、 振る舞い (= ルール / API の契約) を生きている後継 サービスで再現させる移行問題として供養する。

Status: Accepted 2026-06-22
Related: ADR-012 (問題 = plugin / 6 builtin scoring kind), ADR-034 (実攻撃の実現 / attack-blocked スコア統合)
Pilot: battles/waf-classic-kuyo (WAF Classic → WAF v2)

Context

AWS は毎年いくつかのサービスを終了する (例: WAF Classic = 2025-09-30、 Elastic Transcoder = 2025-11-13、 Kinesis Data Analytics for SQL = 2025-10-15、 QLDB = 2025-07-31)。 サ終したサービスは CloudFormation で新規作成できないため、 TenkaCloud の標準的な「競技者アカウントへ stack を deploy して実リソースを触る」型の 問題には使えない。

一方で、 サ終サービスからの移行は実務上の頻出課題であり、 GameDay / Battle の題材として価値が高い。 「去りゆくサービスを問題として残す」ことは、 カタログ (TenkaCloud の中核資産) を感情に訴える供給源で広げる動線にもなる。

採点エンジン側に制約がある。 generic-scoring-handler の attack-detection kind は CFn Output 内の生 counter を差分加点するが、 runtime-status-reconciler は stackOutputs を runtimeStatus が ready になった時点で一度だけ凍結する (採点 tick ごとの 競技者アカウント再読込・assume-role・CloudWatch/SSM 読みは行わない)。 したがって attack-detection で「WAF の BlockedRequests など live なメトリクス」を採点することは 現行アーキテクチャでは成立しない (Output が更新されず常に同値 = 0 点)。

Decision

サ終サービスを題材にした問題は、 次の 3 点を満たす「供養 (requiem)」型として作る。

  1. 死んだサービスは一切 deploy しない。 問題テンプレートが宣言する Type: AWS::* はすべて生きているサービスに限る。
  2. 旧サービスの契約を「遺品」として配布する。 旧設定のエクスポート (ACL / Rule / API スキーマ等) を SSM Parameter と問題リポジトリ (legacy/*.json) の両方で competitor に渡し、 同じ契約を生きている後継で再現することを課題にする。
  3. 採点は実 probe 型 uptime-multi + attackProbes を使う。 採点 tick が公開エンドポイントへ HTTP probe する (クロスアカウント不要)。 正常系が 期待ステータスを返す間は pointsAllOk、 攻撃 probe が vulnerableStatus を返したら penalty。 「防御が効くと攻撃が素通りしない = 減点されない」形で 防御の成否をスコアに写す。

Pilot: waf-classic-kuyo (WAF Classic → WAF v2)

丸腰のプロフィール API (Lambda + API Gateway REST, regional) を deploy し、 旧 WAF Classic の WebACL ダンプ (遺品) を渡す。 competitor は同じ 3 ルールを WAF v2 で再現し、 REST ステージへ WebACLAssociation する。 採点は GET / の uptime (= 過剰ブロック防止) と SQLi probe のブロック有無で行う。

Alternatives considered

案判定理由
attack-detection kind で WAF の BlockedRequests を採点 Rejected stackOutputs が ready 時に凍結され live メトリクスを反映できない。 per-tick の競技者アカウント metric 読み (assume-role + CloudWatch) は cross-account / IAM を伴う platform 拡張であり、 別 ADR で扱う範囲。
サ終サービスのエミュレータを deploy Rejected 大半のサ終サービスにエミュレータは存在しない。 維持コストも高い。
後継のエクスポート設定を渡すだけのドキュメント型問題 Rejected deploy と実採点が無いと「触って直す」競技体験にならない。

Consequences

  • + サ終サービス 1 つ = 問題 1 つで量産でき、 カタログの幅が広がる。
  • + 採点は公開エンドポイントへの HTTP probe のみで cross-account 不要、 運営コストが最小 (競技者の後継リソースは競技者アカウントで完結)。
  • + 死んだサービスを deploy しないため、 サ終で壊れる心配がない (遺品はリポジトリと SSM の静的データ)。
  • − 単発 probe で検証できない旧ルール (IP ブロックリスト / レート制限など) は直接採点されず、 移行課題として残る (運営レビュー、 または将来の 採点拡張に委ねる)。
  • − 後継サービスと再現可能な振る舞い契約が明確なサ終サービスに 限られる (明確な後継のないサービスは供養しづらい)。

Migration

パイロット (waf-classic-kuyo) は uptime-multi / status=ready で カタログに載せ済み。 続く供養候補は「明確な後継 + 再現できる振る舞い契約」を基準に選ぶ。

attack-detection を真に live 採点にしたい場合は、 runtime-status-reconciler に per-tick の競技者アカウント metric 読み (assume-role + CloudWatch GetMetricData) を足す platform 拡張が前提となる。 これは cross-account の IAM 設計を伴うため、 本 ADR の 範囲外とし、 必要になった時点で別 ADR で決める。 各供養問題は本番イベント投入前に、 実 アカウントへの deploy → 後継再現 → probe 採点の E2E を最終ゲートとする。

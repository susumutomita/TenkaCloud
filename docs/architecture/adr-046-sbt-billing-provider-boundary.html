ADR-046: SBT BillingProvider waits for billable lifecycle facts

空の請求プロバイダは配線せず、請求根拠になる成功済みライフサイクル事実を先に固定する

Status: Accepted 2026-06-18
Decision: Reject empty BillingProvider wiring
Related: ADR-014, ADR-012, Architecture harness
Tracking: #1764

Context

TenkaCloud uses @cdklabs/sbt-aws for the Control Plane. SBT exposes ControlPlaneProps.billing?: IBilling; when present, the construct creates a BillingProvider and connects billing Lambda targets to the Control Plane event manager. The default SBT triggers are request-oriented: onboardingRequest calls createCustomerFunction, and offboardingRequest calls deleteCustomerFunction. Optional user, usage, ingestor, and webhook hooks can add more targets or routes.

Issue #1764 requested wiring this SBT billing provider into infrastructure/lib/control-plane-stack.ts, with a first implementation that records events only and has no real Stripe, AWS Marketplace, or other provider integration. The requested goal was a billing foundation for tenant onboarding and offboarding events.

That request crosses an accounting boundary. A tenant onboarding request is not a successful tenant subscription, and an offboarding request is not a completed customer deletion. Provisioning can fail, retry, or be superseded by reconciliation. Treating request events as billable customer facts would produce records that look like billing state without proving the tenant state that billing depends on.

TenkaCloud already has application-side usage metering code for deploy, scoring, and event facts. Physical routing and storage for those facts can be added independently of the SBT BillingProvider. A placeholder Control Plane billing provider would add Lambdas, EventBridge rules, and possibly DynamoDB storage before there is a defined external billing sink, accounting ledger, idempotency model, or reconciliation policy.

Decision

TenkaCloud will not pass an empty or event-recording-only IBilling implementation to the SBT ControlPlane. The SBT BillingProvider remains disabled until a billing design defines the concrete provider or ledger, the billable lifecycle facts, idempotency, replay, failure handling, and reconciliation behavior. Billing lifecycle records must be derived from successful tenant lifecycle facts, not from onboarding or offboarding request events alone.

Accepted now Keep ControlPlaneStack without billing wiring. Continue to emit normal tenant provisioning events on the existing EventBridge bus.
Rejected now A no-op billing provider that records onboardingRequest and offboardingRequest as customer lifecycle facts.
Required before wiring A real provider or ledger boundary with success semantics, idempotency keys, reconciliation, storage ownership, and CloudFormation tests.

Rationale

ConcernReason
Billable event semantics SBT's default billing hooks fire on request detail types. Billing needs facts that reflect tenant lifecycle completion or reversal, such as successful provision and deprovision outcomes, not merely accepted API requests.
Idempotency Tenant onboarding and offboarding can be retried. A billing foundation must define stable event IDs, deduplication scope, and replay behavior before records are used as accounting input.
Operational honesty An "empty provider" still deploys infrastructure and produces artifacts that look like billing integration. That makes the product appear closer to billable readiness than it is.
Cost and blast radius Adding Lambdas, scheduled usage pushes, or DynamoDB tables for a placeholder path creates runtime cost and alerting surface without a provider, ledger, or user-facing dashboard.
Webhook exposure SBT can add /billing/{webhookPath} as an unauthenticated Control Plane API route when a webhook function is configured. A placeholder billing slice must not expose such a route before authentication and signature verification are defined.
Architecture ownership Billing is a Control Plane accounting concern. It should be introduced as a deliberate platform capability with CloudFormation assertions, not as a passive listener beside tenant provisioning.

Accepted Boundary

CapabilitySourceStatus
Tenant provisioning and deprovisioning events Existing SBT EventBridge bus and tenant pipeline events Keep
Usage facts for deploy, scoring, and tenant events Application-side usage metering handlers and a future physical usage table route Independent path
SBT BillingProvider with empty recording-only functions ControlPlaneProps.billing Rejected
Billing webhook route SBT webhookFunction and webhookPath Rejected until provider-authenticated

Allowed Future Work

This ADR does not reject billing. It rejects placeholder billing infrastructure that records request events as if they were accounting facts. A future Control Plane billing change can wire SBT BillingProvider when the proposal includes:

  • A concrete IBilling implementation for a provider or first-party ledger.
  • Event detail types that represent successful tenant lifecycle facts, or an explicit mapping from SBT request events to later success and failure reconciliation.
  • Idempotency keys, replay behavior, duplicate handling, and failure recovery.
  • Storage schema and retention rules. Any DynamoDB table must use provisioned 1/1 capacity to match TenkaCloud's low-capacity invariant.
  • CloudFormation assertions using Template.fromStack() for EventBridge targets, Lambda environment, table capacity, and any API route.
  • Provider authentication and signature verification before any billing webhook route is exposed.

Usage metering can continue on its separate path. Deploy, scoring, and tenant-event usage facts are operational facts, while SBT BillingProvider is the customer billing integration point. The two paths can feed the same eventual ledger, but they should not force each other into a placeholder Control Plane construct.

Consequences

Positive

  • Tenant request events are not misrepresented as billable customer lifecycle facts.
  • No new Lambda, EventBridge rule, DynamoDB table, or webhook route is deployed without a real billing boundary.
  • The existing usage metering work can be wired independently to the physical storage and analytics surfaces it needs.
  • A future billing implementation has a concrete checklist for event semantics and tests.

Negative

  • ControlPlaneStack still does not create an SBT BillingProvider.
  • Tenant onboarding and offboarding are not yet connected to a billing provider or ledger.
  • Cost dashboard and tier quota work still require a later accounting design.

Implementation Status

No runtime implementation is required for this ADR. Issue #1764 is resolved by rejecting the requested empty SBT BillingProvider wiring and by defining the prerequisites for a future billing implementation that can safely become a source of accounting truth.

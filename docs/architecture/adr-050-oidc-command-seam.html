ADR-050 — AWS-native OIDC federation for the Cloudflare → AWS command seam

Status: Accepted Date: 2026-07-10 Supersedes: ADR-049 §7 (signed-intent command seam) Relates: ADR-049 §8 (GitHub OIDC lifecycle), ADR-017 / #795 (trust-bridge)

Always-On mode links a control plane on Cloudflare to an on-demand AWS event runtime. ADR-049 §7 chose a bespoke seam for that link: a Worker signs a CloudActionIntent (a hand-built JWS, the trust-bridge library) and POSTs it to an AWS ingress Lambda that verifies the signature and re-publishes the deploy event. This ADR replaces that bespoke seam with an AWS-native one: the Worker acts as an OpenID Connect identity provider and exchanges a short-lived signed token for scoped, short-lived AWS credentials via sts:AssumeRoleWithWebIdentity — the same federation shape ADR-049 §8 already uses for the GitHub Actions stack lifecycle. The change is confined to Always-On mode. The normal SaaS and Lite deploy paths are unchanged: their security is, and remains, an in-account AssumeRole with a per-tenant ExternalId.

1. Context

The permanent SaaS and Lite deploy paths never leave AWS: a worker Lambda inside the platform account assumes a least-privilege role in the competitor account using that tenant's ExternalId, then runs CloudFormation. The trust is AWS IAM end to end; no credential crosses a cloud boundary.

Always-On mode (ADR-049) moves the control plane out of AWS onto Cloudflare Workers to reach near-zero fixed cost. That creates a new problem the ExternalId pattern cannot solve: the publisher of a deploy command is now a Worker, which is not an AWS principal and holds no AWS identity. ADR-049 §7 answered this with a signed-intent seam — the Worker mints a JWS-signed intent, an AWS Function URL Lambda verifies it (signature, audience, expiry, and a DynamoDB-backed nonce for replay), then re-publishes the frozen EventBridge event. Two properties of that design have not aged well:

  • A bespoke token layer. The signing primitives are delegated to vetted implementations (HMAC via node:crypto, ECDSA P-256 via WebCrypto), but the JWS envelope, canonicalization, and verifier dispatch are hand-built. The deployed ingress resolves both an HS256 shared secret and an ES256 public key and dispatches on the token's own alg header, so it accepts a symmetric-secret token in production even though HS256 was intended for internal tooling and tests only. That is a broader trust surface than an asymmetric-only design, and it is safe today only by the convention that the two key materials stay distinct.
  • A standing charge. The replay-prevention nonce table is a DynamoDB table, which the capacity aspect pins to provisioned 1/1. It is the one always-present cost inside a seam whose entire justification is eliminating fixed cost.

Two facts make replacing the seam low-risk. First, in the normal SaaS and Lite paths trust-bridge is wired only as a shadow — it builds an intent and emits an audit log, fail-open, and never touches the credential flow — so nothing load-bearing depends on it there. Second, the Always-On ingress is opt-in: it is deployed only by make deploy-always-on-ingress, is not composed into any standard bin/*.ts, and has not been exercised in a live end-to-end deploy. The seam can therefore be changed before it carries any production traffic.

2. Decision

Replace the bespoke signed-intent seam with AWS-native OIDC web-identity federation, in the variant where the Worker obtains short-lived AWS credentials and publishes the deploy event itself (“variant A” in §5):

  1. The Always-On control-plane Worker serves an OIDC discovery document (/.well-known/openid-configuration) and a JWKS endpoint exposing the public half of an ES256 signing key it holds in Workers secrets.
  2. AWS IAM registers that issuer URL as an OIDC identity provider. A dedicated role (tenkacloud-alwayson-command) trusts it, with the trust policy conditioned on the token's aud and sub claims so only the Worker's tokens, scoped to a tenant/event, can assume it.
  3. To issue a command, the Worker mints a short-TTL JWT (audience sts.amazonaws.com, subject encoding the tenant/event scope), calls sts:AssumeRoleWithWebIdentity, and uses the returned short-lived credentials to PutEvents the frozen tenkacloud.deploy event onto the existing bus. The downstream state machines are untouched.

2.1 Decision constraints (binding)

  • Normal paths are out of scope. SaaS and Lite deploys keep the in-account AssumeRole + ExternalId mechanism verbatim. No behavior, IAM, or template of those paths changes.
  • No AWS Private CA. The trust anchor is the Worker's OIDC issuer + JWKS, which is free. IAM Roles Anywhere is rejected specifically because its AWS Private CA trust anchor is a fixed monthly charge, which defeats the zero-fixed-cost goal (see §6).
  • The EventBridge contract is frozen. source: tenkacloud.deploy, the detail types, and the field shapes are unchanged. The seam is a transport, not a new API.
  • Least privilege by role, not by nonce. The federated role may only events:PutEvents to the one bus for the frozen source. Scope is enforced by the IAM trust policy claims and the role's permission policy, replacing the ingress's hand-written scope check.

OIDC web-identity federation is the only option that removes both the bespoke token layer and the standing charge, and it reuses a mechanism already trusted elsewhere in the system.

5. Variant A vs. variant B

Two shapes deliver OIDC federation; they differ in whether the Worker ever holds AWS credentials.

VariantFlowTrade-off
A (chosen) Worker → AssumeRoleWithWebIdentity → short-lived scoped credentials → Worker calls PutEvents directly. Simplest and cheapest; no AWS-side ingress at all. The Worker holds scoped, short-lived credentials for the duration of the call.
B Worker mints an OIDC JWT and POSTs it to a retained ingress Lambda, which verifies it against the JWKS and publishes. Preserves “the Worker never holds AWS credentials” but keeps an AWS-side component and replaces bespoke verification with standard JWT verification rather than removing it.

Variant A is chosen. The “never holds credentials” property that B preserves is not a requirement the rest of the system upholds: the normal deploy path already trusts an AWS-native credential exchange (AssumeRole), and the returned web-identity credentials are scoped by the role to a single PutEvents action and expire in minutes. Variant A removes the entire AWS-side ingress — Function URL, verifier, scope check, and nonce table — for the lowest cost and the smallest surface.

7. Security model

  • Trust is asymmetric and AWS-verified. The Worker holds an ES256 private key; AWS holds only the public JWKS. A compromise of the AWS side cannot forge a command. This removes the current design's production HS256 path, whose shared symmetric secret could forge commands if it leaked.
  • Scope is enforced by IAM, not application code. The role trust policy conditions on aud and sub; the permission policy allows only events:PutEvents to the single bus and frozen source. There is no hand-written scope check to audit.
  • Replay is bounded by TTL. Tokens carry a short expiry and are single-audience (sts.amazonaws.com); the credentials they yield are minutes-lived and single-action. This is weaker than an explicit nonce only within that small window, and the target action (a deploy/destroy event keyed to a specific job) is idempotent downstream. If a per-request guarantee is ever required, a jti condition can be added without reintroducing a standing table.
  • Rotation is a redeploy of the Worker's key pair; AWS re-reads the JWKS automatically.

8. Impact on trust-bridge

trust-bridge is not deleted. Its command-seam role — intent-issuer, the JWS sign/verify modules, and the ingress's verifyIntent — is superseded and removed from the Always-On path. The package's other surfaces (the AWS/Azure/GCP credential-exchange abstractions and the cloud-action policy evaluators, which have separate consumers in the deploy handler and the customer-execution plane) are unaffected by this ADR and remain. Separately, the fail-open shadow integration in the normal deploy path is retired: it produces an observational audit log with no security value and no consumer that depends on it, so it is dead weight once the seam it was rehearsing is gone.

9. Migration plan

  1. Add the OIDC discovery + JWKS routes to the Always-On control-plane Worker; keep the ES256 key in Workers secrets.
  2. Register the IAM OIDC provider and the scoped tenkacloud-alwayson-command role in the Always-On CDK, conditioned on the issuer, aud, and sub.
  3. Switch the Worker's command path to AssumeRoleWithWebIdentity + PutEvents.
  4. Delete the ingress stack (IntentIngressStack), its Function URL, verifier, scope check, and nonce table, and the make deploy-always-on-ingress target.
  5. Remove the normal-path shadow integration.

Because the ingress is opt-in and not live, there is no traffic to drain and no rollback window to manage: steps 1–3 stand up the replacement, and steps 4–5 remove the superseded parts once the replacement is verified in a live Always-On deploy.

10. Consequences

  • Positive: no bespoke token layer to maintain or audit; no standing DynamoDB charge in the seam; one federation mechanism shared with the stack lifecycle instead of two.
  • Neutral: the Worker holds scoped, short-lived credentials during a command, accepted as equivalent in trust to the AWS-native exchange the normal path already relies on.
  • Cost of change: requires standing up an OIDC issuer on the Worker and validating AssumeRoleWithWebIdentity in a live Always-On deploy, which has not yet been run end to end.

11. Non-goals

  • Changing the SaaS or Lite deploy security model. They keep AssumeRole + ExternalId.
  • Deleting trust-bridge. Only its command-seam role is superseded.
  • Introducing IAM Roles Anywhere or any component that carries a fixed monthly charge.

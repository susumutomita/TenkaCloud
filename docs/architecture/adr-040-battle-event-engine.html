ADR-040: Battle Event Engine - managed attack and scenario events

Participants choose constrained event cards; TenkaCloud validates target, phase, rate, intensity, and safety boundaries; providers run only inside managed event environments and report evidence back to scoring.

Status: Proposed 2026-06-18
Tracking: #1874
Related: ADR-012 (problem plugin), ADR-014 (reconciliation), ADR-028 (inter-team coordination), ADR-031 (cross-account dispatch), ADR-034 (attack probes), ADR-038 (resilience and termination)
External input: ZANSIN, NTT WEST Engineers' Blog on ZANSIN

Context

ZANSIN is a cybersecurity training tool that runs simulated attacks from a control server against a training server so learners can practice log analysis, recovery, and configuration hardening. Public material describes a two-machine control/training shape and stresses that training environments must be local or private, not aimed at unauthorized Internet targets.

TenkaCloud already models Battle problems, disruption timing, cross-account dispatch, and attack resilience, but it does not yet have a first-class control plane for participant-triggered attack or scenario events. Without a control plane, an unsafe design would let participants choose arbitrary commands, arbitrary targets, or raw exploit code. That would break the product's safety model and make every Battle problem a bespoke security review.

The missing abstraction is a Battle Event Engine: a platform-owned orchestrator that treats attacks, disruptions, crawls, detection probes, and scenario events as data-backed cards. Participants can request only pre-approved cards. TenkaCloud validates the request, dispatches to a provider inside the event boundary, records evidence, and emits scoring updates.

Decision

Introduce Battle Event Engine as the only path for participant-triggered attack/scenario events

Attack/Event Cards are declarative metadata. A participant may select a card and an allowed target team, but may not provide executable code, shell commands, raw IPs, arbitrary URLs, payload bodies, or provider-specific options. The engine validates every request against card metadata, event state, team membership, target allowlists, cooldowns, use limits, provider safety policy, and the global emergency stop before any provider runs.

DecisionRule
D1. Cards are data, not code Problem authors declare battleEventCards[] in problem metadata. Cards name a provider and bounded parameters; they do not embed attack code.
D2. Provider execution is mediated The engine calls a provider adapter with a validated BattleEventDispatch. Providers cannot read participant input directly.
D3. Targets are platform-managed team environments Targets resolve from TenkaCloud event/team/deployment state. A participant never supplies a host, IP, CIDR, or URL as the attack destination.
D4. Every event has bounds Cards declare phase windows, severity, cooldown, max uses per team, max concurrent executions, timeout, and score policy. Runtime checks enforce them.
D5. Evidence precedes scoring Providers report structured evidence and an outcome. The engine stores the evidence pointer and then emits score events. Scoring never trusts client claims.
D6. External tools are providers, not dependencies ZANSIN is a candidate provider adapter. Its code is not vendored or bundled until license, containment, cleanup, and evidence extraction are proven.

Non-goals and prohibited behavior

Security boundary

  • Do not allow arbitrary participant commands, scripts, payload editing, IP entry, URL entry, or provider flags.
  • Do not distribute exploit code through the participant UI.
  • Do not send attack traffic outside TenkaCloud-managed event/team environments.
  • Do not let a provider run without target validation, phase validation, rate limits, and emergency-stop checks.
  • Do not import or vendor ZANSIN code until license review and containment are complete.

Card metadata schema

The first implementation should add this shape to problems/SCHEMA.json as battleEventCards[]. This ADR defines the contract; it does not implement the schema in this PR.

{
  "battleEventCards": [
    {
      "id": "login-pressure-low",
      "name": "Low-intensity login pressure",
      "description": "Run a bounded training event against the target team's managed environment.",
      "provider": "http-synthetic",
      "severity": "low",
      "allowedTargetKinds": ["team-environment"],
      "allowedPhases": ["middle", "final"],
      "cooldownSeconds": 300,
      "maxUsesPerTeam": 3,
      "maxConcurrentExecutions": 2,
      "timeoutSeconds": 120,
      "intensity": {
        "level": "low",
        "maxRequestsPerMinute": 30
      },
      "scoreRules": {
        "attackSuccessPoints": 50,
        "defenseSuccessPoints": 75,
        "availabilityPenalty": 0
      },
      "evidence": {
        "logRetentionDays": 30,
        "redaction": "standard"
      }
    }
  ]
}
FieldValidation rule
providerEnum: zansin, http-synthetic, aws-fault, custom-scenario. Disabled providers cannot be selected.
severityEnum: low, medium, high. Higher severities require stricter phase windows and lower concurrency caps.
allowedTargetKindsInitial value is only team-environment. No free-form external targets.
allowedPhasesMust match the active Battle phase. Empty arrays are invalid.
cooldownSecondsPositive integer. The engine stores last use per attacker/card and rejects early reuse.
maxUsesPerTeamPositive integer. Counts attacker-team card uses per event.
maxConcurrentExecutionsPositive integer. Enforced per event/card/provider to avoid provider overload.
timeoutSecondsPositive integer below the event policy maximum. Provider executions are terminated or marked timeout after this bound.
intensityProvider-specific bounded object. Schema validation rejects unknown unbounded knobs.
scoreRulesPure scoring metadata. Providers return outcomes; the generic scorer applies points.

Provider interface

Provider adapters implement a narrow interface. They receive a resolved target descriptor and bounded provider parameters, not raw participant input.

export type BattleEventProviderId =
  | "zansin"
  | "http-synthetic"
  | "aws-fault"
  | "custom-scenario";

export type BattleEventSeverity = "low" | "medium" | "high";
export type BattleEventStatus = "succeeded" | "failed" | "blocked" | "timeout";

export interface BattleEventDefinition {
  readonly id: string;
  readonly provider: BattleEventProviderId;
  readonly severity: BattleEventSeverity;
  readonly allowedTargetKinds: readonly ["team-environment"];
  readonly allowedPhases: readonly ("early" | "middle" | "final")[];
  readonly cooldownSeconds: number;
  readonly maxUsesPerTeam: number;
  readonly maxConcurrentExecutions: number;
  readonly timeoutSeconds: number;
  readonly scoreRules: {
    readonly attackSuccessPoints: number;
    readonly defenseSuccessPoints: number;
    readonly availabilityPenalty: number;
  };
}

export interface BattleEventExecutionRequest {
  readonly eventId: string;
  readonly problemId: string;
  readonly cardId: string;
  readonly attackerTeamId: string;
  readonly targetTeamId: string;
  readonly idempotencyKey: string;
}

export interface BattleEventTarget {
  readonly kind: "team-environment";
  readonly eventId: string;
  readonly teamId: string;
  readonly deploymentId: string;
  readonly providerAccountRef: string;
  readonly networkBoundaryRef: string;
}

export interface BattleEventDispatch {
  readonly definition: BattleEventDefinition;
  readonly request: BattleEventExecutionRequest;
  readonly target: BattleEventTarget;
  readonly startedAt: string;
}

export interface BattleEventExecutionResult {
  readonly status: BattleEventStatus;
  readonly evidenceLogUri?: string;
  readonly providerRunId?: string;
  readonly scoreDelta: number;
  readonly startedAt: string;
  readonly finishedAt: string;
}

The adapter contract is deliberately small:

export interface BattleEventProvider {
  readonly id: BattleEventProviderId;
  validate(definition: BattleEventDefinition): ProviderValidationResult;
  dispatch(dispatch: BattleEventDispatch, signal: AbortSignal): Promise<BattleEventExecutionResult>;
  stop(runId: string, reason: "emergency-stop" | "event-ended" | "timeout"): Promise<void>;
}

Execution flow

Participant Portal -> POST /portal/me/battle-events { cardId, targetTeamId, idempotencyKey } -> Battle Event Engine 1. authenticate team token 2. load event/problem/card/team/deployment state 3. reject self-targeting if card forbids it 4. verify active phase and event window 5. check global emergency stop and provider enablement 6. enforce cooldown, max uses, concurrency, timeout 7. resolve target to managed team environment 8. create BattleEventExecution row 9. dispatch provider with bounded target descriptor 10. store evidence pointer and normalized outcome 11. emit BattleEventCompleted and ScoreUpdated events

EventBridge remains the system integration layer. The engine emits BattleEventRequested, BattleEventStarted, BattleEventCompleted, BattleEventBlocked, and BattleEventStopped. ADR-014 reconciliation can repair missing terminal states by marking stale executions timeout and releasing concurrency counters.

State and audit records

RecordPurposeMinimum fields
BattleEventExecution One request/run lifecycle. tenantId, eventId, problemId, cardId, attackerTeamId, targetTeamId, provider, status, idempotencyKey, startedAt, finishedAt, evidenceLogUri.
BattleEventQuota Cooldown and max-use enforcement. eventId, cardId, attackerTeamId, usedCount, lastUsedAt.
BattleEventProviderLease Concurrency cap and timeout cleanup. eventId, provider, cardId, executionId, expiresAt.
AuditLog Operator and forensic trace. Actor, request, decision, provider, target descriptor hash, emergency-stop state, and evidence URI. Do not log raw provider secrets.

ZANSIN provider PoC boundary

ZANSIN is a useful reference because it separates a control role from a training environment and is explicitly framed as an education tool. TenkaCloud should treat it as an external provider candidate, not as a bundled dependency.

PoC questionRequired answer before enablement
Can the control/training shape fit inside one team environment?The control component must target only the team's managed training machine or network boundary. No Internet-wide target selection.
Can TenkaCloud extract outcome evidence?Provider runs must emit normalized status, timestamps, event identifiers, and evidence logs to CloudWatch Logs or S3.
Can runs be bounded and stopped?The adapter must honor timeoutSeconds, AbortSignal, provider leases, and emergency stop.
Can resources be cleaned up?All provider-created resources must be tied to the event/team and removed on event teardown.
Can license and distribution be satisfied?No vendoring or image distribution until license obligations are reviewed and documented.

Emergency stop

Operators need two stop levels:

Stop levelEffect
Event-wide stopReject new Battle Event requests for an event, call stop() on active provider runs, mark leases released, and preserve evidence logs.
Provider stopDisable a provider across all events. Existing executions are stopped with reason emergency-stop; new requests with that provider are blocked.

Emergency stop is fail-closed. If stop state cannot be read, the engine blocks dispatch.

Scoring contract

Providers do not write scores directly. They return a normalized outcome and evidence. The engine emits a scoring event containing executionId, cardId, attackerTeamId, targetTeamId, status, and scoreRules. The generic scorer applies points and writes the existing score event stream that participant and admin views already poll.

OutcomeScoring behavior
succeededApply attack success points to attacker and defense result rules to target based on the card policy.
failedNo attack success points. Optional defense success points if the card defines them.
blockedNo score change. Evidence records the block reason for audit.
timeoutNo attack success points. Release leases and preserve partial evidence for operator review.

Alternatives considered

AlternativeWhy rejected
Let participants submit commands or scripts. Unsafe by construction. It makes every request a new exploit review and violates the no-arbitrary-execution boundary.
Let participants enter target URLs. Even with SSRF filtering, this creates ambiguity about external targets. The engine must resolve targets from event/team/deployment state only.
Bundle ZANSIN immediately. Licensing, containment, cleanup, and evidence extraction need a PoC first. ZANSIN remains an external adapter candidate.
Reuse disruptions only. Disruptions are operator/problem-driven. Battle Event Cards add participant choice while preserving platform validation and scoring contracts.

Implementation phases

  1. Schema and validation. Add battleEventCards[] to problems/SCHEMA.json and the problem validator. Reject unbounded cards.
  2. Provider interface package. Add TypeScript types and pure validation helpers in app-owned code. No infrastructure resources required.
  3. API and persistence. Add request, execution, quota, and lease records. Status endpoints use polling; no SSE or WebSocket.
  4. Provider MVP. Start with http-synthetic or custom-scenario in a controlled event environment. Do not ship ZANSIN here.
  5. ZANSIN PoC. Run as an external adapter after license, isolation, logs, stop, and cleanup are proven.
  6. Scoring and UI. Surface cards in Participant Portal and outcomes in Admin Console only after backend controls are enforced.

Infrastructure-touching pieces such as new tables, queues, IAM, or provider runner isolation require maintainer-owned CDK changes per the repo role split. This ADR intentionally defines the contract first.

Consequences

  • Participants get meaningful Battle choices without ever handling attack code.
  • Problem authors can add new event cards through metadata instead of platform-specific attack handlers.
  • Provider authors get a narrow adapter contract that can host ZANSIN-like tools later.
  • Operators gain hard stops, audit evidence, and score traceability for each event execution.
  • The design preserves the Lambda/polling operational model and aligns with ADR-038: every run is bounded, stoppable, and auditable.

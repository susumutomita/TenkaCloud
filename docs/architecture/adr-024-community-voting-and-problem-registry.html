ADR-024: Community voting and on-chain problem registry

Hybrid model for community curation of the problem catalog: a minimal on-chain registry of problem cards, paired with an off-chain voting / adoption / sponsorship layer. Web3 is an optional surface, never a requirement.

Status: Accepted 2026-05-24
Tracking: #1269
Related: ADR-012 (problem = plugin), ADR-017 (Trust Bridge), ADR-022 (inter-team plugin)

Context

TenkaCloud separates the platform from the problem catalog (ADR-012: problem = plugin, platform = host), and the catalog repo is OSS-ready. Multi-cloud problem execution is being unlocked by the Trust Bridge protocol (ADR-017) and the cross-account stack catalog work tracked under the multi-cloud runtime issues. The pieces required to publish, run, and score third-party problems are converging.

Contribution mechanics, however, end at "open a PR to add a problem." There is no community signal layer to answer:

  • Which problems are valuable enough that operators want to run them in events.
  • Which problems need improvement, and in what direction.
  • Which problems deserve sponsorship or maintenance funding.
  • Which contributors built durable learning assets that the community recognises.
  • Which themes organisations want to see created but do not yet exist.

Without that signal layer, the catalog risks becoming a pile of drafts with maintainers as the only filter, contributors getting little recognition, and organisations having no structured way to express demand.

A Web3 mechanism is plausible because voting, ownership, sponsorship, and contributor reputation are the kinds of public, composable records that a chain handles well. A naive Web3 design is also dangerous: a token introduces speculation, mandatory wallets block enterprise adoption, and on-chain governance can lock the project into bad rules before the community is mature enough to know what good rules look like.

This ADR commits to a design that captures the community-curation upside while keeping enterprise usage wallet-free and keeping governance flexible.

Decision

Hybrid: on-chain problem registry + off-chain voting / adoption / sponsorship layer

  1. Phase 1 (on-chain registry): Publish a minimal, public registry of ProblemCard records: id, problemId, title, url, contentHash, author, createdAt. Nothing more. The full problem source stays in the catalog repo.
  2. Phase 2 (off-chain layer): Build voting (ProblemVote), event adoption (ProblemAdoption), and sponsorship interest (ProblemSponsorshipInterest) as off-chain records that reference the on-chain chainProblemId.
  3. Web3 is optional. Wallet login is never required for enterprise users. GitHub / Discord identity is a first-class participation path. Wallet identity is an additional path, not a replacement.
  4. No token, no vote-to-merge, no replacement of GitHub review. Quality control stays with maintainers.

The chain stores the smallest public artefact that lets the community build composable surfaces (voting frontends, leaderboards, Discord bots, sponsorship dashboards). Everything that needs flexible rules, moderation, or private enterprise context lives off-chain.

Layered model

Off-chain records reference the on-chain chainProblemId; catalog UI reads both layers and renders the consolidated signal to operators and authors.

Data model

On-chain: ProblemCard (Phase 1)

The on-chain record is intentionally minimal so any community frontend can read it. The illustrative shape (final wire format is a Phase 1 implementation detail):

struct ProblemCard {
    uint256 id;
    string  problemId;     // catalog slug (e.g. "battle/hello-world")
    string  title;
    string  url;           // canonical catalog URL
    string  contentHash;   // catalog commit hash or content hash
    address author;        // maintainer address (optional in early rollout)
    uint256 createdAt;
}
FieldPurposeMutability
idOn-chain primary key, surfaced off-chain as chainProblemIdImmutable per registration
problemIdCatalog slug; links to the source-of-truth metadata.jsonImmutable per registration
title / urlDiscovery hooks for third-party frontendsTreated as immutable; material changes register a new card version
contentHashCatalog commit hash or content hash of the problem at registration time; provenance anchorImmutable
authorMaintainer or registrar wallet address; may be a multisig in early rolloutImmutable
createdAtBlock timestamp at registrationImmutable

Off-chain: voting / adoption / sponsorship (Phase 2)

type ProblemVoteIntent =
  | "want-to-play"
  | "use-for-training"
  | "important-skill"
  | "needs-improvement";

interface ProblemVote {
  problemId: string;
  chainProblemId?: string;
  userId: string;
  walletAddress?: string;
  intent: ProblemVoteIntent;
  comment?: string;
  createdAt: string;
}

interface ProblemAdoption {
  problemId: string;
  chainProblemId?: string;
  organization?: string;
  eventName?: string;
  participantCount?: number;
  visibility: "public" | "private" | "anonymous";
  feedbackSummary?: string;
  createdAt: string;
}

interface ProblemSponsorshipInterest {
  theme: string;
  problemId?: string;
  chainProblemId?: string;
  organization?: string;
  budgetRange?: "unknown" | "small" | "medium" | "large";
  desiredOutcome: string;
  visibility: "public" | "private" | "anonymous";
}

Mapping rule

  • Catalog ↔ chain: problemId (catalog slug) is the join key. Each off-chain record carries both problemId and the optional chainProblemId; the latter is populated once the problem has been registered on-chain.
  • Versioning: Material changes to a problem register a new ProblemCard rather than mutating the existing one. Off-chain records pinned to a specific chainProblemId stay attached to the version they were cast against.
  • Identity: Off-chain records require an off-chain identity (GitHub / Discord / SSO). A wallet address is captured only when the participant chose to bind one, and is never required.

Phased roadmap

PhaseScopePlatform code change
Phase 0
GitHub/Discord community process		 Define and apply labels on the catalog repo: problem-proposal, problem-needs-review, problem-tested, problem-adopted, sponsor-interest. Use GitHub Discussions and the Discord squad for tester / reviewer feedback. None (process change only)
Phase 1
Lightweight on-chain problem registry		 Stand up a minimal contract or signed registry artefact that stores ProblemCard records (id, title, canonical URL, content / commit hash, registrar address). No token. Registration is initially gated to maintainers; open registration is an explicit later decision. Provide read examples so the community can build voting pages, leaderboards, Discord bots, sponsorship dashboards, and discovery pages on top. New registry artefact + read SDK; no change to the drill runtime
Phase 2
Off-chain catalog voting data model		 Implement ProblemVote, ProblemAdoption, and ProblemSponsorshipInterest records and the API surface that creates them. Identity is GitHub / Discord; wallet addresses are optional attachments. New storage + API; no change to the scoring engine
Phase 3
Catalog UI signals		 Render per-problem signals in the catalog UI: on-chain registry link, vote counts by intent, used-in-events count, contributor badges, open sponsor interests, and a "Request this problem for your org" CTA. Catalog UI extension
Phase 4
Governance rules		 Define how votes influence catalog status: Draft → Community requested → Tested → Official candidate → Official → Deprecated. Promotion always requires technical validation and maintainer review; raw vote counts never auto-promote a problem. Catalog metadata + maintainer tooling
Phase 5
Optional Web3 attestations		 Once Phase 1-4 have proven steady, layer attestations for problem version releases, event participation badges, contributor reputation badges, and sponsorship fulfilment records. Prefer non-transferable or reputation-style credentials to avoid speculation. On-chain attestation contracts; opt-in for enterprise users

Non-goals

Out of scope, by design

  • No token. The community-curation layer must not launch or rely on a fungible token.
  • No required wallet for enterprise users. Wallet login is one identity path among several; enterprise users participate without it.
  • No vote-to-merge. Votes are signals, not merge authority; they never auto-merge a problem.
  • No replacement of GitHub review. Maintainer review remains the quality gate.
  • No leakage of private enterprise adoption. Private adoption signals stay private unless the organisation explicitly opts in.
  • No full problem source on-chain. Only minimal public metadata (ids, titles, hashes, URLs) is on-chain; problem source stays in the catalog repo.

Key design constraints

  • Web3 optional, enterprise neutral. Web3 must be optional for enterprise usage. Enterprise users must be able to use TenkaCloud without wallets. Wallet-based participation may be interesting for community events, but it must not be a blocker for large enterprise buyers.
  • Maintainer quality control wins. Voting must not override maintainer quality control. Sponsorship must not imply a problem is official without review.
  • Quality, not spam. Contributor recognition should encourage quality contributions, not volume farming.
  • Private adoption stays private. Private enterprise usage must be supported without leaking sensitive training themes.
  • Minimal public metadata. The on-chain layer stores minimal public metadata only. Full problem source remains in GitHub / the catalog. On-chain records should reference immutable content hashes or commit hashes where possible.

Trade-offs

Trade-offPosition taken
Minimal on-chain registry vs full on-chain voting Start with a registry. Full voting can be added later, but premature on-chain governance risks locking the project into bad rules before the community is mature enough to refine them.
Public chain reads vs moderation Embrace public reads for composability. Mitigate spam by allowlisting registration (or requiring a merged catalog entry) rather than by restricting reads.
Metadata mutability vs versioning Treat each registered card as immutable. Material changes to a problem register a new version. Off-chain signals pinned to an old version remain valid for that version.
Web3 ownership vs enterprise friction Keep wallet participation optional. The chain is composability infrastructure for the community, not a gate for enterprise users.
Sponsorship vs neutrality Sponsorship can fund development but must never make the catalog pay-to-win or vendor-biased. Sponsored status is visible and separated from official quality status.

Open design questions

Out of scope for this ADR; tracked as follow-up issues so Phase 1-2 implementation can converge.

  • Registration authority. Should on-chain registration be open to anyone, allowlisted to maintainers only, or gated by catalog merge status? Initial Phase 1 stance is maintainer-gated; opening it up is a separate decision.
  • Registry shape. On-chain registry as a smart contract (which chain, which standard) vs a signed JSON registry artefact published to IPFS or a git repo with cryptographic provenance.
  • Wallet identity model. Sign-In-With-Ethereum, SIWS (Solana), Discord, or GitHub as the wallet-binding flow; how a single contributor maps across identities.
  • Off-chain storage backend. Where ProblemVote / ProblemAdoption / ProblemSponsorshipInterest live (catalog-side service vs platform-side service) and the abuse-prevention layer.
  • Visibility defaults. Default visibility for adoption and sponsorship records; how anonymous records affect aggregate counts.
  • Phase 4 promotion thresholds. The concrete signal mix that lets a problem progress through Community requested → Tested → Official candidate, without making counts authoritative.

CDK stacks (Control Plane / App Plane / Problem Deploy)No change. The community-signal layer is an additional surface, not a replacement for any plane.

Plugin contract (ADR-012)No change. The 3-asset model (metadata.json + template.yaml + portal/) is unchanged; community signals are catalog-level, not problem-level.

No code changes ship with this ADR. Phase 1 onwards each land as separate PRs with their own architecture and security reviews.

ADR-0001 — Managed participant access for GCP, Azure, and Sakura composite targets

Status: Accepted Scope: Composite Runtime participant access (multicloud) Supersedes: none Related: Composite Runtime epic; capability-matrix and AWS Console/CLI bridge work that landed before this ADR

A composite problem deploys one logical challenge across two to eight cloud targets (some mix of AWS, GCP, Azure, and Sakura). Each target is a child deployment owned by one competitor team. The platform never asks a competitor to bring their own cloud account: it brokers access into a target the competitor does not own. This ADR fixes, per provider, exactly how that brokered participant access is granted — or explicitly declares that it is not granted yet — so that no contributor invents an ad hoc federation mechanism while implementing the Composite Runtime.

Context

What AWS already does (the reference baseline)

For an AWS target the platform issues two managed access modes, both anchored in the verified competitor-account record and short-lived STS sessions — the platform stores no AWS access keys:

  • Console one-click sign-in — the participant-handler resolves the target row server-side (team-scoped), performs a two-stage AssumeRole (CompetitorDeployRole → ParticipantViewerRole), exchanges the STS session for an AWS federation sign-in token, and returns a login URL whose destination is pinned to the region console home.
  • Short-lived CLI/SDK credentials — the same two-stage AssumeRole, but the STS credentials (AccessKeyId / SecretAccessKey / SessionToken / Expiration) are returned directly for aws configure / SDK use.

The AWS access model rests on four properties that this ADR treats as the bar every provider must clear:

What the non-AWS deploy path holds today

The Composite Runtime resolves each target to a secret-free TargetConnection before any cloud mutation. AWS resolves via the verified competitor-account lookup. GCP, Azure, and Sakura resolve structurally only: the per-team config store is read for validity and only the teamSlug is returned — never the stored config. What that stored config actually contains differs sharply by provider, and that difference drives this decision:

The seam this ADR must respect

A provider-neutral participant-access seam already exists and must not be reshaped by this decision. It has three layers, all read-only and additive over the legacy single-provider AWS path:

  1. Capability resolver — a pure function of provider that returns a capability list, plus a team-scoped lookup that projects a COMPLETE target to a secret-free TargetAccessDescriptor (carrying only targetId, targetDeploymentId, provider, capability[]).
  2. AWS access bridge — verifies the resolved descriptor is aws with the console capability, then delegates to the proven Console/CLI functions with a server-resolved row. A non-AWS or unsupported target is rejected as a capability mismatch before any session call.
  3. Identity boundary — the lookup keys on the authenticated team login key, so a cross-team or absent target is uniformly not_found; the (parentDeploymentId, targetDeploymentId) pair is a lookup key, never authority.

The capability matrix as it stands declares AWS → console + cli-credentials and GCP / Azure / Sakura → external-portal. This ADR ratifies that matrix as the first-release contract and defines the forward path for each non-AWS provider rather than letting an implementer guess.

Decision

D1. First-release capability matrix

In the first release, AWS is the only provider with managed brokered access. GCP, Azure, and Sakura targets are external-portal-only: the participant portal renders the target as reachable and may publish a provider portal URL, but the platform brokers no authenticated session and issues no credential. This is stated explicitly in the matrix, never implied.

D2. Per-provider access model

GCP — deferred managed access via keyless Workload Identity Federation

GCP is the one non-AWS provider where managed access is achievable without storing a secret, because deploy already federates keylessly: the worker's AWS identity is the WIF subject and impersonates a Service Account. The forward design re-uses exactly that path for participants.

  • How a participant authenticates to a target they do not own: they do not present a GCP identity. The platform exchanges the deploy worker's AWS identity for a short-lived OAuth access token scoped to a per-target, least-privilege viewer Service Account, and hands that token (or a token-backed console deep link) to the browser.
  • Credential brokering: WIF token exchange + Service Account impersonation, performed server-side. No GCP key exists to store or leak.
  • Trust boundary: Google trusts the platform's AWS identity (pinned WIF audience and AWS principal); the participant trusts the platform; the participant never holds a standing GCP identity.
  • Why deferred: a participant-scoped viewer Service Account and its least-privilege bindings do not exist yet, and impersonation chain depth, audience pinning, and token-TTL caps need provider-specific validation (see open items). Until that lands, GCP is external-portal-only and the matrix says so.
Azure — external-portal-only; managed access explicitly not pursued in this ADR

Azure deploy authenticates with a stored long-lived client secret because Entra ID has no AWS-native inbound federation. That secret is a deploy-time identity, not a participant identity, and brokering participant sessions from it would mean either (a) handing a participant a token minted as the deploy app — over-privileged and unattributable to the team — or (b) standing up the platform as an OIDC issuer so Entra federated credentials can trust it, which is a heavy subsystem out of scope here.

  • First-release model: external-portal-only. The participant authenticates directly in the Azure portal against an identity the platform does not own and does not assert.
  • Trust boundary: entirely outside the platform; the platform publishes at most a portal URL and never a credential.
  • Follow-up boundary: managed Azure access is gated on a federated-credential design (platform-as-OIDC-issuer, or a per-team app exposing a scoped delegated identity) and would get its own ADR. It must not be improvised by reusing the deploy client secret.
Sakura — external-portal-only; no short-lived issuance to broker

Sakura deploy uses a static API key pair stored as a SecureString because Sakura exposes no OIDC/STS federation and no short-lived-credential endpoint. There is nothing to broker into a scoped, expiring participant credential. Returning the static key to a browser is prohibited outright (it is long-lived and team-shared).

  • First-release model: external-portal-only. The participant authenticates in the Sakura control panel.
  • Trust boundary: entirely outside the platform.
  • Follow-up boundary: managed Sakura access requires either a Sakura-side mechanism to mint short-lived scoped tokens, or a platform-run proxy that fronts the static key and enforces per-team least-privilege scoping and auditing. Both need a dedicated design before any code; neither is in this ADR.

D3. Security invariants that hold for every provider

Invariants enforced uniformly across AWS, GCP, Azure, Sakura
#InvariantHow it is upheld
I1Server-side source of truthThe team-scoped, COMPLETE target deployment record is the only authority. parentDeploymentId / targetDeploymentId from the client are lookup keys, never grants.
I2No participant-supplied authorityRole identifiers, account identifiers, and redirect URLs are never accepted from the participant. Destinations are derived server-side (AWS pins console home; future GCP pins its console URL).
I3Confused-deputy / ExternalId-equivalent protectionAWS: two ExternalId-bound AssumeRole hops. GCP (planned): pinned WIF audience + fixed AWS principal so only the platform identity can impersonate the SA. Azure/Sakura: no platform identity is asserted, so there is no deputy to confuse.
I4Least privilegeAWS: ParticipantViewerRole. GCP (planned): per-target viewer Service Account. Azure/Sakura: no platform grant, so no over-privilege risk from the platform.
I5No long-lived secret at rest for participant accessNo access path stores a long-lived participant credential. Deploy-time long-lived secrets (Azure client secret, Sakura API key) are precisely why those providers are external-portal-only and are never exposed to participants.
I6Browser receives only a scoped, short-lived credentialAWS returns ~1h STS material or a federation URL. GCP (planned) returns a ≤1h OAuth token. Azure/Sakura return no credential.
I7AuditabilityEvery issuance, consumption, expiry, denial, and provider error is emitted as a structured event keyed on tenantId / team / parentDeploymentId / targetDeploymentId / provider (no secret material in the log).
I8Cross-team opacityA target owned by another team is indistinguishable from a missing one (uniform not_found), so participants cannot probe other teams' targets.

D4. How this binds to the existing seam without touching the AWS path

The capability matrix is the only switch. Resolution stays a pure function of provider; the access bridge keeps gating on the descriptor's provider and capability. AWS keeps its two managed modes. GCP/Azure/Sakura resolve to external-portal, so the bridge rejects them as a capability mismatch before any session/token call — the AWS Console/CLI flow is never entered for a non-AWS target and its behavior is unchanged. When GCP managed access lands, it adds a new issuer alongside the AWS bridge and flips GCP's matrix entry; it does not modify the AWS bridge.

D5. API contract draft (TargetAccessDescriptor and future issue boundaries)

The participant-visible descriptor is deliberately secret-free. It is the stable contract every provider shares; adding a field is a conscious widening of the participant-visible surface. 

// Read-only, secret-free. Returned by the team-scoped lookup for a COMPLETE target.
interface TargetAccessDescriptor {
  targetId: string;            // problem-author-defined id, unique within the problem
  targetDeploymentId: string;  // resolved from the row, never echoed as authority
  provider: "aws" | "gcp" | "azure" | "sakura" | "unsupported";
  capability: Array<"console" | "cli-credentials" | "external-portal" | "unsupported">;
}

// Future managed-issue boundary (one issuer per managed capability). Input carries
// NO authority: parentDeploymentId/targetDeploymentId are lookup keys; teamLoginKey
// is the authenticated access boundary. Output is a scoped, short-lived credential
// or an external-portal handoff -- never a stored secret.
interface IssueTargetAccessInput {
  teamLoginKey: string;        // authenticated team -- the access boundary
  parentDeploymentId: string;  // lookup key only
  targetDeploymentId: string;  // lookup key only
  // No role ARN, account id, project id, subscription id, or redirect URL accepted.
}

type IssueTargetAccessOutcome =
  | { kind: "console"; loginUrl: string; expiresAt: string }        // AWS today; GCP planned
  | { kind: "cli-credentials"; credential: ScopedShortLivedCred }   // AWS today; GCP planned
  | { kind: "external-portal"; portalUrl: string }                  // GCP first release, Azure, Sakura
  | { kind: "not_found" }                                           // missing OR cross-team
  | { kind: "not_ready" }                                           // exists for team but not COMPLETE
  | { kind: "capability_mismatch"; provider: string }               // provider has no such capability
  | { kind: "provider_error"; provider: string; reason: string };   // upstream issuance failed

D7. Revocation, early termination, and fallback

  • Revocation / early termination: nothing long-lived is issued, so expiry is the primary termination (AWS ≈ 1h, GCP planned ≤ 1h). Destroying or transitioning the target out of COMPLETE immediately stops new issuance (the row no longer gates). Already-issued short-lived sessions run to their TTL; lifetimes are kept short specifically so no separate revocation channel is required.
  • Fallback when managed access is unavailable: the path degrades to external-portal for that target — the participant authenticates directly with the provider. This is the declared first-release state for GCP/Azure/Sakura, and the safe degradation if a managed issuer errors. Fallback never silently downgrades to returning a stored deploy secret.

Threats and mitigations

ThreatMitigation
Replay of a captured request / old id pairThe grant is the live, team-scoped, COMPLETE row — not a bearer token. A replay re-resolves against current state; a destroyed/incomplete target yields not_found/not_ready. Issued sessions are short-lived (≤ ~1h).

Open provider-specific validation items

These are the items a managed-access implementation must resolve in its own design/PR before flipping a matrix entry away from external-portal-only.

  • GCP: participant-scoped viewer Service Account definition and least-privilege IAM bindings; WIF audience and AWS-principal pinning for the participant exchange (distinct from the deploy exchange); impersonation chain depth; OAuth token TTL cap and console deep-link safety; audit correlation between AWS and GCP logs.
  • Azure: a federated-credential design (platform-as-OIDC-issuer or a per-team app exposing a scoped delegated identity) that never reuses the deploy client secret; Entra conditional-access and tenant-boundary review.
  • Sakura: whether Sakura can mint short-lived scoped tokens at all; if not, a platform-run least-privilege proxy fronting the static key, with per-team scoping and full audit; rotation behavior under proxying.
  • All: confirm the short-lived-credential TTL cap each provider enforces and that issuance refuses past expiry (drives access.expired).

Consequences

Positive

  • The AWS managed experience is preserved unchanged and used as the reference bar.
  • The first-release contract is explicit and security-reviewable: exactly one provider has managed access; the rest are external-portal-only and labeled as such in the matrix — nothing is implied.
  • No long-lived cloud secret is ever introduced into the participant access path or returned to a browser.
  • GCP has a concrete, keyless forward path that reuses the existing WIF investment rather than inventing federation.
  • The secret-free descriptor + per-capability issuer boundary lets each provider be added independently without reshaping the seam or risking the AWS path.

Negative / accepted trade-offs

  • GCP/Azure/Sakura participants get a less seamless first-release experience (external portal sign-in) than AWS competitors.
  • Azure and Sakura managed access is intentionally unsolved here; each needs a dedicated follow-up ADR, accepted to avoid an insecure shortcut built on a stored deploy secret.
  • Short-lived sessions cannot be revoked mid-flight; mitigated by keeping lifetimes to roughly one hour.

Alternatives considered

AlternativeWhy rejected
Mint participant sessions from the stored Azure client secret / Sakura API keyRe-exposes a long-lived secret and yields tokens attributed to the deploy identity, not the team — over-privileged and unauditable. Violates I4/I5.
Return the stored deploy credential to the browser as a fallbackDirectly breaks "no long-lived secret to the browser" (I6) and would leak a team-shared key. Prohibited in the data-classification table.
Accept a provider role/account id or redirect URL from the participant to widen reachable targetsMakes the participant the authority and opens confused-deputy and open-redirect vectors. Violates I1/I2.
Stand up platform-as-OIDC-issuer now so Azure federated credentials work in v1A heavy subsystem disproportionate to the first release; deferred to a dedicated ADR rather than rushed.
Force every provider into the AWS Console/CLI shapeGCP, Azure, and Sakura have materially different federation surfaces; copying the AWS flow would be unsafe (Azure/Sakura) or premature (GCP). The capability matrix exists precisely so providers need not be identical.

Rollout

  1. First release (this ADR): capability matrix ratified — AWS managed (Console + CLI); GCP/Azure/Sakura external-portal-only and labeled in the matrix. No access code changes ship with this ADR.
  2. Next, GCP managed access (separate PR): add a GCP issuer that performs the participant WIF exchange + per-target viewer Service Account impersonation, returning a ≤1h OAuth credential or token-backed console link; flip GCP's matrix entry. The AWS bridge is untouched.
  3. Later, Azure / Sakura (each its own ADR + PR): only after a federated-credential design (Azure) or a short-lived-issuance/proxy design (Sakura) clears the open validation items. Until then both remain external-portal-only.

Out of scope for the first release

  • An identical Console SSO experience across all four providers.
  • Managed Azure or Sakura participant access of any kind.
  • A platform-run OIDC issuer or a Sakura key-fronting proxy.
  • Mid-session revocation beyond short TTL expiry.

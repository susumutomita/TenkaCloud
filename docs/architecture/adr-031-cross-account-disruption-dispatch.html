ADR-031: Cross-account disruption dispatch (Phase B)

operator が fire した disruption を競技者アカウントへ届け、 実際に障害を注入するための cross-account 経路と、 問題が宣言する障害アクションの契約

Status: Proposed 2026-06-02
Related: ADR-013 (disruption 宣言 / Phase A→B / condition trigger), ADR-012 (problem = plugin, platform = host), ADR-029 (game always ends / no disruption is permanent)

Context

障害注入 (Red Team disruption) の現状は Phase A 止まりである。 operator が POST /events/:eventId/disruptions/fire を叩くと、 platform 側 (event-handler/disruption-fire.ts) は次を行う:

  1. problem catalog で (problemId, disruptionId) を解決し、 operatorEditable allow-list で parameters を fold
  2. event 配下 team を列挙し scope (all / team / random-n) を解決
  3. REQUEST#{tenantId}#{requestId} の conditional Put で冪等性を奪取 (race-safe)
  4. operator アカウントの EventBridge bus へ *DisruptionFired を publish
  5. append-only の AUDIT# 行を Put

問題は 4 で publish 先が operator アカウントの bus に閉じていること。 イベントは競技者アカウントへ届かず、 実際の障害は一切注入されない。 コード上も disruption-fire.ts が「cross-account publish (= 競技者アカウントへの forward) は Phase B で追加する」と明記して 意図的に deferred している。 監査ログと Logs Insights で「fire したという事実」は観測できるが、 競技者の問題環境は無傷のままで、 ADR-013 が掲げた「本物の障害でレジリエンスを測る」競技性が成立していない (ADR-029 が前提とする「障害 → 復旧」のループが回らない)。

既に存在する素材 (= 大げさにしないための足場)

素材場所Phase B で果たす役割
競技者アカウントへの AssumeRole + ExternalId パターン describe-stack-handler/index.ts / competitor-accounts-handler/verify.ts そのまま cross-account 実行の足場になる。 RoleSessionName / ExternalId / 1h セッションの作法が確立済
CompetitorDeployRole = AdministratorAccess infrastructure/templates/competitor-bootstrap.yaml 障害注入に必要な権限は既に揃っている。 #721 で個別最小権限の whack-a-mole を畳み、 信頼境界を「account + ExternalId の 2 要素」に集約済。 bootstrap への追記は不要
disruption 宣言 (catalog) metadata.json の disruptions[] + discover-problems-catalog.ts id / eventDetailType / operatorEditable / parameters / triggers を持つ。 障害の 記述はあるが、 どう注入するか (action) の field が無い
冪等 fire + 監査 disruption-fire.ts (Phase A) REQUEST# claim と AUDIT# はそのまま再利用。 Phase B は publish の 下流に実行を足すだけで、 上流の意味論は不変

つまり Phase B は新しい信頼境界を作る話ではなく、 「既に許可されている cross-account AssumeRole の上で、 問題が宣言した障害アクションを実行する executor を 1 個足す」話に落ちる。 唯一の設計上の欠落は 「問題が cross-account でどんな障害を起こすか」を表す宣言契約 (= action) で、 本 ADR の主眼はそこにある。

Decision

fire の publish と実行を分離し、 publish 済イベントを拾う cross-account disruption executor Lambda を新設する。 executor は CompetitorDeployRole へ ExternalId 付きで AssumeRole し、 問題 metadata が宣言した declarative かつ allow-list 済の disruption action を競技者アカウント内で実行する。 platform は action の 種別を dispatch するだけで、 障害の中身 (どの resource をどう叩くか) は問題が所有する (ADR-012 = problem is plugin, platform is host)。

operator ──POST /disruptions/fire──▶ disruption-fire (Phase A, 不変) │ REQUEST# claim → publish *DisruptionFired → AUDIT# ▼ operator EventBridge bus │ (rule: DetailType = *DisruptionFired) ▼ ┌───────────── cross-account disruption executor (Phase B, 新設) ─────────────┐ │ 1. action 宣言を catalog で解決 (= 無ければ no-op で終了 = Phase A 互換) │ │ 2. EXEC#{auditId}#{teamId} を conditional Put で冪等奪取 │ │ 3. team の deployment から competitorRoleArn + ExternalId(SSM) + stackOutputs │ │ 4. AssumeRole(ExternalId, 1h) → action.kind に応じた最小 API 1 本 │ │ 5. ADR-029 INV-2: revert を Scheduler に予約 (TTL 上限内で必ず復旧) │ │ 6. EXEC# 行を terminal 状態へ更新 (= 監査 + 再実行抑止) │ └────────────────────────────────────────────────────────────────────────────┘ │ ▼ competitor account: 実際の障害 (netem delay / Lambda invoke / stack update)

Disruption action の宣言契約

metadata.json の各 disruption に省略可能な action を足す。 これが Phase B の唯一の schema 追加。 action を持たない既存 disruption は Phase A と同じく監査のみで振る舞いが変わらない (後方互換)。 

{
  "id": "ec2-latency-injection",
  "eventDetailType": "DegradedDisruptionFired",
  "operatorEditable": ["afterMinutes"],
  "parameters": { "delayMs": 200, "device": "eth0" },
  "action": {
    "kind": "ssm-run-command",          // allow-list: ssm-run-command | lambda-invoke | cfn-stack-update
    "targetRef": "WorkerInstanceIds",    // team stackOutputs の key (= 注入対象を CFn 出力から解決)
    "documentName": "AWS-RunShellScript", // kind 固有 field (ssm)
    "revert": {                           // ADR-029 INV-2: 永続障害の禁止 (= 必ず復旧)
      "afterSeconds": 600,
      "documentName": "AWS-RunShellScript"
    },
    "paramTemplate": {                    // parameters → API 引数。 値は parameters / operatorEditable 由来のみ
      "commands": ["tc qdisc add dev {{device}} root netem delay {{delayMs}}ms"]
    }
  }
}
action.kindAssumeRole 後に叩く API想定する障害
ssm-run-commandssm:SendCommand (+ revert で復旧コマンド)netem 遅延 / プロセス kill / disk fill 等、 instance 内の fault
lambda-invokelambda:InvokeFunction (問題が同梱した fault Lambda)問題側ロジックで任意の fault (= 最も柔軟。 復旧も同 Lambda の revert mode)
cfn-stack-updatecloudformation:UpdateStack (parameter 上書き)capacity 削減 / SG 閉塞など、 stack parameter で表せる fault。 revert = parameter を戻す

値の出所を 2 つに固定する: ① targetRef は team の stackOutputs の key しか取れない (= 注入対象は CFn が出力した resource id に限定)、 ② paramTemplate の {{...}} 置換は parameters / operatorEditable で fold 済の値しか参照できない。 これにより operator も問題作者も「任意文字列を競技者アカウントの API へ直接流す」ことはできない (injection 面の縮小)。

Trust model

信頼境界は 既存の CompetitorDeployRole をそのまま再利用し、 bootstrap template は変更しない。 deploy worker と同一の 2 要素 (TenkaCloud account id + tenant 固有 ExternalId) で AssumeRole する。

層内容
誰が assume するかexecutor Lambda の実行ロール (operator account)。 信頼 principal は bootstrap の trust policy が既に ${TenkaCloudAccountId}:root + sts:ExternalId 条件で固定
ExternalId の出所tenant ごとの SSM SecureString (externalIdParameterName)。 deploy / describe-stack と同一経路。 コードに埋め込まない
セッションRoleSessionName = tc-disruption-{auditId}、 MaxSessionDuration 3600 は bootstrap が上限
権限の絞りrole 自体は AdministratorAccess だが、 executor が実際に呼ぶ API は action.kind ごとに 1 種類に固定 (SendCommand / InvokeFunction / UpdateStack)。 コードが叩く面は最小
operator 側ロールの最小化executor の実行ロールには sts:AssumeRole (競技者ロール ARN への resource 限定) + audit table の Put/Get + SSM GetParameter (ExternalId) のみ。 deploy worker と分離した専用ロール

Threat model

脅威緩和
Confused Deputy (他テナントの環境へ誤注入)AssumeRole は team の deployment 行が持つ competitorRoleArn + その tenant の ExternalId でのみ成立。 fire 時の event.tenantId === ctx.tenantId assert (Phase A) が上流で効く
Parameter injection (任意コマンドを競技者環境で実行)operatorEditable allow-list で fold 済の値しか paramTemplate に入らない。 targetRef は stackOutputs の key のみ。 問題作者が書いた action 文字列は check-template-security / レビュー対象
Replay / 二重注入EXEC#{auditId}#{teamId} の conditional Put で per-team 冪等。 同一 fire の再配送 (EventBridge at-least-once) は no-op
永続障害 (復旧不能で競技停止)ADR-029 INV-2。 action.revert 必須 (= 宣言が無ければ validate で reject)。 executor は注入と同時に revert を aws-scheduler へ予約し、 TTL 上限 (既定 30 分、 round 長を超えない) で必ず復旧
Blast radiusscope (all / team / random-n) と MAX_AFFECTED_TEAMS は Phase A で既に上限済。 executor は team 単位に分割実行し、 1 team の失敗が他へ波及しない

Liveness との結線 (ADR-029)

ADR-029 の不変条件 INV-2「いかなる disruption も永続しない」を Phase B では 実行レベルで保証する: action.revert を schema 必須とし、 executor は 注入の直後に revert ジョブを予約する。 revert は ① 宣言された afterSeconds 経過、 ② round の endsAt 到達、 ③ 明示の clear API、 のいずれか早い方で発火する。 これにより 「fire したが復旧機構が無い」状態を 宣言時 (validate) と実行時 (scheduler) の二重で排除する。

Alternatives considered

案判定理由
競技者アカウントに EventBridge bus + resource policy を置き、 cross-account publish する Rejected bootstrap への 追記が必要 (bus + policy + 競技者側 rule + target Lambda)。 競技者の事前作業が増え、 「stack 1 個で revoke」の単純さを壊す。 また EventBridge の at-least-once と競技者側 rule の有無で「届いたか」の観測が難しい
SSM RunCommand 専用 (kind を ssm に固定) Rejected SSM Agent が載る EC2/On-Prem にしか効かない。 Lambda / 容量系 / SG 系の fault を表現できず、 問題の多様性 (ADR-012) を縛る。 ssm は kind の 1 つとして残す
問題ごとに専用 disruption Lambda を operator 側にデプロイ Rejected 問題固有コードが platform に侵入する (ADR-012 違反)。 問題が増えるたび operator stack が膨らむ
AssumeRole + 宣言的 action を generic executor が dispatch Accepted 既存 AssumeRole パターンと AdministratorAccess の上に乗るため bootstrap 不変。 問題は action を宣言するだけ (plugin)、 platform は dispatch するだけ (host)。 fault Lambda kind で任意の障害も表現可

Consequences

Positive

  • 競技者アカウントで 実際に障害が起きる = ADR-013 / ADR-029 が前提とする「障害 → 復旧」競技が成立する
  • 競技者の追加作業ゼロ (bootstrap stack は従来のまま)。 信頼境界も deploy worker と同一で監査面が一本化
  • 障害の中身は問題が所有 (plugin)。 platform は action.kind の dispatch に閉じ、 問題追加で platform を触らない
  • 復旧が schema 必須 + scheduler 予約で二重に保証され、 「永続障害で競技停止」を構造的に防ぐ

Negative / trade-off

  • action 文字列 (paramTemplate / documentName) は問題作者が書く = レビュー対象が増える。 check-template-security 同様の静的検査を action にも広げる必要がある (実装 PR で追加)
  • AdministratorAccess ロールの上で実行するため、 executor のバグの理論上の影響範囲は広い。 コードが叩く API を kind ごと 1 本に固定し、 値の出所を 2 経路に限定して縮小する
  • at-least-once 配送に対する per-team 冪等 (EXEC# 行) と revert 予約の整合を実装で正しく扱う必要がある

Migration

  1. 本 ADR (design): cross-account 経路 + action 契約 + 信頼境界の確定。 bootstrap 不変であることの確認。
  2. schema: discover-problems-catalog.ts + SCHEMA.json に action (省略可) と revert 必須制約を追加。 parser に validate を足す。 action 無し = Phase A 互換 (監査のみ)。
  3. executor: *DisruptionFired を拾う専用 Lambda を新設 (deploy worker と分離した最小ロール)。 AssumeRole は describe-stack-handler パターンを踏襲。 unit test は STS / SSM / Lambda / CFn client を mock。
  4. revert: aws-scheduler 予約 + clear API。 ADR-029 INV-2 の実行時保証。
  5. reference 問題: microservice-migration-battle の ec2-latency-injection に action を宣言し、 LocalStack / 実環境で「fire → netem 遅延 → revert」を E2E 確認 (= #1419 Acceptance)。

後方互換: 既存問題は action 未宣言なので Phase A と同じく監査のみ。 Phase B 配備後に 問題側が段階的に action を足していける。 監査ログ (AUDIT#) の形は不変。

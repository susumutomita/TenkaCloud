ADR-047: Scheduled event deploy window & auto-cleanup

競技リソースを「いつデプロイし、 いつ破棄するか」 を event ごとの時間窓として宣言し、 platform が aws-scheduler で既存の bulk-deploy / bulk-teardown を疎結合に駆動する。 課金は窓の幅に必ず収束する。

Status: Proposed 2026-06-19
Related: ADR-037 (aws-scheduler による予約・自動停止の機構), ADR-029 (always-ends / 永続させない原則), ADR-042 (participant 招待), ADR-046 (課金境界)

Context

competitor account へ問題スタックを展開する経路は、 operator が UI から起動する bulk-deploy (bulk-deploy-create-state-machine) と、 撤去する bulk-teardown (deploy-delete-state-machine) の 2 本の Step Functions である。 event は startsAt / endsAt を持つが、 これらは 採点ゲート (HealthCheck が now >= endsAt でスコアを締める) にしか効かず、 リソースの生成・破棄とは無関係である。

つまり「いつ deploy/teardown するか」 は完全に手動の判断であり、 運用上 2 つの形が混在する:

運用形態アクセスの時間分布現状の痛み
定刻イベント (meetup / 社内 GameDay) 開始〜終了が決まっている 開始直前に手で bulk-deploy、 終了後に手で bulk-teardown。 撤去を忘れると課金が続く。
ベータテスター / 個別レビュー バラバラ (人によって触る時刻が違う) 「いつ deploy すれば全員が触れるか」 が決められない。 事前に常時 deploy しておくと 誰も触っていない時間も課金される。 これが本 ADR の主たる動機。

TenkaCloud は AWS Free Tier 内に収める cost-zero を設計原則に置く (DDB を 1/1 PROVISIONED に矯正する等)。 「触られていない競技リソースに課金しない」 はその延長線上の要請であり、 撤去の責任を人間の記憶に委ねている 現状は原則に反する。

Decision

event に deploy window を宣言できるようにする。 window は最大 2 つの時刻を持つ:

field意味駆動
deployAt (任意)この時刻に問題スタックを自動展開するbulk-deploy state machine を起動
teardownAt (任意)この時刻に問題スタックを自動撤去する (= auto-cleanup)deploy-delete state machine を起動

予約の機構は ADR-037 で導入済の aws-scheduler one-shot schedule を再利用する (新しい機構を増やさない)。 event の作成 / 更新時に、 deployAt / teardownAt それぞれに対し at(<ISO>) の schedule を 1 つずつ登録し、 schedule の target は既存の bulk-deploy / bulk-teardown を起動する control Lambda とする。 これにより platform は 「窓の宣言」 と 「窓の駆動」 を疎結合に保つ — UI / API は時刻を書くだけ、 実際の展開・撤去は既存 state machine が担う。

event 作成/更新 (deployAt=T1, teardownAt=T2) │ ├─ aws-scheduler: at(T1) ─▶ deploy-window-control Lambda ─▶ StartExecution(bulk-deploy SM) └─ aws-scheduler: at(T2) ─▶ deploy-window-control Lambda ─▶ StartExecution(deploy-delete SM) billing = [T1, T2] の幅だけ。 window 外は competitor account に何も存在しない。

Always-ends との結線 (ADR-029)

ADR-029 は「いかなる障害も永続しない」 を不変条件に置く。 本 ADR はそれをリソース生成にも拡張する: deployAt を宣言したら teardownAt は必須とし (= 展開したら必ず撤去予約が伴う)、 さらに teardownAt は endsAt 以降でなければならない (= 採点が締まる前にリソースが消えない)。 この 2 つの制約を schema (refine) と control Lambda の両方で enforce し、 「撤去予約のない展開」 を 構造的に作れないようにする。

冪等性と安全性

  • per-event 冪等: schedule 名は tc-deploy-<eventId> / tc-teardown-<eventId> で安定させ、 同 event の再 fire / 二重登録を弾く (ADR-037 の revert schedule と同じ命名規約)。
  • 窓は event の所有スタックのみに作用する。 teardown は当該 event の deployment 行から 解決した stack だけを対象にし、 他 event / 他 tenant のリソースには触れない。
  • deploy がまだ走っている最中の teardown を避けるため、 control Lambda は teardown 起動時に進行中の bulk-deploy execution があれば完了を待つ (= state machine の 終端を確認してから delete を起動)。
  • window を更新したら旧 schedule を delete してから新規登録する (= 時刻変更が確実に反映される)。
  • operator は UI から window を取り消せる (= schedule を削除し、 必要なら即時 deploy/teardown に切替)。

Alternatives considered

案評価却下理由
常時 pre-deploy (現状運用の一形態) 却下 誰も触らない時間も課金される。 cost-zero 原則に正面から反する (= 本 ADR の動機そのもの)。
手動 deploy/teardown のみ (現状) 却下 撤去忘れで課金が続く。 バラバラなアクセスに対し「いつ deploy するか」 を人間が決められない。
on-demand per-team (初回ログインで lazy deploy + idle TTL 撤去) 将来 アクセスが「数日に分散」 する場合の理想形だが、 lazy-deploy 経路 + idle 追跡 + 初回アクセスの 待ち時間 UX が要る。 まず窓で課金を有界化し、 必要が顕在化したら別 ADR で追加する。
app 内 polling で時刻判定 (scheduler を使わない) 却下 polling Lambda を別途常駐させる必要があり、 精度も粗い。 ADR-037 で実績のある aws-scheduler の one-shot を使えば追加の常駐コストなしで分精度に予約できる。

Consequences

  • 課金が必ず window の幅に収束する (= 撤去忘れが構造的に起きない)。 ベータ / 個別レビューでも 「窓を 1 つ宣言するだけ」 で安全に共有できる。
  • 新しい機構を増やさない: 予約は ADR-037 の aws-scheduler、 展開・撤去は既存 2 本の state machine の再利用。
  • window 未宣言の event は従来どおり完全手動 (= 後方互換)。
  • teardown は破壊的操作。 teardownAt >= endsAt 制約と進行中 execution の 待機で誤撤去を防ぐが、 operator への明示的な確認 UI と監査ログ (ADR-020 系) を併設する。
  • aws-scheduler の schedule 数・実行レートの quota を消費する (event 数 × 最大 2)。 one-shot は ActionAfterCompletion: DELETE で自動削除されるため累積はしない。

Migration

追加 (additive) であり破壊的変更はない。

  1. event schema に deployAt / teardownAt を任意で追加し、 deployAt ⇒ teardownAt 必須 / teardownAt >= endsAt を refine で enforce する。
  2. deploy-window-control Lambda を追加し、 aws-scheduler から起動されて bulk-deploy / deploy-delete state machine を StartExecution する。 IAM は対象 state machine への states:StartExecution に scope する。
  3. event 作成 / 更新時に window schedule を登録 / 差し替え / 削除するサービス層を加える。
  4. application-admin-console の Event 編集に「deploy 窓」 (deploy 時刻 / 自動撤去時刻) と 取り消し操作を出す。 i18n は ja / en。
  5. 既存 event は window 未宣言 = 従来の手動運用のまま。 operator が必要な event にだけ窓を付ける。

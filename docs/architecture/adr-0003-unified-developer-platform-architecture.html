ADR-0003 — Unified developer-platform architecture

One architecture decision for the whole TenkaCloud developer surface — the marketing landing page, pack-author and operator documentation, the API reference, interactive API exploration, examples, the changelog, and future pack discovery — taken before any framework or page is implemented. The decision fixes a single design system, one navigation and search model, one analytics boundary, and one auth boundary, so the surface can grow to an authenticated API console and an isolated sandbox without a second frontend rewrite.

1. Context

TenkaCloud today presents a landing page plus a scattering of README links. As the platform opens up — external problem packs (#2085), a public SDK contract (#2106), an HTTP API that operators and pack authors call — the developer-facing surface multiplies into distinct concerns that nonetheless must feel like one product:

  • Marketing: / and /product — first impression, positioning, calls to action.
  • Documentation: /developers/docs/* — pack-author guides, operator runbooks, conceptual docs (MDX with embedded React).
  • API reference: /developers/api/* — rendered from an OpenAPI source of truth.
  • Examples: /developers/examples/* — copyable SDK / CLI / HTTP snippets.
  • Changelog: /developers/changelog — release history, tied to the pack and SDK version axes of ADR-0002.
  • Sandbox: /developers/sandbox/* — a future interactive, authenticated API console (the subject of ADR-0004).
  • Future pack discovery: a browseable catalog of published packs.

If these are built as separate sites or with separate tooling, the platform pays for it forever: duplicated headers / footers / theming, a fractured navigation and search experience, two analytics pipelines, and — most damaging — a second frontend codebase the day an authenticated console or sandbox is needed. The decision below must be made once, before any page is written, so every later increment lands inside one coherent application.

What this decision must guarantee. One domain and one deployment; a shared header / footer / theme / command-search across marketing, docs, and reference; MDX and React coexisting on the same routes; the API reference rendered from the platform's OpenAPI source of truth; room for an isolated sandbox and a shared auth boundary for future logged-in areas without a rewrite; and shipping on the project's current Vercel-oriented, React-based stack.

2. Decision

Build the entire developer surface as one Next.js application that uses Fumadocs for content, navigation, and search, and a dedicated OpenAPI renderer (Scalar) for the API reference, all under a single domain and a single deployment.

  1. One app, one domain, one deploy. Every route in §5 — marketing, product, docs, API reference, examples, changelog, and the future sandbox — is served by one Next.js application behind one origin. No second site, no second build pipeline.
  2. Fumadocs owns content and navigation. MDX pages (docs, examples, changelog) render through Fumadocs, which provides the shared sidebar / nav tree, the command-palette search index, and first-class React-in-MDX so interactive components live inline with prose.
  3. Scalar owns the API reference. /developers/api/* renders from the platform's OpenAPI document (the source of truth defined in ADR-0004), embedded as a React component inside the same app and the same chrome.
  4. One design system, applied everywhere. Header, footer, theme tokens, typography, and the command-search live in a shared app shell that wraps marketing, Fumadocs content, and the Scalar reference alike (§6).
  5. Static / cached by default, dynamic where required. Marketing, docs, the reference, examples, and changelog are statically generated and CDN-cached. Only the future sandbox and authenticated areas are dynamic, gated by the shared auth boundary (§8).
  6. One auth boundary, drawn now, used later. Public routes need no session. The app reserves an authenticated segment (Next.js route group / middleware) so the future API console and sandbox log-in flow plug into the same boundary — not a new frontend.
This names one target architecture, not a menu. The selected stack is Next.js + Fumadocs + Scalar, single app, single deployment. The alternatives in §12 are recorded as rejected, with the specific guarantee each one breaks.

Why A wins. Only candidate A clears every criterion. Candidate B fails C1, C2, C5, and C6: a standalone Docusaurus / Starlight site is excellent at docs but it is a second surface — separate origin, separate theme and search, and no server runtime to host an authenticated sandbox, so an API console would force a third app or a cross-site auth bridge. Candidate C keeps one app but a Vite SPA has no first-class SSR / ISR, no edge auth boundary, and would require hand-building the MDX pipeline, the OpenAPI renderer, the search index, and versioning — re-creating Fumadocs and Scalar by hand.
If a separate docs site (candidate B) were ever forced, here is what it must preserve

Recorded for completeness, since the issue requires it: a separate Docusaurus / Starlight site would only be acceptable if it (a) reused the exact same design tokens, header, and footer via a shared component package so the two surfaces are visually indistinguishable; (b) was served under the same apex domain via path-based routing at the edge so cookies and analytics are shared (no second origin); (c) federated its search into the one command palette; and (d) still delegated every authenticated and sandbox route to the Next.js app, because the static doc site cannot host them. Meeting all four effectively rebuilds candidate A with extra moving parts, which is why B is rejected rather than adopted.

8. Security-boundary model

Four trust zones run through the surface. The frontend draws the boundary; the API tiers enforce it. ADR-0004 specifies the sandbox and API zones in depth; this ADR fixes where the line sits in the unified app.

Trust zones and what the unified app does at each.
ZoneRoutesSessionDefault API target
Public docsmarketing, docs, reference (browse), examples, changelogNoneRead-only / none; Try-It points at sandbox
Authenticated docssandbox console UI, future logged-in areasShared auth boundary (middleware)Sandbox API with a scoped session
Sandbox APIn/a (API tier behind /developers/sandbox)Short-lived, audience/tenant/operation-scoped tokenIsolated sandbox tenant only
Production APIn/a (the real platform API)Real platform authNever the Try-It default; reached only by real, authenticated callers
Prohibition fixed here. The default Try-It target is the Sandbox API. Direct Try-It traffic to production write endpoints is prohibited by default. No API key or bearer token is embedded in static docs. ADR-0004 specifies how this is enforced at the API tier.

9. Is an interactive "API Try It" possible? Yes — and how it is isolated

Yes. Because the reference is rendered by Scalar inside a Next.js app that has a real server runtime and a shared auth boundary, an interactive "Try It" is feasible without a second frontend. The isolation rules:

  1. Default target is the sandbox base URL. Scalar's server / base-URL selector is configured so the default interactive target is the sandbox API, not production. A public, unauthenticated reader can exercise browse-only and sandbox-safe operations only.
  2. Write operations require an authenticated sandbox session. Anything that mutates state is gated behind the shared auth boundary and runs against an isolated sandbox tenant with a short-lived, audience-bound, tenant-bound, operation-scoped token.
  3. Destructive / billable operations are disabled in public unauthenticated Try-It. The endpoint capability matrix in ADR-0004 labels each operation; the renderer only enables what the reader's zone permits.
  4. No traffic crosses the production boundary by default. Reaching production is never the Try-It default and requires real, authenticated platform credentials that are never present in the docs.

The concrete safe-request flow, the denied production-write flow, the token model, the capability matrix, and the sandbox cleanup behavior are specified in ADR-0004. This ADR establishes only that the chosen architecture can host it in the same app.

10. Migration plan from the existing landing + README links

The cutover is incremental and route-by-route; there is no big-bang rewrite and no period with two competing surfaces.

Incremental migration stages.
StageActionObservable result
1. Stand up the shell Create the one Next.js app with the shared shell, theme tokens, header / footer, and command-search. Move the current landing page to / unchanged in content. The landing page renders from the new app; nothing visible regresses.
2. Docs home + Fumadocs Add /developers and /developers/docs/*. Port the highest-traffic README content to MDX. Leave the READMEs in place, linking forward. Authors and operators have a navigable docs home; old links still work.
3. API reference Wire Scalar to the OpenAPI artifact at /developers/api/* (browse-only first). A rendered, searchable reference exists; Try-It targets sandbox once ADR-0004 lands.
4. Examples + changelog Add /developers/examples/* and /developers/changelog; route CI-tested snippets and release notes in. Copyable, tested examples and a release history under one nav.
5. Redirect + retire Add redirects from the old landing URLs and README anchors to the new routes. Update README links to point at /developers/*. One canonical surface; old entry points redirect, no dead links.
6. Auth boundary + sandbox Reserve the authenticated route group / middleware; land /developers/sandbox/* per ADR-0004. The interactive console ships into the same app — no second frontend.
Each stage ships an observable improvement and is independently reversible (a stage can be rolled back to the prior redirect state). The existing READMEs keep working until stage 5 redirects them, so there is never a window where documentation is unreachable.

11. Consequences

Positive

  • One domain, one deployment, one design system — the surface is coherent from day one and stays that way as it grows.
  • The authenticated API console and isolated sandbox land in the same app; there is never a second frontend rewrite (the core acceptance criterion of #2100).
  • The reference cannot drift: it is generated from the OpenAPI source of truth, and the CLI / SDK pages from their own sources.
  • Static-by-default keeps marketing and docs fast and cheap; only authenticated areas pay the dynamic cost.
  • Incremental migration means no big-bang cutover and no dead links.

Costs and obligations

  • Adopting Next.js + Fumadocs + Scalar adds these to the toolchain and to the maintenance surface, versus the existing Vite SPAs.
  • The CI generation steps (OpenAPI, CLI reference, SDK reference, snippet tests) must be built and kept green so the generated pages stay accurate.
  • The auth boundary and sandbox are reserved now but only realized in ADR-0004; until then the authenticated segment is an empty, guarded shell.
Explicitly rejected outcomes. No second standalone docs site with its own theme / search / origin; no hand-rolled MDX + OpenAPI pipeline inside the Vite SPA; no cross-site auth bridge to reach a console; and no default Try-It path to production write endpoints. Any of these breaks a guarantee in §2.

12. Alternatives considered

AlternativeWhy rejected
Separate Docusaurus / Starlight docs site beside a marketing app (candidate B) A second surface: separate origin, theme, and search, and no server runtime to host an authenticated sandbox. It fails C1, C2, C5, and C6, and would force a third app or a cross-site auth bridge the moment a console is needed. Acceptable only if it rebuilt the unified app's shared shell, same-domain routing, federated search, and delegated auth — which is candidate A with extra parts (see §4).
Hand-rolled MDX + OpenAPI rendering in the existing Vite SPA (candidate C) Keeps one app but a Vite SPA has no first-class SSR / ISR and no edge auth boundary, and it would mean re-implementing the MDX pipeline, OpenAPI renderer, search index, and versioning by hand. Fails C4, C5 (partially), C6, and C8.
Embed Try-It pointing at production with read-only scopes Puts interactive traffic one config change away from production writes and risks a key in static docs. The sandbox-default model (§8, ADR-0004) is required instead.
Defer the architecture decision until pages are needed Guarantees an ad-hoc second surface and an eventual rewrite when the console arrives. The whole point of #2100 is to decide once, up front.

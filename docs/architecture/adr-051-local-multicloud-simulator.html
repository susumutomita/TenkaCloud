ADR-051 — Provider-neutral local cloud simulation

Status: Accepted Date: 2026-07-12 Relates: ADR-012, ADR-023, ADR-048 Protocol: 2026-07-11

TenkaCloud delegates local cloud runtimes to the separate TenkaCloud Simulator process through a versioned HTTP boundary. Docker problems keep their existing Compose and /verify path unchanged. The local participant API is the provider-neutral orchestration port: it starts and stops either runtime, persists enough identity to recover a session, and presents both through the same portal lifecycle contract.

1. Context

The original local mode is intentionally narrow: a catalog-owned Docker container exposes the challenge surface and evaluates submissions through POST /verify. That path is valuable and remains the correct fidelity boundary for application drills. Cloud problems, however, describe AWS, GCP, Azure, Sakura Cloud, or a composite of providers. Treating every one as a Docker manifest would erase provider semantics and would duplicate a growing emulator inside the platform repository.

The multi-cloud emulator is therefore an independent product and repository. TenkaCloud owns catalog, portal, score, and lifecycle composition; Simulator owns the event-sourced world, provider plugins, resource projections, deterministic time, and simulation console. This also keeps production deploy adapters unchanged: local simulation is an explicit runtime, never an authentication bypass or a fallback from a failed real-cloud deployment.

2. Decision

  1. Keep the Docker runtime byte-for-byte compatible at its public seams: Compose start/stop, loopback-only endpoints, per-run secret injection, and problem-owned /verify scoring.
  2. Add a provider-neutral local runtime port behind the existing portal start/stop API. A cloud or composite catalog descriptor is dispatched to Simulator; a Docker descriptor is dispatched to the existing container runner. Unsupported capability is an error, not a fallback.
  3. Pin the client to protocol 2026-07-11. Startup performs capability preflight before a world or deployment is created. The lifecycle uses exactly five required operations: GET /v1/capabilities, POST /v1/worlds, POST /v1/worlds/{worldId}/deployments, GET /v1/worlds/{worldId}/deployments/{deploymentId}, and DELETE /v1/worlds/{worldId}. Snapshot, provider-operation, and clock-advance routes are optional lifecycle extensions, but use the same scoped launch-token authorization and strict response validation.
  4. Start Simulator on a random loopback port, either as a real injected executable or as a digest-pinned container. Cloud local play defaults to the reviewed immutable image ghcr.io/susumutomita/tenkacloud-simulator@sha256:049c6c165f9947b386b2c5864983aebefba26e996ec62859dae0e9814c52d505. An explicit executable, image digest, or externally managed loopback URL replaces that default; ambiguous explicit configuration fails before world creation.
  5. Persist participant-safe launcher and world/deployment identity in simulator-session.json. Persist launch secrets, provider credentials, launch tokens, and deployment outputs in a self-contained, mode-0600 simulator-secrets.json generation. Commit that protected source atomically before its public projection; its random record id lets restart regenerate a missing, corrupt, or older public projection. Before an owned process or container starts, commit a private launch intent containing its deterministic cleanup handle. Process mode uses a detached supervisor that registers both its own and its child process identity before readiness and watches a private ownership lease; restart can therefore cancel an uncommitted launch, while a committed session retains the lease until Stop. Stop and reset delete the remote world before terminating an owned process. A resumed CLI verifies the recorded process and deployment instead of trusting stale files.

3.1 Launcher environment

TENKACLOUD_SIMULATOR_PORT=<random free loopback port>
TENKACLOUD_SIMULATOR_LAUNCH_SECRET=<base64url of 32 random bytes>
TENKACLOUD_SIMULATOR_STATE_DIR=<private absolute state directory>
TENKACLOUD_SIMULATOR_AWS_ACCESS_KEY_ID=<simulator-only TCSIM id>
TENKACLOUD_SIMULATOR_AZURE_CREDENTIAL=<simulator-only bearer>
TENKACLOUD_SIMULATOR_GCP_CREDENTIAL=<simulator-only bearer>
TENKACLOUD_SIMULATOR_SAKURA_CREDENTIAL=<simulator-only basic pair>

Container images must match <registry/name>@sha256:<64 lowercase hex>. Tags are rejected. The launcher does not publish ports on all interfaces, mount the repository, or pass host credentials. An injected executable is a real process boundary for development and tests, not an in-process fake API.

A catalog with a digest-pinned workload enables the Simulator workload runner explicitly. A process launch uses the user-owned Docker CLI. A container launch bind-mounts only the daemon UNIX socket, adds only its numeric socket group, and passes the reviewed image allowlist, fixed quotas, and the Simulator container identity. Simulator remains non-root and joins each world-internal network as its control-plane member; participant endpoints still publish on host loopback only. Failure to establish the complete socket and policy boundary removes the workload capability before preflight. This mode is limited to single-user local play and does not authorize Docker socket access for a hosted or shared service.

A validated simulation overlay is sent only at the deployment wire boundary. Any requirement or workload artifact referenced by that overlay is added exactly once to its normalized runtime target's deterministic artifact bundle. A single-file runtime therefore uses the original raw-template form only when no overlay artifact is required; otherwise it uses the versioned bundle so Simulator can verify and consume the exact catalog bytes named by the overlay digest.

4. Authorization and isolation

Each launch generates a fresh 256-bit secret. TenkaCloud mints an HMAC-SHA256 token in the canonical tc_sim_v1.<base64url-json>.<base64url-signature> form. Claims contain exactly tenantId, eventId, teamId, deploymentId, millisecond issuedAt/expiresAt, and a random nonce. The token is sent as Authorization: Bearer; namespace fields in a request must match its claims.

  • The secret is private state and is never logged. Browser console access receives the scoped token only in its link fragment; the private native-CLI environment carries it as a bearer credential.
  • The console receives the token only in the URL fragment: #token=tc_sim_v1.…. Fragments are not sent in HTTP requests.
  • World/deployment ids are generated per local problem and scoped by the local tenant/event/team tuple.
  • Simulator and the participant API bind only to loopback. Codespaces uses a distinct authenticated forwarded origin for each port; challenge and Simulator content never share the portal origin.
  • Every problem target gets a distinct random loopback listener and origin. A listener accepts Origin-free CLI traffic or only its own exact loopback/Codespaces origin; the Participant Portal origin and every sibling target origin are rejected. Exact Host validation prevents DNS rebinding, private forwarding headers are stripped, and an independent worker-src 'none' CSP policy prevents service-worker persistence across listener shutdown.
  • The route forwards only the catalog-required GET, HEAD, POST, and QUERY methods. Every other method is rejected before upstream I/O rather than trusting Fetch to preserve it.
  • Unapproved browser origins are rejected before any participant API mutation. Browser cookies and upstream cookies never cross either Simulator proxy, and request/response I/O is bounded by explicit size and abort deadlines.

5. Snapshots and recovery

Snapshot export/import runs through the owning local API process, uses the Simulator snapshot endpoints, and stores the validated document with mode 0600. Export is explicit and stop cleanup does not silently overwrite a named snapshot. Import first persists a restore intent keyed by the source world and snapshot hash, then asks Simulator to create or recover an idempotent clone. TenkaCloud durably owns both source and restored world ids before it validates the restored deployment. It switches the active participant projection only after the restored deployment is running, persists that switch while retaining source cleanup ownership, deletes the source world, and finally releases the restore intent. A response loss or interrupted commit therefore replays the same restore key or reconciles both worlds; it cannot create an untracked clone or discard the last known-good source.

5.1 Overlay, scoring, and virtual time

The catalog keeps only a versioned simulationOverlay file reference in metadata. The adapter validates and loads that file, then sends the document as the deployment request's top-level simulationOverlay field. Ordinary health probes use the real loopback workload endpoint; attack probes use the authenticated HTTP::Endpoint/AttackProbe provider command. Phased scoring advances time with POST /v1/worlds/{worldId}/clock/advance and accepts only the strict { clock, appliedTransitions } response, keeping provider transition rules outside TenkaCloud. Score cycles are deduplicated per problem. Simulator lifecycle, snapshot, probe, and virtual-clock mutations share a per-problem operation queue, and a deployment-generation check discards a score result if stop/reset replaced its world before commit.

5.2 Native CLI routing

Standard provider CLIs are not assumed to support arbitrary routing headers. TenkaCloud therefore exposes a per-problem/per-target loopback endpoint prefix through the existing participant API. The local proxy removes only that prefix, preserves the provider-native authorization and payload, and injects world, deployment, and target headers before forwarding to Simulator. A private multi-profile environment artifact supplies that endpoint plus local-only provider credentials; query parameters are deliberately not used for routing because AWS Query and ARM APIs own them. Provider request semantics and state reduction remain entirely in Simulator.

6. Consequences

  • One portal lifecycle works for Docker and provider simulations without putting provider branches in the portal.
  • TenkaCloud has a small versioned dependency on Simulator while provider implementation remains outside this repository.
  • Cloud local play is reproducible and auditable because the default and every override are digest-pinned Simulator artifacts.
  • There is deliberately no implicit image tag or Docker-only fallback for a cloud runtime.
  • Production cloud adapters and the established Docker /verify contract are unaffected.

7. Alternatives rejected

  • Embed provider emulators in TenkaCloud: couples the platform to every provider API and duplicates Simulator state.
  • Translate cloud problems into ad-hoc containers: loses native API/IaC behavior and makes unsupported operations look successful.
  • Use a mutable latest image: prevents reproducible recovery and makes capability reports untrustworthy.
  • Expose Simulator publicly: expands the attack surface and is unnecessary for local/Codespaces operation.
This decision implements the platform boundary required by TenkaCloud Issue 2574.

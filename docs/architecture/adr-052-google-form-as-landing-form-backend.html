ADR-052 — Google Form as the landing page's form backend

Status: Accepted Date: 2026-07-25 Scope: landing/ only — no plane, no tenant runtime

The landing page needs to accept inquiries. It is a static site on Cloudflare Pages with no backend, and standing up one — an API, a datastore, spam handling, an on-call story — costs far more than the feature is worth. Until now the page linked out to a hosted Google Form, which works but drops the visitor onto a page that looks nothing like the site. This ADR keeps Google Form as the storage, notification, and aggregation backend while moving the presentation back onto the landing page: the site posts to the form's formResponse endpoint from its own HTML. The one fragile part of that trick — the per-question entry.<digits> identifiers — is closed structurally by defining the form as code and regenerating the identifier map in CI.

1. Context

A Google Form exposes an HTTP endpoint that accepts responses (…/formResponse), and every question on the form carries a generated field name of the form entry.123456. A form posted from arbitrary HTML with those field names is indistinguishable, on Google's side, from one submitted through the hosted UI. So "a Google Form cannot be restyled" is only half true: the rendering and the intake endpoint are separable. Taking the endpoint and leaving the rendering behind buys response storage, automatic spreadsheet accumulation, email notification, and aggregation for no server, no database, and no operational cost.

The catch is the identifiers. They are assigned by Google, so they cannot be authored by hand, and editing the form can change them. Worse, the browser cannot post to Google cross-origin and read the reply: the request must be sent mode: "no-cors", which makes the response opaque. A stale identifier therefore does not fail — it silently discards the submission, and nothing on either side reports it. Any design that leaves identifier maintenance to a human will eventually lose inquiries without anyone noticing.

2. Decision

  1. The inquiry form is rendered by the landing page itself (landing/index.html, styled with the site's own CSS) and submits directly to the Google Form formResponse endpoint.
  2. The form definition — questions, types, required flags, choices, response spreadsheet, notification recipients — lives in version control as an Apps Script project (form/sync.gs), not in the Google Forms editor. Changes to it go through pull request review like any other code.
  3. syncForm() is idempotent and updates questions in place (matched by title) rather than deleting and recreating them, so identifiers survive every change except a question-type change. A type change is refused unless the caller passes allowTypeChange, because it is the one operation that necessarily invalidates an identifier.
  4. On each sync, the identifiers are recovered by reverse-engineering a pre-filled URL and written to landing/contact-form-config.json. The landing page fetches that file at runtime, so the page follows the form rather than embedding a copy of its identifiers.
  5. If the config is missing, malformed, or lists a different field set than the page's own inputs, the inline form is not shown. The page falls back to the pre-existing link to the hosted Google Form and logs the reason to the console.

3. Data flow

4. Why the sync runs through a web app

CI updates the script with clasp push and then needs to execute syncForm(). The direct route, clasp run, requires associating a Google Cloud project and publishing an API-executable deployment. Redeploying the script as a web app onto the same deployment identifier keeps a stable URL and reduces the requirement to one shared secret, so that is what the workflow does. The endpoint is anonymous by necessity and is protected by a SYNC_TOKEN script property compared in constant time; because a web app cannot choose its HTTP status, success is reported in the body (ok) and the workflow branches on that rather than on the status code.

5. Consequences

PropertyResult
Running costZero. No compute, no datastore, nothing to keep alive between inquiries.
Design freedomFull. The form is the site's own markup and CSS, in both Japanese and English.
Delivery confirmationNone. no-cors makes the response opaque; only a network-layer failure is observable.
Spam protectionNone. There is no CAPTCHA and the endpoint is public by design.
File uploadsNot possible through this path.
Server-side validationGoogle enforces its own required/format rules, but the result is unreadable, so the page validates before sending.
Identifier driftStructurally handled: in-place sync preserves identifiers, CI regenerates the map, and a mismatch hides the form instead of losing mail.

The honest reading of the two red rows is that this design suits a low-volume inquiry channel and nothing more. The success message shown to the visitor says so implicitly — it asks them to resend through the hosted form if no reply arrives — rather than claiming a delivery guarantee the transport cannot make. If the landing page ever needs receipts, attachments, or abuse controls, the correct move is a real backend, not a workaround layered onto this one.

6. Alternatives considered

OptionWhy not
Keep linking to the hosted form Works and stays the fallback, but the visitor leaves a carefully designed page for an unstyled one at the moment of highest intent.
Embed the form in an <iframe> Keeps the visitor on the page but not the design; the frame cannot be styled, and it is a poor fit on mobile.
A small serverless endpoint (Cloudflare Worker + D1) Technically the better answer for validation and spam control, and the platform already runs Workers in Always-On mode. Rejected here because it adds a deployable, a schema, and an operational surface to the marketing site for a handful of inquiries a month. This is the migration target if the limits above start to bite.
A third-party form SaaS Solves spam and receipts, but adds a paid dependency and a second place where inquiry data lives, for a channel that already terminates in Google.
Hand-maintained entry identifiers The failure mode is silent data loss. Rejected outright; automating the map is the whole reason this design is acceptable.

7. Security and privacy

  • Inquiry data never touches TenkaCloud infrastructure. The browser posts directly to Google, and responses live in Google's storage — the same processor the privacy policy already names.
  • The endpoint accepts anonymous submissions by design, exactly as the hosted form does. Publishing the formResponse URL discloses nothing that was not already reachable from the public form.
  • The sync web app is the one privileged surface. It is anonymous-accessible, so its only protection is SYNC_TOKEN; the token is a repository secret, is never written to a workflow log, and a successful call can only reshape the form to the definition already committed in form/sync.gs.
  • Credentials for clasp are supplied to CI as secrets and written to the runner's home directory for the duration of the job. They are not committed: form/.clasp.json and form/.clasprc.json are ignored, and only .clasp.json.example is tracked.
  • The page writes status text with textContent, so no submitted or fetched value is ever interpolated as HTML.

8. Rollout

The inline form is progressive enhancement over the existing link, so the two states are both shippable. Before the first sync there is no contact-form-config.json, the inline form stays hidden, and the page behaves exactly as it did before. After the first sync merges, the inline form appears. Reverting is symmetric: delete the config file and the page returns to the link.

Because the workflow's first run acts on a form that already exists and already holds responses, the workflow_dispatch entry point defaults to dry_run: true. A dry run reports the plan — which questions would be created, updated, or recreated — and the identifiers as they stand, without modifying anything. The intended sequence is one dispatched dry run, a review of the plan in the job summary, and only then a real sync.

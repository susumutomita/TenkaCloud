ADR-014: EventBridge 駆動 state reconciliation

Status: Accepted (Phased rollout) Date: 2026-05-14 Decider: susumutomita Driver: #724 / 競技 platform の Lambda invocation cost + state 反映 latency

Context

TenkaCloud の deploy / scoring / event status 反映は現在、 複数の polling 経路で構成されている:

経路主体間隔役割
EventDetail / participant portal の fetchfrontend (browser)30sdeployment status / score の表示更新
reconcileEventStatusesgeneric-scoring Lambda1 minDEPLOYING → READY / TEARDOWN → ARCHIVED の自動遷移
StackProgress fetchadmin-console30sCFn events / resources 表示
Score enginegeneric-scoring Lambda1 minBattle uptime probe / phased-polling 採点

問題点:

  • Lambda invocation cost: 1-min polling × 全 tenant 並列で Lambda 呼び出しが時間あたり線形に増える。 Free Tier の 100 万 invocation/月 を超えると課金 (≒ 0.20 USD per million)、 5 tenant + 4 timer source = 約 60 万/月の constant invocation
  • 状態反映 latency: CFn rollback など operator-visible event が 30s〜2 min 遅延して UI に反映される
  • Stuck state の root cause: #708 (TEARDOWN stuck) / #723 (IN_PROGRESS stuck after ROLLBACK_COMPLETE) はいずれも reconcileEventStatuses が CFn 真の state を polling 前提で書き戻すため、 polling 中の race と silent skip で stuck になりやすい

ユーザー指摘: 「ポーリングじゃなくてイベント駆動とかにできないのでしょうか? 負荷も高くなるし」

制約 (前提として固定)

  • SSE / WebSocket の新規導入禁止 (memory feedback_polling_over_sse): API Gateway WebSocket は Lambda 運用と非整合、 frontend は polling 維持
  • DynamoDB on-demand 禁止: 全 table PROVISIONED 1/1 を DynamoDbLowCapacity Aspect で強制
  • Cost 0 原則: Free Tier 内で完結
  • cross-account event bus 経路あり: 競技者 account の CFn / CodeBuild event を operator account に流す必要がある

Decision

Phased migration を採用。 backend (= reconciler / probe) は event-driven に移行、 frontend は polling 維持。

Phase A — CFn Stack Status Change を EventBridge で受信 (高優先)

競技者 account 側で aws.cloudformation source の "CloudFormation Stack Status Change" event を購読する EventBridge rule を competitor-bootstrap.yaml に追加。 rule target は operator account の event bus (= cross-account event delivery)。 operator side で event を受ける Worker Lambda が DDB Deployments row の status を直接 update する。

Source競技者 account の EventBridge ruleTargetOperator side Worker
aws.cloudformation 
{
  "source": ["aws.cloudformation"],
  "detail-type": ["CloudFormation Stack Status Change"],
  "detail": {
    "stack-name": [{"prefix": "tc-"}]
  }
}
 operator account の event bus ARN
(= CDK_PARAM_OPERATOR_EVENT_BUS_ARN param)		 CfnStackStatusReconciler Lambda:
  • event.detail から stack-name / status-details を抽出
  • namePrefix で Deployments row を Query (GSI 経由)
  • StackStatus が COMPLETE → row.status = COMPLETE
  • 失敗系 → row.status = FAILED + failureReason

これで reconcileEventStatuses の 1-min polling は 不要 になる (= Event status 遷移は EventBridge driven、 Deployments row.status は CFn event で直接更新される)。 #708 / #723 の stuck root cause も同時に解消。

Phase B — CodeBuild State Change で buildId を即時記録

#720 で MarkSucceeded / MarkFailed に buildId を入れる short-term fix を入れたが、 deploy 進行中 (= IN_PROGRESS) は依然 buildId が DDB に無い。 EventBridge "CodeBuild Build State Change" event を購読 (operator account 内なので cross-account 不要) で buildId を即時 record。 

{
  "source": ["aws.codebuild"],
  "detail-type": ["CodeBuild Build State Change"],
  "detail": {
    "project-name": ["tenkacloud-saas-provisioning"],
    "build-status": ["IN_PROGRESS", "SUCCEEDED", "FAILED"]
  }
}

Phase C — Frontend polling は維持 (= SSE 禁止制約遵守)

SSE / WebSocket は新規導入禁止 (= memory feedback_polling_over_sse)。 frontend 側の 30s polling は維持するが、 Lambda 側の応答に If-Modified-Since headers 相当 (= DDB updatedAt の比較) を入れて no-op responses を 200 + 空 payload で返し、 invocation 自体を 0 にはできないが転送量を削減する。

Out-of-scope

  • SSE / WebSocket / AppSync subscription (= 禁止)
  • 外部 endpoint への scoring probe (= 競技者 endpoint への HTTP probe は polling 維持、 仕様)
  • EventBridge Pipes (= 過剰、 Lambda + Rule で十分)

Consequences

Pros

  • Lambda invocation コスト削減: reconcileEventStatuses の 1-min polling 廃止で月あたり ~43,200 invocation/tenant 削減 (= 60 × 24 × 30)
  • 状態反映 latency 改善: CFn rollback 〜 UI 反映が 30s〜2min → ~5s (EventBridge delivery + Lambda invocation)
  • #708 / #723 の stuck root cause が構造的に解消 (= reconcile が race / silent skip しない)
  • operator が「stuck かどうか」を判断する必要が無くなる (= 全ての state 遷移が event-driven trace 可能)

Cons

  • cross-account event bus の設定が増える: 競技者 bootstrap.yaml に EventBridge rule + Target ARN + IAM policy を追加
  • operator account 側に新 Worker Lambda + Rule + DLQ (Phase 2 で +1 Lambda function、 同 Free Tier 内)
  • EventBridge event は at-least-once delivery (= 重複処理あり)。 Worker Lambda は idempotent に書く (= DDB UpdateItem ConditionExpression で版重ね防止)
  • 競技者の tenkacloud-competitor-bootstrap stack を update する必要がある (= #706 / PR-712 の Update bootstrap UX で対応済み)

Open questions

  1. cross-account event bus の方向: 競技者 → operator (= 本 ADR の選択) か、 operator → 競技者 か。 競技者 side で Rule を持つ方が CFn event の source に近く delivery latency が短い (= 採用)
  2. event filter pattern の粒度: tc- 接頭辞 filter は十分か、 同 account に他 stack があるとき false positive を防げるか。 Phase A 実装時に検証
  3. delivery failure 時の retry: EventBridge は 24h retry + DLQ。 operator side で DLQ を Lambda で監視するか、 SNS alert を出すか
  4. Frontend polling 削減: If-Modified-Since 相当の no-op 応答を導入するか、 polling 間隔を 30s → 60s に伸ばすか (= Phase C で判定)

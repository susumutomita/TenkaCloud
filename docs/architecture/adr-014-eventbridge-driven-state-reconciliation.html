ADR-014: EventBridge 駆動 state reconciliation

polling で派生状態を補正していた経路を、CloudFormation / CodeBuild の状態変更イベントへ段階移行する

Status:Accepted 2026-05-14
Tracking: #724
Related: ADR-001、 ADR-005、 ADR-006、 ADR-011、 ADR-012、 ADR-013

Context

TenkaCloud は Lambda + API Gateway + DynamoDB + EventBridge を前提にした AWS マルチテナント SaaS の cloud competition platform。 tenant / event / deployment / score の状態は operator account の DynamoDB に保存し、競技者 AWS account へは CloudFormation stack として問題を deploy する。

本 ADR 起草時点で、deploy / scoring / event status 反映には複数の polling 経路がある。

経路主体間隔役割
EventDetail / participant portalfrontend30 秒deployment status / score 表示
reconcileEventStatusesgeneric-scoring Lambda1 分DEPLOYING → READY / TEARDOWN → ARCHIVED 自動遷移
StackProgress fetchadmin-console30 秒CloudFormation events / resources 表示
Score enginegeneric-scoring Lambda1 分Battle uptime probe / phased-polling / attack-detection

すべての polling が悪いわけではない。 外部 endpoint の uptime probe は TenkaCloud 側が能動観測するしかなく、ADR-005 / ADR-006 で決めた polling over SSE 原則により frontend も SSE / WebSocket へは移行しない。 問題は、AWS 側が既に state-change event を発行している領域まで 1 分 tick の scan / query / conditional update に頼っていること。

現状の問題点

  • Lambda invocation / DDB read が固定費化する: event が無い時でも generic-scoring Lambda は 1 分ごとに起動し、Events table を scan して DEPLOYING / TEARDOWN を探す。採点対象が無い tenant でも reconcile のために起動が必要になる。
  • 状態反映 latency が最大 1 分 + frontend polling になる: CloudFormation / CodeBuild の完了は AWS 側では即時に観測できるのに、DDB row 反映は次 tick まで待つ。
  • #708 / #723 の stuck root cause を残す: Event status が deployment の実状態から派生する設計なのに、派生更新が periodic reconciler に閉じている。Lambda の失敗、scan の取りこぼし、race により DEPLOYING / TEARDOWN が残ると UI からは stuck に見える。
  • operator が見たい stack progress と platform state が分離する: admin-console は CloudFormation API を 30 秒ごとに fetch する一方、participant portal / event detail は DDB row の更新を待つ。 同じ stack state を複数経路で再解釈している。

制約は次のとおり。

制約影響
SSE / WebSocket の新規導入禁止frontend は polling を維持する。EventBridge は backend reconciliation のみに使う。
DynamoDB on-demand 禁止新規 table / GSI は PROVISIONED 1 RCU / 1 WCU 前提。scan 常用より event-driven update を優先する。
Cost 0 原則常時起動の Lambda tick を減らし、AWS service event を活用する。追加 EventBridge / Lambda / IAM は Free Tier 内の運用を前提に小さく保つ。
ExternalId 必須競技者 account への deploy 操作権限は引き続き AssumeRole + ExternalId で保護する。EventBridge ingest は deploy 権限とは別の最小権限に分ける。

Decision

Accepted: state reconciliation を EventBridge 駆動へ段階移行する。 ただし frontend polling と external endpoint scoring probe は維持し、SSE / WebSocket / endpoint 側 push API は導入しない。

PHASE A
CloudFormation stack status を event-driven にする
競技者 account の CloudFormation Stack Status Change event を operator account に転送し、DDB deployment row / event row を直接更新する。
PHASE B
CodeBuild buildId を即時反映する
CodeBuild State Change event を取り込み、buildId / build status を DDB に先行保存する。Issue #720 と統合して扱う。
PHASE C
frontend polling は conditional にする
30 秒 polling は維持し、If-Modified-Since と DDB updatedAt で no-op response を削減する。

Phase A: CloudFormation Stack Status Change event

CloudFormation は stack status の変更を EventBridge に出す。 competitor account 側で TenkaCloud 管理 stack だけを filter し、operator account の EventBridge bus に forward する。 operator account 側の Worker Lambda が event を受け、Deployments table の該当 row を idempotent に更新する。

[competitor account]
CloudFormation Stack Status Change
  source = "aws.cloudformation"
  detail-type = "CloudFormation Stack Status Change"
  detail.stack-id / stack-name / status
        |
        | EventBridge rule (TenkaCloud stack prefix / account / region で filter)
        v
[operator account]
EventBridge bus
        |
        | Rule: source=aws.cloudformation, detail-type=CloudFormation Stack Status Change
        v
CfnStackStatusWorker Lambda
        |
        +-- Update Deployments row.status / updatedAt / stackId / failureReason
        +-- Aggregate sibling deployments and update Events row.status

deployment status への mapping は次を基本にする。

CloudFormation statusDeployment status備考
CREATE_IN_PROGRESS / UPDATE_IN_PROGRESS / IMPORT_IN_PROGRESSIN_PROGRESS現行 Step Functions の MarkInProgress と同じ意味。
CREATE_COMPLETE / UPDATE_COMPLETE / IMPORT_COMPLETECOMPLETEstackId と updatedAt を更新。stackOutputs は引き続き DescribeStacks で取得する。
CREATE_FAILED / ROLLBACK_COMPLETE / ROLLBACK_FAILED / UPDATE_ROLLBACK_COMPLETE / UPDATE_ROLLBACK_FAILEDFAILEDfailureReason には CFn status reason / last event summary を保存する。
DELETE_IN_PROGRESSDELETINGteardown 開始の即時反映。
DELETE_COMPLETEDELETEDparticipant portal lookup index から外す処理も維持する。
DELETE_FAILEDFAILEDoperator の手動復旧対象として残す。

Event status は deployment row 更新の後に同じ Worker が再計算する。 現行 resolveEventStatusTransition の semantics は維持し、DEPLOYING event は全 child deployment が COMPLETE または FAILED になった時点で READY、TEARDOWN event は全 child deployment が DELETED または FAILED になった時点で ARCHIVED にする。

これにより reconcileEventStatuses の 1 分 polling は廃止する。 generic-scoring Lambda は score engine としては残す が、Event status auto-transition のための Events table scan は持たない。

Phase B: CodeBuild State Change event

CodeBuild buildId は operator が CloudWatch Logs / CodeBuild console へ drill-down するための識別子。 現行の Step Functions CodeBuildStartBuild .sync では build completion 後に buildId を DDB へ保存するため、失敗調査したい最中に buildId が UI に出ない window がある。

Phase B では CodeBuild State Change event を operator account で受け、build-status=IN_PROGRESS の時点で deployment row に buildId を保存する。 Issue #720 の buildId 即時反映と同じ PR / rollout unit で扱う。

[operator account]
CodeBuild Build State Change
  source = "aws.codebuild"
  detail.project-name = TenkaCloud DeployCodeBuild project
        |
        v
CodeBuildStateWorker Lambda
        |
        +-- BatchGetBuilds(buildId) で JOB_ID correlation を読む
        +-- Update Deployments row: buildId, buildStatus, updatedAt

State Machine の完了時 update は残す。 event-driven path は buildId / intermediate status の先行反映、State Machine path は最終的な COMPLETE / FAILED と stackOutputs の確定反映、という責務分担にする。

Phase C: frontend polling remains, but no-op is cheap

frontend は引き続き 30 秒 polling を行う。これは ADR-005 / ADR-006 の polling over SSE 原則に従うためで、SSE / WebSocket / Web Push は採用しない。

ただし API は HTTP conditional request を受け付ける。 frontend は最後に見た updatedAt を If-Modified-Since header に入れて request し、backend は DDB row の updatedAt がそれ以降なら 304 Not Modified を返す。 frontend は既存 state を維持し、JSON parse / React render / CFn API fetch を避ける。

対象Phase C の扱い
EventDetail / participant portalDDB updatedAt を watermark にして 304 を返す。 score が変わった時だけ payload を返す。
StackProgress fetch30 秒 polling は残す。 terminal status 後は updatedAt で no-op にできる。進行中の詳細 resource events は必要なら従来どおり CFn API を pull する。
NotificationsADR-006 の 60 秒 polling 方針を維持する。本 ADR は通知配信の push 化を扱わない。

Out of scope

  • SSE / WebSocket: Lambda 運用と整合しないため導入しない。
  • 外部 endpoint への scoring probe: uptime-flat / uptime-multi / phased-polling / attack-detection は TenkaCloud が観測する必要があるため 1 分 polling を維持する。
  • CloudFormation Resource Status Change の完全取り込み: StackProgress の詳細 resource timeline を DDB 化する設計は別 ADR / 別 PR。Phase A は stack-level status reconciliation に絞る。
  • deploy 実行方式の変更: CodeBuild + Step Functions + AssumeRole + ExternalId の deploy path は変えない。

Implementation Steps

Phase A — CloudFormation → EventBridge → DDB

  1. competitor bootstrap / template: infrastructure/templates/competitor-bootstrap.yaml か tenant/problem bootstrap path に EventBridge forwarding rule を追加する。 rule は source=["aws.cloudformation"]、detail-type=["CloudFormation Stack Status Change"]、TenkaCloud stack name prefix / account / region で filter し、operator account の ingest bus を target にする。
  2. operator bus policy: ControlPlaneStack が払い出す既存 bus を使うか、専用 ingest bus を作る。 どちらの場合も competitor account からの events:PutEvents を最小 scope で許可する resource policy を追加する。
  3. correlation key: Deployments row に awsAccountId + region + namePrefix で CFn event を引ける lookup を用意する。 候補は sparse lookup row、または PROVISIONED 1/1 の narrow GSI。 実装 PR で Free Tier 内の WCU / RCU 影響を明示する。
  4. Worker Lambda: infrastructure/lib/problem-deploy/handlers/cloudformation-status-handler/ を追加し、CFn status を deployment status に map する。 UpdateItem は ConditionExpression で stale transition / duplicate event を no-op にする。
  5. CDK wiring: infrastructure/lib/problem-deploy/problem-deploy-backend-stack.ts に Worker Lambda + EventBridge Rule を追加し、Deployments / Events table への最小 read/write 権限だけを付与する。
  6. Event status aggregation: Worker の deployment update 後に同 event の sibling deployments を query し、現行 resolveEventStatusTransition と同じ semantics で Events row を conditional update する。
  7. Polling removal: infrastructure/lib/problem-deploy/handlers/generic-scoring-handler/index.ts から reconcileEventStatuses 起動を削除する。 generic scoring の 1 分 schedule は scoring probe のために残す。
  8. Tests: CFn status mapping、duplicate / out-of-order event、DEPLOYING → READY、TEARDOWN → ARCHIVED、lost correlation の warning path を Vitest で固定する。

Phase B — CodeBuild State Change → buildId

  1. correlation: DeployCreateStateMachine の CodeBuildStartBuild override に JOB_ID を入れる。 Worker は CodeBuild State Change event の buildId から BatchGetBuilds し、environment variable の JOB_ID を読む。
  2. Worker Lambda: infrastructure/lib/problem-deploy/handlers/codebuild-state-handler/ を追加し、buildId / buildStatus / updatedAt を deployment row に保存する。
  3. CDK wiring: DeployCodeBuildProject または ProblemDeployBackendStack に EventBridge Rule を追加し、対象 project-name を filter する。
  4. UI integration: admin-console / application-admin-console は既存 buildId 表示を使い、build 開始直後から CodeBuild console link を出せるようにする。
  5. Tests: IN_PROGRESS event で buildId が保存されること、State Machine 完了時 update と競合しないことを固定する。

Phase C — conditional frontend polling

  1. API contract: GET 系 endpoint は If-Modified-Since を parse し、対象 row の updatedAt が新しくなければ StatusCodes.NOT_MODIFIED を返す。
  2. backend handlers: event-handler、participant-handler、deploy-handler の detail/list 系から順に対応する。 StackProgress は進行中の CFn resource details を維持するため、terminal row から no-op 化する。
  3. frontend clients: apps/admin-console、apps/application-admin-console、apps/participant-portal の API client が last updatedAt を header に入れ、304 では current state を保持する。
  4. render suppression: 既存の updatedAt 比較 helper と整合させ、no-op polling tick で React state を更新しない。
  5. Tests: 304 response、header 不正値の無視、304 時に UI が loading / error へ揺れないことを固定する。

Consequences

Positive

  • Lambda invocation cost が下がる: Event status reconcile のためだけに 1 分ごと起動する処理を削除できる。 generic-scoring Lambda は scoring probe がある時だけ意味を持つ。
  • 状態反映 latency が改善する: CFn / CodeBuild status は AWS service event 到達後すぐ DDB に反映され、次の frontend polling で見える。最大 1 分 tick 待ちは不要になる。
  • #708 / #723 の stuck root cause を回収する: Event status は periodic scan の副作用ではなく、deployment terminal transition の直後に aggregate される。
  • operator debugging が速くなる: buildId / stack status が早く DDB に入り、admin-console から CodeBuild / CloudFormation console へ早期 drill-down できる。

Negative

  • cross-account EventBridge 設定が増える: competitor account 側 rule、operator bus policy、target role / permission の設計が必要になる。
  • IAM surface が増える: events:PutEvents、EventBridge target invoke、Worker Lambda の DDB read/write、CodeBuild BatchGetBuilds などを追加する。
  • event ordering / duplicate handling が必要: EventBridge は at-least-once 前提で設計し、out-of-order status event を stale update として no-op にする必要がある。
  • correlation 設計が必要: CloudFormation event は TenkaCloud の jobId を直接持たないため、stack name / account / region から deployment row を引く lookup を設計する。

Risks

  • lost event: EventBridge rule / resource policy の設定ミスで state が更新されない。Phase A rollout 中は metrics / alarms と manual repair path を用意し、完全移行前に stuck event を検知する。
  • over-broad bus policy: operator bus が任意 account から PutEvents 可能になると spoofing risk がある。許可 principal / source account / expected detail pattern を最小化する。
  • DDB capacity pressure: CFn status event が大量に流れると 1 WCU table が詰まる可能性がある。duplicate no-op、terminal transition のみ aggregate、batch deploy 時の burst を test で見る。

Open Questions

#QuestionRecommendation
1 cross-account bus を operator side / competitor side のどちらに置くか。既存 ControlPlane bus を直接使うか、専用 ingest bus を作るか。 Phase A は operator account の専用 ingest bus を推奨。既存 control-plane business event と AWS service ingest event を分離し、resource policy を狭く保つ。
2 event filter pattern の粒度。stack name prefix だけで十分か、account / region / tag 相当の correlation も要求するか。 account + region + stackName prefix を必須にする。tag は EventBridge detail に常に乗る前提を置かない。
3 CloudFormation event から deployment row を引く correlation storage を GSI にするか、lookup row にするか。 実装 PR で DDB capacity を比較する。初期案は lookup row (= 追加 GSI なし) を優先し、query pattern が増えたら sparse GSI を検討する。
4 StackProgress の detailed resource events も EventBridge で取り込むか。 Phase A では取り込まない。admin-console の StackProgress は 30 秒 polling を維持し、stack-level status の正本だけ DDB に寄せる。
5 reconcileEventStatuses 廃止後の backstop を置くか。 1 分 polling backstop は置かない。必要なら daily / manual repair command と CloudWatch alarm で stuck を検知する。
6 If-Modified-Since の時刻精度と updatedAt の比較ルール。 DDB updatedAt は ISO 8601 UTC millisecond。header が不正なら conditional なしとして扱い、304 にはしない。

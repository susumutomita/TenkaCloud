ADR-023: Provider-specific problem runtime model for multi-cloud drills

Formalize what a TenkaCloud problem runtime is, why CloudFormation-like properties are required, why Terraform is not the default, and how the existing AWS catalog evolves without breakage.

Status: Accepted 2026-05-24
Supersedes: (none)
Related: ADR-012 (problem plugin architecture), ADR-017 (Trust Bridge: provider/action/engine abstraction)

Context

TenkaCloud currently treats a problem as a self-contained package deployed into each team's isolated AWS environment using metadata.json + template.yaml. Three earlier ADRs frame how we got here:

  • ADR-012 established that the problem is a plugin and the platform is the host. Problem-specific scoring, endpoint wiring, portal slots, disruptions are declared in metadata; the platform dispatches against a generic contract.
  • ADR-017 introduced a provider / action / engine abstraction for cross-account authority transfer (Trust Bridge), but kept the problem runtime itself implicitly AWS/CloudFormation.
  • The deploy worker today reads metadata.cfnTemplate, AssumeRoles into the competitor account using a tenant ExternalId, and runs CFn CreateStack. The provider/engine is hard-wired AWS/CloudFormation in the codepath.

To evolve toward multi-cloud drills (Azure, GCP, Kubernetes) without sacrificing the property that has made the current model simple and safe — the cloud owns the runtime, owns the state, and owns the teardown — we must define the problem runtime contract explicitly. This ADR exists because, without it, downstream PRs are at risk of three foreseeable bad directions:

  1. Terraform-by-default multi-cloud. Easy slogan, but it requires the platform to host an external runner and own state, locking, backend, and partial-failure cleanup. Those are not problem-author concerns today; making them so would shift work back to the platform that ADR-012 deliberately pushed out.
  2. Universal cloud-agnostic problem DSL. Conceptually interesting, but effectively a compiler from an abstract resource model to provider-native services. Many TenkaCloud problems exist because of provider-specific semantics (BigQuery analytics, Entra ID conditional access, Security Hub findings) and cannot be expressed in such a DSL without losing the point of the drill.
  3. Ad hoc provider-specific hacks. Wiring Azure / GCP / Kubernetes directly into the deploy worker without a documented runtime contract repeats the pre-ADR-012 failure mode: every new problem shape forces a platform change.

Issue #1265 captured these concerns. Issue #1266 asked for the ADR to land them. Issue #1267 is the matching schema / CLI seam.

Decision

D1: Multi-cloud means provider-specific problems first

The first supported multi-cloud expansion is provider-specific problems. A problem declares its target provider and engine; the catalog presents them side-by-side; the deploy dispatcher selects the right execution path. The same conceptual problem on two providers stays two separate problems.

Portable same-shape problem families (one conceptual problem, multiple provider implementations bundled together) are a later, second-stage model and are sketched here only as a reservation.

Cloud-agnostic single-problem compilation (write once, deploy to AWS / Azure / GCP from a single abstract definition) is explicitly out of scope for the near-term roadmap.

D2: Runtime contract — explicit metadata, AWS/CloudFormation the only executable combination today

Problem metadata gains an optional runtime object:

{
  "runtime": {
    "provider": "aws",
    "engine": "cloudformation",
    "entry": "template.yaml"
  }
}

Backward compatibility:

  • If runtime is absent and cfnTemplate exists, the validator normalizes the metadata as if { provider: "aws", engine: "cloudformation", entry: <cfnTemplate> } were declared. Every existing problem in the catalog keeps validating without modification.
  • If both runtime and cfnTemplate are declared, the two must be consistent — runtime.entry === cfnTemplate — or validation fails with a clear message during the dual-field compatibility window.
  • Long term, runtime.entry is the primary field; cfnTemplate stays as a deprecated alias and is not removed until the entire catalog has migrated.

Schema accepts the runtime field with a permissive shape (any string for provider / engine, regex on entry) so that reserving a future provider value does not require a schema bump. The narrow executable set is enforced at the CLI / validator layer, where the error message is descriptive. Today the only executable combination is aws + cloudformation.

D3: Runtime requirements a first-class engine must satisfy

RequirementWhy
Provider-owned execution environment The platform must not host a generic IaC runner on the default path. Submitting a CFn template to the AWS CFn service is sufficient; the platform does not run terraform apply.
Provider-managed state The cloud's deployment system owns the resource graph. The platform stores deploy metadata (deployment id, status, outputs) but never the source of truth of cloud state. No state file, no lock backend.
Single primary deployable artifact Authoring, review, distribution, and standalone validation are simple when one file represents the deploy. Multi-file modules and shared registries push complexity onto the catalog.
Standalone validation An author must be able to deploy and verify their problem outside TenkaCloud using the provider's native tooling (aws cloudformation deploy, az deployment group create, kubectl apply, etc.). OSS contribution depends on this property.
Self-contained teardown The provider's deployment lifecycle must expose a clear destroy operation. No hidden state file must be required to clean up.
Minimal platform coupling Platform passes parameters in, reads outputs back, hands the outputs to the scoring dispatcher. Problem-specific deploy mechanics never require platform code changes.

D4: First-class candidate runtimes

ProviderEngineStatusNotes
aws cloudformation Executable The current default and the only combination the deploy worker can run today.
azure bicep / arm Reserved Satisfies D3 (Azure-owned execution / state / teardown via Deployment resource). Acceptable target for a Phase 3 experiment.
kubernetes helm / manifest / kustomize Reserved Cluster owns state; teardown via release / namespace deletion. The cluster authority transfer model needs a separate ADR (related to ADR-017).
gcp native-or-investigated-runtime Needs investigation The CloudFormation-equivalent on GCP (Deployment Manager is deprecated, Config Connector / Infra Manager / Terraform via Google) is not obvious. Investigation required before reservation.

D5: Terraform is explicitly not the default multi-cloud runtime

Why Terraform-by-default is rejected: it fails the runtime requirements in D3.
  • External runner. The platform must host a Terraform-capable execution environment (worker container, version pinning, provider plugins). That is a new long-lived component to operate and secure.
  • External state. Terraform requires a state file. The platform becomes responsible for backend choice (S3 + DynamoDB lock today; what about Azure / GCP?), encryption, ACL, and per-team state isolation. None of this exists in the current CloudFormation path.
  • Locking. Concurrent apply against the same state requires coordination. Cloud-native engines provide this implicitly per Stack / Deployment / Release; Terraform demands explicit lock backend operations.
  • Partial-failure cleanup. A crashed run can leave state and reality out of sync, with no provider-owned reconciliation. Authors and operators must reason about terraform state rm and similar low-level operations.
  • Standalone validation. An author wanting to verify a problem outside TenkaCloud must also stand up the state backend, defeating the property that today they can just run aws cloudformation deploy.
Terraform is not banned as a problem-author tool — an author may use it locally to design a stack — but the deployed artifact must be a provider-native template that the cloud itself executes.

D6: Pulumi is unevaluated

Pulumi is marked Needs investigation and is neither accepted nor rejected by this ADR. Its execution model (program rather than declarative artifact), state model (Pulumi Service / self-managed backend), standalone validation flow, and teardown semantics need to be inspected against D3 before any decision. A separate ADR may follow if there is demand.

D7: Problem family model (reservation only)

For the second-stage model, the same conceptual problem with provider-specific implementations could be expressed as:

{
  "id": "public-object-storage-remediation",
  "kind": "problem-family",
  "learningObjectives": ["..."],
  "variants": [
    { "provider": "aws",   "engine": "cloudformation", "entry": "aws/template.yaml" },
    { "provider": "azure", "engine": "bicep",          "entry": "azure/main.bicep" }
  ]
}

This is documented here as a reservation only. The schema in Phase 1 does not introduce kind: "problem-family". Adding it requires a follow-up ADR once we have at least one working non-AWS provider.

D8: Cloud-agnostic single-problem deployment is out of scope

A shape such as:

{
  "id": "cloud-agnostic-object-storage-remediation",
  "kind": "universal-problem",
  "abstractResources": [
    { "type": "object-storage", "publicAccess": true },
    { "type": "identity", "permissions": "overbroad" }
  ],
  "compileTo": ["aws", "azure", "gcp"]
}

requires a cloud drill compiler that maps an abstract resource model to provider-native services and failure modes. The model breaks down for provider-native services (BigQuery, Entra ID, IAM, Security Hub) where the point of the drill is the provider-specific semantics. TenkaCloud does not commit to this direction in the near-term roadmap. Such a compiler is closer to a separate research / product invention than a platform extension and is explicitly out of scope of this ADR and the issues it tracks.

Options considered

Option A: Keep AWS-only until full multi-cloud is implementable Rejected

ProsCons
  • No schema churn.
  • No partial abstraction in code.
  • Smallest current product surface.
  • Misses the chance to define the design boundary while the runtime path is still single-engine.
  • Future contributors are likely to default to "just add Terraform" because no documented contract steers them otherwise.
  • OSS messaging on multi-cloud stays vague, which slows community contribution.

Option B: Add runtime metadata now, support AWS only Accepted

ProsCons
  • Backward compatible — every existing problem normalizes to the same shape.
  • The extension seam is explicit; future provider work is a localized PR rather than a platform refactor.
  • Documentation and authoring guides can speak honestly about future provider-specific support without overpromising.
  • Validator rejects unsupported provider/engine values clearly, so authors do not silently ship a non-executable problem.
  • Avoids premature Azure / GCP / Kubernetes execution work; the engine count stays at one until a real second provider is wired up.
  • Adds future-looking metadata before any non-AWS runtime exists.
  • Risk that contributors infer "Azure is supported" from the schema's permissiveness if docs are unclear. Mitigated by: (a) CLI error message naming the only executable combination, (b) AUTHORING.html stating AWS/CloudFormation is the only executable runtime today.

Option C: Introduce Terraform as the universal engine Rejected

ProsCons
  • Superficially broad provider coverage from a single engine.
  • Familiar to many infrastructure engineers.
  • Fails every requirement in D3 (external runner, external state, locking, partial-failure cleanup, harder standalone validation).
  • Makes the platform responsible for another execution and security boundary.
  • Pulls authoring complexity back to the platform — the opposite of ADR-012.

Migration plan

PhaseScopeStatus
Phase 0 This ADR — direction, requirements, terminology, non-goals. Shipped with this PR
Phase 1 Schema accepts optional runtime; validator normalizes legacy cfnTemplate; CLI create scaffolds the runtime block; CLI validate rejects unsupported provider/engine combinations. Shipped with this PR (Issue #1267)
Phase 2 Deploy worker reads normalized runtime metadata internally. Still only the aws + cloudformation path is wired. Dispatch table exists but has one entry. No behavior change for existing problems. Planned (Issue #1268, separate PR)
Phase 3 One non-AWS provider experiment behind a feature flag. Most likely azure + bicep or kubernetes + helm, chosen for the cleanest cloud-owned execution / state / teardown story. Includes ADR-017-equivalent authority transfer for the second provider. Planned (separate ADR + PRs)
Phase 4 Problem-family model (D7) revisited only after Phase 3 succeeds with at least one second provider. Reserved

Consequences

Gains

  • The multi-cloud roadmap has a documented boundary: provider-specific first, family later, cloud-agnostic never (as a single-problem compiler).
  • The platform retains its CloudFormation-like simplicity: the cloud owns execution, state, and teardown.
  • Catalog metadata can already distinguish AWS problems from reserved-but-not-yet-executable provider targets, enabling honest authoring documentation.
  • Future PRs that add a second provider have a single seam to extend (runtime dispatch) rather than the whole deploy worker.

Costs

  • An optional metadata field exists that today only takes one effective value. The cost is borne by the schema and CLI; existing problems are unaffected.
  • Documentation must keep emphasizing that the schema reserves provider values that are not yet executable, to avoid raising expectations.
  • If Phase 3 is delayed indefinitely, the reservation has carrying cost in code review and harness rules. Mitigated by Phase 1 / Phase 2 being thin (validator + dispatch table only).

Open questions

  • Which second provider lands first in Phase 3 — Azure / Bicep, Kubernetes / Helm, or another. Decision deferred to a separate ADR once the maintainer team has bandwidth to operate a non-AWS test environment.
  • Authority transfer model for non-AWS providers — ADR-017 covers AWS AssumeRole + ExternalId; Azure Service Principal, Kubernetes ServiceAccount, and GCP Workload Identity Federation each need their own document.
  • Catalog UI presentation of reserved providers — whether to surface them as "coming soon" cards or hide them entirely until executable. UI decision, not schema decision; can be made when Phase 3 is scheduled.
  • Whether cfnTemplate ever gets removed. The current decision is "deprecated alias, not removed until the catalog is migrated"; the trigger for removal is a separate PR after Phase 2.

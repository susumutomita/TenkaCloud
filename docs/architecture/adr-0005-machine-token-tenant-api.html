ADR-0005 — Scope-bound machine tokens for the Tenant API

Status: Accepted Date: 2026-08-08 Issue: 2939 (epic), 2948 (Phase 1) Relates: ADR-0004, ADR-018, ADR-020

The Tenant API — 46 routes that run a competition — could only be called by a human signing into Cognito through a browser. This ADR adds a machine-to-machine path that a CLI, a CI job, or an agent operator can use, without widening what a machine can reach. The decisive choice is that a machine principal is given a brand-new role value, TenantMachine, that appears in no existing requireRole allowlist. Destructive routes are therefore unreachable for a machine token even if the guard middleware is deleted outright.

1. Context

The tenant Cognito UserPool had exactly one app client, and its AllowedOAuthFlows was code only. There was no client_credentials flow, so every operating action required a browser login. The Control Plane (SBT) side already had a MachineClient; only the tenant side had the gap. There was also no OpenAPI artifact in the repository, so the 46-route surface was only discoverable by querying API Gateway directly.

Three candidate designs were explored and adversarially reviewed. The same critical finding landed on all three: a machine access token can pass the existing human TenantAPI authorizer, which binds only the user pool and pins neither the client id nor a scope. All three designs then relied on a handler middleware as the only barrier, and that middleware fired on the presence of a machine marker — so a missing marker failed open.

2. Decision

Bind the tenant through the scope string itself, and give the machine principal a role that no route accepts.

  1. New role value. TENANT_MACHINE_ROLE = "TenantMachine". TENANT_ROLES stays the three human values so that human-only consumers (the console's resolveTenantConsoleAccess, for example) are not widened. A separate TENANT_BLANKET_ROLES exists for blanket middleware only.
  2. Tenant binding is a scope string. tc-tenant-<tenantId>/bind. No lookup table, no side table, no IAM or KMS grant, no per-request I/O.
  3. Capabilities are scope strings. tenkacloud/ops.read and tenkacloud/ops.deploy in Phase 1. ops.write, disruptions.fire, and audit.read are reserved but not declared.
  4. A separate REST API. TenantMachineAPI-<tenantId> carries the 7 allowlisted methods with a per-method authorizationScopes. Paths are byte-identical to the human API. The human API is not modified, because attaching authorizationScopes to its methods would break the console, which sends an ID token.
  5. The handler guard is fail-closed and is the second barrier. It fires when a request is not confirmably human, not when a machine marker is present.
  6. No pre-token-generation trigger. ADR-018 and the existing regression guard in build-app-plane-core.test.ts stay green.

2.1 Why the new role is the load-bearing part

requireRole is a strict allowedRoles.includes(role) test. Every destructive route asks for TenantAdmin or TenantAdmin + TenantOperator. TenantMachine is in neither list, so POST /events/{id}/disruptions/fire, POST /events/{id}/teams/{teamId}/rotate-login-key, DELETE /deployments/{jobId}, PATCH /events/{id}/schedule, POST /events/{id}/end, DELETE /events/{eventId}, every /admin/* route, and GET /events/{eventId}?withTeamLoginKeys=true all reject a machine token unconditionally. The test suite asserts this holds with the guard middleware removed.

3.1 Phase 2 — the write surface (issue 2955)

Phase 2 adds one operation, POST /deployments/retry, under a separate capability tenkacloud/ops.write. Re-queueing a failed job is deliberately not folded into ops.deploy: "create something new" and "retry what failed" are handed out separately, and a read-only credential must not be able to do either.

That route already existed in the handler but had no API Gateway resource, so it had never been reachable — by a machine or by a human. It is wired on both APIs in the same change, because a surface that differs by caller is a surface nobody can reason about.

Phase 2 also turns the review question into data. Every entry in MACHINE_ROUTE_SCOPES now carries a required reachability field (none, deploy-pipeline, or scheduler) plus the file-level evidence for the claim. Omitting it is a type error; declaring scheduler fails a test. This exists because one of the rejected candidate designs proposed PATCH /events/{eventId}/schedule, which looks like a single-field write and in fact drives competition progression through a scheduler. The question "what asynchronous work can this reach?" is now impossible to skip rather than merely written down somewhere.

4. Default OFF is cryptographic, not conventional

The path is gated by features.machineTokenPath, default off. When it is off the capability resource server does not exist, so Cognito cannot issue a tenkacloud/* scope at all, so the handler's machine branch is unreachable. This is a different kind of safety from "the configuration namespace is empty".

5. What is deliberately outside CloudFormation

The per-tenant bind resource server (tc-tenant-<tenantId>) and the machine app clients (tc-m2m-*) are created at runtime by scripts/issue-machine-client.sh, not by CDK. If CloudFormation owned the bind resource server, the next cdk deploy would reconcile its scope list to empty and invalidate every issued token. The same property gives a deploy-free kill switch: deleting the bind resource server stops Cognito issuing the binding scope. The cost is that these resources do not appear in cdk diff and are not reclaimed by cdk destroy; reclamation lives in scripts/deprovision-tenant.sh.

6. Consequences

ConsequenceAssessment
Destructive routes are unreachable for machines by role, not only by allowlist. The guard becomes defence in depth rather than the only barrier.
The human console path is byte-identical; no authorizer or user pool client changes. No risk of logging out tenant admins.
Machine reads are not in the admin audit log; only mutations and denials are. The repository has no precedent for read auditing. Machine reads are observable through the machine API access log. The "complete audit" that issue 2911 asks for is therefore partially achieved in Phase 1, and is written up that way.
Tenant suspension does not gate machine principals. Suspension is inert platform-wide today, so claiming machines are gated by it would be false. Stated rather than implied.
Two REST APIs per tenant instead of one. Accepted. Merging them would require putting scopes on human methods, which breaks the ID-token console.
Projecting TenantOperator onto machine principals. Rejected. It makes the middleware the only barrier, which is exactly the failure all three candidate designs shared.
Binding the tenant through an SSM namespace. Rejected. It adds per-request I/O and a second source of truth.

7. Relationship to ADR-0004

This is a new ADR rather than a phase of ADR-0004. ADR-0004 is the contract for public API documentation and a safe interactive sandbox. This decision concerns operator machine-to-machine access to real tenant data, and the threat model differs: there is no sandbox, the credentials are real, and the blast radius is a live competition.

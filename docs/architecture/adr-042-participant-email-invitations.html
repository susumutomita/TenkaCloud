ADR-042: Participant email invitations are not a platform delivery primitive

競技者招待は invite link + facilitator channel で運用し、SES 一斉送信を基盤機能にしない

Status: Accepted 2026-06-18
Decision: Reject SES invite broadcast
Related: ADR-004, ADR-006, Participant onboarding runbook
Tracking: #1778

Context

TenkaCloud participants authenticate with a team login key, or with a federated sign-in flow when the event operator has configured SSO. Issue #1772 shipped the low-infrastructure improvement: the application admin console can generate a participant portal invite link whose login key is placed in the URL fragment. The browser does not send that fragment to the server, and the participant portal clears it after reading the key.

Issue #1778 proposed the next step: bulk email invitations from the application admin console. That would require SES sender identity decisions, an invitation table with TTL, issue/accept/expire handlers, replay handling, templates, tenant and event authorization rules, and a participant acceptance flow. It also creates a new operational responsibility: TenkaCloud would become the delivery system for participant credentials rather than only generating the credential handoff artifact.

The existing participant onboarding runbook deliberately assigns credential delivery to the facilitator's chosen channel: 1:1 email, Slack DM, printed card, or an event-specific equivalent. The platform's job is to produce the login key or invite link and make it easy to copy. The facilitator's job is to choose a channel that matches the event's identity, support model, and privacy expectations.

Decision

TenkaCloud will not add SES-backed bulk participant invitations as a platform delivery primitive. Participant onboarding remains invite-link based: the platform generates per-team login links, and the facilitator distributes them through the event-approved 1:1 channel.

Platform Generate team login keys and fragment-based invite links.
Facilitator Deliver each link through the agreed private channel and confirm receipt before kickoff.
Participant Portal Prefill the key from #invite=..., clear the fragment, and start the normal login flow.

Rationale

ConcernReason
Security boundary Bulk email turns the platform into a credential delivery system. That expands the threat model to sender identity takeover, accidental cross-team sends, replayed invitations, mailbox compromise, and template data leakage.
Operational ownership Event organizers already own the participant contact channel. They know whether the event uses corporate aliases, school mail, Slack, Discord, printed handouts, or a private LMS. A single SES path cannot model those policies without becoming an onboarding product of its own.
Infrastructure cost and setup SES requires sender/domain verification, sandbox graduation, bounce handling, and deliverability monitoring. Those are real production operations, not a small UI enhancement.
Existing platform shape ADR-006 handles in-event notifications after a participant has a team context. It is not a credential bootstrap channel. Invite links already solve the pre-login handoff without new tables, handlers, or mail infrastructure.
Failure mode If email delivery fails silently, participants cannot even enter the platform. The onboarding runbook's explicit receipt confirmation is a simpler and more observable control.

Allowed Future Work

The decision does not prohibit improving the invite-link workflow. The following remain acceptable:

  • Copyable invite links in team tables and event detail screens.
  • CSV export of team names and invite links for a facilitator-managed mail merge.
  • Printable per-team cards or QR codes, provided the login key remains scoped to the team and is not posted to a shared channel.
  • Runbook improvements that help facilitators confirm receipt before kickoff.

A future proposal may re-open email delivery only if it includes a full sender identity model, per-tenant authorization rules, bounce handling, audit retention, rate limiting, template review, and a security review for credential delivery. That proposal would need a separate ADR because it would change TenkaCloud's operational boundary.

Consequences

Positive

  • No new SES identity, DynamoDB table, TTL workflow, invitation handler, or acceptance API is introduced.
  • Credential delivery stays visible to the facilitator, who can confirm receipt directly.
  • The platform keeps the existing pre-login surface: generated login keys and invite links.
  • ADR-006 notifications remain scoped to authenticated, event-linked participants.

Negative

  • The application admin console will not send participant email invitations by itself.
  • Facilitators must continue using their event-specific private channel for credential distribution.

Implementation Status

No runtime implementation is required for this ADR. Issue #1778 is resolved by this decision: SES-backed bulk participant invitation is out of scope for TenkaCloud's platform primitives. The accepted path is invite-link generation plus facilitator-managed delivery.

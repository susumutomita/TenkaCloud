ADR-030: Coordination plugin loader — security boundary

問題が同梱する coordination plugin を runtime に動的 load する際、 未信頼コードを安全に実行するための境界

Status: Proposed 2026-06-01
Related: ADR-028 (plugin contract / dispatcher), ADR-012 (problem = plugin, platform = host), ADR-008 (problem payload を S3 で配信)

Context

ADR-028 は、 Battle の他チーム interaction を「問題が CoordinationPlugin を同梱し platform の dispatcher が host する」 plugin 方式に決めた。 問題カタログは community が拡張するため (ADR-012)、 plugin を platform に静的バンドルすると「coordination 付き問題を 1 つ足すたびに platform を再デプロイ」 となり moat を殺す。 そこで ADR-028 D6 は plugin module を runtime に動的 load する方針を採った。

動的 load とは、 問題が同梱した coordination/<name>.ts を取得 → materialize → import() で platform 側プロセスに読み込むことを意味する。 これは platform のプロセス内で「問題が書いたコード」を実行するということであり、 問題コードが完全に信頼できない限り、 単なる data 読み込みとは質的に異なるリスクを伴う。

ADR-028 D6 は「別 isolate は立てない。 plugin の bug は当該 event の 1 row に閉じ、 platform 全体には波及しない (optimistic lock + DDB write fail で停止)」 と述べた。 これは bug (= 誠実だが誤った plugin) には当てはまるが、 悪意あるコード には当てはまらない。 現行の participant-portal Lambda (= D6 が dispatcher を相乗りさせる候補) は、 Console SSO / CLI 資格情報発行のために次の強い権限を持つ:

権限用途未信頼コードが悪用した場合
sts:AssumeRole on arn:aws:iam::*:role/TenkaCloud-*競技者アカウントへの federation (SSO / CLI creds)競技者 AWS アカウントの資格情報を取得し外部送信できる
dynamodb:Query/UpdateItem/PutItem on Deployments全 team の deployment 行 (自 team scope は app 層で絞る)他 team / 他 tenant の行を read/write しスコア・状態を改竄できる
ssm:GetParameter + kms:Decrypttenant ExternalId の復号AssumeRole に必要な ExternalId を入手できる

つまり この Lambda 内で未信頼コードを実行すると、 1 つの悪意ある (または supply-chain 汚染された) coordination plugin が競技者アカウントの資格情報・全テナントのデータに到達しうる。 blast radius は「当該 event の 1 row」 では全くない。 importer を実装する前に、 この境界を明示的に設計する必要がある (= 本 ADR)。

Decision

coordination plugin の loader は、 「信頼の単位 = レビュー済みカタログ」「実行の権限 = 最小」「契約 = 純 reducer」 の三層で境界を引く。 動的 load による community 拡張性 (= platform 再デプロイ不要) は維持しつつ、 未信頼コードが competitor 資格情報・cross-tenant データに到達する経路を構造的に断つ。

S1 — 信頼の単位はレビュー済みカタログ (= 任意アップロードではない)

plugin は PR レビューを経た問題カタログ (TenkaCloudChallenge、 ADR-008 の S3 配信経路) からのみ load する。 participant や任意の第三者が runtime に任意コードを差し込む経路は存在しない。 community 拡張は「カタログへの PR → 人間レビュー → 公開」 を通る。 動的 load の対象は 公開済みカタログ bundle であり、 platform 再デプロイは不要だが、 コードは必ずレビューを経ている。 レビュー観点はカタログ側 AGENT.md + reviewer checklist に明文化し、 @aws-sdk/* / fetch / OS / 環境変数アクセスを含む plugin は reject する。

S2 — 実行は専用の最小権限 Lambda (= competitor 資格情報に触れない)

coordination dispatcher は participant-portal Lambda に相乗りさせない。 専用 Lambda (CoordinationDispatcherFunction) を立て、 IAM は次だけに絞る:

  • dynamodb:GetItem / PutItem on Deployments テーブルの coordination row のみ (= PK = COORD#<tenantId>#<eventId> に dynamodb:LeadingKeys 条件で限定)。
  • 無し: sts:AssumeRole / ssm:GetParameter / kms:Decrypt / 他テーブル。

これにより、 仮にレビューをすり抜けた悪意ある (または supply-chain 汚染された) plugin が任意コードを実行しても、 到達できるのは coordination state row だけになり、 competitor 資格情報・他 tenant データ・ExternalId には構造的に到達できない。 S1 (レビュー) をすり抜けた場合の最終防壁が S2 (最小権限) である。 別 isolate (vm2 / Worker) は立てない — ADR-028 D6 の判断 (cost/複雑度) を踏襲しつつ、 isolate の代わりに IAM で blast radius を縛る。

S3 — 契約は副作用なしの純 reducer (= 防御の多層化)

SDK (@tenkacloud/coordination-plugin-sdk) の契約は既に全 hook を純関数とし、 AWS SDK / fetch に依存しない。 platform は validateOp → applyOp → projectForTeam を呼ぶだけで、 DDB I/O は platform 側が握る。 これは型では強制できない 規約 なので、 S1 のレビューと S2 の最小権限で裏打ちする (= 純 reducer は唯一の防壁ではなく、 多層防御の一層)。 plugin の import() 時に top-level で副作用を走らせる余地があるため、 materialize は レビュー済みカタログ由来のコードに限定 (S1) し、 実行権限を最小化 (S2) することが本質的な担保となる。

Threat model

脅威緩和残留リスク
plugin が import() 時 / hook 内で AWS SDK を呼び competitor 資格情報を抜くS2 (Lambda に AssumeRole/SSM/KMS 権限なし) + S1 (レビューで AWS SDK import を reject)資格情報経路が IAM 上存在しない
plugin が他 tenant / 他 team の DDB 行を read/writeS2 (COORD#<tenantId>#<eventId> の LeadingKeys 条件 + platform が key を組み立て、 plugin は state 値しか触れない)key は plugin が指定不可
supply-chain: 依存パッケージ汚染で plugin が悪性化S2 (最小権限で被害限定) + カタログ側の lockfile / 依存レビューcoordination state の改竄は可能 → optimistic lock + 異常検知で対応
plugin が無限ループ / 巨大 state で DoSLambda timeout + DDB item size (400KB) で自然停止当該 event の dispatch が遅延 (polling は継続)
projection が他 team の機密を漏らすplugin 設計上 projection は「公開してよい投影」 + safeProjectForTeam fail-safe + レビュー問題設計の責務 (= 機密を state に入れない)

Mechanisms

機構担保する層
専用 CoordinationDispatcherFunction (新 Lambda、 IAM = coordination row のみ)S2。 既存 participant-portal Lambda の AssumeRole/SSM/KMS を継承しない。
動的 load 対象 = 公開済みカタログ bundle (ADR-008 の S3 経路)。 participant 入力からは到達不能。S1。 community 拡張は維持しつつ、 任意コードアップロードを禁止。
カタログ reviewer checklist: @aws-sdk/* / fetch / node:* / process.env を import/参照する coordination plugin は rejectS1 + S3。 純 reducer 規約の人間による enforcement。
DDB PutItem に Condition: aws:dynamodb:LeadingKeys = COORD#<tenantId>#<eventId> 相当の scope 制約S2。 cross-tenant write を IAM で封じる。
loader の契約検証 (isCoordinationPlugin) + safeProjectForTeam fail-safe (実装済み、 #1617)S3。 契約不一致 / throw を null / fallback に倒し participant API を壊さない。

Alternatives considered

A1: participant-portal Lambda に相乗り (ADR-028 D6 の素案)

却下 実装は最短だが、 当該 Lambda は competitor アカウントへの AssumeRole + 全テナント DDB + ExternalId 復号権限を持つため、 未信頼コードの blast radius が競技者資格情報まで広がる。 「bug は event row に閉じる」 は成り立つが「悪意あるコードも閉じる」 は成り立たない。

A2: 別 isolate (vm2 / 分離 Worker / WASM) で sandbox 実行

却下 (現段階) 最も強い分離だが、 Node の in-process sandbox (vm2 等) は歴史的に脱出 CVE が多く「安全な sandbox」 とは言い難い。 WASM 化は SDK / 問題 author の DX を大きく損なう。 cost/複雑度に見合わない。 S2 (IAM 最小権限) が実質同等の封じ込めを安価に達成する。 将来 plugin の規模が上がれば再検討する余地は残す。

A3: plugin を platform に静的バンドル (動的 load しない)

却下 最も安全 (任意コード実行なし) だが、 coordination 付き問題を足すたびに platform 再デプロイが必要になり、 community が問題を後から追加できなくなる (= ADR-012 / ADR-028 の前提を破壊)。 S1 (レビュー済みカタログ bundle の動的 load) が「レビュー済み = 準信頼」 と「再デプロイ不要」 を両立する。

Consequences

得るもの

  • 未信頼 (= community 製) coordination plugin を、 competitor 資格情報・cross-tenant データに触れさせずに実行できる (S2)。
  • community 拡張性 (platform 再デプロイ不要) を維持する (S1)。
  • ADR-028 D6 の blast-radius 主張を「bug にも悪意にも成り立つ」 形に正す。

失うもの / コスト

  • 専用 Lambda (+ IAM + デプロイ配線) の新設コスト。 participant-portal Lambda への相乗りより配線が増える。
  • カタログ reviewer に「coordination plugin の import 監査」 という負荷が乗る (checklist 化で軽減)。
  • in-process 実行のため、 timeout / メモリ枠内での DoS 耐性は IAM では縛れない (Lambda の実行制限に依存)。

Migration

  1. Phase 1 (済): loader + dispatcher orchestration + participant route を importer を seam として 配線。 importer 未配線の間は unavailable / fallback で安全に応答する。
  2. Phase 2: 専用 CoordinationDispatcherFunction (最小 IAM) を CDK で新設し、 coordination route をそちらへ移す。 participant-portal Lambda は coordination を扱わない。
  3. Phase 3: レビュー済みカタログ bundle から plugin を materialize → import() する実 importer を実装し seam に差す。 PROBLEM_COORDINATION env を CDK が配線する。
  4. Phase 4: カタログ reviewer checklist (import 監査) を AGENT.md / PR template に追加し、 reference 問題 (microservice-migration-battle) で end-to-end を確認する。

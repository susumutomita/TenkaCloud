ADR-039: Customer Execution Plane — keep privileged deploy authority inside the customer boundary

The hosted control plane sends a signed, digest-bound CloudActionIntent; a customer-controlled execution plane validates it against local policy and deploys with authority the hosted plane can never obtain. A signed signature is authenticity, not authorization.

Status:Accepted 2026-06-09 — design + library + production parts (DDB nonce store, local CFn executor, policy/inspector, orchestrator, SQS Lambda CDK) shipped; control-plane integration phased
Extends: ADR-017
Builds on: ADR-002, ADR-009
Issue: #1727

1. Context

TenkaCloud's cross-account deployment path is intentionally centralized. The hosted control plane assumes a role in the competitor account and runs CloudFormation there:

Tenant API → EventBridge (DeployCreateRequested) → Step Functions → central Deploy CodeBuild project (scripts/deploy-battles.sh) → sts:AssumeRole into TenkaCloud-CompetitorDeploy-Role (account-id + ExternalId trust) → aws cloudformation deploy

The competitor installs infrastructure/templates/competitor-bootstrap.yaml, which creates TenkaCloud-CompetitorDeploy-Role. The trust policy is restricted to the control-plane account id plus a tenant-scoped ExternalId (read from SSM SecureString in scripts/deploy-battles.sh before the switch to temporary credentials). The control-plane CodeBuild role may only assume roles matching arn:aws:iam::*:role/TenkaCloud-*.

The role currently attaches the AWS-managed AdministratorAccess policy. This is a deliberate trade-off: challenge templates touch unpredictable services, so a granular policy would be a perpetual IAM whack-a-mole. It is already recorded as a documented gap (IAM-05) in the hardening checklist.

1.1 Existing defense in depth (not understated)

The current model already includes meaningful controls, and this ADR preserves all of them:

  • tenant-scoped ExternalId stored in SSM SecureString (no Secrets Manager — cost-zero principle)
  • verified competitor-account onboarding (ADR-002 / ADR-009: CompetitorAccounts registry, only verified accounts are selectable)
  • a dedicated Lambda for account verification and secret handling
  • ExternalId rotation-age audit (external-id-audit-lambda.ts, Issue #603)
  • role-name restriction via the TenkaCloud-* prefix
  • separation of the central CodeBuild role from the in-account CloudFormation execution role
  • tc-* stack-name scoping where IAM supports it
  • problem-template review as a separate trust boundary

1.2 The residual blast radius this ADR addresses

ExternalId defends against the confused-deputy problem: another tenant cannot trick the control plane into using account A's authority for account B. It does not protect a customer from compromise of the trusted control plane itself.

If the control plane API, the deploy worker, and the secret-access path are compromised together, the attacker obtains the same temporary administrative authority used for legitimate deployment across every connected competitor account. The honest statement today is:

TenkaCloud uses tenant-scoped ExternalId, verified onboarding, temporary STS credentials, isolated workers, audit controls, and reviewed templates.

The statement the current model cannot make is:

A compromise of the TenkaCloud control plane cannot obtain administrative authority in connected customer accounts.

2. Decision

Accepted: add an enterprise Customer Execution Plane deployment mode that extends — not replaces — the Trust Bridge protocol from ADR-017. The hosted control plane signs a CloudActionIntent bound to an immutable artifact digest and a recipient audience; a customer-controlled execution component validates authenticity, applies local policy, verifies the artifact, and deploys using authority that is unavailable to the hosted control plane.

The decisive change is not where a queue consumer runs. It is where provider-native authority is exchanged and exercised.

TenkaCloud hosted control plane Customer Execution Plane - tenant/event/team/problem state - outbound pull of work - approved-artifact metadata - JWS / issuer / audience / TTL / replay - CloudActionIntent + JWS signing ──────▶ - local PolicyEvaluator (fail-closed) - status tracking (Deployments) - artifact digest + provenance verify - NO AWS credential - LOCAL authority acquisition - NO customer-role AssumeRole - CloudFormation deploy/delete - signed result reporting │ ▼ Dedicated challenge / sandbox accounts

2.1 Why a follow-on ADR rather than amending ADR-017

ADR-017 is Accepted and already shipped as packages/trust-bridge (schema, canonical serialization, JWS sign/verify, TTL, nonce hook, audit, AWS/GCP/Azure adapters). Amending an accepted, shipped ADR would obscure its record. ADR-039 is therefore a follow-on that reuses ADR-017's CloudActionIntent, PolicyEvaluator, and audit concepts and adds the customer-execution semantics on top. No competing signed-job protocol is introduced.

2.2 Decisions

D1
Extend CloudActionIntent, don't fork it
Add two backward-compatible, signature-covered fields to the existing v1 schema: top-level audience (recipient binding) and action.artifact (immutable sha256: digest). The central CodeBuild path keeps working — both fields are optional.
D2
Five-property separation, fail-closed
authenticity → authorization → artifact integrity → artifact safety → execution authority. Each is a distinct, independently-failing stage. A valid signature satisfies only the first.
D3
PolicyEvaluator is local and pluggable
ADR-017 D4's PolicyEvaluator is realized in code for the first time here. Authorship is the customer's (inline allowlist / OPA / Cedar). Any non-allow verdict — or a throwing evaluator — denies.
D4
Execution authority never leaves the customer
The plane deploys via a LOCAL adapter (same-account CloudFormation service role / LocalStack), never by assuming a role the hosted control plane trusts. authorize() returns a verified intent, never provider credentials.
D5
Reuse the Deployments state model
Results map back into the existing Deployments table + Step Functions semantics via signed result reporting. No second, unrelated product model.
D6
Coexist, then migrate
The central AssumeRole path stays a supported compatibility mode per tenant/account. Modes are selected by configuration; the central path is not deleted before a migration story exists.

3. Security properties (validated in order, fail-closed)

The proof-of-concept core (packages/trust-bridge/src/customer-execution-plane.ts) enforces these as separate stages so a failure names exactly which property was violated:

  1. Intent authenticity — JWS signature, trusted issuer/secret, schema, issued/notBefore/expiresAt TTL, and nonce replay protection (delegated to verifyIntent). Did TenkaCloud sign this exact request?
  2. Intent authorization — audience equals this plane; target providerAccountRef ∈ local allowlist; region ∈ local allowlist; action type permitted; source.problemId ∈ locally approved set; privilege-escalation tolerated only if locally allowed; TTL within the local ceiling; then the local PolicyEvaluator. Does this customer allow this action here?
  3. Artifact integrity — the supplied bytes hash to the sha256: digest the signature covers (constant-time compare), with an optional size check. Are these the approved bytes?
  4. Artifact safety — an optional fail-closed ArtifactInspector inspects the now-proven bytes (e.g. template risk analysis). Is the approved template acceptable under local controls?
  5. Execution authority — exercised by the caller's LOCAL adapter, outside this module. The plane never holds or returns hosted authority. Which local principal can deploy it?

Modified, unsigned, expired, replayed, wrong-audience, wrong-target, unapproved-problem, over-budget, digest-mismatch, and locally-rejected intents are each rejected at the corresponding stage. The library's test suite (test/customer-execution-plane.test.ts) covers all of them.

3.1 CloudActionIntent v1 extension

// Added to the existing schema (both optional → central CodeBuild path unaffected):
audience?: string;                  // recipient execution-plane identity (JWT aud style)
action.artifact?: {
  digest: string;                   // "sha256:" + 64 lowercase hex, signature-covered
  mediaType?: string;
  sizeBytes?: number;
};

The digest lives inside the signed payload, so the artifact binding cannot be altered without invalidating the signature. This is what makes "the bytes are bound to the intent" a cryptographic property rather than a convention.

3.2 Local authority & CloudFormation execution-role strategy

The execution plane should not run CloudFormation as an administrator role directly. The preferred shape is a dedicated in-account CloudFormation service role that the plane passes to CreateStack, scoped by an SCP-protected dedicated challenge OU. Recommended customer-side controls: deny Organizations/billing mutation, deny production/shared-service roles, deny unapproved cross-account role chaining, region restriction, protection of CloudTrail/Config/GuardDuty, permission boundaries on challenge-created IAM roles, and stack naming/tagging contracts. This ADR does not claim AdministratorAccess can be removed from every challenge; the objective is to confine broad authority to isolated accounts and customer-controlled execution.

Risks eliminated: control-plane compromise → admin in customer accounts; artifact-store swap. Reduced: signing-key compromise, agent staleness, DoS. Merely moved: trust into the customer-operated execution component and its policy configuration. The remaining hard residuals are a compromised signing key, an approved malicious artifact, and a compromised execution component — none of which a single hosted-plane compromise can exploit by itself.

6. Proof of concept (shipped)

A minimal, offline, executable PoC ships with this ADR:

  • packages/trust-bridge/src/customer-execution-plane.ts — the validation core (CustomerExecutionPlane.authorize, PolicyEvaluator, ArtifactInspector, computeArtifactDigest).
  • packages/trust-bridge/src/schema.ts — the audience + action.artifact extension.
  • packages/trust-bridge/test/customer-execution-plane.test.ts — accept + every rejection path.
  • packages/trust-bridge/poc/customer-execution-plane-demo.ts — run with bun run poc:cep. The hosted side only signs (holds no AWS credential); the customer side validates against local policy and deploys through a LOCAL adapter (MockCloudAdapter, standing in for a same-account CFn service role / LocalStack). It asserts that an approved deploy succeeds and that wrong-audience, un-approved-account, un-approved-problem, over-budget, tampered-artifact, expired, and replayed intents are all rejected.

The PoC demonstrates the core acceptance criterion: a perfectly signed intent for an account the customer did not approve is still rejected, because the hosted control plane has no principal trusted by the target deployment authority and local policy is decisive.

7. Coexistence & migration

  1. Done — protocol + library + PoC: the CloudActionIntent extension, the CustomerExecutionPlane validation core, and the offline PoC.
  2. Done — production parts (shipped): a DDB-backed nonce store (DdbNonceStore, conditional PutItem + TTL on a 1/1 PROVISIONED table), a local CloudFormation executor (CloudFormationExecutor, create-or-update / delete via a same-account CFn service role — no AssumeRole back to the control plane), reusable PolicyEvaluator / ArtifactInspector implementations (local-policy.ts), and an end-to-end orchestrator (CustomerExecutionAgent) that audits every decision. A CustomerExecutionPlaneStack CDK construct wires an SQS-driven Lambda in the customer account; its IAM has no sts:AssumeRole into any control-plane role (asserted in the stack test). All library parts hold 100% coverage.
  3. Next: register/authenticate the customer execution component end-to-end, report results back into the Deployments state model, and per-tenant / per-account mode selection from the control plane.
  4. Later: KMS asymmetric signing keys (per-tenant) replacing the HS256 shared secret, a signed plugin/artifact manifest, an artifact store for templates above the inline CFn limit, and an agent upgrade flow that cannot silently widen policy.

Delete operations must remain possible if the hosted control plane is unavailable: the execution plane can run a locally-initiated destroy against its own approved problems, so teardown never depends on the hosted plane being reachable.

8. Consequences

Positive

  • Enables the stronger security statement: customer AWS authority never leaves the customer-controlled execution boundary.
  • Cryptographically binds approved bytes to the signed request.
  • Realizes ADR-017's PolicyEvaluator with a concrete, fail-closed consumer.
  • The hardening checklist now describes the bootstrap role accurately (AdministratorAccess + residual risk + resolution path).

Negative / costs

  • Customers must operate an execution component and author local policy.
  • One more protocol surface to version and maintain (mitigated by extending the existing v1 schema).
  • The central path's residual control-plane risk remains for tenants who stay on it during migration.

9. Non-goals

  • Deploying into production accounts.
  • Replacing ADR-017 with a second competing protocol.
  • Claiming ExternalId protects against control-plane compromise.
  • Claiming permission boundaries alone solve control-plane compromise.
  • Removing all broad permissions from every isolated challenge account in this ADR.
  • Deleting the central CodeBuild path before a migration strategy exists.
  • Building a full fleet-management / auto-update platform in the first PoC.

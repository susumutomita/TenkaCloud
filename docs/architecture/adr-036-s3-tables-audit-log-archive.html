ADR-036: S3 Tables (Iceberg) for long-retention audit / operational logs

Accepted — deferred (conditional adoption)

Context

A cost-reduction idea was raised: move logs to Amazon S3 Tables (Apache Iceberg) + Athena, as in Kaminashi's write-up, which reports an 80%+ ingestion-cost reduction. Before adopting it we measured TenkaCloud's actual log/audit cost profile, which differs materially from that case study.

LogWhere it lives todayCost today
Audit log (deploy / event / sign-in / disruption operations)DynamoDB, PROVISIONED 1 RCU / 1 WCU (the DynamoDbLowCapacity aspect pins every table to 1/1) + TTL (AUDIT_RETENTION_DAYS, 90 default / 365 SOC2)≈ $0 — within the Free Tier 25 GB storage + 25 WCU/RCU. Audit rows are small; even ~1,000 events/day × 365 days ≈ a few hundred MB.
Lambda logsCloudWatch Logs, 1-week retentionLow volume, short retention → cents.
High-volume application logsNone — the platform is Lambda-based; there is no always-on ECS app emitting high-volume logs.—

Kaminashi's saving came from high-volume CloudWatch ingestion (their primary cost factor). TenkaCloud has no such ingestion: audit data is low-volume in a 1/1 DynamoDB table, and Lambda logs are short-retention. So the premise "S3 Tables cuts our log cost" does not hold at the current scale.

Decision

Do not adopt S3 Tables now. At the current scale it would increase cost and complexity, not reduce it: Firehose (per-GB + per-record), a Glue Data Catalog, Athena (per-query), and Iceberg schema management would add a fixed monthly baseline and operational burden on top of an audit store that is effectively free today. Building it now would be a "cost optimization" that does not optimize.

Define the target architecture and adopt it only when the trigger conditions below are met — at which point the Kaminashi pattern applies directly: 

audit / operational events
   └─ system-audit-writer Lambda  ──►  DynamoDB (hot, recent, cursor-paginated reads)
                                  └─►  Amazon Data Firehose ──► S3 Tables (Iceberg)  ──► Athena (long-retention, analytical)
error logs / alarms  ──────────────►  CloudWatch Logs (kept — CloudWatch Alarms integration)
  • Error logs stay in CloudWatch (CloudWatch Alarms / Logs Insights for alerting), exactly as in the source article.
  • Audit / operational logs dual-write (DynamoDB for hot recent reads + S3 Tables for the long-retention archive), or shift fully to S3 Tables once the DynamoDB hot window is short.
  • The seam is the existing system-audit-writer Lambda (infrastructure/lib/problem-deploy/system-audit-writer-lambda.ts) — add a Firehose put there; the read path (audit-log-read / admin-insight) gains an Athena-backed query for the cold range.

Trigger conditions (adopt when ANY holds)

SignalThreshold
Audit storage approaches the Free Tier ceilingDynamoDB audit table → ~25 GB (≈ tens of millions of rows). Watch via the existing Free Tier DDB storage alarm.
Sustained audit write rate throttles 1 WCUaudit writes approach ~1/sec sustained (≈ 86k/day) → tenkacloud-freetier-ddb-write-* alarm fires on the audit table.
Analytical queries over long history are neededoperators need ad-hoc SQL across > 90–365 days (beyond the current cursor-paginated DynamoDB reads).

Consequences

  • No change now — the audit store stays DynamoDB 1/1 + TTL (free, simple, already SOC2-retention capable).
  • When triggered, expect Iceberg's trade-offs (from the source article): schema-on-write (vs CloudWatch's schema-on-read) and partitions cannot be altered from Athena (Glue/Spark rewrite needed) — so design the audit Iceberg schema + partitioning (by tenantId / day) carefully up front.
  • This ADR is the standing record so the idea is not re-litigated each time; revisit when an alarm above fires.

Alternatives considered

OptionVerdict
Adopt S3 Tables nowRejected — increases cost + complexity at current volume; the saving case (high-volume ingestion) does not exist here.
Keep DynamoDB + TTL (status quo)Chosen for now — free at current scale, already supports 365-day SOC2 retention.
Move audit to CloudWatch Logs + InsightsRejected — more expensive at long retention; loses the cheap DynamoDB key-value reads.
OpenSearch for auditRejected — violates the cost-zero principle (always-on cluster).

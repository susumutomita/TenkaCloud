ADR-027: Azure and GCP as federated problem-target providers

Add Microsoft Azure and Google Cloud as problem targets using the existing Trust Bridge federation (short-lived credentials, not stored keys) and each cloud's native state-owning IaC — Azure Deployment Stacks (Bicep) and GCP Infrastructure Manager.

Status: Proposed 2026-05-29
Builds on: ADR-012, ADR-017, ADR-023, ADR-026
Scope: problem runtime + credential path only — not the platform itself

Context

ADR-023 set the multi-cloud contract: a problem declares runtime: { provider, engine, entry }; a first-class engine must let the cloud own the runtime, state, and teardown (D3, no platform-side state file/lock); Terraform is not the default where the platform owns state (D5). ADR-017 (Trust Bridge) abstracts cross-cloud authority transfer as "verified intent → short-lived provider-native credential", and packages/trust-bridge already ships adapters for aws-assume-role, azure-federated-credential, and gcp-workload-identity.

ADR-026 added Sakura Cloud, but on a stored-key path with a documented weaker isolation — because Sakura offers neither OIDC/STS federation nor a state-owning native IaC. Azure and GCP are the opposite case: both support Workload Identity Federation (an AWS workload exchanges its credentials for short-lived cloud-native credentials) and both have cloud-native IaC that owns state. They therefore belong on the federated path — the same strong, short-lived-credential isolation the AWS path enjoys — and the Trust Bridge adapters for them already exist. This ADR applies the ADR-023 runtime contract to Azure and GCP and selects each engine.

Decision

D1: Azure and GCP use Trust Bridge federation — short-lived credentials, no stored keys

Both providers authenticate via Workload Identity Federation: the AWS-hosted deploy worker presents its identity (an OIDC token / AWS identity) and the team's Azure tenant or GCP project exchanges it for a short-lived, scoped, cloud-native credential. This is exactly the ADR-017 exchange, and the azure-federated-credential / gcp-workload-identity adapters in packages/trust-bridge already implement it. Unlike ADR-026 (Sakura), there is no long-lived stored key — these providers regain the AWS-grade isolation property (credentials expire). The per-team trust bootstrap (configure the team's workload identity pool / federated credential to trust the platform identity) is the Azure/GCP analog of the AWS competitor-account trust policy + ExternalId.

D2: Azure engine = Bicep + Deployment Stacks

Azure Deployment Stacks (the Microsoft.Resources/deploymentStacks resource, GA since 2024) manage a collection of resources as one unit and own their lifecycle: --action-on-unmanage deleteResources tears the managed resources down. Authored in Bicep, this is the direct CloudFormation-equivalent and satisfies ADR-023 D3 with no platform-side state. ADR-023 D4 already named Bicep a first-class candidate.

"runtime": { "provider": "azure", "engine": "bicep", "entry": "main.bicep" }

D3: GCP engine = Infrastructure Manager (cloud-owned Terraform)

ADR-023 D4's original GCP candidate, Deployment Manager, reaches end of support on 2026-03-31 and is not a viable engine. The replacement, Infrastructure Manager (Infra Manager), runs Terraform where Google Cloud owns the deployment, its state, and its lock — the platform holds no state file. That ownership is what matters for ADR-023 D3, and it resolves the ADR-023 D5 tension precisely: D5 rejected Terraform where the platform owns state/lock; with Infra Manager the cloud owns them, so D5 is satisfied, not violated.

"runtime": { "provider": "gcp", "engine": "infra-manager", "entry": "main.tf" }
Why this is not a D5 violation. D5's concern was the platform running a Terraform backend and owning locking / partial-failure cleanup. Infra Manager is a managed service: it stores state, takes locks, and reconciles inside Google Cloud. The platform calls "create/update/delete deployment" and reads outputs — identical in shape to calling CloudFormation. No terraform.tfstate, no lock backend on the platform side.

D4: Container engines (optional, container-shaped problems)

For purely container-shaped problems, Azure Container Apps and GCP Cloud Run are the AppRun analog (ADR-026 D1): the platform owns the running app + teardown. These are a lower priority than the IaC engines (which give AWS-parity breadth) and may be added later as engine: "container-apps" / engine: "cloud-run". The IaC engines (D2/D3) are the primary parity with AWS CloudFormation.

D7: The control plane stays on AWS

Only the deploy engine, the credential path (already-built Trust Bridge adapters), and the scoring target become provider-aware. The Control Plane (SBT Cognito + EventBridge + tenant CRUD), Application Plane, deploy-worker host, and participant portal remain on AWS. Each provider-problem is a separate catalog entry (ADR-023 D7 family model); the same conceptual drill on AWS, Azure, and GCP is three problems.

Rollout

  1. Schema + samples (no execution). Add azure+bicep and gcp+infra-manager to the validator and add a sample problem for each. AWS / Sakura paths untouched.
  2. Azure engine + federation. Wire the Azure Trust Bridge adapter into the deploy worker; implement the Deployment Stacks branch.
  3. GCP engine + federation. Wire the GCP Workload Identity adapter; implement the Infra Manager branch.
  4. Catalog provider badges. Surface provider in catalog + portal.

Open questions

  • Platform federated identity. What identity does the AWS-Lambda deploy worker present to Azure/GCP for the federation exchange (an AWS IAM role mapped into the team's workload identity pool, or a platform-issued OIDC token), and how is per-team scoping expressed in that pool's trust condition (the ExternalId analog).
  • Per-team trust bootstrap UX. How a team registers the federation trust (workload identity pool / federated credential) during onboarding, and how revocation works.
  • Engine control surface. Confirm the API/SDK calls for Azure Deployment Stacks and GCP Infra Manager (create/update/delete + output retrieval) and how parameters are passed in.
  • Deny / safety settings. Use Deployment Stacks deny-settings and Infra Manager service-account scoping to bound what a problem deploy can touch in the team's account.
  • Private artifact delivery. Bicep modules / Terraform sources / container images for private problems and how they map to the ADR-012 private-payload model.

ADR-049: Defense-Gated Disruptions

Status: Proposed

Date: 2026-06-19

Scope: Operator-fired disruptions, the cross-account injection effect, and scoring during Battle events.

Relates: ADR-012 (problem = plugin), ADR-033 (disruption effect), ADR-034 (defense detection), ADR-037 (disruption timing), ADR-038 (resilience).

Context

Battle events let an operator fire disruptions at competitor stacks (ADR-037). The injection and its scoring effect (ADR-033) are applied unconditionally: every targeted team is degraded and penalized the same amount, regardless of how well that team hardened its application. In live play this means a red-team attack lands 100% of the time, so building a well-defended site changes nothing. That removes the point of a defense game: a correctly-hardened team should be able to block the attack and ideally earn a reward, while only an under-defended team takes the hit.

ADR-034 already defines how a team's defensive posture is observed: a problem exposes a posture/attack-probe signal (for example a /posture endpoint polled by the phased-polling scoring kind), and the result is recorded per deployment. Two realization patterns exist for attacks:

PatternHow the attack landsDoes defense change the outcome?
A — availability degrade The injected fault saturates or breaks the app; the uptime probe loses points. No. It degrades regardless of hardening. This is what makes today's attacks feel unstoppable.
B — defense test The attack probes; the competitor app self-reports blocked/breached via an output counter, scored by the attack-detection kind. Yes, but only for problems that implement self-report and use that kind.

The platform-side gap is that the injection effect never consults posture. Even when a problem does expose a posture signal, the operator-fired disruption degrades and penalizes a hardened team identically to an open one.

Decision

Introduce defense-gated disruptions: a declared disruption MAY carry a blockedWhen defense condition expressed over the problem's own posture keys. When such a disruption fires at a team, the platform evaluates that team's current posture before injecting:

Fire → resolve target → read team posture →
  • posture satisfies blockedWhen → skip injection, waive the penalty, award a defense bonus, record "attack blocked".
  • posture does not satisfy it → inject as today, apply the ADR-033 effect, record "breached".

Posture evaluation stays problem-owned (ADR-012): the platform dispatches the check against keys the problem declares and reports, and never hardcodes a specific problem's gates. A disruption that declares no blockedWhen behaves exactly as it does today, so the change is fully backward compatible and opt-in per disruption.

ConcernOwnerDecision
Defense condition declaration Problem (metadata) A blockedWhen field on the disruption entry referencing the problem's own posture keys (for example ssh_closed, rate_limited). The keys are the problem's contract, not a platform enumeration.
Posture signal Problem (runtime) Reuse the ADR-034 posture probe already recorded per deployment. No new probe path.
Gate evaluation + injection skip Platform (executor) The disruption executor reads the recorded posture, evaluates blockedWhen, and short-circuits injection when satisfied.
Penalty waiver + defense bonus Platform (scoring) The scoring effect applies neither degradation nor penalty for a blocked attack and credits a bounded defense bonus instead.
Outcome explanation Platform (score events) Each disruption resolution emits a score event that reads "attack blocked — defense bonus" or "breached — penalty".

Scoring model

A breach is not punished beyond the existing ADR-033 effect; defending is the scored property, so the asymmetry favors hardening:

  • Blocked: no degradation, no penalty, plus a fixed defense bonus declared by the problem (bounded and per-fire, so repeated fires cannot farm unlimited points).
  • Breached: the existing degrade/penalty effect, unchanged.

The bonus is declared problem-side alongside the disruption so the platform stays generic. Because a defense bonus is credited only when a fire is actually blocked, the value of hardening scales with how often the operator attacks — which is the intended incentive.

Interaction with existing mechanics

MechanicBehavior under defense gating
Recurring / scheduled fires (ADR-037) Posture is re-evaluated on every individual injection. A team that hardens mid-event starts blocking subsequent fires even if earlier ones breached.
Competitive hiding (publicHint) A blocked fire still respects the disruption's hiding policy. Surfacing "attack blocked" to the defender is gated by the same policy that governs whether a fault is announced, so hidden attacks stay hidden.
Scope (all / team / random-n) Gating is evaluated independently per targeted team, so one fire can block on a hardened team and breach on an open one.
Auto-fire triggers (ADR-013) Trigger conditions decide when a disruption fires; blockedWhen decides whether that fire lands. They compose without overlap.

Alternatives considered

OptionWhy not chosen alone
Problem-side only (Pattern B everywhere) Requires every attack problem to implement self-report and adopt the attack-detection kind. It does not make existing availability-degrade attacks (Pattern A) defensible, and migrating all of them is slow.
Platform-side only (hardcoded gates) Would force the host to know each problem's posture semantics, violating ADR-012. The host must dispatch a declared check, not encode gates.
Hybrid: declared condition + platform dispatch (chosen) Makes even Pattern A attacks defensible without per-problem self-report, keeps gate semantics problem-owned, and stays opt-in and backward compatible.

Consequences

  • Hardening becomes the scored property: a defended team blocks the attack and is rewarded; an under-defended team takes the hit. Attacks are no longer 100% successful.
  • Existing disruptions are unaffected until a problem opts in by declaring blockedWhen and a defense bonus.
  • The host remains generic — it evaluates declared posture keys and never references a specific problem's gates.
  • Score events explain each outcome, which directly supports participant and operator status visibility.
Risk: A defense gate is only as trustworthy as the posture signal it reads. If a problem's posture probe can be spoofed by the competitor, the gate can be gamed. Problems that adopt blockedWhen must source posture from a signal the competitor cannot trivially forge, consistent with ADR-034.

Implementation slices

The work is platform-side plus an opt-in problem-side recipe. Suggested ordering:

SliceWhereChange
1. Schema infrastructure/lib/utils/discover-problems-catalog.ts Add an optional blockedWhen (posture predicate) and a defense-bonus value to the disruption entry, with validation at catalog discovery.
2. Gate infrastructure/lib/problem-deploy/handlers/disruption-executor-handler/execute.ts Read the recorded posture for the target, evaluate blockedWhen, and short-circuit injection (with a "blocked" outcome) when satisfied.
3. Scoring infrastructure/lib/problem-deploy/handlers/generic-scoring-handler/disruption-effects.ts Waive the effect for a blocked fire and credit the bounded defense bonus; keep the existing effect for a breach.
4. Explanation Score events Emit a per-resolution event reading "attack blocked — defense bonus" or "breached — penalty".
5. Recipe .claude/skills/create-problem, .claude/templates/problems Document and scaffold a Pattern-B attack recipe so new attack problems reward defense by construction.
Migration: Disruptions without blockedWhen are injected exactly as today. Existing Battle problems continue to run unchanged; authors adopt defense gating incrementally, one disruption at a time.

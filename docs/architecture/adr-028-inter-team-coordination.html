ADR-028: Inter-team coordination plugin contract

Accepted   Scope: Battle inter-team interaction, coordination dispatcher, participant portal coordination surface

Context

Battle problems are head-to-head: their interest lies in how competing teams interact through shared state — a service router every team registers into, alliances that form and dissolve, a queue of contested shared resources. That interaction is problem-specific. A router problem and a resource-contention problem share no state shape, no validation rules, and no scoring consequence. Three forces shape the contract:

  • The platform must stay generic. The catalog is the product's moat and grows through community contribution (TenkaCloudChallenge). Hardcoding any one Battle's interaction rules into the platform would mean every new interaction shape needs a platform change.
  • Problem code is untrusted at runtime. A problem's interaction rules run on the platform side (teams control only the accounts their own stack deploys into), so whatever executes them must hold no cross-account credentials and must not be able to corrupt another problem's state.
  • Interaction is real-time and shared. Multiple teams act on one shared board concurrently, so the store needs a single authoritative row per event and an optimistic-concurrency discipline, aligned with the platform's polling-first operating model (ADR-014) rather than sockets.

Decision

Adopt the plugin model: a problem ships its interaction as a pure state machine, and the platform hosts it. The problem owns the semantics; the platform owns persistence, delivery, and isolation. The contract is @tenkacloud/coordination-plugin-sdk — types plus pure utilities only, with no React or AWS SDK dependency. A problem opts in by default-exporting a CoordinationPlugin and declaring it in metadata.json.

This ADR is adopted with a working reference: the in-repo pack packs/reference-coordination-battle ships a Battle (cross-account-capture) whose plugin arbitrates a shared roster of contested cross-account regions. It is the canonical worked example and the first real consumer of the SDK, exercised branch-by-branch in infrastructure/test/problem-pack/reference-coordination-battle-coordination.test.ts.

The plugin contract

A problem default-exports a state machine over three problem-defined types — shared State, a team Op, and a per-team Projection:

HookPurityResponsibility
initialState(ctx)pureThe opening shared board for an event (given eventId and the participating teamIds).
validateOp(state, teamId, op)pureAccept or reject an op with a short machine-readable reason. Rate limits, phase gates, input checks live here.
applyOp(state, teamId, op)pureProduce the next state. Called only when validateOp accepted.
tick?(state, eventNowMs)pureOptional time-driven advance (e.g. close a capture window, expire an alliance).
projectForTeam(state, teamId)pureThe view one team may see — must never leak another team's confidential state.

The SDK provides the host-side pure core: dispatchOp (validate then apply, state unchanged on reject), runTick (advance only if the plugin defines tick), defineCoordinationPlugin (identity helper for type inference), and safeProjectForTeam (wraps projection so a throwing plugin returns a caller-supplied safe fallback instead of breaking a participant's portal).

Host mechanism

A problem declares the plugin by a directory-relative path in its metadata.json:

"interTeamCoordination": {
  "plugin": "coordination/sector-control.ts",
  "name": "Cross-Account Sector Control"
}

Discovery is metadata-driven — a problem with no such field is invisible to the coordination pipeline and every route answers not_configured. The runtime data flow for one op:

POST /portal/me/coordination/op (Bearer team login key) → resolve team → event scope → download & import() the plugin bundle → read the shared row → dispatchOp → optimistic write (version guard) → projectForTeam back to the caller.
  • Bundling. At synth the declared plugin is esbuild-bundled into a self-contained ES module (the SDK inlined) and published to a private bucket, keyed by problem id.
  • Shared store. One DynamoDB row per event (PK = COORD#<tenant>#<event>, SK = STATE) holds the state and a monotonic version. Writes use attribute_not_exists(version) OR version = :expected and answer conflict on a lost race, so concurrent team ops never clobber each other.
  • Outcome mapping. ok → 200, rejected → 422, conflict → 409, unavailable → 503, not_configured → 404.

Security posture

  • No credentials in the dispatcher. The coordination dispatcher is its own Lambda with a minimal role: DynamoDB read/write on the coordination row only. sts:AssumeRole, ssm:GetParameter, and kms:Decrypt are deliberately absent, so an untrusted plugin can never reach a competitor account or an ExternalId.
  • Pure reducer. Hooks are side-effect-free. The plugin has no clock (time arrives only via tick's eventNowMs), no network, and no cloud SDK, so behaviour is deterministic and reviewable.
  • Safe fallback. A buggy or opted-out problem never breaks a participant's portal: projection is wrapped, and problems without the metadata field return not_configured cleanly.
  • No cross-team leak. The obligation not to leak a rival's confidential state rests with projectForTeam; the reference plugin models this by returning only a team's own holdings plus anonymous free/taken counts.

Alternatives considered

OptionWhy not
Hardcode interactions in the platformEvery new interaction shape becomes a platform change; the catalog cannot scale independently, contradicting the three-asset model (ADR-012).
Keep the mechanism dormant behind a feature gatePreserves the code but leaves it with zero consumers indefinitely, which conflicts with the project rule against abstractions justified only by future use. Without a reference problem the contract cannot be validated against real semantics.
Remove the mechanism until a problem needs itDiscards a fully-built host (dispatcher, store, loader, bundler) and its tests, and forecloses the Battle interaction design space. A single reference problem retires the "unused" objection at far lower cost.
Run untrusted plugins in a hardened isolateOut of proportion for a pure reducer with no I/O; blast radius is instead contained by giving the dispatcher no credentials at all.

Consequences

  • The coordination SDK exports (dispatchOp, runTick, defineCoordinationPlugin, safeProjectForTeam) have a real, tested consumer and are retained as public contract rather than removed as dead code.
  • Battle authors have a copyable pattern for inter-team interaction that requires no platform change.
  • The platform carries one small always-on dispatcher for events that use coordination; its cost is bounded by the polling cadence and the single per-event row.

Open items

The following extend this decision and are tracked as follow-up work; none blocks the contract above.

  • Pack-path activation. The live dispatcher is fed from the core problems/ catalog today. Carrying pack-declared coordination through the installed-snapshot composition (SnapshotCatalogSource) so an in-repo or installed pack reaches a running dispatcher is a separate activation step.
  • Scoring-driven tick. tick is defined and unit-tested but has no host caller yet; wiring the generic scoring engine's per-minute pass to invoke runTick is pending.
  • Full roster in scope. The scope resolver currently seeds the context with the requesting team's id; supplying the complete event roster to initialState is a refinement.
  • Bundle integrity pinning. The plugin importer has a digest-verification seam (sha256:) that can be turned on to fail closed on a tampered bundle.

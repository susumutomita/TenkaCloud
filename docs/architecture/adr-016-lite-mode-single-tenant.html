ADR-016: Lite mode — single-tenant deployment with tenantId "local"

Accepted   Scope: deploy topology, default of make deploy, tenant-isolation invariant

Context

Full SaaS mode stands up the SBT Control Plane, the tenant-provisioning CodePipeline, and a three-phase install (Control Plane → admin-console hosting → callback/CORS re-deploy), then requires a SystemAdmin invitation and tenant onboarding before anyone can run a competition. That is the right shape for a multi-tenant operator — and far too heavy for the dominant early use case: one organizer running one event in their own AWS account (a community meetup, a classroom, a play-test of a new problem). Making that person operate SBT undermined adoption and contradicted the free-tier cost principle.

At the same time, the architecture invariant "tenant isolation lives in the infra layer; no tenant logic in the app" must survive: application code that is shared with SaaS mode cannot grow if (isLite) branches around tenant handling.

Decision

  • Lite mode is a topology, not a fork. It deploys exactly two stacks from its own CDK entrypoint (infrastructure/bin/tenkacloud-lite.ts):
    1. tenkacloud-lite — the same AppPlaneCore builder SaaS mode uses (tenant API + Cognito + application-admin-console hosting), instantiated once with the constant tenant id LITE_TENANT_ID = "local";
    2. tenkacloud-lite-problem-deploy — the same ProblemDeployBackendStack, with eventBusArn omitted (a local bus is created) and the participant portal enabled with the development runtime-config.
    No SBT Control Plane, no tenant pipeline, no SystemAdmin invitation.
  • The tenant id is real, just constant. Every table keeps its TenantId partition key and every request keeps its Cognito JWT; Lite simply has one tenant named "local". Since a single-tenant install has no tenant-admin onboarding flow, a pre-token-generation Lambda injects the admin claims for Lite users at sign-in — auth is still enforced at the infra layer, never bypassed in the app.
  • tenantId === "local" is the only Lite signal the frontend may use, and only for cosmetic/degrade decisions (e.g. hiding SaaS-only operations). Business logic remains tenant-generic.
  • Lite is the default. make deploy runs Lite; multi-tenant operators opt in with make deploy-saas. make destroy removes the stacks and deletes DynamoDB by default; retaining history requires a prior deploy with CDK_PARAM_RETAIN_DATA_TABLES=true. Explicit make destroy-all derives exact physical ids from those stacks and removes any retained Lite data before stack teardown.

Consequences

  • One organizer goes from clone to a scoreable event with a single deploy command, inside free-tier limits.
  • SaaS and Lite share the application code and the core CDK builders, so features land in both modes by construction; the wiring layer is the only place the modes diverge (and duplication there must be kept minimal, since a field wired only in SaaS silently disappears in Lite).
  • Upgrading a Lite install to SaaS is a re-deploy, not a migration of application code: the pooled tenant-template is the same stack shape with a real tenant id.
  • The constant tenant id means Lite offers no isolation between multiple concurrent events beyond what one tenant provides; running competing organizers on one Lite install is out of scope by design.

Alternatives considered

AlternativeWhy rejected
SaaS mode with a pre-seeded single tenant Still pays for and operates SBT, the pipeline, and the three-phase install — everything the target user does not need.
Docker-only local runtime (no AWS) Valuable for frontend iteration and problem play-testing, and it exists separately (make local), but it cannot exercise real cross-account problem deployment, IAM, or Cognito — Lite is the smallest real deployment.
Feature-flagging tenancy inside the application code Violates the tenant-isolation invariant: the app would learn about deployment modes, and every future feature would need mode-conditional code.

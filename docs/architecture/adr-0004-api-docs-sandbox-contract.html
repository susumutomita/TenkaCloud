ADR-0004 — OpenAPI reference and safe interactive sandbox contract

Treats the TenkaCloud API documentation as a product surface: a human-readable reference, copyable SDK / CLI / HTTP examples, and a future interactive "Try It" console that never exposes production write paths. It fixes the OpenAPI publication pipeline, the trust boundaries, the auth and scope model for the docs console, the per-endpoint capability matrix, the sandbox isolation and cleanup rules, and the error behavior — so the interactive surface is safe by construction, not by reviewer vigilance.

1. Context

ADR-0003 chose one Next.js app with Scalar rendering the API reference under /developers/api/*, and reserved an authenticated segment for a future console. That answers where the API docs live. This ADR answers the harder question: how can the reference be interactive — a developer clicks "Try It" and gets a real response — without that capability ever becoming a path to mutate, destroy, or bill against production, and without leaking a credential into static docs.

The platform's real API is dangerous to expose to an anonymous "Try It":

  • It creates tenants, triggers per-competitor problem deployments, and AssumeRoles into competitor AWS accounts (always with an ExternalId).
  • Write operations have real side effects: CloudFormation stacks created in real accounts, scores recorded, resources billed.
  • Some inputs are themselves attack surface — a customer cloud role ARN, provider credentials, an external webhook URL — that must never be accepted from an unauthenticated docs reader.
What this contract must guarantee. An OpenAPI document generated and validated from the platform source of truth in CI; a reference that renders under /developers/api/*; interactive requests that target a dedicated sandbox base URL by default; production never the default Try-It target; write operations only against an authenticated sandbox session with a narrow, short-lived scope; destructive / billable operations disabled in public unauthenticated Try-It; no API key or bearer token embedded in static docs; and every example labeled mock, sandbox, or production-compatible.

2. Decision

Adopt the following contract for the API docs and interactive sandbox.

  1. OpenAPI is generated and validated from the platform source of truth in CI and published as the single artifact the reference renders (§4). The docs never hand-maintain endpoint shapes.
  2. The default Try-It target is a dedicated sandbox base URL. The production API is never the default target. The base-URL selector cannot default to production (§3, §5).
  3. Reads / browse are open; writes require an authenticated sandbox session carrying a token that is short-lived, audience-bound, tenant-bound, and operation-scoped (§5).
  4. Every endpoint carries a capability label — browse-only sandbox-safe authenticated-sandbox never-interactive — and the renderer only enables what the reader's session permits (§6).
  5. The sandbox is a hard-isolated tenant with strict TTL and automatic cleanup; it refuses arbitrary customer cloud role ARNs, provider credentials, and external webhook URLs (§7).
  6. No secret is ever embedded in static docs. Sandbox tokens are minted server-side, per session, on demand, from the authenticated segment of the unified app — never baked into the OpenAPI document or any rendered page (§5.3).
  7. Rate limits, size limits, and audit logging apply to every sandbox request, and examples are labeled mock / sandbox / production-compatible (§9, §10).

4. OpenAPI publication pipeline

The reference renders from one artifact: an OpenAPI document derived from the platform's own API definition, validated in CI, and versioned with the platform. The docs are never a second place the API shape is hand-written.

StageRule
GenerateThe spec is generated from the platform API definition (Hono routes + Zod schemas), not hand-edited. Each operation carries an x-tenkacloud-capability extension (the label of §6) and a servers list whose first / default entry is the sandbox base URL.
ValidateCI lints the spec and runs a breaking-change diff against the previously published version, tied to the version axes of ADR-0002. A breaking change without the matching version bump fails the build.
Capability checkCI fails if any operation lacks a capability label, or if a write / destructive / billable operation is labeled in a way that would expose it to public unauthenticated Try-It (§6).
No-secret checkCI fails if the published spec or any rendered example contains an embedded API key or bearer token (§5.3).
PublishThe validated artifact is published and Scalar renders it under /developers/api/* via ISR. The default servers entry is the sandbox base URL; production is not selectable as a default.

5. API auth and scope model for the docs console

5.1 Read vs write

Browse and sandbox-safe reads need no session — they run against read-only sandbox paths. Any write requires an authenticated sandbox session established through the shared auth boundary ADR-0003 reserves.

5.2 The sandbox token

A sandbox token is minted per session and is constrained on every axis:

PropertyConstraintWhy
LifetimeShort-lived (minutes); auto-expires, no silent refresh into a long sessionA leaked token is useless quickly.
AudienceAudience-bound to the sandbox API onlyThe token cannot be replayed against the production API.
TenantTenant-bound to the isolated sandbox tenantIt can never address a real tenant's data.
OperationsOperation-scoped to the specific endpoint(s) the console is invokingLeast privilege; a read token cannot write, a create token cannot delete.
ResourcesBound to resources created within the same session, all carrying the session TTLCleanup is automatic and total.

5.3 No secret in static docs

Tokens are minted server-side, never embedded. The sandbox token is issued by the authenticated segment of the unified app at the moment a logged-in developer initiates a write, scoped to that operation, and injected into the request by the console — it is never written into the OpenAPI document, never rendered into a page, and never present in a static example. CI fails the build if a key or bearer token appears in the spec or examples (§4). Static examples that show an Authorization header use an obvious placeholder (for example Bearer <your-sandbox-token>), never a real value.

6. Endpoint capability matrix

Every operation in the OpenAPI document carries exactly one capability label. The label decides whether a Try-It button appears, and for whom.

The four capability classes.
LabelTry-It availabilityTargetExamples of operations
browse-only Public, no session Sandbox API (read paths) List problem catalog; get a problem's metadata; read public health / version.
sandbox-safe Public, no session Sandbox API (idempotent, side-effect-free) Validate a manifest; dry-run a scoring evaluation against fixture input.
authenticated-sandbox Logged-in only, scoped token Sandbox API (ephemeral, TTL'd resources) Create a sandbox deployment of a sample problem; register a sandbox team; submit a flag in the sandbox.
never-interactive None — no Try-It button anywhere Documented only Create a real tenant; trigger a production cross-account deploy; anything accepting a customer role ARN, provider credential, or external webhook URL; billable / destructive production operations.
Default-deny on the dangerous classes. Destructive and billable operations are never-interactive in public unauthenticated Try-It. The renderer derives the button state from the label, so a new endpoint with no label or a mislabel is caught by the CI capability check (§4) rather than silently shipping an exposed write.

7. Sandbox isolation rules

The sandbox is a dedicated, hard-isolated tenant. Its rules are absolute:

RuleSpecification
Isolated tenantOne dedicated sandbox tenant, separate from every real tenant by the same stack / partition-key isolation the platform already enforces. Sandbox data and real data never share a table partition.
Strict TTL + auto cleanupEvery resource a session creates carries a TTL and is automatically reaped on expiry. No sandbox resource outlives its short session; cleanup is automatic, not operator-triggered.
No arbitrary role ARNsThe sandbox refuses an arbitrary customer cloud role ARN. Any cross-account behavior is simulated within the sandbox tenant or fixed to a sandbox-owned role; a caller-supplied ARN is rejected.
No provider credentialsThe sandbox never accepts provider credentials (AWS / GCP / Azure / Sakura keys) from a docs reader. Inputs that would carry credentials are rejected or stubbed.
No external webhook URLsThe sandbox refuses arbitrary external webhook URLs (no SSRF / callback-abuse surface). Outbound callbacks, if any, target sandbox-internal endpoints only.
Rate + size limitsPer-session and per-IP rate limits and request / response size caps apply to every sandbox call.
Audit loggingEvery sandbox request is audit-logged (who, when, which operation, outcome) for abuse detection.
The three never-accept inputs. Arbitrary customer cloud role ARNs, provider credentials, and external webhook URLs are the highest-risk inputs (cross-account pivot, credential capture, SSRF). The sandbox rejects all three by contract, regardless of capability label or session.

8. Try-It flows

8.1 One concrete safe Try-It request flow (allowed)

A logged-in developer wants to create a sandbox deployment of a sample problem — an authenticated-sandbox operation. 

1. Developer is on /developers/api in the unified app, logged in via the shared auth boundary.
2. They open POST /sandbox/deployments and click "Try It".
3. The console requests a sandbox token from the app's authenticated segment:
   scope = { aud: "sandbox", tenant: "sandbox", op: "POST /sandbox/deployments", ttl: 5m }
   -> token minted server-side; NEVER shown in the page or the spec.
4. The console sends the request to the SANDBOX base URL (the default server),
   Authorization: Bearer <minted-sandbox-token>, body referencing a built-in sample problem
   (no customer role ARN / no provider creds / no external webhook URL).
5. Sandbox API validates: token aud=sandbox, tenant=sandbox, op matches, within rate/size limits.
6. It creates an ephemeral deployment in the isolated sandbox tenant, tagged with a 30-minute TTL.
7. Response 201 returns the sandbox deployment id; the call is audit-logged.
8. On TTL expiry the deployment and all its resources are auto-reaped. No production resource touched.
Why it is safe. The default target was the sandbox (not production); the token was short-lived, audience/tenant/operation-scoped, and minted server-side; the input could not carry a role ARN, credential, or webhook URL; the resource was TTL'd and auto-cleaned. Nothing crossed the production isolation barrier.

8.2 One concrete denied production-write flow (blocked)

Someone tries to use Try-It to create a real tenant and trigger a real cross-account deploy — a never-interactive operation against production. 

Attempt A — find a Try-It button for the production write:
  POST /tenants (create real tenant) is labeled never-interactive.
  -> The renderer shows NO Try-It button for it (derived from x-tenkacloud-capability). Denied at the UI.

Attempt B — hand-edit the request to point at the production base URL:
  The base-URL selector cannot default to or offer production; even a forged production URL
  -> fails: the sandbox token's aud != production, so the production API rejects it (401/403). Denied at auth.

Attempt C — supply a customer role ARN to drive a cross-account deploy via the sandbox:
  body: { "roleArn": "arn:aws:iam::<victim>:role/x", "webhookUrl": "https://attacker.example/x" }
  -> the sandbox refuses arbitrary role ARNs and external webhook URLs by contract (§7). Denied at input.

Result: no real tenant created, no cross-account AssumeRole performed, no billable/destructive
        production side effect. The attempt is rate-limited and audit-logged.
Three independent denials. The UI never offers the button (capability label); the token cannot authenticate to production (audience binding); the sandbox rejects the dangerous inputs (isolation rules). Defeating one layer still leaves the other two — the production write has no path.

9. Error and cleanup behavior

How the sandbox responds and cleans up.
SituationBehavior
Unauthenticated write attemptRejected with an unauthorized status; the UI prompts to log in. No partial resource is created.
Token expired mid-sessionRejected with an unauthorized status; the console re-mints a fresh scoped token rather than extending the old one.
Out-of-scope operation for the tokenRejected with a forbidden status naming the required scope; nothing executes.
Rejected input (role ARN / credential / webhook URL)Rejected with a bad-request status explaining the input class is not accepted in the sandbox; logged.
Rate or size limit exceededRejected with a too-many-requests / payload-too-large status; the limit and reset window are returned.
Session ends or TTL elapsesAll resources created in the session are auto-reaped. Cleanup is idempotent and total; a missed reap is retried.
Production endpoint reached with a sandbox tokenRejected by the production API on audience mismatch; the production side never trusts a sandbox token.

Status codes follow the platform rule (the StatusCodes enum from http-status-codes); this ADR names the behavior by meaning rather than by numeric literal so the contract is implementation-agnostic.

10. Example labeling

Every example in the docs and reference carries one of three labels so a reader always knows what running it does:

LabelMeaningWhere it runs if executed
mockIllustrative only; shows shape, not a live call. Not runnable.Nowhere — it is a static snippet.
sandboxRunnable against the sandbox, possibly requiring a logged-in scoped session for writes.Sandbox API (TTL'd, isolated).
production-compatibleThe same request also works against production when the caller supplies their own real credentials — never executed from the docs by default.The caller's own environment, with their own auth; not from a Try-It button.
A production-compatible label documents that a request is valid against production but does not make the docs send it there. The default executable target stays the sandbox; production requires the reader's own credentials in their own client.

11. Consequences

Positive

  • The reference is interactive yet safe by construction: three independent layers (capability label, audience-bound token, sandbox input rules) each block the production-write path.
  • The reference cannot drift from the API: it is generated and validated from the source of truth in CI.
  • No secret is shippable in static docs — CI fails the build if one appears.
  • Sandbox resources are ephemeral and auto-cleaned, so the interactive surface has a bounded, self-healing footprint.
  • It composes with the unified app of ADR-0003 — the console is the authenticated segment already reserved there, not a new frontend.

Costs and obligations

  • A dedicated sandbox tenant, token-minting service, TTL reaper, rate limiter, and audit log must be built and operated.
  • Every API operation must carry and maintain a correct capability label; CI enforces presence but correctness is an ongoing authoring duty.
  • The OpenAPI generation, validation, capability, and no-secret CI checks are recurring pipeline maintenance.

12. Alternatives considered

AlternativeWhy rejected
Point Try-It at production with read-only scopes and "be careful"One mislabeled scope or one config change exposes a write. Safety would rest on vigilance, not structure. The sandbox-default + audience-bound token removes the path entirely.
Embed a shared demo API key in the docs so anyone can Try-ItA committed secret, rotatable only by breaking the docs, and a standing abuse target. Prohibited; tokens are minted server-side per session (§5.3).
Hand-maintain the OpenAPI document separately from the APIGuarantees drift between the documented and the implemented API. Generation from the source of truth (§4) is required.
Let the sandbox accept real role ARNs / credentials to feel "realistic"Turns the docs into a cross-account pivot and credential-capture surface. The three never-accept inputs (§7) are non-negotiable.
Long-lived sandbox sessions for convenienceA long-lived, broadly scoped token is a durable abuse credential. Short-lived, operation-scoped tokens (§5.2) are required instead.

13. Staged implementation plan

Each stage ships an observable, safe increment; the interactive write path is the last thing enabled, only after isolation is in place.

StageDeliversObservable result
1. OpenAPI pipelineGenerate + validate the spec from the API source in CI with capability and no-secret checks.A validated, versioned OpenAPI artifact; drift / unlabeled / secret-bearing specs fail the build.
2. Read-only referenceScalar renders the spec under /developers/api/*; only browse-only / sandbox-safe reads get a Try-It button, targeting the sandbox base URL.A live, searchable reference with safe read-only Try-It. No writes, no session.
3. Sandbox tenant + isolationThe isolated sandbox tenant, TTL reaper, rate / size limits, audit log, and the three never-accept input rejections.A self-cleaning, hard-isolated sandbox; dangerous inputs rejected.
4. Auth + scoped tokensThe authenticated segment mints short-lived, audience/tenant/operation-scoped sandbox tokens server-side.Logged-in developers can authenticate; tokens are scoped and never embedded.
5. Authenticated-sandbox writesEnable Try-It for authenticated-sandbox operations end-to-end (the safe flow of §8.1).Real, scoped writes against the sandbox; never-interactive operations still have no button.
6. Example labeling + polishLabel every example mock / sandbox / production-compatible; finalize error and cleanup UX.Every example states what running it does; the denied flow of §8.2 holds at all three layers.

Until the implementation lands, this ADR governs by review: any interactive API surface must default to the sandbox, gate writes behind a scoped session, label every operation and example, and reject the three never-accept inputs. The production-write path must remain blocked at the UI, the token audience, and the sandbox input layers simultaneously.

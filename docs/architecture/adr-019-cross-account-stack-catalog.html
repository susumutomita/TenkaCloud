ADR-019: cross-account 問題 deploy stack のカタログ化 — Resource Groups Tagging API は採用せず、 platform DDB を single source of truth に据える

Status:Accepted 2026-05-17
Supersedes: (なし)
Superseded-by: (なし)
Related: ADR-001 §6 (stack カタログ 2 案)

1. Context

ADR-001 §6 は \"operator が cross-account で deploy された問題 stack をどう逆引きするか\" に対して 2 案を提示していた:

案方法必要な要素
(a) 競技者 account に AssumeRole → resource-groups:GetResources (= Resource Groups Tagging API、 tag filter native 対応) を fan-out competitor-bootstrap.yaml の IAM Role に tag:GetResources 追加、 platform 側 fan-out Lambda、 並列度 / RPS 制御
(b) cloudformation:ListStacks + client-side filter (= tag を取得してから絞る) 競技者 account に AssumeRole → cloudformation:ListStacks + DescribeStacks で tag を 1 stack ずつ取得

ADR-001 は MVP 段階 (= 同一 account 内) で (b) を選択した。 Issue #912 (#895 Phase 2.E) は \"cross-account になったとき (a) に切替検討\" を要求していた。 Phase 2.A (PR #908) で stack に TenkaCloud:TenantId / JobId / BatchId tag が打たれるようになった今、 改めて (a) / (b) / 第 3 の案を評価する。

2. Decision

decision本 ADR の結論
D1 Resource Groups Tagging API (= 案 a) は採用しない。 platform 側 DDB (= Deployments テーブル) を stack カタログの single source of truth として運用する。
D2 Phase 2.A で打った CFn tag (TenkaCloud:TenantId / JobId / BatchId / ProblemId) は 競技者 account 側の debug 補助 として残す (= operator が competitor account の console で stack を探すとき identify できる)。 platform 側の逆引き経路には依存しない。
D3 platform 側 DDB の \"stack 所在カタログ\" responsibility は Deployments テーブルが既に担っている (= tenantId / jobId / stackId / region / awsAccountId が row として書かれる)。 別 catalog テーブルを新設しない。
D4 re-evaluate trigger: 次のいずれかが起きたら本 ADR を見直し:
(a) platform DDB と competitor account 上 stack の drift 検出 が要件化された (= operator が \"DDB には無いけど stack が残ってる\" 経路を発見したい場合)
(b) Disruption / Red Team 系で \"competitor account 内の任意リソース (= stack 経由以外で作られたもの) を tag で全集計\" が必要になった
(c) AWS が tag filter の cross-region / cross-account 集約 API を出した

3. Resource Groups Tagging API を採用しない理由 (= D1 の根拠)

3.1 platform は既に書いた deploy を全件知っている

競技者 account 上の stack は 全て platform 側の POST /deployments / Step Functions 経由で作られる。 操作主が platform 自身なので、 platform は何を deploy したか完璧に知っている。 deploy ごとに Deployments DDB に row が書かれる (= jobId / tenantId / awsAccountId / region / stackId / status):

PK = "DEPLOYMENT#<jobId>"
SK = "META"
{
  jobId, tenantId, awsAccountId, region,
  stackId, status, createdAt, updatedAt, problemId, ...
}

operator が \"tenant A の deploy 一覧が欲しい\" と問い合わせるとき、 Deployments を tenantId GSI で query するだけで完結。 競技者 account に AssumeRole する必要が無い。

3.2 Resource Groups Tagging API は 真実源として劣る

観点platform DDB (D1 採用)Resource Groups Tagging API (案 a)
整合性 platform が write したものを read。 race / lag 無し tag indexing は eventual consistency (~3 分 lag)。 stack 作成直後の query で見えない
cost DDB query = 1 RCU / query (= 1/1 PROVISIONED で運用) per-account AssumeRole + GetResources call、 API request charge + STS cost、 並列化で linear に増える
latency ~10 ms (= DDB 1 query) ~500 ms-数秒 (= AssumeRole + GetResources、 account 数で線形)
IAM 表面積 variant なし (= 既存の dynamodb:Query のみ) competitor account 側 IAM Role に tag:GetResources 追加が必要 (= bootstrap.yaml mutation = 全競技者再 deploy)
失敗モード DDB throttle / row 欠落 (= platform write 失敗) AssumeRole 失敗 / GetResources rate limit / 競技者の Role 削除 / tag service 障害

= 真実源として platform DDB が strictly 優位。

3.3 単独問題: \"platform DDB に無いけど stack が残っている\" drift

唯一の使い道は \"platform DDB と stack の drift 検出\" = orphan stack の発見。 これは:

  • 頻度: 非常に低い (= deploy 経路を経由しない stack 作成は cross-account では原理上不可)
  • 必要性: operator が手で competitor account console を見れば足りる (= 緊急対応の領域)
  • cost: 全競技者に対して定期 audit する場合、 上の表の cost を毎回払う

= ROI が見合わない。 drift が問題化したら別途専用 audit Lambda を立てる (= 6 ヶ月後 review)。

4. CFn stack tag の役割 (= D2)

Phase 2.A で打った tag (= TenkaCloud:TenantId / JobId / BatchId / ProblemId) は本 ADR の D1 で platform 側 query 経路として依存しない。 では何のために打つか:

  • competitor 側 operator 補助: 競技者が AWS console で自 account を見たとき、 stack tag から \"これが TenkaCloud platform から来たもの\" + \"自分の team / problem 識別子\" を即座に見られる
  • incident 時の AssumeRole なし audit: platform DDB が完全 down のとき、 competitor 自身が console で全 TenkaCloud stack を tag filter で identify できる (= self-service)
  • billing tagging: 競技者組織が AWS cost allocation tag を有効化していれば、 TenkaCloud 由来 stack の cost を分離できる

= tag は local debug / billing 用途。 platform 側 query は DDB を見る。

5. Alternatives considered

Alt-A: Resource Groups Tagging API を fan-out で集約 (= ADR-001 案 a)

本 ADR §3.2 で示した eventual consistency / cost / IAM 増加で却下。

Alt-B: cloudformation:ListStacks + client-side filter (= ADR-001 案 b 維持)

同一 account 時代の MVP 設計。 cross-account に拡張すると AssumeRole + ListStacks pagination で更に slow / cost。 採用しない。

Alt-C: 独立した StacksCatalog DDB テーブルを新設

Deployments テーブルと別に StacksCatalog を立てる。 deploy / delete が両方を書く dual-write。 race / inconsistency の温床。 Deployments 1 本で同等情報を持っているので追加しない。

7. Follow-up

  • drift audit Lambda (= optional、 priority low): platform DDB と competitor account stack の drift を定期 scan する Lambda。 6 ヶ月後 review で要否判断
  • cost allocation tag: 競技者組織向け doc に \"TenkaCloud から来た stack を billing 分離する方法\" を載せる (= AWS Cost Allocation Tag 機能の使い方)
  • ADR-001 §6 update: 案 (a) / (b) のうち \"platform DDB を真実源、 tag は補助\" を正式採用と書く (= 本 ADR が ADR-001 §6 を上書き)

ADR-028: Inter-team coordination plugin contract

Battle 問題が宣言する他チーム interaction primitive を platform が dispatch する plugin 契約

Status: Proposed 2026-05-20
Related: ADR-012 (problem = plugin, platform = host)

Context

Battle 問題はリアルタイム対戦である以上、 何らかの形で 他チームとの interaction を仕込まないと「複数 team が同じ event に参加している」 だけで実際の競争にならない。 一方、 TenkaCloud で既に存在する / 検討されている Battle 問題を並べると、 必要な inter-team interaction の primitive (= 一次プリミティブ) は問題ごとに大きく違う。

問題想定 inter-team primitive例
microservice-migration-battle service router team A が公開した service URL を team B が直接 call する route 登録 (= 他チームのアウトプットを部分参照)
security-battle-royale alliance team どうしの相互合意による「同盟」 関係。 同盟内は攻撃しない / 互いを助ける
stackstack (#1137) TBD (= 本 ADR ship 後に declare) 当初 「共有組織リソース queue (SSO Proxy 2 slot 先着 / Security Review 待ち行列)」 を想定したが、 tenant 境界を越える shared resource registry の security 設計の難度が現 platform の整備状況と釣り合わないため 明示却下。 stackstack の inter-team primitive は本 ADR 上で別の (= tenant 境界を越えない) 形に置き換える

共通項は 「team どうしの interaction を介する小さな共有状態 + 状態を mutate する operation 集合 + 各 team への投影」 の 3 点であり、 具体的な primitive (router / alliance / queue / partition / etc.) は完全に問題依存である。

現状の platform は inter-team coordination のプリミティブを 一つも 持たない (= per-team deployment + per-team scoring engine のみ)。 仮にどれか 1 つ (例: shared resource pool) を platform 側に hardcode で実装すると、 他の問題タイプ (router / alliance) に汎用化できず、 1 問題に最適化された platform 機能が他 問題の足を引っ張る。

Goals

  1. 問題ごとに独自の inter-team primitive を declare できる: metadata DSL の一部として 「この問題はこういう inter-team coordination を持つ」 と宣言できる
  2. platform は primitive を一つも hardcode しない: platform 側 code は dispatcher 1 つだけを持ち、 中身の意思決定は plugin に委譲する (= ADR-012 同型)
  3. tenant 境界を越えない: shared state は per-tenant per-event scope に閉じる。 cross-tenant data flow は作らない。 security 監査範囲は問題 plugin code + 1 個の per-tenant per-event DDB row に閉じる
  4. fallback safe: 既存問題は interTeamCoordination field 未宣言で動く (= inter-team interaction 無しの Battle として既存挙動を維持)
  5. plugin code は問題リポジトリ同梱: problems/<category>/<id>/coordination/ に書く (= ADR-012 で portal slots を problems/<...>/portal/ に同梱したのと同じ局所性)
  6. operator が runtime に scope を見られる: 競技中に application-admin-console から coordination state を観察 / debug できる

Decision

D1: metadata に interTeamCoordination field を追加

SCHEMA を拡張し、 問題が次のように coordination plugin を宣言する。

"interTeamCoordination": {
  "plugin": "coordination/router.ts",
  "name": "サービスルーター",
  "description": "team が公開する service URL を register / lookup する router。",
  "publicHint": true
}

plugin は問題ディレクトリ相対 path (pattern ^coordination/[A-Za-z0-9._-]+\.ts$、 dashboard.slots の portal/*.tsx 規約と同形)、 name / description は portal / operator 表示用の人間可読情報、 publicHint は disruptions と同じ fairness フラグで、 true のときだけ participant-portal に coordination の存在を予告表示する (default は hide = fail-closed)。 field 自体は optional。 省略すると inter-team interaction 無しの Battle として動く (= goal #4 fallback)。 platform は plugin の意味論を解釈せず host するだけ。

D2: Plugin contract = TypeScript interface (state machine + 3 hooks)

plugin module は次の interface を default export する。 platform 側 SDK @tenkacloud/coordination-plugin-sdk が型 (CoordinationPlugin) と純 util を提供する: defineCoordinationPlugin() (型推論付き authoring helper)、 dispatchOp() (validate→apply の純 reducer)、 runTick()、 safeProjectForTeam() (plugin が throw しても fallback を返す fail-safe projection)。 dispatcher はこれら純 util を副作用 (DDB / S3) の外側で呼ぶだけで、 問題依存の意味論を一切持たない。

// problems/<category>/<id>/coordination/router.ts
import { type CoordinationPlugin, defineCoordinationPlugin } from "@tenkacloud/coordination-plugin-sdk";

interface RouterState {
  readonly routes: Record<string /* teamId */, string /* serviceUrl */>;
}

type RouterOp =
  | { kind: "register"; serviceUrl: string }
  | { kind: "unregister" };

const router: CoordinationPlugin<RouterState, RouterOp> = {
  initialState(_ctx) {
    return { routes: {} };
  },

  validateOp(state, teamId, op) {
    if (op.kind === "register" && !op.serviceUrl.startsWith("https://")) {
      return { ok: false, error: "must_be_https" };
    }
    return { ok: true };
  },

  applyOp(state, teamId, op) {
    if (op.kind === "register") {
      return {
        ...state,
        routes: { ...state.routes, [teamId]: op.serviceUrl },
      };
    }
    const { [teamId]: _, ...rest } = state.routes;
    return { ...state, routes: rest };
  },

  // 各 team が portal で見える view (= 他 team の URL 一覧を return する等)
  projectForTeam(state, teamId) {
    return { otherRoutes: state.routes };
  },
};

export default defineCoordinationPlugin(router);

5 つの hook は state machine の必要最小:

  • initialState(ctx): event 開始時の初期 state
  • validateOp(state, teamId, op): operation を受理可能か判定 (= rate limit / 入力検証 / 競技 phase 制約)
  • applyOp(state, teamId, op): state を変える pure function (= 副作用なし)
  • tick?(state, eventNowMs): scoring engine が tick ごとに呼ぶ optional hook (= 経過時間で alliance 解消等)
  • projectForTeam(state, teamId): その team の portal に渡す projection (= 他 team の機密を漏らさない投影)

D3: 状態保存は per-tenant per-event DDB row

tenant 境界を越えない (= goal #3)。 platform は新規 DDB table EventCoordinationState を追加し、 partition key = tenantId#eventId、 sort key = なし、 attribute は state: Map + updatedAt + version (= optimistic locking)。 既存 ADR-012 の per-team scoring state とは完全に分離 (= 1 event につき 1 row、 N teams 共有)。 DynamoDbLowCapacity aspect で 1 RCU / 1 WCU に強制 (= cost 0 原則)。

D4: operation 提出経路は portal API + scoring tick の 2 系統

経路誰が trigger使用
POST /portal/me/coordination/<eventId> 競技者 (= team key 認証) register / propose-alliance 等、 team が能動的に呼ぶ operation
tick(state, eventNowMs) scoring engine (= 1 分ごとの polling tick と同期) 経過時間で alliance 期限切れ / queue front 進行 / 等の自動進行

portal API 側は body の Zod 検証 + plugin の validateOp を通したあと、 DDB の optimistic locking で applyOp 結果を書き込む。 conflict 時は 409 を返し、 portal は退避リトライ。

D5: per-team projection が見える場所

2 系統に分かれる。 (1) 静的予告: interTeamCoordination の name / description を publicHint: true のときだけ portal catalog (PortalCoordinationEntry) 経由で plugin slot props (PortalSlotProps.coordination) に流す (= disruptions と同じ fairness projection。 deploy 前から「この問題には coordination がある」 と予告できる)。 (2) 動的 projection: 各 team の /portal/me response に coordination: PluginProjection field を追加し、 dispatcher が safeProjectForTeam(plugin, state, teamId, fallback) で plugin の projectForTeam を fail-safe に呼ぶ (= plugin が throw しても fallback を返し portal を壊さない)。 portal の dashboard.slots で問題が独自 UI を render する (= router なら他 team の URL 表、 alliance なら同盟関係 graph、 等)。 portal 標準 UI は coordination state を直接 render しない (= 問題依存 UI を platform が知る必要がない)。

D6: platform 側 dispatcher Lambda の責務

新規 Lambda CoordinationDispatcherFunction:

  • portal API POST /portal/me/coordination/<eventId> の backend
  • plugin module を S3 (= ADR-008 で problems を payload 配信する経路) から fetch + bun runtime で load
  • SDK の dispatchOp(plugin, state, teamId, op) (= validateOp → ok なら applyOp の純 reducer) を DDB read と optimistic-lock write の間で実行 (= 副作用は dispatcher、 意味論は plugin)
  • scoring tick で SDK の runTick(plugin, state, eventNowMs) を呼ぶ (= 同 Lambda の別 entrypoint)
  • participant lookup から safeProjectForTeam で plugin の projectForTeam を fail-safe に call する経路を export

plugin code は bun の import() で動的 load。 sandbox は別 isolate を立てない (= cost と複雑度のため)。 plugin の bug は当該 event のみに影響し、 platform 全体には波及しない (= optimistic locking + DDB write failure で停止する)。

Consequences

得るもの

  • 各問題が完全に自由な inter-team primitive を持てる (= microservice-migration の router / security-battle-royale の alliance / stackstack の TBD primitive を同じ contract 上に乗せられる)
  • platform は coordination の意味解釈を一切しない (= ADR-012 の thick metadata DSL と同じ抽象化)
  • tenant 境界を越えないので security 監査範囲は問題 plugin code + 1 DDB row に閉じる (= cross-tenant data flow を audit する必要なし)
  • fallback で coordination 未宣言の問題 (= 既存 4 問題 + Challenge 系) は影響を受けない

失うもの / コスト

  • plugin SDK の version 互換管理が必要 (= TypeScript interface の breaking change で全問題が壊れうる)
  • plugin が bug を持つと当該 event の coordination が機能不全に陥る (= scoring の core 経路は影響しないが、 inter-team interaction だけが落ちる)
  • 新規 DDB table + 新規 Lambda + 新規 portal route の運用コストが platform に増える (= 既存問題は使わない reseurces だが maintenance は必要)
  • plugin code の sandbox を持たないので、 problem author の信頼境界 = platform operator の信頼境界 (= 既存 ADR-012 の portal/*.tsx と同じ前提)

Alternatives considered

A1: 1 つの primitive を platform に hardcode 却下

例えば shared resource pool だけを platform に組み込み、 全問題に強制する。 microservice-migration / security-battle-royale / stackstack のいずれにも fit せず、 1 問題に最適化された platform 機能が他問題の足を引っ張る。 ADR-012 で確立した 「問題 = plugin、 platform = host」 原則に反する。

A2: tenant 横断 shared resource registry 却下

stackstack の当初構想にあった 「SSO Proxy 2 slot 先着 / Security Review 待ち行列 / Claude API quota」 のような cross-tenant shared state を platform 側で持つ。 検討の結果、 security 設計の難度 (= cross-tenant authorization model / rate limiting / data isolation / audit trail) が現 platform の整備状況と釣り合わないため明示却下した。 tenant 境界を越えない別 primitive (= 本 ADR の D3 = per-tenant per-event scope) で代替する。

A3: 各問題が独自 Lambda + DDB を CFn 側で deploy 却下

問題 template.yaml 側に inter-team coordination 用 Lambda + DDB を入れる。 deploy が競技者 account に走るため cross-team write が原理的に不可能 (= team A の deployment が team B の deployment に直接 write できない)。 platform 側 plane でしか shared state を持てない。

A4: GraphQL / RPC service を platform 側に立てて問題が consume 却下

汎用 RPC service を platform が提供し、 問題側はその client として coordination を実装する。 plugin contract と比べて (1) platform code が問題依存 schema を持ち込む、 (2) operator から見て debugging surface が増える、 (3) 問題 author の学習コストが上がる、 のため却下。 plugin contract の方が局所性が高い。

Migration

Phase 1: SDK + dispatcher + DSL ship

  • @tenkacloud/coordination-plugin-sdk パッケージ作成 (= TypeScript types + util)
  • problems/SCHEMA.json に interTeamCoordination optional field 追加
  • CoordinationDispatcherFunction Lambda + EventCoordinationState DDB table を infrastructure/lib/problem-deploy/ に追加
  • portal API POST /portal/me/coordination/<eventId> 追加
  • /portal/me response に coordination projection 入れる

Phase 2: 既存 problem の onboarding

  • microservice-migration-battle: coordination/router.ts を書いて他 team service URL の register / lookup を提供 (= 現状の hypothetical を実装に変換)
  • security-battle-royale: coordination/alliance.ts を書いて propose / accept / dissolve の alliance state machine を提供
  • hello-world-battle: 未宣言のまま (= goal #4 fallback で従来挙動維持)

Phase 3: stackstack の inter-team primitive を declare

stackstack (#1137) の Phase 2 として、 tenant 境界を越えない形の inter-team primitive を coordination/<something>.ts で declare する。 候補 (= ADR ship 時点では未確定):

  • review-queue per-tenant per-event の Security Review 待ち行列 (= 同じ tenant 内の他チームと枠を奪い合うが、 cross-tenant ではない)
  • shared-incident-board 同 tenant 内の他チーム incident 状況の公開 board (= 「あのチームも .env 流出があった」 を見せる)
  • blueprint-trade hardening 完了済 slot の blueprint を他 team に共有 / 受領する trade 機構

選定は stackstack 自体の game design 判断であり、 本 ADR の scope 外。

Open questions

  • plugin module の依存解決: 問題 author が npm package を import したい場合の取り扱い (= 現状の portal/*.tsx と同様、 peer dep に閉じる方針か?)
  • plugin の動的 reload: event 進行中に plugin code を patch できるべきか? (= 初期実装は不可、 event 終了まで固定で良いか確認)
  • DDB row size: state attribute の上限 (DynamoDB の 400KB) を超える coordination が必要な問題が出てきた場合の split 戦略
  • operator debug UI: application-admin-console に coordination state inspector を立てる範囲
  • plugin error の血液型: plugin throw を 4xx (= 競技者向け) と 5xx (= operator alert) のどちらに分類するかの基準

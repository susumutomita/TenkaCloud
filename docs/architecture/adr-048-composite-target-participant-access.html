ADR-048 — Managed participant access for composite targets (AWS / GCP / Azure / Sakura)

Status: Proposed Date: 2026-06-30 Epic: Composite Runtime (#2058) Supersedes: none

A composite problem deploys one logical challenge across two to eight provider targets (AWS / GCP / Azure / Sakura). Competitors need a way to reach each target's live environment. This ADR fixes the security contract for managed participant access to a composite target before any provider-specific credential issuance is built, so that the access surface is designed deliberately rather than improvised per provider. The companion code contract (the provider-neutral TargetAccessDescriptor and capability resolver) already landed in #2076; this ADR is the security-reviewable decision that governs it and everything built on top.

1. Context

The single-provider AWS path lets a competitor open the target account in the AWS console (or obtain short-lived CLI credentials) through a platform-issued, time-boxed sign-in derived from the deployment's participant viewer role. Composite Runtime cannot assume every provider can copy that flow: GCP, Azure, and Sakura have different identity models, and the platform stores no long-lived cloud keys for any of them.

Three forces shape the decision:

  • Uniform contract, uneven capability. Participants and the organizer UI want one shape to describe "how do I reach this target," even though providers differ in what the platform can safely offer.
  • Server-side authority. The participant must never supply the role, account, project, or redirect destination that grants access — those are read from the target deployment row, which the platform owns.
  • No standing secrets. Per the project's cost-zero and least-privilege rules, the platform keeps no long-lived provider access keys; any credential is short-lived, minted on demand, and never persisted.

2. Decision

Adopt a single provider-neutral capability model plus a one-time, server-side grant consumption step that issuance flows must honor. Access is always resolved from the target deployment row for a target that belongs to the authenticated participant team; the participant supplies only the identity of the target they are asking about. 2.3 Decision constraints (binding on all issuance flows)

  • No long-lived cloud access keys are written to TenkaCloud storage, for any provider.
  • Provider role identifiers, account / project / subscription identifiers, and redirect URLs are never accepted from the participant as authority. They are read from the target deployment row only.
  • The target deployment row is the single server-side source of truth for what a target is and who owns it.
  • AWS managed access is the baseline reference, but other providers do not inherit its flow; each provider's mode is the explicit value in Table 1.
  • A provider declared external-portal-only must be visible as such in the capability matrix, not silently degraded.

3. One-time grant consumption model

Where the platform mints a credential (AWS, today), issuance is gated by a one-time grant that is consumed server-side before any provider call. The grant binds the request to a single target, team, and tenant and is single-use with a short expiry, which removes replay and confused-deputy classes by construction. The grant is an internal server-side record; it is not a participant-presentable bearer token beyond the brief redemption window.

5. API contract draft

The provider-neutral descriptor already exists in code (#2076). The issuance boundary below is a draft for the follow-up issues; only the descriptor and lookup ship at this ADR's acceptance. 

// Shipped (#2076): provider-neutral, secret-free description of a target.
type TargetAccessCapability =
  | "console"
  | "cli-credentials"
  | "external-portal"
  | "unsupported";

type TargetAccessDescriptor = {
  targetId: string;
  targetDeploymentId: string;
  provider: "aws" | "gcp" | "azure" | "sakura" | "unsupported";
  capability: readonly TargetAccessCapability[];
};

// GET /participant/composite/{parentDeploymentId}/targets/{targetDeploymentId}/access
//   -> 200 { descriptor }            // team-owned, COMPLETE
//   -> 409 { reason: "not_ready" }   // team-owned, not COMPLETE
//   -> 404                           // not found OR another team (indistinguishable)

// Draft (future issuance boundary; AWS managed mode only at first release):
// POST /participant/composite/{parentDeploymentId}/targets/{targetDeploymentId}/session
//   body: { capability: "console" | "cli-credentials" }   // no role/account/redirect from caller
//   -> 200 { url?, credentials?, expiresAt }   // returned once; never persisted
//   -> 404 / 409 / 410                          // not found / not ready / grant consumed or expired
//   external-portal providers: no session endpoint; the descriptor is terminal.

6. Audit, revocation, and fallback

6.1 Required audit events

  • issuance — grant consumed and credential minted (target, team, tenant, capability, expiry; no secret value).
  • consumption — first redemption of a grant (with the resulting session's expiry).
  • expiry — a grant lapsed unredeemed (TTL).
  • denial — replay, expired grant, cross-team, not-ready, or unsupported provider, with the machine reason.
  • provider error — the provider call (e.g. STS) failed; no partial credential leaked.

6.2 Revocation / early termination

Minted credentials are short-lived and self-expiring; there is no separate revocation list. Early termination is achieved by target teardown — once a target is no longer COMPLETE, the lookup returns not_ready and no new grant can be created. Already-minted sessions expire on their own short TTL.

6.3 Fallback when managed access is unavailable

If managed issuance is unavailable for a provider (or fails), the platform does not silently fall back to a different mode. The descriptor's capability is the declared truth: an external-portal provider never gains a console/CLI session, and an AWS issuance failure surfaces as a provider-error denial, not a downgrade.

8. Open provider-specific validation items

These remain explicitly open and must be resolved in each provider's own implementation issue, not assumed here:

  • GCP Whether a future managed mode uses Workload Identity Federation for a viewer-scoped, keyless session, and what the audience / attribute binding would be.
  • Azure Whether a viewer-scoped managed session is feasible via Entra ID without storing app secrets, and the equivalent of an ExternalId confused-deputy guard.
  • Sakura Whether any managed access is offered at all, or it stays external-portal indefinitely.
  • All providers The exact external-portal URL shape (if any) and whether presenting it constitutes information disclosure for a given problem.
  • AWS Final max session TTL and console sign-in token TTL within the bounds in Table 1.

9. Security review checklist

  • A supported first-release mode is defined for all four providers (Table 1).
  • Managed vs external-portal-only is explicit and visible in the capability matrix (Table 2), not implied.
  • No long-lived cloud access keys are stored for any provider (Table 4).
  • Issuance authority (role / account / ExternalId / redirect) is read server-side, never from participant input.
  • The target deployment row is the single source of truth for target identity and ownership.
  • Grants are single-use and time-bounded; replay and expiry are denied before any provider call (Figure 2).
  • Cross-team and cross-tenant requests are indistinguishable from not-found.
  • Minted credentials are returned once and never persisted or logged.
  • Required audit events cover issuance, consumption, expiry, denial, and provider error.
  • Fallback never silently downgrades a capability.
  • Open provider-specific items are listed for follow-up rather than assumed (Section 8).

10. Consequences

Positive: one descriptor shape across providers; a security model fixed before any credential code is written; AWS keeps its existing managed experience while GCP / Azure / Sakura have an honest, non-misleading first-release answer. Negative / cost: external-portal providers give competitors a less seamless experience at first release; a grant store with TTL is an added (small, 1/1-provisioned) data structure; each provider's managed mode is deferred to its own issue.

11. Alternatives considered

Copy the AWS console flow to every provider

Rejected: it would require storing or federating standing credentials for GCP / Azure / Sakura, violating the no-standing-secrets constraint, and it assumes identity models that do not map cleanly onto AWS STS sign-in.

Accept a participant-supplied redirect / role to "just open the right place"

Rejected: it makes the participant the authority for access, opening confused-deputy and malicious-redirect classes.

Long-lived bearer token per target

Rejected: a persisted, replayable token contradicts single-use, short-lived issuance and increases leakage blast radius.

12. Non-goals

  • Identical console SSO experience across all four providers.
  • Managed (non-portal) access for GCP / Azure / Sakura in the first release.
  • A revocation list — short TTLs and teardown cover early termination.
  • Granting access to legacy single-provider deployments through this path.

ADR-037: Disruption timing & recurrence (scheduled / recurring / adaptive)

障害をワンタイムで終わらせず、 予約・定期・「対策が不十分なら再発」 を、 問題が宣言し platform が疎結合に駆動する timing モデル

Status: Proposed 2026-06-03
Related: ADR-031 (cross-account 注入 / action 契約 / revert), ADR-013 (condition-triggered 発火 / 一度きり), ADR-034 (attackProbe = 防御状態の検知), ADR-029 (game always ends / 永続障害禁止), ADR-012 (problem = plugin, platform = host)

Context

TenkaCloud の障害 (disruption) は、 問題が metadata.json の disruptions[] に データとして宣言し、 platform の汎用 executor が競技者アカウントへ AssumeRole して注入する (ADR-031)。 注入の実体は 3 つの汎用 action.kind — ssm-run-command / lambda-invoke(問題が自前の障害 Lambda を同梱して呼ばせる) / cfn-stack-update — に閉じており、 platform は問題固有コードを一切 import しない (= 疎結合)。

現状、 障害が「発火」 する経路は 2 つあり、 いずれも実質ワンタイムである:

発火経路現状の挙動限界
operator fire (POST /events/:id/disruptions/fire, ADR-031 Phase A) operator が押した瞬間に DisruptionFired を publish → 即注入 → revert を予約 即時 1 回のみ。 「30 分後に」 や 「5 分ごとに」 は表現できない
condition-triggered (scoring tick, ADR-013 / #1422) tick が after-deploy / team-score-above / phase-entered を評価し発火。 firedDisruptions set で 一度発火したら抑制 一度きり。 条件が再成立しても二度と撃たない

Battle を競技として成立させるには、 これでは足りない。 現実の運用 (例: Web サイト書き換え、 レイテンシ注入、 リソース枯渇) は 一度直して終わりではなく、

  • 定期的に再発させたい — 例: 5 分ごとに改ざんし直し、 防御を維持し続けないとスコアが落ちる。
  • 対策が不十分なら再発させたい — 表面的に復旧しても根本対策 (WAF / 入力検証 / patch) を打っていなければ、 次の tick で同じ障害がまた起きる。 これが無いと 「1 回 revert を待てば勝ち」 になり、 防御の巧拙が点差にならない。

「対策が不十分か」 の判定は 既に存在する — ADR-034 の attackProbe は毎 tick 攻撃 payload を撃ち、 防御が破れているか (例: SQLi が通る / 改ざんが書き戻せる) を観測して減点する。 不足しているのは、 その観測を「再注入」 に接続する timing 層と、 operator が予約・定期発火を選べる UI/API だけである。

Decision

disruption 宣言に timing/recurrence ポリシーを 1 つ足し、 既存の 2 つの発火ドライバ (operator fire API / scoring tick) を拡張する。 注入の実体 (executor + 3 kind + revert) と 疎結合契約は 一切変えない — 変わるのは「いつ・何回 DisruptionFired を publish するか」 だけ。

1. timing モデル (4 mode)

mode駆動意味新規/既存
one-shot (default)operator / tick 1 回注入 → revert。 既存の操作・条件発火と完全互換 既存
scheduledoperator operator が「N 分後に」 を選んで予約。 defaultAfterMinutes / operatorEditable:["afterMinutes"] で既定値と上書き可否を宣言 新規
recurringoperator / tick window 中 intervalMinutes ごとに再注入。 maxFires 必須 (= 上限到達で停止) 新規
while-undefended (適応的)tick 毎 tick、 宣言した防御 probe を評価し、 まだ脆弱な間だけ再注入。 minIntervalMinutes で throttle、 maxFires で上限 新規

2. 宣言スキーマ (問題作者が書くもの)

既存の action / triggers はそのまま。 disruption に recurrence を足し、 triggers[].kind に 防御状態を見る defense-insufficient を 1 つ追加する (= ADR-034 の attackProbe を probeRef で参照、 検知 primitive を再利用)。 

{
  "id": "homepage-defacement",
  "name": "トップページ改ざん",
  "action": { "kind": "lambda-invoke", "targetRef": "DefaceLambdaArn",
              "paramTemplate": { "path": "/index.html" },
              "revert": { "afterSeconds": 120, "kind": "lambda-invoke", "targetRef": "RestoreLambdaArn" } },

  "recurrence": {
    "mode": "while-undefended",   // one-shot | scheduled | recurring | while-undefended
    "minIntervalMinutes": 3,      // recurring/while-undefended: 再注入の最小間隔 (throttle)
    "maxFires": 8                 // recurring/while-undefended: 必須。 0 でも event 終了でも必ず止まる
  },

  "triggers": [
    { "kind": "defense-insufficient", "probeRef": "tamper-detect" }   // ← 新 kind。 probe が「脆弱」なら再発
  ]
}

後方互換: recurrence 未宣言 = one-shot。 既存の全問題は無改修で従来どおり動く。

3. 発火フロー (platform 側・汎用)

── operator 経路 ─────────────────────────────────────────────── operator ─fire(timing)─▶ disruption-fire (Phase A) timing=immediate ─▶ PutEvents(DisruptionFired) [既存] timing=scheduled ─▶ aws-scheduler one-shot at(T+N) ─┐ timing=recurring ─▶ aws-scheduler rate(N) ×maxFires ─┤ ▼ ── tick 経路 ─────────────────────────────────────────────────── PutEvents(DisruptionFired) scoring tick ─評価─▶ condition-disruption-fire │ one-shot trigger : firedDisruptions で抑制 (既存) │ defense-insufficient: probe=脆弱 かつ (now-lastFired)≥minInt │ かつ fireCount<maxFires なら再発 ──────┤ ▼ ────────────────────────────────────────────────────────▶ DisruptionExecutorLambda AssumeRole(ExternalId) ─▶ sendDispatch(kind) ─▶ scheduleRevert

scheduled / recurring は schedule-revert.ts で実証済みの aws-scheduler one-shot/rate パターンをそのまま転用する (= 新機構ゼロ)。 schedule の target は 既存の経路に合流させるため、 注入そのものではなく DisruptionFired の再 publish を行う (= fire→executor の経路・冪等性・監査を 1 本に保つ)。

4. 状態管理

one-shot は既存の DeploymentScoringState.firedDisruptions: string[] (発火済み set) のまま。 recurring / while-undefended は再発を許すため、 per-disruption の { lastFiredAtMs, fireCount } を同 state に足す (DynamoDB は 1/1 PROVISIONED のまま、 既存 item の属性追記なので追加 RCU/WCU 無し)。 tick は fireCount < maxFires かつ now - lastFiredAtMs ≥ minIntervalMinutes を満たす時だけ再 publish する。

Always-ends との結線 (ADR-029)

再発は 無限ではないことを多重に保証する (INV-2: どの障害も必ず復旧し、 競技は必ず終わる):

停止条件機構
注入ごとの復旧action.revert は ADR-031 で 必須。 再発しても各注入に revert が予約され、 永続化しない
回数上限recurring / while-undefended は maxFires 必須。 validate で未宣言を reject
時間上限scoring lock / event 終了 (ADR-029) で tick 自体が止まる。 operator の recurring schedule は event teardown で削除
適応的の自然停止while-undefended は probe が「防御済み」 を返した瞬間に再発が止まる (= 対策すれば終わる、 これが狙い)

Trust model (ADR-031 から不変)

timing 層は 「いつ publish するか」 しか変えないため、 ADR-031 の信頼境界はそのまま効く: AssumeRole は team の competitorRoleArn + tenant の ExternalId でのみ成立、 operatorEditable allow-list で fold 済の値しか paramTemplate に入らない、 EXEC#{requestId}#{teamId} conditional Put で per-team 冪等。 再発は requestId に fire 連番 (#{n}) を付与して別注入として監査する (= 重複配送は依然 no-op、 再発は別レコード)。

Alternatives considered

案判定理由
EventBridge Scheduler でなく Step Functions で再発ループ Rejected state machine の常設 = コスト/運用増。 既に schedule-revert.ts で one-shot scheduler が実証済みで、 tick が周期エンジンを兼ねる
再発を問題側 Lambda の中で完結 (自分で setInterval 相当) Rejected 停止保証 (always-ends) を platform が握れない。 maxFires / event 終了で止める責務は host 側に必要
while-undefended を専用の新 probe 機構で作る Rejected ADR-034 attackProbe が既に「毎 tick 防御状態を検知」 を実装済。 probeRef で再利用すれば二重実装を避けられる
recurrence + defense-insufficient trigger を宣言で表現し、 既存 2 ドライバを拡張 Accepted 疎結合・後方互換・always-ends を全て満たし、 新規機構ゼロ。 問題作者の学習面は recurrence 1 ブロックのみ

Consequences

Positive

  • 「対策が不十分なら再発」 が成立し、 防御の巧拙が初めて点差になる (= Battle が競技として成立)。
  • operator は即時 / 予約 / 定期を 1 つの fire UI で選べる。
  • 新規 AWS リソース機構はゼロ (scheduler / tick / executor は既存)。 DynamoDB も属性追記のみで 1/1 維持。
  • 後方互換 — 既存問題は recurrence 無しで従来どおり one-shot。

Negative / trade-off

  • operator recurring は schedule を作るため、 event teardown での確実な削除が要る (cleanup に追加)。
  • while-undefended の体感粒度は tick 間隔 (≈1 分) に律速される (= 秒単位の再発はしない。 運用上は十分)。
  • 監査ログは再発のたびに 1 行増える (= 意図どおり。 「何回・いつ再発したか」 が可視化される)。

Migration

  1. SCHEMA: problems/SCHEMA.json の disruptions[] に recurrence を追加、 triggers[].kind に defense-insufficient を追加。 旧説明文 (「Phase 4 future-facing / カタログ用途のみ」) を実装済みの内容へ更新。
  2. tick: condition-disruption-fire.ts の抑制を「one-shot のみ抑制、 recurring/while-undefended は interval+cap 判定で再発」 に拡張。 defense-insufficient 評価を disruption-triggers.ts に追加。
  3. operator fire: fire schema に timing (immediate|scheduled|recurring) + afterMinutes/intervalMinutes を追加。 即時以外は aws-scheduler に登録。
  4. fire UI: DisruptionsPanel に timing トグル (即座 / N 分後 / N 分ごと) を追加。
  5. author ガイド: docs/problems/ に 「障害の足し方」 (3 kind + 自前 Lambda + recurrence + revert + 注入フロー) を追加。

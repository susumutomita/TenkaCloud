ADR-007: outside-in architecture — user observable scenario を PR ゲートにする

Status:Proposed 2026-05-11
Issue: #561
Related ADR: ADR-001、 ADR-004、 ADR-006、 harness

Context

2026-05-10 の 1 日 dogfood で 30+ 件の Issue が起票された。ほぼ全部「PR は merge 済 / unit test green / typecheck green」 にも関わらず、ブラウザで触ると次のような 事象が観測された:

  • 配線忘れ (#535 / #553 / #560): handler は書けたが API GW route / Lambda env / IAM 配線が抜け、frontend が 5xx
  • 用語 mismatch (#549 / #531): 「COMPLETE」 を operator が「問題解いた」と誤解、Bulk Deploy が初見殺し
  • affordance 不足 (#533 / #547): Badge を Link で wrap しただけだと click 可能か分からない、dropdown でなく button にすべきだった
  • 状態遷移漏れ (#539 / #557 / #559): bulk deploy / teardown 後の Event status が手動操作必須、子集約から親遷移する経路なし
  • 初見 operator が次に何を押すか分からない (#531): EventDetail の primary action 不明、ドキュメント読まないと正常運用に辿り着かない

共通根本: 各 layer (backend handler / CDK / frontend) が isolated に unit test を持ち、その層内では green。しかし「user が観察可能な outcome から逆算する scenario」がレポジトリに 1 本も無いため、layer 間の seam (= 配線) と user 視点の affordance が抜け落ちる。

inside-out (現状) では「動いた = 各 layer の unit test が green」。outside-in では「動いた = browser を開いて user が目的を達成した」。前者は配線忘れ / 用語 mismatch / affordance 不足を顕在化しない。
制約由来本 ADR への影響

cost 最小化 (DDB 1/1、Lambda 限定)repo の経済設計 scenario 環境は ephemeral / per-PR を避け、shared staging に集約

D1. scenario DSL / framework

案採否内容欠点
D1-A採用 Playwright + TypeScript。ブラウザ 3 種 (Chromium / Firefox / WebKit) の native runner、network mock / trace viewer / video recording 内蔵 scenario 1 本あたり container image 起動 5-10 秒
D1-B却下 Cypress 同オリジン制約・iframe 制約があり Cognito Hosted UI redirect / cross-domain callback が扱いにくい
D1-C却下 Selenium / Webdriver flake 率が高く、scenario debug 体験が劣る
D1-D却下 Vitest + Testing-Library のみ (= browser を起こさない component test) jsdom 内なので「browser 上で実機 fetch して CFn が動く」を観測できない (= 配線忘れの検出不可)
Playwright 採用根拠の補足
  • TypeScript native — repo の他 code と type 共有可能 (= API response 型を scenario でも使える)
  • Cognito Hosted UI の redirect / OAuth Code+PKCE flow を page.waitForURL で素直に書ける
  • video / trace 自動取得で flake 解析が楽 (= CI で fail したら video を artifact 化)
  • locator API が auto-wait 内蔵で polling-friendly (= setInterval を scenario 側で書かなくて済む)
  • repo 既存の MCP server mcp__playwright__* と整合 (= AI agent も同じ DSL で操作できる)

D2. scenario 実行環境

案採否内容欠点
D2-A採用 shared staging account + environment=staging stack 一式。CI が main / 各 PR で同じ stack を共有、scenario の data setup は eventId / tenantId prefix で衝突回避 PR 並列実行で同一 tenant に対する race の可能性 → eventId に PR 番号を入れて scope 分離
D2-B却下 per-PR ephemeral stack (CDK deploy → scenario → destroy) 1 PR あたり 15-30 分の deploy + destroy 時間、月数百ドルの CodeBuild / Lambda / CFn 課金。本 repo の cost 最小化制約と不整合
D2-C却下 LocalStack で AWS をエミュレート SBT / Cognito Hosted UI / CodePipeline / CodeBuild の挙動を完全には再現しない (= 配線忘れ検出の信頼度低下)。outside-in の目的に反する
D2-D却下 production account をそのまま使う scenario 中の事故が prod に波及するリスク。冪等 cleanup を間違えると課金累積
D2-A の前提 staging stack
  • infrastructure/environments/staging/config.json と .env.example は既に存在
  • 本 ADR 実装時に make deploy ENV=staging で 3-phase 一気通貫が通ることを確認
  • scenario は STAGING_*_URL 環境変数 (= GitHub Actions secrets) を読んで対象 URL を確定
  • 競技者 AWS account は別途 staging-competitor account を用意し、ExternalId は staging 専用値

D3. scenario 数の方針

tierscenario 例方針
Tier 1 (= 必須) operator: event 作成 → bulk deploy → status=READY → 即座に開始 → 終了 → teardown
competitor: teamLoginKey login → 問題一覧 → flag 提出 → score 反映		 5-7 本。main への merge 前に必須通過。落ちたら release / deploy ブロック
Tier 2 (= 推奨) operator: 部分 deploy / failed-only 再試行 (#555)、scoring lock/unlock (#558)
competitor: Battle 攻撃通知 / Notifications		 3-5 本。週次 build で実行、fail は warning。リリースは止めない
Tier 3 (= optional) edge cases: 30 問 × 10 team 同時、token expired retry、bulk teardown 並列度 nightly / 手動 trigger のみ。perf 系は別系列で計測

初期 5 本 (Tier 1) を ADR-007 採択と同時に scaffolding する。残 Tier は機能追加と同 PR で増やす。

D4. flake 戦略

分類処理
network transient (DDB ProvisionedThroughputExceeded、TLS handshake 失敗) 1 回 retry。Playwright retries: 1 を CI 固定
polling 待ち (status 遷移、deploy 完了) Playwright の auto-wait + 明示 timeout。Tier 1 は最大 10 分
state machine race (= 同時更新) quarantine: 該当 scenario を test.skip.fixme で隔離し別 issue で扱う。retry はしない (隠蔽になる)
unknown video + trace artifact を CI に保存、scenario を quarantine、issue 起票

D5. data setup / teardown

案採否内容
D5-A採用 scenario 毎に fresh tenant + event を作る (= SBT control plane API を direct invoke)。各 entity に e2e-${PR}-${nanoid} prefix を付けて衝突回避。afterAll で tenant ごと delete
D5-B却下 shared fixture tenant を再利用 scenario 間の state leak が flake の温床、debug が難しい
D5-C却下 DDB 直書き seed 外部 API 層を skip するため「観察可能 outcome」を破壊する。outside-in の趣旨に反する
cleanup 失敗時の保険
  • tenant の expiresAt を 24 時間後に設定 (DDB TTL で自動 delete)
  • nightly cron で e2e-* prefix の tenant を sweep する Lambda を別 ADR で追加検討
  • cost guardrail: staging account に Budget Alarm (月 $50 上限) を入れる

D6. 既存 unit / CDK test との関係

layer本 ADR 後役割
vitest unit (= 582 件)維持 + 増加 handler / lib の純粋ロジックは unit で押さえる (= scenario が遅いので fast feedback loop を維持する役)
CDK assertion (= Template.fromStack)維持 resource property の細部 (DDB プロビジョン値 / IAM 最小権限 / route 配線) を pin する
Playwright scenario (= 本 ADR で新設)新規 layer seam (= 配線) + user observable affordance を保証する

方針: scenario は unit を置き換えない、補完する。unit を削る誘惑があるが「scenario の遅さ × CI 時間」を考えると unit を残した方が dev 体験が良い。

D7. PR ゲートとの結合

案採否内容欠点
D7-A採用 段階的 gate: 採択直後は warn ( CI で run + fail でも block しない)、6 PR 経過後に required check に昇格 初期に scaffolding cost が下がる代わりに、不正引き返しの猶予がある
D7-B却下 採択即 required check 既存 PR 流れが止まる。staging stack 安定化前にゲートを掛けると ROI が逆転する
D7-C却下 warn のまま据え置く 軟弱化、結局 PR が爆増して 30+ 件 issue 再来する

追加で 新 invariant INVARIANT_PR_HAS_OUTSIDE_IN_SCENARIO を harness に追加する。最初は warn 出力のみ、Phase 2 で error 化する。harness の rule は .claude/harness/src/architecture.ts に新規 case を追加。

Consequences

positive

  • 配線忘れ regression が PR ゲートで止まる (#535 / #553 / #560 系の再来防止)
  • UI affordance 不足 が scenario 実行で顕在化 (= 操作 sequence が描けないなら UI が間違っている)
  • 用語 mismatch が「scenario が user 語彙で書かれる」 ことで運営側にとって読みやすい仕様書になる
  • state machine 整合性 が end-to-end で保証される (#539 / #557 / #559 系)
  • 新人 / AI agent も 「scenario を読めば動作が分かる」 のでオンボード時間短縮

negative

  • scenario 1 本あたり 5-15 分かかる。Tier 1 全体で 30-60 分 (= CI 時間が増える)
  • staging account の AWS cost (= 月 $30-50 想定、Budget Alarm で抑止)
  • scenario maintenance cost (= UI 変更で locator が壊れる → role-based locator 推奨)
  • 初期 setup 工数大 (= Phase 2-3 で計 5-10 PR 規模)

open questions (= follow-up issue)

  • staging account の cost 実測 (1 ヶ月計測)
  • scenario の data fixture を AI に書かせる 仕組み (= MCP server mcp__playwright__* 経由)
  • per-PR ephemeral stack の cost が下がれば D2 を再評価
  • nightly e2e-* cleanup Lambda (D5 の保険)

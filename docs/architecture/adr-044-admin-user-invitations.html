ADR-044: Admin user invitations stay plane-scoped

System Admin 招待 UI は戻さず、Tenant Admin staff 招待は App Plane 内で完結させる

Status: Accepted 2026-06-18
Decision: Reject System Admin invite UI
Related: ADR-018, ADR-020, Architecture harness
Tracking: #1769

Context

TenkaCloud has two authenticated operator planes. The System Admin console operates the SBT control plane: tenant CRUD, identity provider configuration, provisioning jobs, audit, usage, and operations views. The application admin console operates inside one tenant: events, deployments, competitor accounts, participant handoff, audit, and tenant staff management.

Issue #1769 requested invitation UI for both System Admin users and Tenant Admin users. The request bundled two different authority boundaries:

  • System Admin invitation: adds another principal that can operate the control plane across all tenants.
  • Tenant Admin staff invitation: adds a principal scoped to one tenant's application plane, with one of TenantAdmin, TenantOperator, or TenantViewer.

The Tenant Admin side is already implemented in the application admin console. The /users page calls tenant-scoped admin/users routes, validates email and role input, sends Cognito invitations with server-owned custom:tenantId and custom:userRole attributes, and prevents read-only viewers from mutating user state.

The System Admin side was previously removed from apps/admin-console. The route comment records the product boundary: System Admin user management is intentionally kept out of the UI because it expands control-plane authority and blurs the separation between operator activity, identity bootstrap, and tenant operations.

Decision

TenkaCloud will not restore a System Admin invitation or user-management page inside apps/admin-console. System Admin bootstrap and emergency user lifecycle remain an explicit Cognito or SBT operator action outside the product UI. Tenant-scoped staff invitation remains in apps/application-admin-console under the tenant-owned /users route.

System Admin Created and recovered through controlled Cognito / SBT operator procedures. No always-on in-product invite button.
Tenant Staff Managed by a tenant operator in the application admin console. The API sets custom:tenantId and custom:userRole server-side.
Audit Boundary Tenant staff changes are tenant audit events. System Admin lifecycle changes remain platform operator actions.

Rationale

ConcernReason
Control-plane authority A System Admin can create tenants, configure control-plane identity providers, inspect operations data, and affect all tenants. Adding a casual invite button makes the highest authority path easier to trigger from a browser session.
Plane separation The application admin console already has a safe tenant-scoped staff model. Putting System Admin lifecycle beside tenant and operations pages would mix identity bootstrap with day-to-day control-plane operation.
Existing implementation Tenant staff invitation no longer requires CLI-only operation. The shipped TenantUsersPage and admin/users routes cover TenantAdmin, TenantOperator, and TenantViewer with UI and handler tests.
Supply-chain and token hygiene Keeping System Admin bootstrap outside the SPA avoids adding new frontend flows around platform-wide identity lifecycle. The SPA continues to use only the normal authenticated session for ordinary operations.
Operational clarity System Admin creation should remain rare, intentional, and documented. A runbook can require a human approval trail without encoding that policy in a product page.

Accepted Implementation

CapabilityLocationStatus
Invite tenant staff apps/application-admin-console/src/pages/TenantUsers.tsx Shipped
Tenant staff API infrastructure/lib/problem-deploy/handlers/competitor-accounts-handler/users-routes.ts Shipped

Allowed Future Work

The decision does not prohibit improving System Admin lifecycle operations. The following remain allowed if they preserve the same boundary:

  • Document the Cognito or SBT command sequence for creating, disabling, and recovering System Admin users.
  • Add a read-only System Admin roster in the operations or audit area if it does not create, delete, or mutate users.
  • Add audit ingestion for externally performed System Admin lifecycle actions.
  • Add break-glass runbooks for lost System Admin access.

Restoring an in-product System Admin invite flow requires a separate ADR. That proposal must cover approval semantics, audit retention, least-privilege route authorization, self-demotion and self-delete prevention, recovery, and a security review for platform-wide authority escalation.

Consequences

Positive

  • The highest-privilege identity lifecycle remains rare and explicit.
  • Tenant operators still get the practical collaboration feature they need: tenant-scoped staff invitations and role changes.
  • No new Control Plane handler or IAM change is introduced for System Admin invitations.
  • The existing plane boundary comments in apps/admin-console/src/App.tsx remain accurate.

Negative

  • Operators cannot invite a new System Admin from apps/admin-console.
  • System Admin lifecycle remains a runbook or CLI operation until a future ADR changes that boundary.

Implementation Status

No runtime implementation is required for this ADR. Issue #1769 is resolved by splitting the bundled request along the existing plane boundary: Tenant Admin staff invitation is already shipped in the application admin console, and System Admin invitation UI is intentionally out of scope for the control-plane SPA.

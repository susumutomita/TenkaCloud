ADR-020: 認可モデル — role enum (TenantAdmin / Operator / Viewer + SystemAdmin) と段階導入

StatusAccepted Date2026-05-17 Issue#926 RelatedADR-011 (admin-insight 認可境界)、 ADR-018 (pooled UserPool)

背景

TenkaCloud の Cognito JWT 認可は 2 段で動く:

  1. API Gateway Cognito Authorizer — token 署名 / expiry / aud を検証 (= 1 段目)
  2. handler の role check — Issue #854 で導入された requireTenantAdmin(c) が custom:userRole claim を見る (= 2 段目)

ただし役割 (role) は "TenantAdmin" の 1 種類しか定義されていない。 結果として:

  • 監査担当に read-only token を渡せず、 destructive 操作可能な admin token を渡すしかない (= 最小権限違反)
  • オンコール / monitor bot に発火権を渡すと user 管理権まで一緒に渡る
  • 削除 / archive のような重い操作と、 単なる list との 認可境界が同じ

加えて次の認可関連ギャップが Issue #926 で flag された:

  • SystemAdmin endpoint の role 強制が SBT 任せで repo 側 audit 未済
  • custom:userRole の set 経路が provision-tenant.sh admin-create-user の 1 回のみ (= 後から変える UI 無し)
  • 認可エラー / 成功 admin 操作の audit log が CloudWatch Logs しか無く、 「誰が何をしたか」 を後追いする集約 storage が無い
  • destructive operation で MFA 再認証が無い (= 1 JWT で全部通る)
  • tenant 越境チェックが resolveTenantId 1 本に依存し、 path / body から到来する tenantId と JWT の照合 middleware が無い

判断

4 role を正本とする。 名称は SBT 同型 (= ControlPlane が SystemAdmin Cognito group を払い出す) に揃え、 tenant 内は 3 段とする。

不採用案

OPA / Cedar / IAM-style policy DSL の導入

policy DSL は将来 role 数が 10+ になり、 attribute-based access control (ABAC) が必要になったときの選択肢。 現状 4 role + route 単位の allow list で十分扱え、 DSL を導入すると runtime evaluator + policy storage + audit + テストのコストが requireRole array literal 1 行よりはるかに高い。 必要になった時点で別 ADR で再評価する。

Cognito Group ベースに移行

Cognito UserPool Group は 1 user が複数 group に属せて、 SAML 連携 / Federation 時に IdP attribute mapping で割り振れる利点がある。 ただし現行は custom:userRole string 1 個の単純モデルで Phase 1 user 管理 (#925) を出した直後。 Group 化は migration コスト (= 全 user の Group 振分 + handler の cognito:groups 検査への switch) が大きく、 Phase B では custom:userRole string で進める。 SAML federation で role mapping が必要になったら別 ADR で migration plan を立てる。

1 role per token (= scope claim) ではなく、 hybrid (= role + scope)

例えば read-only audit user に「 deployment は read 可、 user 管理 は不可」 のような細粒度を表現するには role + scope claims を組合せる必要がある。 これは Phase B (= 4 role string で十分) と Phase D (audit log で誰がどの粒度を触ったか可視化) を経て、 必要なら別 ADR で進める。

影響

Backwards-compat

  • requireTenantAdmin(c) は requireRole(c, [TENANT_ADMIN_ROLE]) の alias として残す (= 既存 handler / test の caller 互換)
  • 既存 custom:userRole=TenantAdmin な user は Admin 扱いで動作不変
  • provision-tenant.sh で払い出される初期 admin は TenantAdmin。 後から AdminConsole 経由で Operator / Viewer を追加できる (#925 frontend を Phase B で role dropdown 拡張)

セキュリティ

  • middleware は blanket TenantAdmin gate を Phase B で維持する (= 新 role の user が誤って destructive route を叩いても落ちる)。 Phase B.1 で route 単位 granular に置換するまで「 broken-glass safety 」 として残る
  • InviteUserRequestSchema は Zod enum で TenantAdmin | TenantOperator | TenantViewer に絞る (= 任意文字列を custom:userRole に注入できない)
  • SystemAdmin 系 endpoint (admin-insight) は isSystemAdmin(c) 既存 helper が cognito:groups ⊇ {SystemAdmin} を検査済 (ADR-011 D2 採用)。 本 ADR では tenant 側 role のみ追加

運用

  • AdminConsole 配下 user 管理: TenantAdmin が自 tenant 内の Operator / Viewer を 招待 / 削除 できる (= #925 frontend を Phase B で role dropdown 拡張)
  • role 変更: 既存 user の role を後から変える PATCH /admin/users/:username は Phase B.1 で追加
  • audit: 当面 CloudWatch Logs ベース (= ForbiddenRoleError / 成功時の console.log)。 Phase D で DDB 集約

テスト要件

  • requireRole(c, allowedRoles[]): 一致なら pass、 不一致 / 不在なら ForbiddenRoleError を throw。 allowedRoles 空配列は always reject
  • requireTenantAdmin(c) alias: Phase A の挙動と同じであることを既存 test で pin (= regression なし)
  • InviteUserRequestSchema: 3 role を受け入れる + 未定義 role は reject
  • extractUserRoleFromClaims: 既存テストを Operator / Viewer でも回す

ADR-008: Problem payload separation — private / answer content via S3 + presigned URL

Status:Accepted 2026-05-13 — implemented but dormant (no repo binds the publish secret yet).
Related ADR: ADR-003 (problem catalog) · ADR-012 (problem = plugin)
Related issues: PR-1184 (ChallengePayloadStack)

Context

Problems are delivered as plugins (ADR-012): the public catalog lives in the problems/ git submodule (TenkaCloudChallenge), is packaged into source.zip, and is deployed into each competitor account from its metadata.json + template.yaml.

Two kinds of problem content do not belong in that public OSS submodule:

  • Answer / private competitive content — anything that would leak the solution if it shipped publicly (graded payloads, hidden flags, full exploit chains).
  • Large binary payloads — Docker images, datasets, or fixtures that would bloat the submodule and source.zip.

We need a way for the deploy-handler to pull a per-problem payload at deploy time from a separate, optionally-private source, without bloating or exposing the OSS repo, and without long-lived credentials.

Decision

Separate the problem payload from the catalog. A private (or simply separate) repo publishes per-problem zips to an S3 bucket; the deploy-handler fetches them via a short-TTL presigned URL when it deploys a problem. The work lands in phases so each is independently observable.

PhaseWhatWhere
Phase 2 Deploy-handler consumption path. When challengePayloadBucketName is bound, the handler resolves a 15-minute TTL presigned URL for s3://<bucket>/<problemId>/<sha>.zip (and latest.zip) and passes it into the competitor-account deploy. Unbound → the in-submodule template is the only source. ProblemDeployBackendStack (resolveChallengePayloadBucket → CHALLENGE_PAYLOAD_URL)
Phase 3 Publish bucket. A versioned, fully-private S3 bucket for the payloads. ChallengePayloadStack (infrastructure/lib/challenge-payload/)
Phase 4 Publish identity. A GitHub OIDC IAM Role (least-privilege, scoped to the repo + branch via the OIDC sub claim) that the publishing repo's publish.yml AssumeRoles to upload changed problem dirs. No long-lived keys. ChallengePayloadStack (OIDC role)

Binding

Activating the path is an explicit, manual bind on the publishing repo:

  • bucket name → repo vars (display-only, no secret needed),
  • publish Role ARN → repo secrets.AWS_CHALLENGE_PUBLISH_ROLE_ARN.

Once bound, the repo's main-push trigger starts publishing and the deploy-handler starts resolving presigned URLs. Until then the path is dormant.

Consequences

Positive

  • The public OSS catalog stays lean and safe to publish — private / answer content never ships in the submodule or source.zip.
  • Presigned URLs are short-lived (15 min), so a payload URL cannot be replayed long after a deploy.
  • Publishing uses GitHub OIDC (no static AWS keys), scoped to a single repo + branch.
  • Cost is ~zero while dormant; the bucket only accrues storage once a repo publishes.

Negative / open

  • Dormant by default. No repo binds AWS_CHALLENGE_PUBLISH_ROLE_ARN today, so the deploy-handler falls back to the in-submodule template. The stack + handler path exist but are inactive until a private/answer repo opts in.
  • A second source of truth for problem content (submodule template vs. published payload) — authors must understand which assets ship where.

Constraints

  • This is the cost-zero, least-privilege path: do not substitute long-lived publish keys or AWS Secrets Manager (see secrets-manager-forbidden in the architecture harness).
  • The OIDC role trust policy must stay scoped to the publishing repo + branch via the sub claim; widening it re-opens a cross-repo publish vector.

ADR-008: 問題カタログを Community Contribution Registry にする

Status:Proposed 2026-05-11
Version:v2 — community contribution model 中心に大幅改訂
Driver:#572 (microservice-migration-battle) + user feedback「コミュニティでオリジナル問題を追加できる設計に」
Tracking:#574
v1 「自分用 private repo + 答え漏れ防止」モデル → v2 寄稿モデルが本筋。v1 は「寄稿モデルの特殊ケース 1 つ」として吸収

Context

v1 は #572 (microservice-migration-battle) で「完成形のサービスコード自体が答え」となる Battle が起票され、答えが public repo にあると競技が成立しないという問題を解くために、 「自分用 private repo + 運営 S3 publish + presigned URL fetch」を提案した。

v1 を書いた直後 (2026-05-11)、ユーザーから次のフィードバックが入った:

要はオリジナル問題をコミュニティで追加できる設計になっていればいいんだけど。 S3 とかにプッシュしてそこからロードしているとかならサードパーティーの問題もプッシュしてもらえばいい。

これを受けて v1 を見直すと、「自分が答え漏れを気にする」のは寄稿モデルの 1 ユースケース にすぎず、本筋は「誰でも問題を追加できる仕組み」(= 答え漏れも結果として解決) である ことが分かった。本 ADR v2 はそれを設計する。

現状アーキテクチャの寄稿不可性

Explore agent で本体 repo の問題ロード経路を調査した結果 (= 2026-05-11 セッション):

layer現状寄稿の障害
カタログ表示 apps/application-admin-console/src/data/problems.ts:61-64 で Vite import.meta.glob が build 時に problems/*/*/metadata.json を bundle サードパーティー問題追加 = 本体 repo の rebuild & redeploy 必要
CDK 配線 infrastructure/bin/infrastructure.ts:214 の discoverProblemsCatalog() が build 時に走査 → Lambda env BATTLE_PROBLEMS_CATALOG に inject build 時固定、動的追加不可
template.yaml の deploy install.sh が repo 全体を zip → S3、CodeBuild が source.zip 内の problems/<id>/template.yaml を 直読 問題が「本体 repo の一部」前提。S3 に他者が push しても CodeBuild は見ない
validate-problems scripts/validate-problems.ts が problems/SCHEMA.json で全 metadata.json を JSON Schema 検証 本体 repo にあるものしか検証できない

つまり現状は 「問題 = TenkaCloud 本体のコードベース」 が完全に前提で、 寄稿の余地がない。寄稿モデル化は MVP-1 → ADR-003 Phase 2 (= DB-backed catalog) への 移行と合流させる形で、本 ADR で前倒しする。

制約 (= 既存方針として動かさないもの)

  • 本体 repo は public OSS のまま(CLAUDE.md)
  • カタログ UX を維持 — admin-console / participant-portal の表示・検索・フィルタが既存と等価以上に動く
  • deploy パイプラインの I/F を維持 — Worker Lambda の DeployRequested 処理、ExternalId による cross-account AssumeRole (ADR-002) はそのまま
  • CFn ペライチ規約 (problems/README.md) を維持
  • Free Tier 25 RCU/WCU 内 (DynamoDbLowCapacity Aspect)

解くべき設計判断

D1. カタログ storage

案採否概要主な決め手
D1-A却下 本体 repo の problems/<id>/metadata.json 静的ファイル (= 現状) 寄稿に rebuild 必要、寄稿者 PR を待つしかない
D1-B却下 本体 repo の problems/index.json 集約 (= v1 案) 動的 CRUD ができない、寄稿者 metadata の attribution / 検索ができない
D1-C採用 DDB ProblemRegistry table (= ADR-003 Phase 2 を前倒し) 動的 CRUD / 寄稿者 attribution / 検索 / フィルタ / 検証ステータス管理がすべて 1 ヶ所で完結

D2. 問題 payload (template.yaml + 実装ファイル) の storage

案採否概要主な決め手
D2-A却下 本体 repo の problems/<id>/ (= 現状) 寄稿不可
D2-B却下 GitHub Releases (寄稿者の repo の release artifact) 寄稿者ごとの GitHub 認証管理が複雑、CFn ペライチ規約と合わない
D2-C却下 ECR private images にビルド済イメージを置く CFn 規約と無関係、寄稿者ハードル高い
D2-D採用 S3 multi-tenant prefix (s3://tc-challenges-<env>/<contributor>/<problem-id>/<version>/) AWS-native / 寄稿者ごとに prefix 分離 / presigned URL 経路を流用 / 既存 S3 zip 配信モデルと自然に共存

D3. 寄稿フロー (= 寄稿者の入口)

案採否概要主な決め手
D3-A採用 (MVP) GitHub PR ベース。寄稿者は本体 repo に contributions/<contributor>/<problem-id>/{metadata.json,template.yaml} + 実装ファイルを PR OSS 慣習 / レビュー文化が継続 / MVP の実装最小 / 検証 = GitHub Actions に乗せられる
D3-B後回し Web UI (admin-console から template.yaml ドラッグ&ドロップ) 寄稿者ハードル低いが検証 UI / プレビューの実装重い、Phase 6+ で追加
D3-C後回し CLI (tc challenge publish ./my-problem) git なしで投稿可能だが CLI 配布 / 認証が独立、Phase 7+ で追加

MVP は A のみ。B / C は将来の追加経路として interface (= 検証 Lambda + S3 + DDB) を共有する設計にしておけば、後付けで足せる。

D4. 検証パイプライン

寄稿者が任意のテンプレートを投げてくる以上、運営アカウントが攻撃される / 課金爆弾を仕掛けられる リスクがある。完全マニュアルレビューは scale しないので、自動 + 人間承認の二段構成にする。

レイヤー内容実装
自動 (CI 段階) ① CFn lint (cfn-lint) / ② IAM 権限スキャン (cfn-policy-validator 相当) / ③ cost estimator (infracost or AWS Pricing API) / ④ 禁止リソース検査 (例: AWS::Lambda::Function の reserved concurrency 上限) GitHub Actions on PR + 検証 Lambda
運営承認 System Admin が PR を最終 review。問題説明 / scoring 設計 / 学習目的の妥当性 GitHub PR の review = merge 権限
publish 後 S3 への upload は merge 後の Actions が OIDC role で実行 GitHub Actions OIDC + IAM

「悪意ある寄稿者の deploy 一発で運営 acct が破綻する」事態を防ぐため、publish された template.yaml は競技者 acct 側にしか展開されない (= 運営 acct 側で展開しない) 原則を厳守する。これは ADR-002 の cross-account federation で既に成立。

D5. 寄稿者 identity

案採否概要主な決め手
D5-A採用 GitHub OAuth / GitHub App (= 寄稿者は GitHub username で identify) D3-A (GitHub PR フロー) と自然に整合 / 追加の認証基盤不要 / 寄稿者ハンドル = GitHub username
D5-B却下 Cognito (= System Admin と同じプール) 寄稿者にとって sign-up ハードルが高い、外部寄稿促進に逆行
D5-C却下 API token のみ identity の attribution ができない (= 誰が投稿したか不明)

D6. 答え漏れ (= visibility)

案採否概要主な決め手
D6-A却下 全問題 public で OK (= 答え漏れ気にしない) #572 系の競技性問題が成立しない
D6-B採用 寄稿時に visibility: public | private を選択。public = 全 file が見える / private = metadata + 説明だけ表示、payload は 15 分 TTL presigned URL で deploy 時のみ取得 教材性のある問題と競技性のある問題が共存 / 寄稿者が選択責任
D6-C却下 全問題 private (= 一切公開しない) OSS 教材としての価値を失う / 既存 3 問題と矛盾

private 問題の payload S3 URL は presigned URL 発行のみ。S3 bucket は BlockPublicAccess + bucket policy で Worker Lambda role からのみ read 可。

D7. 既存 problems/ の扱い

案採否概要主な決め手
D7-A却下 削除して全部 DDB Registry に移行 OSS としての教材価値を失う / 既存 vitest / validate-problems が壊れる
D7-B採用 既存 3 問題は public sample として残し、Registry には contributor: "system" として seed import 既存資産を壊さず、Registry の動作確認の seed として使える / 「公式問題」と「寄稿問題」が同じ仕組みで共存
D7-C却下 そのまま残し、Registry とは別管理 2 系統並列運用は複雑、カタログ表示の分岐が増える

D8. 検索 / フィルタリング UX

寄稿者が増えると問題数も増えるので、カタログ画面で facet 検索を提供する:

  • contributor (= GitHub username)
  • category (Battle / Challenge)
  • difficulty (1〜5)
  • tags (= metadata.json の tags)
  • validation status (validated / pending / rejected)
  • visibility (public / private)

full-text search (= description 内容まで検索) は Phase 6+ で追加 (OpenSearch などを足す)。

D9. version 管理と stack 同一性

項目決定
version 識別子git SHA 短縮 8 桁 + semver 任意 (例: 1.2.0+a1b2c3d4)
同一問題の version 上書き禁止 — immutable
競技中の version 固定Deployments DDB に problemVersion 列追加。teardown まで固定
新 version 投稿新 PR を立てて検証 → publish。古い version は deprecated にできるが、競技中の stack には影響なし
S3 layouts3://<bucket>/<contributor>/<problem-id>/<version>/{metadata.json,template.yaml,code.zip}

アーキテクチャ図

Figure 1 — 寄稿者 → 検証 → 配信 → deploy のライフサイクル

図の読み方: ① の寄稿者は誰でも (自分含む)。② の PR が ③ の自動検証と ④ の運営承認の二段で merge される。⑤ で OIDC publish → ⑥ DDB と ⑦ S3 が更新。⑧ は DDB だけ見る。⑨ は deploy 時に DDB と S3 両方を見る。private 問題でも答えは ⑦ の S3 にしか存在せず、⑪ の競技者 browser からは見えない。

寄稿フロー (= MVP の入口、D3-A の詳細)

contributor 側: $ git clone https://github.com/susumutomita/TenkaCloud $ cd TenkaCloud $ mkdir -p contributions/<your-handle>/<problem-id>/ $ cp problems/SCHEMA.json … (= metadata.json を SCHEMA に沿って書く) $ vim metadata.json template.yaml … $ git checkout -b contrib/<your-handle>/<problem-id> $ git push -u origin HEAD $ gh pr create --title "feat(contrib): <problem-name> by <your-handle>" … CI (= 自動検証): on pull_request: .github/workflows/contrib-validate.yml が走る ├─ cfn-lint contributions/<handle>/<id>/template.yaml ├─ iam-scan (= 過剰権限 / wildcard resource 検出) ├─ cost-estimate (= deploy の月額試算上限を 5 USD/team とか) └─ schema validate metadata.json operator (= System Admin): PR を開いて学習目的 / scoring / 説明の妥当性を review → approve → merge post-merge (= GitHub Actions): on push to main で contrib-publish.yml が走る (changed paths: contributions/**) ├─ AssumeRole (OIDC, 短期 token) ├─ zip contributions/<handle>/<id>/code/ → code.zip ├─ aws s3 cp template.yaml metadata.json code.zip (= s3://tc-challenges-<env>/<handle>/<id>/<sha>/) └─ DDB upsert: ProblemRegistry に PROBLEM#<id> / VERSION#<sha> を入れる これ以降、catalog UI に「contributor: <handle>」付きで表示される。

寄稿者の repo は 本体 repo の fork で十分 (= 別 repo でも可だが、PR 経路は本体 repo に投げる)。 寄稿者は GitHub アカウントさえあれば追加の sign-up 不要。

Worker Lambda の変更

// 現状 (= MVP-1, build-time bundle)
const template = readFileSync(`./problems/${id}/template.yaml`);

// 変更後 (= ADR-008 v2)
const entry = await registry.lookup(id);  // DDB GetItem
const { templateBody, codeBundleUrl } = await s3Fetcher.fetch(entry);
//   ├ public 問題: codeBundleUrl は public S3 URL or 同梱
//   └ private 問題: codeBundleUrl は 15min TTL presigned URL
await cfn.createStack({
  TemplateBody: templateBody,
  Parameters: [
    ...,
    { ParameterKey: "CodeBundleUrl", ParameterValue: codeBundleUrl },
  ],
});

検証 Lambda (新設)

GitHub Actions の contrib-validate.yml から API GW 経由で叩かれる。受け取った template.yaml + metadata.json を以下で検証:

  • cfn-lint で構文 / リソース妥当性
  • IAM ポリシー scan (= wildcard resource / 過剰 action 検出)
  • cost estimator で月額上限超過チェック
  • 禁止リソース検査 (= reserved concurrency 上限など)
  • SCHEMA.json で metadata.json validate

結果を JSON で返し、Actions が PR にコメント。

Migration plan

  1. Phase 1 — ProblemRegistry stack (CDK by user)
    • DDB ProblemRegistry + GSI 2 本
    • S3 tc-challenges-<env> bucket (BlockPublicAccess + bucket policy)
    • GitHub OIDC role (tc-challenges-publisher)
    • Worker Lambda role に S3 read 追加
  2. Phase 2 — schema 拡張 + seed (Claude)
    • SCHEMA.json に visibility / contributor field 追加 (default 後方互換)
    • seed-problem-registry.ts で既存 3 問題を contributor: "system" として DDB に upsert
    • validate-problems を新 schema に対応
  3. Phase 3 — カタログ DDB 化 (Claude)
    • カタログ API (GET /catalog/problems 等) 新設
    • admin-console / app-admin / portal の Vite glob を API client に置換
    • Worker Lambda を DDB lookup + S3 fetch に切替 (= public 問題は従来パス互換、private は presigned URL)
  4. Phase 4 — 寄稿パイプライン (Claude + user)
    • 検証 Lambda 実装
    • .github/workflows/contrib-validate.yml + contrib-publish.yml
    • contributions/<handle>/<id>/ ディレクトリ規約をドキュメント化
  5. Phase 5 — microservice-migration-battle 本実装 (Claude, #572)
    • 本 ADR v2 と 並行で problems/battles/microservice-migration-battle/ に skeleton 作成 (= 後で contributions/<your-handle>/ に移動)
    • 3 サービス (users / orders / catalog) の FastAPI 実装 + slow endpoint 仕掛け
    • EC2 + docker compose の template.yaml
    • scoring engine は次 PR (= 共通基盤として切り出し)

Phase 1〜4 を順次走らせている間に Phase 5 を並行で進められる (= 既存パイプラインで public 問題として動かせるので、Phase 1〜3 完了後に contributions/ 配下に移動するだけ)。

Consequences

Pros

  • コミュニティ寄稿が一級市民 — 自分の問題も他人の問題も同じ仕組みで配信
  • 答え漏れも結果として解決 — private visibility + presigned URL で payload は本体 repo に出ない
  • ADR-003 Phase 2 (DB-backed catalog) を自然に達成 — 既存の方向性と整合
  • カタログが動的 — 寄稿のたびに本体 rebuild 不要
  • 寄稿者 attribution — 誰の問題か分かる、コミュニティ評価が機能する
  • 既存 deploy パイプライン互換 — 公式 3 問題はそのまま動く (Phase 3 の Worker Lambda 改修で吸収)

Cons / 注意

  • 新 stack 増 (DDB + S3 + 検証 Lambda + OIDC) — Free Tier 範囲だが運用面は増える
  • 検証パイプラインの実装コスト — Phase 4 が最大の工数
  • 悪意ある寄稿リスク — 自動検証 + 運営承認の二段で防ぐが、完全ではない (例: 課金爆弾の new pattern)
  • カタログ API の遅延 — DDB 経由で 1 段増、cache が必要かも
  • Vite glob 廃止 — 既存 frontend のテスト書き換え
  • multi-version 管理の運用 — 古い version の cleanup ポリシーが要る

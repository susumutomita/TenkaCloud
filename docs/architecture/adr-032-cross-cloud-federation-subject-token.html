ADR-032: Cross-cloud federation subject-token mechanism

非 AWS の問題ランタイム (Azure / GCP) へ deploy する際、 AWS Lambda 上の deploy worker が どうやって provider-native の短命クレデンシャルを得るか — ADR-017 OQ#1 の解決

Status: Accepted 2026-06-02
Related: ADR-017 (Trust Bridge / verified intent → credential), ADR-027 (Azure / GCP problem runtimes), ADR-026 (Sakura stored-key path), ADR-023 (multi-cloud expansion path)

Context

ADR-017 (Trust Bridge) は cross-cloud の権限委譲を「verified intent → short-lived provider-native credential」と抽象化し、 provider 別の交換アダプタを規定した。 ADR-027 は Azure / GCP の問題ランタイムを Workload Identity Federation (WIF) で扱う方針を採り、 packages/trust-bridge に AzureFederatedCredentialExchange / GcpWorkloadIdentityFederationExchange を プロトタイプとして実装した。 両アダプタは交換のオーケストレーション (= STS / token endpoint 呼び出し → 短命トークン) を持つが、 subject token をどう構成するか を caller 注入の toClientAssertion / toSubjectToken hook に委ね、 その具体形を未決 (ADR-017 OQ#1) として残した。

deploy worker の実体は AWS Lambda (problem-deploy backend) である。 ここから Azure / GCP の WIF へ federate する際の subject token には、 前提として無視できない制約がある:

制約内容
プロトタイプの想定が成立しない 両アダプタの doc comment は「trust-bridge の JWS (HS256) を subject token としてそのまま乗せる」 想定を記す。 だが HS256 は対称鍵であり、 GCP STS / Microsoft Entra ID は subject token を 発行者の公開鍵 (JWKS) で検証する OIDC モデルを前提とする。 共有秘密を検証側に渡さない限り HS256 JWS は WIF で検証できない。 = OQ#1 は「wire 整形」ではなく 信頼モデルの選択の問題。
AWS Lambda は OIDC token を native 発行しない GitHub Actions / GitLab CI のような OIDC issuer を AWS Lambda は持たない。 Lambda が持つのは AWS IAM の実行ロール identity (= SigV4 で署名できる) であって、 任意 audience 向けの OIDC JWT ではない。
provider ごとに federate 元の選択肢が異なる GCP WIF は AWS を first-class の credential source として受け付ける (subject token = 署名済 sts:GetCallerIdentity リクエスト)。 Microsoft Entra ID の federated identity credential は OIDC issuer のみを受け付け、 AWS-native の経路を持たない。

したがって OQ#1 は provider 一律には解けない。 「AWS Lambda という発行元から、 各 provider が実際に検証できる subject をどう作るか」を provider 別に決める必要がある。

Decision

federate 元として最も強い isolation を、 各 provider が native に受け付ける範囲で採る。 具体的には GCP は鍵レスの AWS-native WIF、 Azure は (native AWS 経路が無いため) stored client secret から始め、 OIDC issuer 化は将来のアップグレードとして留保する。

providersubject / credential署名鍵isolation
GCP (#1411) WIF AWS provider。 subject token = 署名済 sts:GetCallerIdentity (subjectTokenType = urn:ietf:params:aws:token-type:aws4_request)。 GCP STS で federated token に交換し、 iamcredentials.generateAccessToken で per-team service account の 短命 access token を得る。 不要 (deploy Lambda の AWS identity がそのまま subject) 短命 (federated token + SA token、 stored key なし)
Azure (#1410) per-team の Entra ID app registration の client secret を SSM SecureString に保管し、 client_credentials grant で ARM access token を得る (ADR-026 の Sakura stored-key と 同型の保管経路)。 stored secret (long-lived、 SSM SecureString) 弱め (Sakura と同等。 per-team app + 最小ロール + rotation で補償)
Sakura (#1412) 変更なし。 静的 API key (Access Token + Secret) を SSM SecureString 保管 (ADR-026)。 stored key 弱め (ADR-026 D3 の通り)
AWS 変更なし。 sts:AssumeRole + ExternalId + 1h セッション (ADR-002)。 不要 最短命

GCP — 鍵レス AWS-native WIF

GCP WIF プール (per-team GCP プロジェクト) を、 platform の AWS アカウントを信頼するよう構成する (#1413 onboarding)。 deploy worker は 自身の実行ロールで sts:GetCallerIdentity を SigV4 署名し、 GCP の規定形式 ({url, method, headers} を base64url 化) で subject token を作る。 これを GcpWorkloadIdentityFederationExchange に toSubjectToken として渡す。 プロトタイプの HS256 JWS 前提はこの方式で置き換わる。 platform 側に署名鍵を持たないのが利点 (鍵の保管 / ローテーション / 漏洩の管理対象が増えない)。

Azure — stored client secret を起点に、 OIDC issuer は留保

Microsoft Entra ID は AWS-native の credential source を持たないため、 鍵レスにするには platform を OIDC issuer 化 (RS256 JWT 発行 + JWKS 公開 + per-team app への federated credential 登録) する新サブシステムが 要る。 これは JWKS ホスティング・鍵ローテーション・issuer 運用を抱える重い投資であり、 最初の deployable バージョンの blocker にするのは過剰である。 そこで Azure は ADR-026 の Sakura stored-key 経路を再利用し、 per-team app registration の client secret を SSM SecureString に保管して client_credentials grant で ARM token を得る。 これは ADR-027 が掲げた「Azure は stored key 不要」を意図的に緩和する判断であり、 理由は上記の native 経路の欠如である。 OIDC issuer 化は 将来のアップグレードとして AzureFederatedCredentialExchange (既存プロトタイプ) を活かす形で留保する。

なぜ Azure も AWS-native にできないのか (詳細)

Entra ID の federated identity credential は issuer + subject + audience の 3 つで OIDC トークンを照合する。 issuer は HTTPS で /.well-known/openid-configuration と JWKS を 公開していなければならない。 AWS Lambda はこれを満たす issuer を内蔵しない。 GCP のように 「AWS の GetCallerIdentity を信頼する」設定は Entra ID 側に存在しない。 したがって鍵レス化は 「platform が OIDC issuer になる」以外に道がなく、 それは独立した設計判断 (本 ADR の scope 外、 将来 ADR) を要する。

Consequences

  • GCP は stored key を一切持たず、 short-lived credential で deploy できる (= AWS と同等の isolation)。
  • Azure は long-lived な client secret を 1 つ抱える。 これは Sakura と同じ 弱い isolation で、 同じ補償 (per-team app registration / 最小 ARM ロール / SSM SecureString のみ保管 / rotation 対応) を課す。 secrets-manager-forbidden 準拠で Secrets Manager は使わず SSM SecureString に保管する。
  • scoring は provider 非依存の HTTP probe のままで影響を受けない (ADR-026/027)。
  • Control Plane (SBT / Cognito / EventBridge) と deploy worker のホスト (AWS) は不変。 追加されるのは deploy 経路の credential 解決と、 onboarding の per-team 登録 (GCP WIF プール / Azure app secret) のみ。

Implementation order

  1. GCP resolver: SigV4 署名 GetCallerIdentity → subject token、 GCP STS / iamcredentials の REST client、 GcpWorkloadIdentityFederationExchange をオーケストレーションする getCredential、 deploy.ts の deps.gcp 配線。 REST client (Infra Manager) は実装済 (#1411)。
  2. Azure resolver: per-team client secret の SSM SecureString store (Sakura store と同型)、 client_credentials token client、 getCredential、 deps.azure 配線。 REST client (Deployment Stacks) は実装済 (#1410)。
  3. onboarding (#1413): per-team の GCP WIF プール / SA mapping と Azure app registration + secret 登録 UX。
  4. 非 AWS ランタイムの getStatus / destroy / collectOutputs を status / teardown / scoring 経路へ配線。

Alternatives considered

案判定理由
両 provider とも platform-as-OIDC-issuer (RS256 + JWKS) 却下 (現時点) JWKS ホスティング・鍵ローテーション・issuer 運用という独立サブシステムを deployable v1 の blocker にするのは過剰。 Azure の将来アップグレードとして留保する。
GCP も stored key (SA key JSON) 却下 GCP WIF の AWS-native 経路が鍵レスで動くため、 long-lived な SA key を持つのは厳密に劣る。 Google も SA key を非推奨とする。
HS256 JWS をそのまま subject token (プロトタイプの当初想定) 却下 対称鍵のため WIF / Entra の OIDC 検証を通らない。 検証側に共有秘密を渡すことになり信頼モデルが破綻する。

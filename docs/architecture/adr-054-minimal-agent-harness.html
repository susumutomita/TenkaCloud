ADR-054 — Minimal agent harness with verifiable autonomy

Status: Accepted Date: 2026-08-01 Scope: repository agent instructions and local hooks Relates: Principle Registry, Enforcement Registry

TenkaCloud gives coding agents a task, safety boundaries, and a deterministic way to verify completion. It does not require a fixed planning document, a mandatory skill, a fixed set of subagents, or a universal implementation sequence. Always-on prompts and hooks are kept only where they protect a stable product or security boundary.

1. Context

The repository accumulated overlapping controls in CLAUDE.md, AGENTS.md, skills, subagents, path-scoped rules, and hooks. Several controls encoded implementation methods rather than outcomes: mandatory planning files, ordered documentation and refactoring phases, fixed review skills, commit-time full gates, and edit-time formatting or reminder injection.

Those controls were useful responses to earlier model behavior, but each one consumes context or interrupts the work loop on every task. As models and tooling improve, stale compensating instructions can constrain exploration, duplicate CI, and make a legitimate change to a configuration or enforcement rule harder than the underlying product change. TenkaCloud still needs strict tenant isolation, authentication, IAM, cross-plane contracts, supply-chain checks, infrastructure review, and required CI. The distinction is between stable boundaries and temporary implementation guidance.

2. Decision

  1. Keep CLAUDE.md as a small entry point that imports AGENTS.md and points readers to architecture records.
  2. Keep AGENTS.md focused on repository ownership, platform guardrails, verification commands, and PR evidence. Do not prescribe a universal work sequence.
  3. Treat skills and subagents as optional tools. Their use is justified by the current task, not by a completion checklist.
  4. Limit local hooks to secrets protection and pre-execution blocking of clearly destructive shell commands. Do not inject session reminders, require a planning file, auto-format every edit, or run the full repository gate at commit time.
  5. Use tests, type checking, the architecture harness, synthesis, previews, and CI as the closed loop through which an agent can determine whether its change is complete.
  6. Add new steering only after the same failure is reproduced repeatedly and existing deterministic feedback cannot prevent it. Re-evaluate controls after a model or toolchain generation change by first removing the control.

3. Retained and removed controls

Retained Removed from the mandatory path
Tenant isolation, JWT validation, mandatory ExternalId, and least-privilege IAM Mandatory Plan.md and fixed documentation-first sequence
Cross-plane producer and consumer contract checks Mandatory /change, review, security-review, and simplify skills
Architecture harness, tests, type checks, synth assertions, and CI Fixed subagent roles and model-specific orchestration advice
Secret access denial and destructive-command prevention SessionStart, Stop, PreCompact, edit-time, and commit-time reminder hooks
Infrastructure physical-impact reporting and one-time live verification notes Rules that prohibit changing configuration even when configuration is the defect

4. Verification contract

Routine changes run make harness and make before-commit. Changes to dependencies, CI, the harness, cross-workspace contracts, or infrastructure use make ci-local. Infrastructure changes also use make check-synth, CDK template assertions, and the pull request physical impact section.

The most direct evidence is preferred: a regression test for a defect, a contract test for an API boundary, a browser preview for a user-visible change, a synthesized template for infrastructure, or a clearly identified one-time live verification when local evidence cannot establish the external behavior.

5. Consequences

Positive

  • Always-on context becomes smaller and less likely to encode obsolete model behavior.
  • Agents can choose an implementation strategy while remaining inside stable boundaries.
  • Completion is tied to reproducible evidence instead of workflow ceremony.
  • Configuration and enforcement code can be corrected when evidence shows they are defective.

Accepted costs

  • Different tasks may use different planning and test sequences.
  • Local formatting and full gates require an explicit command instead of running after every edit.
  • Optional skills may be used less often and must demonstrate value through observed outcomes.

6. Alternatives considered

Alternative Reason not selected
Keep every existing instruction and hook Preserves duplicated context and old compensating behavior without evidence that every control remains necessary.
Remove all repository guidance Would discard stable product boundaries, security constraints, and the commands needed for self-verification.
Move every rule into a hook Hooks are poor at semantic judgment, interrupt exploration, and duplicate CI when used as general workflow orchestration.

7. Re-evaluation

A new prompt, rule, hook, skill, or subagent becomes mandatory only when a repeated failure has a reproducible example, cannot be prevented by an existing test or gate, has a narrow scope, and includes a way to measure whether the added steering improves outcomes. Saturated or redundant controls are removed rather than preserved for historical reasons.
This ADR governs repository agent steering. It does not weaken TenkaCloud's product security, infrastructure, tenancy, supply-chain, or required CI contracts.

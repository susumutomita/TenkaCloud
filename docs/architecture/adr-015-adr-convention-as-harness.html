ADR-015: ADR convention を harness invariant に格上げする

HTML 正本 + self-contained 規約を repo 同梱の機械検査に閉じ、 別 contributor / 別エージェントセッションでも自然と守れる状態にする

Status:Accepted 2026-05-15
Tracking: #763
Related: ADR-007、 ADR-010、 ADR-012、 harness.md

Context

TenkaCloud は docs/architecture/ 配下に手書き HTML の ADR (= Architecture Decision Record) を蓄積している。 ADR-001 から ADR-014 までに、 problem deploy CRUD、 cross-account federation、 problem plugin architecture、 EventBridge 駆動 reconciliation など、 SaaS 基盤の主要な設計判断が記録されている。

この ADR 群には 2 つの暗黙の運用ルールがあった。

  1. ADR は HTML で書く — Markdown ではなく手書き HTML を正本にし、 row span / color / SVG / collapsible / decision card grid などの表現力を使って判断と影響範囲を読みやすくする。 docs 全体の SSG (scripts/build-docs.ts) は ADR を上書き対象から除外して、 ADR HTML は build artifact ではなく source として扱う。
  2. ADR は self-contained に書く — chat session の文脈 (今回 / 本タスク / このターン / 先ほど)、 段階反映 metadata (順次反映 / Phase X.Y で書く / あとで追記)、 AI agent との役割分担メモ (Claude 担当 / user 担当) を本文に残さない。 OSS readers が ADR 単体で背景・判断・影響を理解できることを基準にする。

この 2 ルールは、 これまで repo owner の personal memory (~/.claude/projects/.../memory/feedback_design_docs_html.md および feedback_adr_self_contained_oss.md) にのみ存在していた。 結果として次の問題が起きていた。

症状例
memory を持たない contributor / セッションが MD で ADR を書きうる別環境の AI agent が docs/architecture/adr-015-foo.md を提案して PR を出す。 SSG が touch しないため build は通り、 reviewer が指摘するまで HTML 正本ルールに気づかない。
chat 痕跡が ADR に持ち込まれて累積するadr-002 / 006 / 009 / 013 に Claude 担当 / user 担当 の役割分担メモが残存。 OSS readers にとって意味不明な metadata が決定文書に混入する。
規約を CLAUDE.md / AGENTS.md にも書いていなかったcodebase 内に正本がなく、 memory 同期できないツールチェーン (Codex CLI / Cursor 等) が違反を再生産する。

制約

制約影響
Cost 0 原則 (Free Tier 内運用)追加の SaaS linter / cloud build service を要求しない。 ローカル + GitHub Actions 内で完結させる。
既存 PR Discipline (INVARIANT_PR_*)harness 実行は staged ファイル限定で fast に保ち、 make before-commit ゲート前に走らせて開発体験を壊さない。
既存 ADR を 1 PR で全部書き直さない14 本ある既存 ADR の本文を一括で修正するのは scope 過大。 既知違反は baseline で suppress し、 新規 regression のみを落とす。
ADR HTML の表現力を維持するSVG / decision card grid / collapsible <details> を活かす想定なので、 純テキスト変換 (Markdown 経由 SSG) には戻さない。

Decision

Accepted: ADR convention (HTML 正本 / self-contained) を harness invariant に格上げし、 repo 同梱の機械検査と CLAUDE.md / AGENTS.md による明文化の 2 段構えで強制する。

D1
adr-must-be-html rule
docs/architecture/adr-*.md が staged または tracked にあると error を出す。 ADR は HTML 手書き正本だけを許容する。
D2
adr-self-contained rule
docs/architecture/adr-*.html 本文中の chat 痕跡 / 段階反映 metadata / 役割分担メモを行単位で error にする。 <pre> / <code> 引用ブロック内は除外する。
D3
既存違反は baseline 化
.claude/harness/baselines/adr-self-contained.json に既知違反 (ruleId / filePath / line / match) を列挙する。 baseline に載っている finding は harness が suppress し、 新規 regression のみが落ちる。
D4
CLAUDE.md / AGENTS.md にも明文化
memory 非保持の contributor / エージェントセッションにも規約が届くよう、 codebase 内に正本を置く。 機械検査と人間 review の両側で強制する。

D1: adr-must-be-html

新規 ADR を MD で起こすこと自体を禁止する。 検査は単純な path match で、 docs/architecture/adr-[a-z0-9-]+\.md に該当する staged / tracked ファイルがあれば error を返す。 例外は docs/architecture/harness.md のみで、 これは invariant の source-of-truth であり ADR ではないため対象外とする。

検査が走るタイミングは次のいずれか。

  • make harness (= --staged --fail-on=error) — pre-commit hook と PR ゲートから呼ばれる。
  • make harness-test — rule そのものの unit test (vitest) を走らせる。
  • full scan モード (--staged 省略) — CI で全 tracked ファイルを scan する保険として残す。

D2: adr-self-contained

ADR HTML 本文を行単位で走査し、 chat session 文脈や段階反映 metadata に該当する正規表現にマッチする行を error として報告する。 検出パターン群は次のとおり。

カテゴリマッチ語の例禁止理由
時間的指示語今回 / 本タスク / このターン / 先ほど / さきほどADR は時間軸を持たない決定文書。 「いつ書かれたか」に依存する表現は読者を混乱させる。
chat session 参照このチャット / このスレッドADR は会話 log ではない。 必要な context は本文に取り込む。
段階反映 metadata順次反映 / 順次更新 / あとで書く / TODO: あとで追記 / Phase X.Y で書く未確定状態の ADR を merge する signal になり、 後続 PR が忘れられる。 段階分割は別 ADR / 別 issue に切り出す。
一人称 / 役割分担Claude が書いた / Claude 担当 / user 担当 / 私が決めたOSS readers にとって意味不明な metadata。 ADR は TenkaCloud は X を採用する のような impersonal な決定文体で書く。

引用コード (<pre> / <code> ブロック内) は line-level mask で除外する。 fixture / code example として上記語を引く場面はあるため、 ブロック内の出現は finding にしない。

D3: baseline 機構

既存の 14 本の ADR を 1 PR で書き直すのは scope 過大なため、 既知違反は .claude/harness/baselines/adr-self-contained.json に entry として列挙する。 baseline schema は次のとおり。

{
  "entries": [
    {
      "ruleId": "adr-self-contained",
      "filePath": "docs/architecture/adr-006-notifications.html",
      "line": 601,
      "match": "user 担当"
    },
    ...
  ]
}

harness runner は rule check 結果から ruleId / filePath / line / match が一致する finding を suppress する。 新規 ADR / 既存 ADR の修正で新たに違反を入れた場合は baseline に載っていないため finding が落ちる。 baseline entry の削除方向 (= 既存違反を本文修正で消す PR) は許容するが、 追加方向 (= 新規違反を baseline に逃がす PR) は code review で禁じる。

D4: docs 上の明文化

codebase 内の 2 つの正本ファイルに ADR 規約を書く。

  • harness.md の Enforcement Rules 表に adr-must-be-html / adr-self-contained の 2 rule を追加する。 これにより rule ID と意図が secrets-manager-forbidden / handler-must-not-call-fetch と同じ粒度で参照可能になる。
  • CLAUDE.md および AGENTS.md に ADR 規約 セクションを追加する。 memory にしか書いていなかった HTML / self-contained 規約を、 contributor / エージェント向けの開発フロー文書に格上げする。

Consequences

Positive

  • harness が初めて成立する: 本 ADR 採択以前、 make harness は .claude/harness/bin/architecture.ts が repo に存在せず Module not found で常に落ちていた。 ADR-015 で .claude/harness/ 配下に CLI scaffold + rule registry + baseline filter + vitest 設定を一式持ち込み、 make harness / make harness-test が動作する状態になる。 既存の secrets-manager-forbidden / handler-must-not-call-fetch も同じ scaffold に後から追加可能になる。
  • memory 非保持の contributor / エージェントに規約が届く: Codex CLI、 Cursor、 別環境の Claude Code、 human contributor のいずれが ADR を書いても、 make before-commit 経由で同じ規約が適用される。 規約が memory にしか無い状態の脆さが解消される。
  • 既存違反の見える化: baseline JSON が「どこに残存違反が居るか」のインデックスになり、 ADR 本文を修正する PR で 1 entry ずつ削れる。 違反一覧を grep で抜くより accurate に追える。
  • Enforcement Rule 追加の foothold: 今後 architecture invariant や PR Discipline の 機械検査を増やすとき、 ADR-015 が確立した rule 登録 / baseline / 単体テストの pattern に乗せられる。

Negative / Trade-off

  • 正規表現ベースの検出は false positive / false negative がある: 「順次 deploy する」 (= normal 用法) は通すよう regex を狭めているが、 將來に新しい禁止表現が出てきたら pattern 追加 PR を要する。 false positive が起きた場合は文章を書き換えるか、 引用なら <code> 内に置く運用で逃げる。
  • baseline は永続的な技術負債になりうる: baseline に置いた違反を「既知なのでいい」と放置すると、 本来削るべき残骸が ADR に残り続ける。 baseline は新規 PR の足枷を外す回避策であって、 段階的に空にしていく前提で運用する。
  • harness 本体が 1 つの workspace になる: .claude/harness/ は独自 package.json / tsconfig.json / node_modules を持つ。 monorepo の workspaces 一覧には載らないため、 ルート make install とは別に cd .claude/harness && bun install が必要 (= make harness / make harness-test 内で吸収される)。
  • ADR-015 自身も self-contained rule の対象になる: 本 ADR 内に検出パターン語 (今回 / Claude 担当 等) を 説明として 含める必要があるため、 該当部分は <code> でラップして mask 範囲に逃がしている。 同様の self-referential ADR を将来書くときは同じパターンを踏襲する。

Risk

Risk影響緩和策
harness が空白 / 改行 / unicode variant で誤検出する新規 PR が unrelated に落ちるregex を厳格に保ち、 vitest fixture で代表例を pin。 issue が出たら pattern + test を 1 PR で更新する。
baseline JSON のメンテが止まる残存違反が永久に残るtech-debt スキャンの観察対象として baseline entry 数を追跡する。 ADR を修正する PR で entry 削除をセットにする習慣を CLAUDE.md に書く。
新規 ADR を MD で書きたい誘惑adr-must-be-html rule への bypass PR が出るharness を make before-commit ゲートに据え置き、 bypass 不能にする。 CI でも同じ check を走らせる。
harness 自体の bug が ADR PR をブロックするcontributor の生産性低下vitest を unit test として常時 green に保つ。 harness の動作変更は --fail-on=warning 等の段階導入経路を残す。

Alternatives considered

選択肢判定理由
A. docs だけに書いて harness を作らない却下memory の延長と変わらず、 規約を読まない contributor / エージェントには届かない。 reviewer が毎回指摘するコストが残る。
B. external linter (textlint / vale / markdownlint plugin)却下HTML 内の chat 痕跡を高精度で検査できる既製 ruleset は無い。 plugin 化のコストが harness 自前実装と同等で、 baseline 機構を別 tool に外出しすると統制が分散する。
C. pre-commit hook だけで CI には載せない却下local で hook を無効化されると bypass 可能。 GitHub Actions 側でも make harness を再実行することで二重ゲートにする方針と整合しない。
D. .claude/harness/ 配下に CLI + rule registry + baseline + vitest を持ち込む採用既存 secrets-manager-forbidden / handler-must-not-call-fetch の rule 登録先と同じ場所に拡張する自然な経路。 harness 本体を初めて成立させ、 後続の Enforcement Rule 追加にも再利用できる。
E. 全 ADR の本文を 1 PR で書き直して baseline 不要にする却下14 本ある ADR 本文の修正は scope 過大。 reviewer に diff の文脈解読を要求しすぎる。 baseline で suppress しつつ別 PR で削減する方が安全。

Implementation outline

harness scaffold と rule 群は次の構造で .claude/harness/ 配下に閉じる。

.claude/harness/
├── package.json              # 独自 workspace (bun install 対象)
├── tsconfig.json
├── vitest.config.ts
├── bin/
│   ├── architecture.ts       # CLI entrypoint (= make harness が呼ぶ)
│   └── tech-debt.ts          # 将来の tech-debt scanner placeholder
├── src/
│   ├── cli.ts                # 引数 parser + run + formatFindings
│   ├── baseline.ts           # baseline JSON loader + finding suppress
│   ├── types.ts              # Finding / Rule / Severity 型
│   ├── rules/
│   │   ├── index.ts          # rule registry
│   │   ├── adr-must-be-html.ts
│   │   ├── adr-self-contained.ts
│   │   ├── adr-must-be-html.test.ts
│   │   └── adr-self-contained.test.ts
│   └── utils/
│       └── staged-files.ts   # git diff --cached / ls-files wrapper
└── baselines/
    └── adr-self-contained.json

Makefile target との対応は次のとおり。

Make target実コマンド用途
make harnessbun run .claude/harness/bin/architecture.ts --staged --fail-on=errorpre-commit / PR ゲート。 staged ファイルのみ scan する fast path。
make harness-testcd .claude/harness && bunx vitest runrule そのものの unit test。 rule を増減するときに必ず通す。
full scanbun run .claude/harness/bin/architecture.ts --fail-on=errorCI 側で全 tracked ファイルを scan する保険。 staged モードで漏れた違反を catch。

新規 Enforcement Rule 追加手順

  1. .claude/harness/src/rules/<rule-id>.ts に rule 本体を書き、 同階層の <rule-id>.test.ts で fixture を pin する。
  2. .claude/harness/src/rules/index.ts の architectureRules 配列に rule を登録する。
  3. docs/architecture/harness.md の Enforcement Rules 表に 1 段落で rule ID / 検査対象 / 違反理由を書き、 make build-docs で harness.html を再生成する。
  4. CLAUDE.md / AGENTS.md に違反パターンが反映される場合は規約セクションも更新する。
  5. 既存違反がある場合は baseline JSON に列挙する。 entry 削減を別 PR の作業項目として issue で trackable にする。

Rollout

  • PR #770 で harness scaffold と 2 rule、 baseline、 docs 反映を同時 merge する (= ADR-015 と同 PR / 同 rollout unit)。
  • merge 直後から make harness が Module not found ではなくなる。 contributor / エージェントの開発フロー文書 (CLAUDE.md / AGENTS.md) を読んだ時点で規約が伝わる。
  • 既存 ADR の baseline entry 削減は別 PR で 1 entry ずつ進める。 baseline が空になった時点で adr-self-contained rule は新規 ADR / 既存 ADR の修正の両方で完全に効くようになる。
  • 次の Enforcement Rule (= ADR-014 で予告した EventBridge 移行に伴う polling-budget-forbidden 等) を追加する際は、 ADR-015 で確立した手順に従う。

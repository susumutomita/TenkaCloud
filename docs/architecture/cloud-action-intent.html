CloudActionIntent — protocol spec

Status: Phase 1 published Version: tenkacloud.cloud-action-intent.v1 Audience: implementors of cross-cloud authority transfer Relates: Issue #795, ADR-017

1. Purpose

Multi-cloud automation の hard part は「あるクラウドのワークロードが、 別クラウド/別アカウントで cloud action を安全に要求すること」 である。 既存 primitive (OAuth Token Exchange, AWS AssumeRole, GCP Workload Identity Federation, Azure Federated Credential, SPIFFE, OPA/Cedar) はすでに揃っているが、 これらを束ねる higher-level な「cloud action authority transfer」 protocol 層が欠けている。

CloudActionIntent はこの層を埋める最小プロトコル仕様である。 中心原則は次の 1 文に集約される。

Do not move credentials. Move signed intents. Exchange them for short-lived, provider-native authority.

2. Protocol Pipeline

CloudActionIntent → canonicalize (= sorted-key JSON) → sign (JWS compact) → transport (network / queue) → verify (signature) → schema check (strict) → TTL / notBefore check → nonce / replay check → policy evaluation (allow / deny / needs_approval) → provider token exchange (= AssumeRole / WIF / FederatedCredential 等) → cloud action execution → audit record (= 失敗系も含む)

本 spec は上 4 ステップ (canonicalize / sign / verify / schema/TTL/nonce) の wire format を pin する。 policy / provider exchange / audit は本 spec の拡張点として hook 形で開放する (= 各組織が自分の policy engine / provider adapter / audit sink を差し込めばよい)。

4. Canonical Serialization

確定的 byte 表現を作るため、 JSON object の key を lexicographic sort し、 array は順序を保ったまま recurse する。 undefined property は drop、 null は preserve する。 number / string / boolean は JSON.stringify と同等の表現を使う (= JCS RFC 8785 の subset)。

例

{ "b": 1, "a": 2 }                  →  {"a":2,"b":1}
{ "outer": { "z": 1, "a": 2 } }     →  {"outer":{"a":2,"z":1}}
[3, 1, 2]                           →  [3,1,2]
{ "a": 1, "b": undefined }          →  {"a":1}
{ "a": null }                       →  {"a":null}

確定的表現の用途は (1) JWS payload の byte 一致を保証すること、 (2) audit log の hashing を再現可能にすること。

5. Wire Format (JWS Compact)

CloudActionIntent は JWS compact serialization (RFC 7515) で transport される。 形式は <header>.<payload>.<signature> の 3 part dot-separated base64url。

5.1 Header

{
  "alg": "HS256",        // Phase 1 は HS256 のみ、 Phase 2 で ES256 / RS256 を追加
  "typ": "JWS",
  "kid": "key-001"        // optional (= rotation 時の鍵識別)
}

5.2 Payload

Section 4 の canonical serialization 出力 (= sorted-key JSON) を UTF-8 → base64url する。 verifier 側は payload を decode して再 parse してから schema check に通す。

5.3 Signature

HMAC_SHA256(secret, "<header_b64>.<payload_b64>") を base64url 表現で。 verifier は同じ計算をして timingSafeEqual で照合する (= side channel 防御)。

6. Verification Order

verifier は必ず次の順序で検査を進める。 途中で fail したら以降は実行しない (= short-circuit)。

順stepfail 時 reason
1token 形式 (= 3 part) checkjws-malformed
2header parse + typ === "JWS"jws-malformed
3alg whitelist 照合jws-unknown-algorithm
4secret resolve (= kid 等から鍵を引く)jws-secret-not-resolved
5signature 検証 (timingSafeEqual)jws-signature-mismatch
6payload base64url decode + JSON parsejws-payload-parse-failed
7schema strict check (= section 3)schema-invalid
8expiresAt > nowexpired
9notBefore ≤ now (省略時 pass)not-yet-valid
10nonce store record (= 重複 reject)nonce-replay
11policy 評価 (= 拡張点)policy-deny / needs-approval

step 11 (policy) より前で fail した場合も、 audit record は必ず生成する (= attacker による fuzzing を後追い分析可能にする)。

7. Threat Model

Token replay

同じ token を 2 回 verify されないよう、 nonce store で (tenantId, nonce) の重複を reject。 store TTL は expiresAt + 安全マージン。

Confused deputy

verifier は intent の target.provider / target.providerAccountRef を必ず policy decision に渡し、 別アカウントの credential を payload と紐付けて発行することを禁ずる。

Over-broad provider scope

policy 側で requestedScopes を element 単位に allowlist 照合。 ワイルドカード scope (*) は allowPrivilegeEscalation: true を必須にする。

Tenant boundary escape

nonce store / audit sink は tenant 単位に partitioned。 verifier は source.tenantId と caller principal の tenant claim を必ず照合する。

Leaked signed token

短 TTL (= 上限 1 時間) で blast radius を抑える。 鍵 rotation は kid 経由。 emergency revocation は nonce store に negative cache (= explicit deny) を入れる方法を recommend。

Malicious template / module

policy 側で template / module の risk analysis を実施する hook を expose。 specific: CFn template scan / Terraform plan diff / Pulumi preview。

Destroy without context

action.type === "destroy" は source.deploymentId の存在を必須化することを recommend。 reproducible context が無い destroy は policy で reject。

Schema drift attack

schema check は strict mode (= 不明 property reject)。 attacker が将来 field を仕込んで未来版で reinterpret される攻撃を防ぐ。

9. Audit Record

すべての decision に audit record を生成する。 失敗系も同じ shape で記録し、 attacker の fuzzing を後追い分析可能にする。 

{
  "requestId":   "req-001",
  "tenantId":    "tenant-a",
  "eventId":     "event-001",        // optional
  "teamId":      "team-alpha",       // optional
  "problemId":   "hello-world",      // optional
  "deploymentId": "deploy-9",        // optional
  "targetId":    "endpoint-main",    // optional
  "provider":    "aws",
  "action":      "deploy",
  "decision":    "allow" | "deny" | "needs_approval",
  "denialReason": "expired",         // only when decision !== "allow"
  "issuedCredentialExpiresAt": "2026-05-15T20:00:00.000Z", // only when allow
  "policyVersion": "policy-v1",      // optional
  "createdAt":   "2026-05-15T19:30:00.000Z"
}

10. Non-Goals (= This Spec Does NOT...)

非 goal理由
OAuth / OIDC / JWT を replace すること本 spec は higher-level な「cloud action authority transfer」 protocol。 OAuth / OIDC は workload identity の wire layer であり、 本 spec はその上の semantic layer を埋める
SPIFFE / SPIRE を replace することSPIFFE は source.workloadId field の供給源として活用される (= 競合せず compose)
custom cryptography を導入することJWS (RFC 7515) + 既存 HMAC / ECDSA / RSA を使う。 spec 全体で「no custom crypto」 原則を守る
universal standard を直ちに主張することPhase 1 は TenkaCloud 内部での testable / reusable な最小実装。 real use case で abstraction が proven されたあとで standard 化を議論する
full policy engine を内蔵することpolicy 評価は hook のみ。 inline allowlist / OPA / Cedar / tenant policy doc / template risk analysis は呼び出し側で組み立てる

11. Versioning

version field は literal tenkacloud.cloud-action-intent.v1。 将来の breaking change は新 literal (例: v2) で出荷し、 schema は oneOf で discriminate する (= TS 側の discriminated union + zod の z.discriminatedUnion)。 v1 / v2 が共存する期間は短くする (= 6 ヶ月以内)。

12. Reference Implementation

TenkaCloud 内 reference 実装は packages/trust-bridge (= @TenkaCloud/trust-bridge) に置く。 Phase 1 (= 本 spec が pin する範囲) は次を export する。

  • CloudActionIntentSchema (zod strict)
  • canonicalize(value)
  • parseCloudActionIntent(raw)
  • signIntent(intent, options) / verifySignature(token, options)
  • verifyIntent(token, options) (= JWS → schema → TTL → nonce 全部)
  • NonceStore interface
  • buildAuditRecord(input)

Phase 2 で AwsAssumeRoleExchange adapter を、 Phase 3 で tenkacloud-deploy backend への internal integration を、 Phase 4 で GCP / Azure adapter prototype を追加する。

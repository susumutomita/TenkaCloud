ADR-005: Battle 形式 Portal UI を「攻撃の有無は見える、原因は隠す」3 タブで設計する

Status:Proposed 2026-05-09
Issue: #501, #164
Related ADR: ADR-002 (federation)、 ADR-004 (Event/Team)
Memory: project_battle_challenge_hybrid

Context

Phase 2c までの Participant Portal は Challenge 形式 (= flag 提出 / 1 回限り採点) を前提に設計されており、ProblemDetail / Scoreboard / ScoreEvents の 3 画面で完結していた。 Battle 形式 (= uptime 攻撃防御、時間軸で勝敗が動く) の問題が運用上 1 件 (hello-world-battle、security-battle-royale) 立ち上がった一方で、 Battle に固有の「自チームへの攻撃が今どう進行しているか」「どの程度耐えているか」という 時間軸情報を見る UI は未整備。

本 ADR を駆動する制約は次のとおり。

制約由来本 ADR への影響
Game balance: 防御側自身が壊れている原因を調査して回復する lookup.ts:38-40 既存決定 「どの endpoint が 503」と教えるとゲーム性破壊 → 隠す
観戦者体験: Scoreboard で他チームの状況も見たい運用想定 aggregate (uptime%) は OK / 内部状態は NG
polling over SSELambda は long-lived connection を持てないため、 real-time 更新は polling で実装する設計原則 real-time は polling、SSE 不使用
DDB は 1 RCU/1 WCU PROVISIONEDコスト最小化の設計原則。 全 DDB table を DynamoDbLowCapacity Aspect で強制 新 DDB は立てない方向
Battle / Challenge は完全分離しないBattle 内部に Challenge 風 sub-quest を持つ問題があり、 scoring / flag / UI を共有する設計 ProblemDetail に Tabs 追加で対応、別画面化しない

現状

項目現状
攻撃ログの保存health-check-handler が deployment 行の endpointsHealth JSON を毎 tick 上書き。timeline は残らない
score event の保存Deployments テーブルの SCORE#<eventId>#<jobId>#<ulid> row として残る (shared/score-event.ts)。再利用可能
Portal 側 UIProblemPanel が flag 提出フォームを出すのみ。Battle 専用表示は無い

解くべき設計判断

D1. per-endpoint health の見える粒度

防御側のゲーム性を保つため、per-endpoint の OK/NG breakdown は participant に出さない。 ただし「攻撃が成功した / していない」「現在 healthy か劣化中か」程度の aggregate 情報は出す (= 防御側に「いま自分が攻撃を受けている」自覚を与えるため)。

見せる 見せない
情報判断備考
全 endpoint OK か (boolean)見せるProblemPanel の Status バッジで
健全 endpoint 数 / 全 endpoint 数見せる3 / 5 風に
どの endpoint が NG か (名前 / URL)隠す原因を Portal で答え合わせさせない
直近 N 分の uptime ％見せるaggregate なのでゲーム性に干渉しない
攻撃検知時刻 (= lastResult=fail 遷移)見せる「いま攻撃を受けた」自覚は OK
攻撃元 (= 誰が攻撃したか)隠す観戦者にも非公開、Battle = 公平試合

→ Decision 1 は 「aggregate のみ可視化、per-endpoint は隠す、攻撃元は隠す」。

D2. 攻撃 log の保存先

3 タブ (Attack Statistics / Application Status / Attack History) すべて時系列データを要求する。 保存場所候補は次のとおり。

案採否内容欠点
D2-A採用 既存 Score Event row を流用 (source: "attack-detected" を追加) 1 試合で row が増える (TTL で expire)
D2-B却下 新 DDB BattleAttackLog 新テーブル運用コスト + DynamoDbLowCapacity Aspect 影響範囲が広がる
D2-C却下 CloudWatch Logs に書いて Insights で query 料金 / 整合性 / latency が劣る、Portal 側との結合が重い
D2-A を採用する 3 つの理由
  1. 既に Score events 画面 (/score-events) が同テーブルを polling している。Battle の attack timeline は「種別: 攻撃検知」として混ぜれば 1 source of truth。
  2. 新 DDB を立てない (DynamoDbLowCapacity Aspect の影響範囲を増やさない、コスト 0 維持)。
  3. Score event の expiresAt TTL に乗るので自動削除されて運用コスト低い。

実装上は shared/score-event.ts の source フィールドに "attack-detected" を追加する。

D3. 3 タブの表示粒度 / 配置

issue body の 3 タブ案を維持しつつ、D1 に従って粒度を絞る。タブ切替は ProblemDetail 画面の中の Cloudscape Tabs で実現。Challenge 形式問題ではタブを表示せず ProblemPanel のみ (= 既存挙動)。

TAB 1
Application Status
  • 「全 endpoint healthy」「一部劣化」「全停止」の 3 状態 Badge
  • 直近 5 分の uptime ％ (= 5 分内の score event success / total tick)
  • per-endpoint は出さない
TAB 2
Attack Statistics
  • 直近 1h の「攻撃検知回数 (= fail tick の回数) / 防御成功 tick 数 (= ok tick の回数)」の 2-line graph (Cloudscape LineChart)
  • 5 分粒度 bucket、source: "attack-detected" を集計
  • per-endpoint breakdown は出さない
TAB 3
Attack History
  • Table: occurredAt / 結果 (= 攻撃成功 or 防御成功) / 自動回復までの秒数
  • (uptime 復活時刻 − 攻撃検知時刻) を回復秒数として併記
  • 攻撃元 / target endpoint は出さない

D4. real-time 性 / polling 間隔

feedback_polling_over_sse に従い SSE / WebSocket は使わない。 backend の tick が rate(1 minute) なので、frontend polling も 1 分間隔に統一する (= 5 秒 polling は over-polling で Lambda 呼び出し回数 / DDB RCU を無駄に消費する)。

層tick / 間隔根拠
backend HealthCheck LambdaEventBridge rate(1 minute) 既存。コスト最適 (= 60 deployment × 1/min × 1 月で Lambda free tier 内)
frontend TeamViewProvider60 秒 polling backend tick と同じ粒度。data 更新頻度に揃えて余分な負荷を避ける。Phase 3.1 の PR で 5s → 60s に変更 (= 既存 PR-509 の調整)
frontend BattleAttackPanel (新)60 秒 polling attack timeline は data update 頻度が低い (1 attack/5 分想定)。team view と同じ tick で十分。専用 polling を立てるが間隔は同じ

UX trade-off: 攻撃検知から画面反映までの最大ラグは backend tick (最大 60s) + polling (最大 60s) = 約 2 分。 Battle のゲーム性 (= 「気づいて調査して直す」) はもともと数分単位なので、この遅延は許容範囲。 逆に過剰な polling は (a) 観戦者多数のとき DDB RCU を圧迫、(b) 試合中の Lambda 呼び出し 回数を増やして Free Tier を消費する、というデメリットの方が大きい。

  • 既存 TeamViewProvider の polling 間隔を 5s → 60s に変更 (Application Status の uptime ％ も 60s で十分)
  • Battle 系 deployment が 1 つでもある team は 追加 polling として attack log を 60 秒で fetch (= team view と同 tick だが endpoint は別系統)
  • 新 endpoint: GET /portal/me/battle-attacks?jobId=<ulid>&sinceMin=60

D5. 観戦者向けの leaderboard 表示 (撤回)

撤回 当初は Scoreboard に「直近 5 分 uptime ％」列を 追加することを検討したが、UI モックアップ (Mockup 2) を見たユーザー判断で撤回。理由:

  • 他チームの uptime ％ は aggregate でも攻撃側へのヒントになる (例: uptime 42% = 「あの team は今攻撃が刺さってる」「自分の攻撃も同じ脆弱性で通るかも」が読める) → D1 の「攻撃元 / 内部状態は隠す」原則と 整合性が弱い
  • 自チームの uptime は ProblemDetail の Application Status タブで十分確認できる (= Scoreboard に同じ情報を持つ動機が薄い)
  • Scoreboard は「rank + score」というシンプルな勝敗表示に専念する方が混乱が少ない

結果として Scoreboard は 既存仕様のまま (順位 / チーム / Score) とし、 本 ADR では Scoreboard を変更しない。

API 設計

本 ADR で新設 / 変更する HTTP API を以下に定義する。すべて Participant Portal Lambda (Function URL、AuthType=NONE、bearer は teamLoginKey) に乗せる。Cognito JWT 経路は別系統 (operator UI) なので本 ADR では触らない。

新設 API

GET /portal/me/battle-attacks 新規 — Phase 3.1 で追加

自チームの 1 deployment における attack-detected event の時系列を返す。 ProblemDetail の Attack Statistics / Attack History タブが poll する。

Backend 実装

  • auth: 既存の queryTeamItems で teamLoginKey → deployments を引き、jobId が含まれることを check (= 自 team の deployment かを保証)

API GW / Function URL の routing 変更

Participant Portal Lambda は Function URL (AuthType=NONE) で公開され、内部 Hono が path で route する。新 endpoint /portal/me/battle-attacks は Hono の app.get 配線のみで完結し、CDK 側 (API GW) の resource 追加は不要 (= Function URL は path-prefix でなく path-pattern なし、すべて Lambda にプロキシされる)。

IAM の ParticipantPortalLambda Role に必要なら DDB Query 権限を 追加する (= 既に SCORE# prefix を読む score-events handler が持っているはず、 追加変更不要を期待。Phase 3.1 の PR で確認)。

Migration

Phase 3.1 (本 ADR 実装の最初の PR、scope 中)
  1. shared/score-event.ts に source: "attack-detected" を追加
  2. health-check-handler で lastResult=fail 遷移時 (= 直前 tick が ok だった場合) に attack-detected event を 1 件書く。連続失敗 tick では重複 write しない (= row 爆発防止の hard guard)
  3. lookup.ts の endpointsHealth を aggregate (= ok count / total / overallStatus) に絞った view を新設、participant API でこちらを返す
  4. GET /portal/me/battle-attacks?jobId=&sinceMin= Lambda route + ParticipantPortalLambda の IAM に必要なら Query 権限を追加
  5. sinceMin の上限は 60 分とし、defaults は 30 分。Battle UI の uptime ％は「直近 5 分」、attack history は「直近 60 分」を最大として固定 (= read RCU 暴発の防止策)
  6. TeamViewProvider (PR-509) の polling 間隔を 5s → 60s に変更 (D4)。1 行差し替え + 既存テストの interval 期待値を更新

追加するテスト

  • health-check-handler が ok → fail 遷移時に attack-detected event を 1 件のみ 書く (連続 fail tick で重複しない)
  • lookup.ts の aggregate view に endpointsHealth 内の URL / endpoint 名が含まれない (snapshot test)
  • GET /portal/me/battle-attacks が jobId / sinceMin で正しい SCORE#<eventId>#<jobId> を Query (mock DDB)
  • sinceMin > 60 を渡すと 400 (= clamp ではなく reject、operator が UI で渡す前提)

Phase 3.3 (運用ガイドライン)

Consequences

Positive

  • 防御側のゲーム性 (= 自分で調査) を維持しつつ、「攻撃を受けている」自覚は与えられる
  • 新 DDB を立てない (D2-A) ので運用コスト 0 維持 (DynamoDbLowCapacity Aspect の影響範囲が広がらない)
  • Challenge / Battle で Portal の base layout が同じ (= ProblemDetail に Tabs が増えるだけ) で UX 一貫性
  • Scoreboard に uptime ％ を出すことで観戦者にも盛り上がる viewing 要素ができる

Negative

  • LineChart 表示は Cloudscape LineChart を新規 import するので bundle が少し増える
  • 「per-endpoint visibility 禁止」を強く守る必要があり、handler の view 変換ロジックで漏れがあると即ゲーム性破壊。lookup.ts の変換層を test で固める必要

Capacity 見積もり

D2-A (Score Event row 流用) で row 爆発を防げるかを定量的に押さえる。

項目値根拠
典型 Battle 試合の長さ1 〜 2 時間運用想定
HealthCheck tick1 分health-check-lambda.ts:21 rate(1 minute)
attack-detected event を書く頻度1 deployment × 1 attack あたり 1 件のみPhase 3.1 hard guard: ok → fail 遷移時のみ書く。10 分連続 fail でも 1 件
典型攻撃の頻度1 deployment 1h 内 5 〜 10 attack 想定運用想定 (大規模競技でも uptime% を意味のある値に保つ前提)
1 event 規模 (FR-1 想定)25 teams × 1 〜 2 Battle problem = 25 〜 50 deployments1 event の Battle 系 deployment 数
1 event での総 attack-detected event250 〜 500 行50 deployments × 10 attack/h × 1h
row size~1 KBjobId / problemId / source / occurredAt / metadata だけで小さい
Query (60 分分、1 deployment) のサイズ~10 KB (10 events × 1KB)個別 deployment scope の Query は team scope で絞る
必要 RCU (eventually consistent)2 〜 3 RCU10 KB / 8 KB = 1.25 RCU/req、複数 team 同時 polling 想定で safety margin 含む

結論: DynamoDbLowCapacity Aspect の 1 RCU / 1 WCU PROVISIONED でも 典型運用は許容範囲。ただし bursty access (= 25 teams が同時に Scoreboard を開く) で 1 RCU を超えるシナリオはあり得る。 Phase 3.1 で sinceMin 上限 60 分 + Burst Capacity (= DDB の自動 burst credit) 任せ で運用し、実測でスロットルが起きたら GSI を切るか on-demand reads に上げるかを検討する。

Anti-pattern として避けたもの

  • 毎 fail tick で event を書く (= 10 分連続 fail で 10 events) → row 爆発 + 採点誤読 (= 単発 attack なのに高 RCU)。Phase 3.1 で hard guard
  • sinceMin 無制限 → 1 試合の累計 row を Scan 風に読む。Phase 3.1 で 60 分上限

Unknown

  • Battle event の長時間化 (例: 1 日連続) で score event row が deployment あたり 1000 件超える可能性。TTL で expire するが、Scan する handler 側でページネーション再確認が必要 (= Phase 3 の PR で計測してから判断)

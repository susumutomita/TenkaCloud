ADR-055 — Docker-only participant local mode

Status: Accepted Date: 2026-08-07 Issue: #2906 Supersedes: none

Participant local play (make local) ran the scoring API and the Participant Portal as host Bun/Vite processes, with only the per-problem challenge containers on Docker. A non-engineer field tester on macOS needed five recovery steps — a missing Bun, a Homebrew/Xcode install failure, a second manual make install — to reach a product whose problems already run entirely in Docker. This ADR moves the control plane (API + Portal) into a container too, so the participant path needs only Docker Engine and Docker Compose v2 on the host.

1. Context

scripts/tenkacloud-local.ts already delegates each problem's challenge surface to Docker Compose (scripts/local-play/docker-adapter.ts). The control plane around it — the scoring API (scripts/local-play/server.ts) and the Participant Portal (vite dev) — ran directly on the host, so a Docker product still required Bun, Node, and a full workspace node_modules install before a participant reached anything. Issue #2907 and PR #2912/#2913 fixed the immediate onboarding-instruction drift (self-healing make local, an official Bun installer instead of Homebrew) but left the underlying dependency in place, as apps/participant-portal/src/auth/local-onboarding-contract.ts already noted: "Participant-facing fresh-clone contract while local play still needs Bun ... Issue #2906 can replace this one value with the Docker-only sequence."

2. Decision

Containerize the control plane into one image (docker/local-control-plane/Dockerfile) that serves the API and the prebuilt Portal static build from the same Bun HTTP server on one port, orchestrated by compose.local.yaml and a POSIX launcher (scripts/local/docker-launcher.sh) that make local calls. The developer hot-reload path survives unchanged as make local-dev (make local-onboard → Bun/Vite on the host).

2.1 Same-origin API + Portal, and a request-derived runtime-config.json

The Portal's prebuilt dist/ is served as static files from the same server and port as the API (a new portalDistDir option on startLocalPlayServer, active only in the container — the host/dev path is untouched). /runtime-config.json is now a dynamic route built in-process instead of a file the CLI writes and the dev server serves statically — the container has no Vite dev server to serve it. This also collapses the cross-port CORS setup the two-process host model needed into same-origin, with one caveat: the /local/operator/ Origin-header check that a cross-port setup made airtight for every method now relies on the Bearer-token check alone for a same-origin request with no Origin header (a plain top-level GET can omit it). No operator route accepts GET today — pinned by a regression test — and the token check is unconditional regardless, but a future operator GET route must carry the same check explicitly; it can no longer lean on Origin rejection alone.

The dynamic route builds apiBaseUrl from the incoming request's own Host / X-Forwarded-Proto headers, not a fixed http://127.0.0.1:<port> computed once at startup. Same-origin serving means whatever origin just successfully answered this GET is, by construction, an origin the browser can already reach — 127.0.0.1:<port> for a plain local run, or a reverse proxy's forwarded HTTPS origin (GitHub Codespaces' port forwarding) when one sits in front. The old two-port host/dev model needed a Codespaces-specific /__tenkacloud-local-api proxy-prefix rewrite (codespaces-links.ts) to reach a different port than the Portal's; the container has no second port to reach, so that rewrite does not apply here and is not used on this path. Codespaces' own forwarded-Origin CORS check (cors.ts) still needs CODESPACE_NAME / GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN passed through from the host shell (compose.local.yaml) — a separate concern (validating the browser's incoming Origin) from what URL the config hands back.

2.2 Network reachability: a container's own 127.0.0.1 is not the host's

A per-problem sibling container publishes its challenge surface and /verify to the HOST's loopback (docker-adapter.ts, e.g. 127.0.0.1:18080:8080) — unchanged, and correct for the participant's browser, which runs on the real host. But orchestration calls the control-plane container makes to that same address — readiness polling (docker-adapter.ts's waitForReachable), flag submission (verify-client.ts), and the workbench/terminal proxy (workbench-client.ts) — originate from inside the control-plane container now, and a container's 127.0.0.1 is its own network namespace, not the host's. Docker's sibling-container pattern does not implicitly share loopback between a DooD controller and what it starts; this is a distinct hazard from §2.3's daemon-side path problem, on the network axis instead of the filesystem axis, and an earlier draft of this design missed it entirely — caught by adversarial review before merge.

An earlier draft tried host.docker.internal (extra_hosts: host.docker.internal:host-gateway on Linux Engine) with a containerReachableUrl(url) rewrite at those three call sites. A second adversarial audit pass rejected it: a per-problem sibling container publishes its port bound specifically to the HOST's 127.0.0.1, not 0.0.0.0 — a deliberate security choice (the challenge surface must not be LAN-reachable) — and on native Linux Docker Engine (including GitHub Codespaces' docker-in-docker) a loopback-bound publish is unreachable from any other network namespace, gateway IP or not. That is not a missing route; it is what binding to 127.0.0.1 instead of 0.0.0.0 is for. host.docker.internal would have worked only on Docker Desktop, silently failing on exactly the Linux Engine / Codespaces path this project's own dev environment uses.

The fix actually shipped: network_mode: host on the control-plane service (compose.local.yaml) puts the container directly in the host's network namespace, so its 127.0.0.1 genuinely is the host's — restoring the exact relationship the pre-#2906 host Bun process had, rather than routing around a namespace boundary. This made containerReachableUrl and the TENKACLOUD_LOCAL_BIND_HOST-gated rewrite in scripts/local-play/loopback.ts unnecessary — removed entirely, along with the matching call sites in docker-adapter.ts's waitForReachable, verify-client.ts, and workbench-client.ts; those now dial the already loopback-validated URL unmodified, same as the host/dev path. The server's own listener bind stays hardcoded to 127.0.0.1 (not configurable) precisely because host networking is in play: binding 0.0.0.0 here would leak the control-plane API onto the LAN once this container's network stack is the host's. Host networking requires Docker Desktop >=4.34 on macOS/Windows (it was Linux-Engine-only before that); it is native on Linux Engine and WSL2's Docker Engine, including Codespaces. It adds no privilege beyond what §2.3's Docker-socket mount already grants — a process holding docker.sock could start a --network host sibling itself regardless. The browser-facing URLs shown in the Portal (challengeEndpoints, verifyUrl as displayed) are unaffected either way — the browser was never inside Docker and always dialed the real host-published 127.0.0.1 address.

Docker Desktop host networking is opt-in, not automatic. A third adversarial audit pass on this fix flagged that Docker Desktop (macOS/Windows) requires enabling host networking once, under Settings → Resources → Network (Desktop >=4.34) — unlike Linux Engine and Codespaces, where it needs no setting. When it is not enabled, the container still starts, and its own compose healthcheck (which runs inside that same container, so it always sees its own loopback regardless of whether host networking is actually active) still reports healthy — the exact "healthy but unreachable" false success this ADR's other guardrails (§2's overall goal of not converting failure into a silent green light) exist to prevent. scripts/local/docker-launcher.sh's host_reachable() now probes /healthz from the HOST side (using whichever of curl/wget happens to be present — best-effort only, neither is a stated prerequisite) immediately after the container reports healthy; a healthy-but-unreachable container fails make local/make local-status loud with the exact Settings path to fix, instead of printing a Portal URL nothing can load. README/README.ja/docs/local-play.md now document the Desktop version floor and setting up front, so an affected participant reads it before hitting the failure at all.

2.3 Docker-outside-of-Docker for sibling problem containers

The control-plane container still needs to start/stop per-problem containers — the exact same docker compose shell-out (scripts/local-play/docker-adapter.ts) the host process already performs today, now issued from inside a container against the host's Docker socket (/var/run/docker.sock bind-mounted in, the standard sibling-container pattern — Portainer, Testcontainers, GitLab's Docker executor use the same approach). The socket is mounted only into the control-plane container, never into the Portal's responses or any per-problem container.

This is not a newly granted privilege — a local participant account able to run make local already has host Docker access, and the host Bun process already reaches that same socket via the same shell-out today. It is a more homogeneous, more automatable path to that same privilege: today's equivalent capability requires an attacker to locate the Docker socket in whatever shape the host happens to expose it; after this change it is always the same fixed mount, reachable by any code execution inside the control-plane container. For a single-user, non-multi-tenant local tool this is judged an acceptable trade against the alternative (below), but it is the honest framing, not "no new risk."

A scoped docker-socket-proxy sidecar was considered and rejected: Compose up/down needs container create/start/stop/remove, network, and volume operations — close to the full Engine API surface — so a proxy narrow enough to matter would also be narrow enough to break problem startup.

2.4 Every relative bind mount in a problem's compose file must resolve on the HOST

This is the sharp edge of docker-outside-of-docker: docker compose running inside the control-plane container resolves a problem's relative volume binds (13 catalog problems have one, including wp-exposed-backup's wpinit init script) to an absolute path from its own filesystem view, then sends that path string to the Engine API — but the daemon on the other end of the socket is a HOST process, and resolves that same string against the host's filesystem. If those two views disagree, Compose does not error; it silently creates an empty directory at the unresolved host path and mounts that instead, so the problem container starts successfully with none of its intended content — a silent failure mode, not a loud one.

The fix: problems/ is bind-mounted into the control-plane container at the identical absolute path it has on the host (docker-launcher.sh passes its own $(pwd)/problems as TENKACLOUD_REPO_ROOT/ TENKACLOUD_PROBLEMS_HOST_PATH), and scripts/local-play/catalog-loader.ts's problemSearchRoots resolves the problems directory from that host-real path instead of the container's own /app when the env var is set. Every path Compose hands the daemon for a per-problem project is therefore already correct on both sides, without touching docker-adapter.ts/container-runner.ts at all.

2.5 problems/ submodule fetch stays host-side

autoInitProblemsSubmodule() shells out to git submodule update --init problems — meaningless inside a container that has no .git history for it. docker-launcher.sh checks and fetches the submodule on the host, with the same consent-before-install UX as make local-onboard, before ever starting the container. .gitmodules is excluded from the image build context (.dockerignore) so the container-side self-heal path — unreachable in practice — fails its own existence check immediately rather than shelling out to a git that would not work anyway.

2.6 Teardown does not depend on the control plane being alive

make local-down must reclaim every TenkaCloud-owned resource even when the control-plane container already crashed. docker-launcher.sh down therefore runs two independent reclaim paths: a best-effort in-container tenkacloud-local.ts down (the exact existing host teardown logic, unchanged — stops every problem container it has a record of and clears persisted progress) when the control plane can still answer, and unconditionally a host-side sweep by container name (every per-problem container/network is named with the tc-local- compose-project prefix) that reclaims orphans the first path could not reach. The sweep's docker ... --filter name= is anchored (^tc-local-) — Docker's name filter is an unanchored substring match, and an earlier draft's unanchored filter could have force-removed an unrelated host container that merely contained that string (e.g. a participant's own btc-local-node), caught by adversarial review before merge. compose down -v removes the control plane's own named data volume last, so "clear all progress" holds either way. make local-status similarly cannot depend on that same host-oriented state.json the containerized entrypoint never writes — it polls the compose healthcheck via docker inspect instead.

2.7 Pinned, auditable Docker Compose version

The control-plane image fetches a specific Docker Compose release binary (v2.40.2 at minimum) rather than whatever version apk add docker-cli-compose happens to resolve from the base image's package index. CVE-2025-62725 (fixed in 2.40.2, CVSS 8.9) is a path-traversal-to-host-write bug in an OCI-artifact compose feature — and this container's whole job is processing compose files from problems/, a catalog that accepts outside contributions. An unpinned, possibly-vulnerable Compose binary sitting exactly where untrusted compose files get processed is not an acceptable floor.

2.8 Build-time supply-chain hygiene carries over unchanged

The image build runs bun install --frozen-lockfile --ignore-scripts — the same flag make install already requires repo-wide as a standing defense against the mini-shai-hulud-class attack (Flatt Security, 2026-05-12; Bun does not honor npm_config_ignore_scripts or .npmrc's ignore-scripts, so every invocation must set it explicitly). A build step that forgets this flag would quietly reopen a risk this repository already closed.

3. Consequences

  • A participant needs only Git, Make, Docker Engine, and Docker Compose v2 — no Bun, Node, node_modules, Homebrew, or Xcode Command Line Tools.
  • SQLite progress moves from a host bind path to a named Docker volume, surviving container restarts the same way.
  • GitHub Codespaces needs no devcontainer change — Docker-in-Docker is already provisioned in .devcontainer/devcontainer.json.
  • GitHub Codespaces DOES need onboarding-script changes (round 2 audit finding): make local now triggers a real docker compose build (full workspace install + Portal build inside the image) instead of a warm vite restart, which blew through codespaces-start-local.sh's old 120s postStart deadline on a fresh Codespace. Fixed by having codespaces-setup.sh (postCreate) pre-build the image so the postStart build is normally a cache hit, plus raising the deadline to 240s as a margin.
  • The control-plane container holds a Docker socket mount — see §2.2. Accepted for this single-user, loopback-only tool; not a pattern to generalize to any multi-tenant surface.
  • The Docker path fixes the combined API+Portal port (default 5175, overridable via LOCAL_API_PORT) instead of the host path's automatic free-port selection — a `docker compose up` failure on a busy port is loud, not silently avoided.
  • Docker Desktop (macOS/Windows) requires enabling host networking once (Settings → Resources → Network, Desktop >=4.34) — see §2.2. make local/make local-status detect and fail loud on a healthy-but-unreachable container instead of reporting false success, but the manual setting itself cannot be automated from inside the container.
  • Known limitation, this PR: PROBLEM=<id> pre-start (supported on make local-dev) is not yet wired on the Docker path — every problem starts on demand from the Portal. Tracked as follow-up.
  • Known limitation, this PR: the experimental, opt-in TenkaCloud Simulator runtime (cloud/Composite problems, TENKACLOUD_LOCAL_SIMULATOR=1, off by default) stays on make local-dev only. Containerizing a second Docker-socket consumer inside an already-DooD container needs its own design pass, out of scope here.

4. Alternatives considered

AlternativeRejected because
Host-side watcher process polls a file/queue the container writes desired container state to, avoiding the Docker socket mount entirelyReintroduces exactly the "something must run continuously on the host" problem this ADR removes, while adding IPC latency and a new class of race condition (watcher crash, stale command file) — for a local, loopback-only, single-user tool the marginal safety of avoiding DooD does not clear that cost.
docker-socket-proxy sidecar scoping the Engine API surfaceSee §2.3 — Compose's own operation set is already close to the full API; a proxy narrow enough to add real defense is narrow enough to break problem startup.
Bake the entire monorepo into the image at a fixed path (/app) and bind-mount only problems/ thereThis is what broke §2.4 in the first draft of this design (caught by adversarial review before merge) — the daemon-side path mismatch silently produces empty mounts for every problem with a relative bind.
Publish a pre-built, registry-hosted control-plane image instead of building from source on first make localNo registry publishing pipeline exists yet for this repo, and every per-problem image already builds from source on first use — consistent with the existing model. Tracked as a possible follow-up once a release pipeline exists.
A shared user-defined bridge network with container-name DNS instead of host networking, for §2.2Would require every one of the ~60 catalog problems' compose files to additionally join that network and would need dual addressing (container-DNS for internal orchestration, host-published-port for the browser) instead of one network-mode change on one service. Also does not fix the underlying issue: problems still publish to the HOST's 127.0.0.1 by design, which a bridge network does not reach either.
host.docker.internal + extra_hosts: host-gateway, for §2.2 (tried first, shipped, then reverted after a second adversarial audit)Works on Docker Desktop only. On native Linux Docker Engine — including this project's own GitHub Codespaces dev environment — a port published bound to 127.0.0.1 is unreachable from any other network namespace regardless of gateway routing, so the "fix" silently no-opped on exactly the platform this repo develops on. network_mode: host fixes the actual cause (separate network namespaces) instead of adding a route across them.

5. Migration

  • LOCAL_ONBOARDING_COMMANDS (apps/participant-portal/src/auth/local-onboarding-contract.ts) is the single source of truth for the fresh-clone sequence; README.md, README.ja.md, docs/local-play.md, and the onboarding drill fixture are pinned to it by tests.
  • No data migration: local-play state is ephemeral participant progress with no server-side record, so a fresh named volume on first make local is equivalent to any other local-play reset.
  • Rollback is a plain revert — zero CloudFormation diff, zero AWS resources, no shared/production system touched.

6. Non-goals

  • Removing the developer Bun/Vite path — make local-dev stays.
  • Converting CI or the build system to Docker-only.
  • Changing AWS Lite/SaaS execution.
  • Auto-installing Docker itself.
  • Native Windows support (WSL2 + Docker Desktop only, matching the platform's existing WSL2-only Windows story).

7. Unverified in the authoring environment

This ADR's design was authored and unit-tested in a sandboxed session with no Docker Hub registry access (an intentional network policy, not a defect), so the following are one-time verifications pending, not claims of having been exercised:

  • An actual docker build of docker/local-control-plane/Dockerfile and a full docker compose up against it (GitHub Actions runners have Docker Hub access; a CI-facing check exercises this even though this session could not).
  • A live fresh-clone run on macOS, Linux, and WSL2 with no Bun/Node/node_modules present.
  • Highest priority: starting one full problem (e.g. the pinned intro drill) through the Docker path end to end — readiness, challenge-surface load in a real browser, and a real /verify submission — confirming §2.2's network_mode: host fix actually lets the control-plane container reach a sibling container's 127.0.0.1-published port on a real Docker daemon, not just that docker compose config resolves the expected YAML shape in a unit test. This gap was caught only on a second Fable adversarial-audit pass, after a first fix (host.docker.internal + extra_hosts) had already shipped and later turned out to be Docker-Desktop-only — a reminder that this item stays highest priority until it is exercised against a real daemon, on Linux Engine specifically, not just Docker Desktop.
  • End-to-end play of a relative-bind-mount problem (e.g. wp-exposed-backup) through the Docker path specifically, confirming §2.4's fix in a real daemon, not just docker compose config's static interpolation.
  • That network_mode: host genuinely behaves as documented on Docker Desktop >=4.34 (macOS/Windows) as well as Linux Engine — this session can only confirm the compose file's shape, not runtime behavior on any platform.
  • That Docker Desktop's host-networking opt-in setting (Settings → Resources → Network, §2.2) is accurately described — this session's knowledge of Desktop's exact UI path and version floor is unverified against docs.docker.com (blocked by this session's network policy), and, more importantly, that docker-launcher.sh's host_reachable() post-check actually fires and shows the right message on a real Desktop install with the setting off, rather than just passing its unit tests against a mocked reachability probe.
  • That the Codespaces postCreate image pre-build (round 2 fix for the build-time-vs-120s-deadline gap) actually keeps codespaces-start-local.sh's postStart build a fast cache hit on a real fresh Codespace — this session confirmed the code paths and updated the deadline, but has no way to time an actual Codespaces container lifecycle.
  • A live GitHub Codespaces run confirming the request-derived runtime-config.json (§2.1) and the passed-through CORS env vars actually let the forwarded Portal reach the API with no manual step.
  • A live run with LOCAL_API_PORT overridden away from its default, confirming the CORS fix in cors.ts/server.ts (round 2 audit warning: the allowlist previously hardcoded port 5175, which would have silently rejected same-origin POSTs under a non-default port in container mode) actually passes end to end in a browser — unit-tested in this session (local-play-server-cors.test.ts), but not exercised against a real running container.

ADR-013: Disruption Phase 2 — condition-triggered runtime disruption

platform が観測条件で sub-second に disruption を trigger する設計

Status: Draft 2026-05-13
Related: ADR-012 (Disruption Phase 1 = self-triggered Scheduler)
Tracking: #615

Context

ADR-012 で確立した Disruption Phase 1 は self-triggered パターン: 問題の template.yaml に bake された EventBridge Scheduler + Disruption Lambda が deploy 時刻 + offset で発火する。 platform は cross-account write 権限を持たず、 全ロジックが競技者 account 内で完結する。

Phase 1 の制約:

  • 静的 timing: 発火タイミングは deploy 時刻 + CFn parameter の固定 offset。 deploy 後に動的変更不可 (= CFn update が要る)
  • 条件に反応できない: 競技者のスコアが伸びすぎたら難度を上げる / 攻撃が止まったら spike を入れる、 のような condition-triggered な disruption を組めない
  • runtime 強度調整不可: operator が runtime に「latency を 200ms → 400ms に」 のような動的調整ができない

これらは Battle のゲーム性を強化する上で重要だが、 ADR-012 では「まず動くものを ship する」 ため Phase 1 (self-triggered) で MVP 化し、 condition-triggered は本 ADR で扱う方針にした。

Goals

  1. observation → action loop: platform scoring Lambda が観測条件 (= 競技者 score / 経過時間 / endpoint health / 任意 CW metric) を検知し、 該当 deployment の disruption を sub-second で発火させる
  2. cross-account 発火: 競技者 account 内の Disruption Lambda を、 operator account 側から (EventBridge cross-account bus 経由で) trigger する
  3. runtime 動的 parameter: operator UI から「latency を変える」 「disruption を一時 disable する」 等の調整を行える
  4. blast radius は 1 team 1 deploy: Phase 1 と同じく、 1 競技者 deployment にしか影響しない
  5. fail-safe: platform から trigger できなくなったら自動 fallback で Phase 1 の Scheduler だけ動作する (= 重要 disruption は確定で発火する)

Decision (= 仮)

D1: trigger 経路は cross-account EventBridge bus + Disruption Lambda 直起動

platform 側 scoring Lambda が「発火条件」 を満たすと、 operator account の専用 EventBridge bus (= tc-disruption-trigger) に { detailType: <eventDetailType>, detail: { competitorAccountId, deploymentId, parameters } } 形式 event を put する。 cross-account rule が競技者 account の bus に forward し、 competitor 側の rule が disruption Lambda を invoke する。 disruption Lambda の I/F は Phase 1 と同じ (= 同 Lambda が両 path をサポート)。

metadata disruptions[].eventDetailType は本 Phase で初めて意味を持つ (= Phase 1 では将来枠 placeholder だった)。

D2: 観測条件は scoring Lambda 内 DSL (= metadata 拡張)

metadata.disruptions[].triggers[] を新設し、 観測条件を宣言的に書く:

"disruptions": [
  {
    "id": "ec2-latency-injection",
    "name": "EC2 ネットワーク遅延注入",
    "eventDetailType": "DegradedDisruptionFired",
    "parameters": { "delayMs": 200, "device": "eth0" },
    "triggers": [
      // (a) Phase 1 と同じ self-fire (= fallback)
      { "kind": "after-deploy", "afterMinutes": 60 },
      // (b) 新: condition-triggered
      { "kind": "team-score-above", "threshold": 5000 },
      { "kind": "phase-entered", "phaseName": "degraded" }
    ]
  }
]

scoring Lambda は per-tick で各 deployment の trigger 条件を eval し、 condition 真化のタイミングで cross-account event を put する。 同一 disruption の重複発火は idempotency token (= ${deploymentId}#${disruptionId}) で抑制。

D3: cross-account 信頼境界は EventBridge resource policy

operator account の bus に events:PutEvents を許可する resource policy を、 競技者 account の bus 側に書く。 つまり cross-account から event を流す権利は arn:aws:iam::<operator>:role/TenkaCloud-* に限定。 競技者の bus 側 rule が detailType match で Lambda を invoke する。 Lambda の execution role は Phase 1 で既に minimum 必要 IAM (SSM RunCommand / S3 / 等) を持っているため再利用。

D4: operator UI で runtime parameter 調整

application-admin-console に「Disruption console」 page を追加。 deployment 単位で当該 disruption の parameters を viewing / editing する。 編集は DDB (新規 DisruptionOverrides table)、 scoring Lambda が tick で読んで cross-account event の parameters field に反映する (= 競技者 Lambda は metadata の値ではなく event detail の値を使う)。

D5: fail-safe = Phase 1 Scheduler は常に保持

operator 側 trigger 経路が機能不全になった場合 (= cross-account permission 切れ、 scoring Lambda crash 等) でも、 Phase 1 の self-fire Scheduler が deploy 時刻 + offset で確定発火する。 重要 disruption (= microservice-migration の tc qdisc 等) は 「両方の経路がある」 状態を維持し、 condition-triggered は augmentation として位置付ける。

Open Questions — Recommendations

Issue #644 で検討対象となった 7 件。 各 question について本 ADR が採用する recommendation と rationale を以下に固定する。

#QuestionRecommendationRationale
1 idempotency 保証: cross-account event が重複到達するケース (= EventBridge at-least-once 配信) に対し、 競技者 Lambda 側でどう冪等にするか。 競技者 Lambda 側で event ID (= EventBridge の id field) を 24h TTL DDB (新規 DisruptionFireLog table、 PK=jobId+SK=eventId) で重複判定。 既出なら no-op。 SSM Parameter は write quota が低く (= 1 TPS/account)、 competitor account に新規 IAM 権限を 1 つ追加するだけで実装可能な DDB 方式が clean。 24h TTL は競技セッション (90〜120 分) を上回る window で safety margin あり。
2 operator UI の権限境界: tenant admin が他 tenant の disruption を弄れないよう RBAC を細かく切る必要があるか (= multi-tenant 環境での切替)。 tenant admin は自 tenant の event/team scope の disruption だけ操作可能 (= 既存の Cognito custom:tenantId claim で fence)。 system admin (admin-console) のみ全 tenant の override が可能。 SBT pooled stack の既存 RBAC モデル (custom:tenantId filter) を踏襲。 新規 IAM policy / Cognito group は不要 (= 最小変更)。
3 observation latency: scoring Lambda が 1 分 polling なので最短発火は 1 分後。 sub-second 反応が必要なら scoring を SQS-based event-driven に変える必要あり。 Phase 2 では 1 分 latency を許容 (= 既存 scoring 経路を維持)。 sub-second 反応が必要な disruption は別 ADR (= Phase 3) で扱う。 Battle 競技の体感として 1 分 latency は許容範囲 (= 攻防の駆け引きとして遅延を含めた設計)。 SQS event-driven に切替えると existing scoring Lambda の冪等性 + retry が複雑化するため、 必要性が顕在化するまで延期。
4 metadata version: triggers[] 追加は SCHEMA 拡張なので問題 metadata の version 互換性が要る。 SCHEMA 上 triggers は optional (= Phase 1 で着地済、 PR-637)。 既存 Phase 1-only 問題は無変更で動く。 新規問題は宣言可能。 SCHEMA バージョン bump (semver の minor) で community contributor に向けて変更を告知する。 Backward compat を保つことで existing problems の publish が壊れない (= ADR-008 catalog-pr.yml が破綻しない)。 minor bump で changelog に明示すれば community も気づける。
5 同一 disruption × 複数 triggers の semantics: 「after-deploy 60 分」 と 「team-score-above 5000」 が両方 OR で発火するのか AND か。 OR セマンティクス (= 最初に true になった trigger が発火)、 fire 後は他 trigger を suppress (= idempotency と整合)。 直感的 (= 「どれかの条件が達したら発火」)。 AND は表現力が低い (= 「全条件満たすまで遅延」 は実用上稀)。 fire suppress は #1 の idempotency と同 mechanism で実現できるので追加複雑性ゼロ。
6 無効化 trigger: 一度発火した disruption を「rollback」 する逆 trigger (= 例: latency 撤去) は本 Phase 2 で扱うか、 Phase 3 で扱うか。 Phase 2 では rollback trigger を扱わない。 Phase 1 既存の self-fire rollback (= disruption template 内で rollbackAfterMinutes 宣言済) でカバー。 condition-triggered rollback は条件 DSL の倍化を招く (= fire condition + rollback condition の 2 軸)。 既存 self-fire rollback で大半の Battle UX は満たせるため、 ニーズが見えるまで delay。
7 事前告知 UI: 「team-score-above 5000」 のような条件は competitor から見えづらい。 portal で 「次の disruption は score 4500 で発火 (今 4200)」 のような可視化を出すか、 隠すか。 metadata で triggers[].publicHint?: string を optional 宣言。 publicHint がある trigger は portal の disruption timeline に表示、 無い trigger は隠す (= operator 判断で運営の "サプライズ" 余地を残す)。 透明性と "ゲーム性" のトレードオフを問題作成者が決められるよう逃げ道を残す。 hello-world-battle 等の sample は publicHint を埋めることで competitor 体験を改善できる。

Status: 上記 7 件の recommendation を確定したことで本 ADR は Proposed に移行し、 Rollout Phase 1 以降の実装に着手できる状態とする。

Rollout

Phase内容Layer
1 SCHEMA に triggers[] 追加 (Schema 互換性: optional)、 既存 Phase 1 metadata は無変更で OK docs / schema
2 cross-account EventBridge bus + resource policy + 競技者 account 側 Rule の CDK infra
3 scoring Lambda に triggers eval + cross-account PutEvents 実装 app
4 application-admin-console に Disruption console page + DisruptionOverrides table app
5 microservice-migration-battle の disruption に condition trigger を追加 (= POC integration) app

Consequences

Positive

  • Battle のゲーム性が高まる (= 競技者の行動に reactive な disruption)
  • operator が runtime に競技難度を調整できる
  • self-fire fallback で「platform 障害でも重要 disruption は確定発火」 が保たれる

Negative

  • cross-account permission の設計が増える (= operator account → 競技者 account に PutEvents 権限を渡す、 セキュリティレビュー対象)
  • metadata 表現が複雑化 (= triggers[] の semantics を author に学習させる)
  • competitor 側から見ると 「いつ発火するか分からない」 disruption が出るので、 ゲームバランス調整が難しくなる

Risks

  • operator account compromise: cross-account 経路を使うため、 operator account の侵害が直ちに全競技者 account の disruption Lambda 起動権限を渡す。 minimum-privilege + IAM resource policy + GuardDuty 監視で緩和する。
  • cross-account bus 障害: EventBridge cross-account 配信は SLA 99.99% だが、 障害時には condition-triggered だけが停止する (= self-fire は引き続き発火、 D5 fail-safe 設計)。

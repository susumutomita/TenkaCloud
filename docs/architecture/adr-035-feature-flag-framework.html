ADR-035: Centralized feature-flag framework

Accepted

Context

We need to ship experimental / not-yet-verified features (per-tenant SAML SSO, non-AWS problem runtimes) without operators mistaking them for production-ready, and we need to add more such features over time. The first cut introduced ad-hoc config.featureSamlSso / config.featureNonAwsRuntime booleans. Left unchecked, that pattern sprawls: flags get read with scattered ?? false defaults, there is no single list of what exists, dead flags linger, and each SPA reinvents resolution — i.e. it becomes spaghetti.

Decision

One typed mechanism, shared across the three SPAs.

#DecisionWhy
1Single registry per app — src/features.ts declares every flag once: key → { description, stability, defaultEnabled }.The whole flag list is one object; discoverable, no hunting.
2Typed keys. ResolvedFeatures<typeof FEATURE_REGISTRY> gives a union of valid keys; referencing an unknown flag is a compile error.No string typos; deleting a graduated flag surfaces every dead usage.
3Shared resolver in @tenkacloud/web-kit: resolveFeatureFlags(registry, overrides) (pure).Resolution + its tests live once, not per SPA.
4One override channel — runtime-config.json features: { <key>: boolean } (dev: VITE_FEATURES JSON).Flip per environment with no rebuild; matches how the rest of runtime-config is injected.
5Resolved once in config.ts → config.features.No scattered ?? false; one resolution point.
6One access pattern: config.features?.<key>.Consistent, refactor-safe.
7Experimental ⇒ default OFF; graduate ⇒ delete the entry.Keeps the flag table short and honest; no permanent flags.

Resolution rules (robust to a hand-edited config)

  • A boolean override wins over the registry default.
  • A non-boolean override ("true", 1, null) is ignored → default wins.
  • An override key not in the registry is ignored — no crash, no silently-introduced flag.
  • Only registry keys appear in the result, so consumers get exactly the typed surface.

Authoring a new experimental feature

// src/features.ts
export const FEATURE_REGISTRY = {
  myThing: { description: "...", stability: "experimental", defaultEnabled: false },
} as const satisfies FeatureRegistry;

// component
if (!config.features?.myThing) return <FeatureDisabled />;   // gate the page too, not just the nav

Consequences

  • Adding an experimental feature = one registry entry + gate on config.features?.<key>. Nothing else.
  • Flags are discoverable in one file per app; the resolver is shared + unit-tested once (web-kit).
  • Gate the page/route, not just the nav link, so a direct URL cannot expose a disabled feature.
  • To enable in an environment: set features.<key>: true in that environment's runtime-config.json. Surfacing this as a deploy-time CDK parameter on the console hosting stacks is a follow-up; today the key is read from runtime-config.json.

Alternatives considered

OptionVerdict
Scattered config.featureX booleansRejected — the spaghetti this ADR exists to prevent.
External flag service (LaunchDarkly etc.)Rejected — violates the cost-zero principle; runtime-config.json is already our per-environment injection channel.
Build-time env onlyRejected — cannot flip a flag in a deployed environment without a rebuild.

Scope

Frontend (the three Cloudscape SPAs). Backend Lambda feature toggles, when needed, read their own environment / SSM and are out of scope here. The shared resolver lives in packages/web-kit/src/feature-flags.ts; the first registry is apps/application-admin-console/src/features.ts (samlSso, nonAwsRuntime).

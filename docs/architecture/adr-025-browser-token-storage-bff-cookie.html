ADR-025: 管理コンソールのトークン保管 — sessionStorage から first-party httpOnly cookie + BFF へ

System Admin (テナント管理) と Tenant Admin (アプリケーション管理) の 2 つのコンソールは、Cognito の id / access / refresh token を JavaScript から読める sessionStorage に保持している。これは XSS によるトークン持ち出しに対して構造的に無防備である。短期のアプリ層強化と、中期の first-party httpOnly cookie + BFF への移行を二段で定義する。

Status: Tier 1 Accepted / Tier 2 Proposed 2026-05-28
Scope: admin-console / application-admin-console
Related: ADR-020 (認可モデル: role enum), ADR-018 (pooled UserPool / SAML), ADR-016 (Lite mode)

Context

TenkaCloud には認証境界を持つフロントエンドが 3 つある。本 ADR が対象とするのは、Cognito で認証する 2 つの管理コンソールである。

両コンソールは共有クライアント packages/auth-client 経由で同一の OAuth フローを通る。Hosted UI で code を受け取り、code_verifier を添えて token endpoint で交換し、得た TokenSet を sessionStorage に JSON.stringify して保存する。バックエンドは Authorization: Bearer ヘッダで JWT を受け取り、API Gateway の Cognito / JWT Authorizer が署名・失効を検証する。cookie 経由の認証は存在しない。SPA は CloudFront で配信され、API は別オリジンの API Gateway に置かれている。

participant-portal を対象外とする理由

competitor の認証はログインキーであり、その有効期間は 1 イベントの競技時間 (数時間) に限定される。キーが漏れても価値があるのはその競技の最中だけで、イベント終了後は無効になる。localStorage 保管は「タブ / リロードをまたいで session を保つ」という競技 UX 要件に対する、期間が区切られた許容リスクとして扱う。本 ADR は、より価値が高く長命な管理コンソールのトークンに焦点を絞る。

管理コンソールが本丸である理由

管理コンソールのトークンは competitor キーと性質が異なる。

  • 権限が広い。 System Admin はテナント CRUD を、Tenant Admin はそのテナントの運用を握る。漏れた場合の被害はイベント 1 回に閉じない。
  • refreshToken が載っている。 access / id token は 1h 程度で失効するが、refresh token が漏れると新しい token を継続的に再発行されうる。sessionStorage に置かれた refresh token はこの設計で最も価値の高い資産である。
  • 常用される業務画面。 競技時間に閉じず、日常的にログインされる。

既存の緩和策

このトークン保管設計に対しては、すでに「盗まれた後の窓を狭める」方向の防御が積まれている。

  • idle timeout 15 分 — 操作のない session を失効させ、盗まれた JWT の利用窓を idToken 寿命 (1h) より短くする。
  • refresh token の server-side revoke — logout 時に /oauth2/revoke を叩き、Cognito Hosted UI の session cookie も /logout で破棄する。
  • fail-closed な OAuth state 検証 — sessionStorage に state が無い callback を CSRF / session 切れとして拒否する。
  • XSS 注入面の縮小 — innerHTML / eval / React の危険な HTML 注入 prop はリポジトリ規約で禁止。依存サプライチェーンは 4 層防御 (Bun trustedDependencies / .npmrc / audit / Safe Chain) で固めている。

残る構造的なギャップ

上記をもってしても、トークン本体が JavaScript から読める場所に置かれている事実は変わらない。XSS が一度成立すれば、攻撃スクリプトは次の一行で refresh token まで抜き出せる。

JSON.parse(sessionStorage.getItem("TenkaCloud.tokens")).refreshToken

誤解しやすい点: sessionStorage は localStorage より安全ではない

両者は同一オリジンの任意の JavaScript から等しく読める。XSS に対する防御力は同じで、違いは「タブを閉じると消えるか」という永続性だけである。管理コンソールが sessionStorage を使っていることは XSS 持ち出しへの防御にはならない。

この設計判断は、徳丸浩による「JWT を localStorage に置く時代から、ブラウザ境界では cookie に回帰する」という整理 (末尾の参考文献) が指摘するアンチパターンに該当する。本 ADR はその指摘を TenkaCloud のサーバーレス / コストゼロ制約の中でどう受けるかを定める。

httpOnly cookie は XSS そのものを防がない

cookie 化で得られるのは「トークン持ち出し耐性」であり、session riding は残る。したがって XSS の根本対策 (CSP、出力エスケープ、危険な HTML 注入 sink の禁止、依存サプライチェーン防御) は引き続き第一防御線である。本 ADR の cookie 移行はそれを置き換えるものではなく、漏出経路を 1 本断つ多層防御の追加である。

Decision

二段で、管理コンソールの高価値トークンを JS 可読ストレージから外す

  1. Tier 1 / アプリ層 即時の縮小 (インフラ変更なし、実装済)。 両コンソールの Cognito トークンを sessionStorage から メモリ (React state) のみへ移し、永続層から JWT を消す。completeLogin は TokenSet を返すだけで保存せず、旧バージョンが残した token は起動時に purge する。
  2. Tier 2 / インフラ層 目標アーキテクチャ。 同一オリジンの BFF (Backend for Frontend) を置き、Cognito トークンを server 側に保持する。ブラウザが持つのは不透明な httpOnly + Secure + SameSite cookie だけにする。OAuth code 交換は BFF 内で行い、code_verifier をブラウザから消す。

Tier 1 はフロントエンドのみで完結し、すぐに「持ち出し時の価値」を下げる。Tier 2 は CloudFront / API Gateway / Lambda / cookie ドメインの設計変更を伴うインフラ層の判断であり、本 ADR はその設計の叩き台を提示する。

Tier 1 の既知のコスト: リロードは silent re-auth (リダイレクト往復)

セッションを保持しているのは sessionStorage ではなく Cognito Hosted UI 自身の session cookie (Cognito ドメイン上の httpOnly cookie、アプリの JS からは読めない) である。メモリ保持にすると、リロードで token が消えるたびに /oauth2/authorize への redirect 往復が挟まる。Cognito session cookie が生きていれば資格情報の再入力は発生しない (= ログアウトではなく無音バウンス) が、token 有効中のリロードでも即時復元はできなくなる (非 SAML 時はログイン画面が mount で自動 redirect するため手動クリックは増えない)。リロードまたぎを完全シームレスにするには server 側 httpOnly cookie が要る = それが Tier 2 を正当化する。

付随する観察: 共有クライアントは refreshToken を保存していたが、用途は logout 時の /oauth2/revoke のみで、grant_type=refresh_token による無音のその場更新には使っていない。保存された refresh token は XSS に晒される一方で silent refresh の利益を生んでいなかった。メモリ化で機能的に失うものはない (logout の revoke はメモリ上の値を beginLogout に渡して継続する)。

現状 vs 目標フロー

目標フローでは、ブラウザは不透明な session 識別子を持つ httpOnly cookie だけを保持する。BFF が同一オリジンに座り、ブラウザからの cookie を受けて server 側に保持した JWT を API へ中継する。XSS が成立しても cookie は読めないため、refresh token を含むトークン本体は流出しない (session riding は残るため XSS 対策は別途必要)。

Tier 2 設計の論点

同一オリジン BFF を成立させるには、フロントエンド (CloudFront) と BFF を同じオリジンに揃える必要がある。代表的な構成は CloudFront に /bff/* 等の behavior を足し、その path だけを BFF (Lambda function URL もしくは API Gateway) にルーティングする方式である。これにより cookie は first-party になる。両管理コンソールはオリジンが分かれているため、各オリジンに BFF behavior を配置する。

API 到達経路の 2 案

案仕組みトレードオフ
C-1. BFF が API を proxy ブラウザは API Gateway を直接叩かず、cookie 付きで BFF にだけアクセスする。BFF が session から JWT を取り出して API へ中継する 境界が一点に集約され分かりやすい。一方で管理画面の操作のたびに BFF を経由するため、Lambda invocation が増える
C-2. API Gateway に cookie を読む Lambda authorizer ブラウザは API Gateway を直接叩き、Lambda authorizer が cookie から session を引いて JWT claims を注入する hop が増えない。一方で既存の Cognito / JWT Authorizer を Lambda authorizer に差し替える必要があり、認可ロジック (ADR-020 の role enum) の再実装が要る

API 所有者によって C-1 / C-2 の選べる幅が変わる

cookie を読む authorizer (C-2) は、その API の authorizer を TenkaCloud が所有している場合にだけ差し込める。SBT (@cdklabs/sbt-aws) の ControlPlane が同梱する control-plane API は Cognito JWT authorizer を内蔵し、TenkaCloud はそれを差し替えられない (内部 child に手を入れる形になり脆い)。したがって経路ごとに選択肢が分かれる。

admin-console → AdminInsight HTTP APITenkaCloud 所有可可

BFF を SPA 前段に置くこと自体は TenkaCloud 自前のホスティング層 (CloudFront behavior + Lambda) の話で、SBT は禁じない。harness の INVARIANT_CONTROL_PLANE_USES_SBT も、BFF は control plane の置き換えではないため抵触しない。SBT が課す制約は「control-plane API の authorizer に手を入れられない」一点に限られ、そこは BFF proxy で囲えば回避できる。

session ストアの選択

コストゼロ原則 (Free Tier 25 RCU/WCU、Secrets Manager 禁止) を踏まえると、選択肢は次のいずれか。

  • stateless 暗号化 cookie — session の中身を server 鍵で暗号化して cookie に格納し、ストアを持たない。鍵は SSM Parameter Store SecureString に置く (Secrets Manager は規約で禁止)。即時失効が弱いため失効リストの併用を要する。
  • DynamoDB session テーブル — PROVISIONED 1/1 (DynamoDbLowCapacity Aspect 準拠) の session テーブルを持つ。server 側失効が容易。管理画面のアクセス頻度に対する RCU を見積もる。

CSRF 防御

cookie 方式は CSRF 面を新たに生むため、SameSite=Strict または Lax を基本とし、状態変更系には origin 検証または double-submit token を併用する。bearer ヘッダ方式では不要だった防御を足すことになる。

Non-goals

本 ADR の対象外

  • participant-portal のトークン保管。 competitor のログインキーは競技時間に限定された短命 bearer であり、localStorage 保管は期間が区切られた許容リスクとして扱う。本 ADR では変更しない。
  • XSS の根本対策の置き換えではない。 CSP / 出力エスケープ / 危険な HTML 注入 sink の禁止 / 依存サプライチェーン防御は引き続き第一防御線として独立に維持する。
  • Cognito そのものの置き換えではない。 認証基盤は Cognito (Hosted UI + OAuth Code + PKCE) のまま。変えるのはトークンのブラウザ保管方式だけ。
  • 認可モデルの変更ではない。 role enum と plane 分離 (ADR-020) はそのまま。
  • SSE / WebSocket の導入ではない。 フロントエンドの polling 方針は維持する。

Open design questions

Tier 2 実装の収束のために残る論点。

  • API 到達経路 — SBT 所有の control-plane API は BFF proxy (C-1) 固定。TenkaCloud 所有 API は C-1 か cookie 対応 Lambda authorizer (C-2) かを invocation コストと authorizer 移植コストで比較する。
  • session ストア — stateless 暗号化 cookie (即時失効が弱い) か DDB session テーブル (RCU を要する) か。idle timeout / logout 失効の要件との整合。
  • cookie ドメイン — admin-console と application-admin-console のオリジン構成と、各 CloudFront behavior 上で BFF を同一オリジンに揃える具体的な配置。
  • 移行順序 — bearer 系を一気に廃止せず、cookie と bearer を一定期間併存させるか。併存させる場合の認可面の二重化をどう閉じるか。
  • CSRF 方式 — SameSite の Strict / Lax 選択と、状態変更系に対する double-submit token / origin 検証の要否。

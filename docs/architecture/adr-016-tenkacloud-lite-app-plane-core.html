ADR-016: AppPlaneCore 抽出 + TenkaCloud Lite mode

Control Plane 不要の Lite 経路を作るために、 Tenant Template から App Plane コア構成を独立 construct に切り出す

Status:Accepted 2026-05-15
Tracking: #778
Related: ADR-007、 ADR-010、 ADR-012、 ADR-015

Context

TenkaCloud は AWS マルチテナント SaaS として設計されており、 Control Plane (= SBT) + Tenant Pipeline + per-tenant Application Plane が前提になっている。 この構成は enterprise tenant にとって価値があるが、 OSS / Product Hunt / Hacker News / 個人開発者向けの最初の体験としては重すぎる。

TenkaCloud を「触ってみる」 段階の理想は次のような one-command UX。

$ tenkacloud lite up --problem problems/battles/hello-world-battle
✓ Deployed AppPlaneCore (tenantId=local)
✓ Application Admin Console: https://d123.cloudfront.net
✓ Participant Portal:        https://e456.cloudfront.net
✓ Team login key:            7f3a-...
✓ Problem deployed:          hello-world-battle (Battle, scoring active)

現状の scripts/install.sh は 3-phase deploy で次の stacks を立てる。

Stack役割Lite 必要性
ControlPlaneStackSBT 同梱の System Admin + tenant CRUD + EventBridge bus不要 (= Lite は tenant 1 つ固定)
BootstrapTemplateStackSBT BashJobRunner + TenantMappingTable + SSM API key不要 (= tenant 動的作成 / multi-tier API key 経路を使わない)

TenantTemplateStacktenant API Gateway + Cognito UserPool + ApplicationAdminConsoleHosting + tier API key 参照 + TenantMappingTable 登録部分必須 (= API Gateway + Cognito + Hosting は要、 tier API key + TenantMappingTable は不要)

現在の TenantTemplateStack の構成解析

既存の infrastructure/lib/tenant-template/tenant-template-stack.ts は次を担っている。

  1. ApplicationAdminConsoleHosting (= SPA + runtime-config 配信) を作る
  2. tenant Cognito IdentityProvider (= UserPool + UserPoolClient + Hosted UI domain) を作る
  3. tenant ApiGateway (= REST API + DeployApi / EventApi / CompetitorAccountsApi 統合) を作る
  4. deployRuntimeConfig で runtime-config.json を S3 配置する
  5. TenantMappingTable に DDB Put (= SaaS pipeline の per-tenant deploy chain 上流)
  6. tier API key SSM Parameter を ssmLookup で参照する
  7. SBT provisioning / pipeline flow に組み込まれる

このうち 1〜4 は Lite mode でもそのまま必要、 5〜7 は Full SaaS だけが必要。

Decision

Accepted: TenantTemplateStack から App Plane コア構成を AppPlaneCore Construct として抽出し、 Full mode と Lite mode の両方が同じ Construct を再利用する形に倒す。 Lite mode は TenkaCloudLiteStack + CLI runner (scripts/tenkacloud-lite.ts) を追加。 既存 Full SaaS 経路は AppPlaneCore を内部利用する形で挙動を変えない。

D1
AppPlaneCore 抽出
infrastructure/lib/app-plane-core/ に再利用可能 Construct を切る。 ApplicationAdminConsoleHosting + IdentityProvider + tenant ApiGateway + deployRuntimeConfig を内包。 tier API key / TenantMappingTable は持ち込まない
D2
TenantTemplateStack は AppPlaneCore を内部利用
既存 stack を AppPlaneCore のラッパーに書き換える。 TenantMappingTable 登録 / tier API key 参照 / SBT pipeline 統合 / SaaS tag は wrapper 側に残し、 既存 outputs (= API URL / Cognito Domain / Console URL) を保持する
D3
TenkaCloudLiteStack 新設
AppPlaneCore (tenantId=local) + ProblemDeployBackendStack の 2 stack 組合せで動く軽量 stack。 Control Plane / Bootstrap / Pipeline / AdminConsoleInsight に依存しない
D4
CLI runner 追加
scripts/tenkacloud-lite.ts (Bun + AWS SDK) を提供。 up / down / deploy <problemId> / portal-url / team-key を sub-command で持つ。 Cognito Hosted UI URL + Participant Portal URL + team login key を console 出力
D5
ProblemDeployBackendStack は eventBusArn を optional 化
既存は ControlPlane の bus ARN を必須引数で受けるが、 Lite mode では Control Plane が無い。 eventBusArn?: string にし、 undefined のとき local EventBus を stack 内で作る fallback を入れる
D6
runtime-config 互換性は契約として固定
apps/application-admin-console / apps/participant-portal の runtime-config.json shape は Lite / Full で完全に同じ。 frontend は mode-aware なロジックを持たない (= ADR-007 outside-in)

D1: AppPlaneCore Construct

新規ファイル infrastructure/lib/app-plane-core/app-plane-core.ts。

export interface AppPlaneCoreProps {
  readonly tenantId: string;
  readonly tenantName: string;
  readonly environment: string;
  readonly deployApiLambda: IFunction;
  readonly eventApiLambda: IFunction;
  readonly competitorAccountsApiLambda: IFunction;
  readonly participantPortalUrl?: string;
  readonly competitorBootstrapTemplateUrl?: string;
  readonly isPooledDeploy?: boolean;
  /** Full mode の tier API key 参照を Lite mode では省略する。 */
  readonly apiKeyConfig?: ApiKeyConfig;
}

export class AppPlaneCore extends Construct {
  public readonly tenantApi: ApiGateway;
  public readonly identityProvider: IdentityProvider;
  public readonly applicationAdminConsoleHosting: ApplicationAdminConsoleHosting;
  public readonly applicationAdminConsoleUrl: string;
  // ...
}

API Key ロジックは apiKeyConfig? で Lite mode 経由を保つ。 undefined のとき API Gateway 側の Usage Plan / API Key 配線をスキップする。

D2: TenantTemplateStack の wrap 化

既存 TenantTemplateStack は次の責務に縮小される。

  1. new AppPlaneCore(this, "AppPlane", { tenantId, tenantName, ..., apiKeyConfig: { ... } }) で内部 instance を作る
  2. TenantMappingTable に Put (= SaaS pipeline 上流の DDB 登録)
  3. SBT tag (TenantId / IsPooledDeploy) を付与
  4. 従来 outputs (= API URL / Cognito domain / Console URL) を AppPlaneCore から re-export

外部 caller (= bin/infrastructure.ts / app-wiring/wire.ts) の interface は維持する (= no breaking change)。

D3: TenkaCloudLiteStack

新規ファイル infrastructure/lib/tenkacloud-lite/tenkacloud-lite-stack.ts。

export class TenkaCloudLiteStack extends Stack {
  constructor(scope: Construct, id: string, props: TenkaCloudLiteStackProps) {
    super(scope, id, props);

    // ProblemDeployBackend を内部に直接立てる (Control Plane bus 無し)。
    const problemDeploy = new ProblemDeployBackendStack(this, "ProblemDeploy", {
      ...props,
      eventBusArn: undefined, // D5: local bus に fallback
      participantPortal: { runtimeConfig: "default-dev-mock" },
    });

    // AppPlaneCore を tenantId=local で立てる。
    const appPlane = new AppPlaneCore(this, "AppPlane", {
      tenantId: "local",
      tenantName: "TenkaCloud Lite",
      environment: props.environment,
      deployApiLambda: problemDeploy.deployApiLambda,
      eventApiLambda: problemDeploy.eventApiLambda,
      competitorAccountsApiLambda: problemDeploy.competitorAccountsApiLambda,
      participantPortalUrl: problemDeploy.participantPortalUrl,
      // apiKeyConfig: undefined = Usage Plan / API Key 配線スキップ
    });

    new CfnOutput(this, "ApplicationAdminConsoleUrl", { value: appPlane.applicationAdminConsoleUrl });
    new CfnOutput(this, "ParticipantPortalUrl", { value: problemDeploy.participantPortalUrl });
  }
}

install.sh とは別に scripts/tenkacloud-lite.ts CLI を経由して cdk deploy TenkaCloudLiteStack を起動する。

D4: CLI runner (scripts/tenkacloud-lite.ts)

Bun + @aws-sdk/client-cloudformation ベースの軽量 CLI。 sub-command と最小 UX。

Command動作
tenkacloud lite upcdk deploy TenkaCloudLiteStack 起動 + 完了後に Application Admin Console URL と Participant Portal URL を表示
tenkacloud lite deploy <problemId>Lite stack の EventApiLambda に直接 invoke して event 作成 + 問題 deploy。 完了後 team login key を出力
tenkacloud lite portal-urlParticipant Portal URL を表示 (= clipboard / mailto 用)
tenkacloud lite team-key <eventId>競技者 team の login key を CFn output / DDB から取得して出力
tenkacloud lite downcdk destroy TenkaCloudLiteStack + 関連 S3 bucket 削除 (= cleanup.sh の lite 版)

CLI は AWS access key を出力しない (= 競技者 portal URL + team login key の組合せで access、 AWS console access が要るなら ADR-002 の federation 経路を別途使う)。

D5: eventBusArn の optional 化

現行 ProblemDeployBackendStack は次のように受けている。

readonly eventBusArn: string;

これを次に変更する。

readonly eventBusArn?: string;
// 内部: undefined のとき new events.EventBus(this, "LocalBus") を作って自前 publish 経路を持つ

Full mode (= ControlPlane bus を受ける) では引数が埋まるので挙動不変。 Lite mode は undefined を渡して local bus に倒す。 cross-stack event 受信は元々 Full mode の ServerlessSaaSPipeline 側だけが行うため、 Lite では発生しない。

D6: runtime-config 互換性の契約

apps/application-admin-console/src/config.ts の loadConfig() は次の shape を期待する。

{
  cognitoDomain: string;
  userClientId: string;
  tenantId: string;
  tenantName: string;
  apiUrl: string;
  participantPortalUrl?: string;
  competitorBootstrapTemplateUrl?: string;
}

Lite mode はこの shape を完全に維持し、 tenantId = "local" / tenantName = "TenkaCloud Lite" を埋める。 frontend は mode-aware な分岐を持たず、 同じ artifact (apps/application-admin-console/dist/) を再利用する (= INVARIANT_APP_CODE_IS_UNMODIFIED)。

Consequences

Positive

  • 外部 adoption の障壁を 1 桁下げる: 「TenkaCloud を試したい」 開発者は tenkacloud lite up 1 コマンドで AWS account に最小 stack を deploy できる。 SBT / SaaS Ref Arch / Cognito Hosted UI の知識を要求しない
  • Full mode を壊さない: AppPlaneCore を間に挟むだけで、 既存 TenantTemplateStack の outputs / runtime-config / SBT pipeline 統合は維持。 CFn 出力同等性を invariant 化する
  • Plugin architecture との相補: ADR-012 の問題プラグイン経路 (= problems/<id>/template.yaml) を Lite mode でも同じ動作で利用可能。 OSS contributors が問題を 1 つ書いて Lite で試す閉ループが成立
  • CLI-first 経路の foothold: ADR-010 の API-first / CLI / MCP 思想に乗る。 CLI runner が事実上 ControlPlane の代替 UI として機能する場面が Lite mode から見えてくる

Negative / Trade-off

  • 2 つの mode を並行 maintain: Full / Lite で 2 経路の synth / deploy / test を維持する。 invariant (= runtime-config shape / AppPlaneCore interface) を共通化することで分岐コストを最小化する
  • Lite mode の "toy path" 化リスク: 機能の差分が広がると Lite が長期 maintain されない懸念。 mitigation として AppPlaneCore / ProblemDeployBackend / problem template を Full と完全共有する規律を docs/architecture/harness.md に invariant として追加する
  • CLI 実装コスト: scripts/tenkacloud-lite.ts の sub-command を一通り書く必要がある (= up / down / deploy / portal-url / team-key)。 既存 install.sh / cleanup.sh 経路と共通化できる部分は再利用する
  • eventBusArn optional 化の影響範囲: ProblemDeployBackendStack 内で local EventBus を作る経路を追加するので、 既存 test の event publish 経路を双方で pin する必要あり

Risk

Risk影響緩和策
Full mode の synth が refactor で意図せず変わる既存 deploy で CREATE/REPLACE が発生synth snapshot test を追加し、 CFn template の resource list / logical ID / dependency を 1 件ずつ pin する。 ADR-015 harness に cdk synth diff rule の検討余地
Lite mode が divergent toy path 化長期 maintain 不能、 dead code 蓄積AppPlaneCore / ProblemDeployBackend / problem template を Full と完全共有する規律を harness invariant 化 (= INVARIANT_LITE_REUSES_APP_PLANE_CORE の新規追加候補)
CLI が AWS credential を露出する誤運用OSS user の AWS account が漏洩CLI は long-lived access key を絶対に出力しない。 必要なら ADR-002 の federation 経由で短命 SigninToken を発行する
runtime-config shape の driftfrontend が Lite / Full で挙動分岐する誘惑shape を 1 つの zod schema として apps/application-admin-console/src/config-schema.ts に固定し、 Lite / Full 両方の runtime-config builder が同 schema を passthrough することを test で pin する

Alternatives considered

選択肢判定理由
A. Lite mode のために TenkaCloud 全体を別 repo / 別 fork に切り出す却下fork は問題 plugin / scoring engine / participant portal の整合性を保つコストが線形に増える。 Full mode の進化に Lite mode が追従しなくなる
B. install.sh を簡略化して "minimal install" モードを生やす却下3-phase deploy + ControlPlane + Cognito Hosted UI 経路を維持したまま「軽量化」 を試みると条件分岐が複雑化し、 結局 Full mode を壊す。 stack の構造を変えるべき
C. Lite mode は CloudFormation template 直書きで CDK を回避却下CDK の Construct 再利用が効かなくなり、 Full mode の進化に追従できない。 そもそも問題 deploy 経路は CDK + Step Functions + Lambda の組合せで、 plain CFn では書けない
D. AppPlaneCore を抽出 + TenkaCloudLiteStack + CLI runner採用既存の Tenant Template から共通部分を Construct として切り出すだけで、 Full mode を壊さず Lite mode を追加できる。 CDK Construct の再利用性を活かす
E. Lite mode は AWS account を要求せず LocalStack / dev container で動かす却下本物の S3 / CloudFront / Cognito / Lambda が必要 (= 競技者が実際に AWS resource を deploy する性質の product)。 LocalStack で Cognito Hosted UI を再現するのは構造的に困難

Implementation phases

本 ADR は単一 PR では完結しない。 次の phase に分割して進める。

Phase内容受入条件
1. AppPlaneCore 抽出infrastructure/lib/app-plane-core/ 新設。 TenantTemplateStack を wrapper 化既存 cdk synth 出力が CFn 物理差分 0 件 (= synth snapshot test で pin)
2. ProblemDeployBackend の eventBusArn optional 化eventBusArn?: string + local bus fallback。 既存 test を Full / undefined 双方で greenFull mode の event publish 経路は不変。 Lite mode の同 path が local bus 経由で動く unit test 追加
3. TenkaCloudLiteStack新規 stack。 cdk synth TenkaCloudLiteStack が通るLite stack の synth が成功し、 Application Admin Console URL + Participant Portal URL を CFn output に持つ
4. CLI runnerscripts/tenkacloud-lite.ts + Makefile target (make lite-up / make lite-down)1 コマンドで up → deploy → portal-url → down が通る
5. 動作確認 + docsサンプル問題 (problems/battles/hello-world-battle 等) を Lite mode で deploy → scoring 動作 → destroyOSS readers が README の Lite mode セクションだけで up / down できる

各 phase は独立 PR として merge 可能 (= INVARIANT_PR_SHIPS_WORKING_INCREMENT に従う)。 Phase 1 は AppPlaneCore 抽出という refactor のみで Lite mode 自体は未追加でも、 「TenantTemplateStack の内部構造改善」 として独立価値を持つ。

Open Questions

本 ADR では下記を Phase 1 着手時に再検討するものとして残す。

  1. Lite mode は ProblemDeployBackendStack を直接 deploy するか、 ProblemDeployLiteBackendStack を別に切るか: 現状は直接 deploy 案。 Lite 専用の機能差分 (= ParticipantPortal を default-dev-mock で固定する等) が増えるなら別 stack の検討余地あり。 Phase 2 で実 deploy して runtime cost / feature 差分を実測してから判断
  2. Lite mode の Cognito を dev-mode (= 自動 confirm) に倒すか: 招待メール経由は OSS user の onboarding 摩擦になる。 Lite では initial password を CLI に直接表示する fast-path を検討 (= ただし INVARIANT_AUTH_INJECTED_AT_INFRA_LAYER に違反しない範囲で)
  3. Application Admin Console を Lite mode CLI MVP に含めるか: 「CLI + Participant Portal だけで十分」 シナリオも考えられる。 まずは AppPlaneCore に含めておき、 CLI から URL を出すだけにする (= 必要なら competitor は URL を踏まなくてもいい運用)
  4. team login key の発行主体: 既存 EventApiLambda が ULID 32-byte 生成。 CLI から直叩きするか、 CLI が Lambda invoke するか。 後者で統一する想定
  5. 状態保管: Lite でも DDB 経由を維持する (= Free Tier 圏内、 local state 経路は複雑度が割に合わない)
  6. AdminConsoleInsight: Lite では不要 (= tenant 1 つのみで cross-tenant 観察対象が無い)

Rollout

  • Phase 1 (AppPlaneCore 抽出) を最初の PR として出す。 CFn 物理差分 0 件を invariant 化
  • Phase 2-5 は順に独立 PR で merge する
  • 各 Phase が完了するごとに Issue #778 の Acceptance Criteria を 1 つずつチェックしていく
  • Full mode の deploy 経路は phase 全期間で壊さない。 各 PR で make synth を旧 main と比較する手順を PR body に明記する
  • Phase 5 完了時点で README.md の冒頭に Lite mode セクションを追加 (= OSS user の最初の体験経路として明示する)

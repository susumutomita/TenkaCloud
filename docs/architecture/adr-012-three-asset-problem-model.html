ADR-012: Three-asset problem model and built-in scoring kinds

Accepted   Scope: problem authoring contract, scoring engine, participant portal plugin surface

Context

TenkaCloud delivers competition problems into competitor-owned cloud accounts. Three forces shape the problem contract:

  • The platform must stay generic. The problem catalog is the product's moat and grows through community contribution in a separate catalog repository (TenkaCloudChallenge). If adding a problem required changing platform code, the catalog could not scale.
  • Scoring must run inside the platform, not inside the problem. Competitors control the account the problem is deployed into, so any scoring logic shipped with the problem is tamperable, and per-problem scoring Lambdas would multiply cost and supply-chain surface.
  • Deployment must be a single, reviewable artifact. The deploy worker assumes into the competitor account (always with ExternalId) and creates exactly one stack per problem; multi-file deploy trees make review and least-privilege analysis harder.

Decision

Every problem is exactly three assets in its problem directory:

packs/<pack>/problems/<category>/<id>/
├── metadata.json    # source of truth: catalog display, runtime target, scoring config, portal wiring
├── template.yaml    # the deploy body — one single-page template, deployed into the competitor account
└── portal/          # optional .tsx files declared in metadata dashboard slots
  • metadata.json declares identity (id, title, category), the runtime target (runtime.provider/engine/entry, or runtime.targets[] for composite problems), and the scoring section. The schema is owned by @tenkacloud/problem-sdk (validateProblemMetadata / parseScoringMetadata), which both the platform and the authoring CLI consume.
  • template.yaml is the entire deploy body for the declared engine (CloudFormation for aws/cloudformation; other engines use their native single-artifact form). The platform never patches or concatenates templates.
  • portal/ is optional competitor-facing UI, loaded only through slots declared in metadata — problems cannot inject arbitrary UI.

Built-in scoring kinds only

A problem selects exactly one scoring kind in metadata.json:scoring. The platform's generic scoring Lambda dispatches on the kind; no problem-specific scoring code exists in the platform.

KindModelTypical use
flagOne secret value submitted once; points on matchChallenge (self-paced)
multi-flagN sub-flags, each scored independentlyMulti-step challenges
uptime-flatPeriodic probe; flat points per successful check (legacy metadata may spell it uptime; both are honoured)Battle (keep-it-running)
uptime-multiMultiple endpoints probed; pointsAllOk when all are healthyBattle, multi-service
phased-pollingPlatform-defined phases with per-phase point rulesStaged scenarios
attack-detectionpointsPerAttack for detected/blocked attack eventsDefensive battles
composite-probeProbe-based scoring across the targets of a composite (multi-provider) runtimeCross-cloud problems

Parsers are pure and fail soft: an unrecognised or malformed scoring section parses to undefined rather than throwing, so a bad catalog entry cannot take the scoring Lambda down. This no-throw contract is part of the public SDK surface and must be preserved by refactors.

Consequences

  • New problems (and whole packs) ship without platform releases; platform releases never need catalog changes.
  • Adding a genuinely new scoring behaviour is a platform decision: it means adding a kind to the SDK and the generic scoring Lambda, reviewed once, reused by every future problem.
  • The scoring configuration is data, so the participant portal can render points and progress from the same metadata without executing problem code.
  • Problems cannot express bespoke scoring; authors must map their idea onto a built-in kind or propose a new kind upstream. This is accepted as the price of a tamper-resistant, fixed-cost scoring engine.

Alternatives considered

AlternativeWhy rejected
Per-problem scoring Lambda shipped with the problem Runs attacker-influenceable code inside the platform trust boundary; one Lambda per problem breaks the free-tier cost model; every problem becomes a supply-chain review.
Scoring script executed in the competitor account Fully tamperable by the competitor; results cannot be trusted for a leaderboard.
Free-form multi-file deploy trees Harder to review for least-privilege and answer leakage; single-page templates keep the competitor-bootstrap IAM role auditable.

Migration

Problems originally lived under a repository-root problems/ tree. Distribution moved to problem packs (packs/<pack>/tenkacloud-pack.json + the same three-asset problem directories, see ADR-0002 for pack compatibility and release policy). The three-asset contract itself was unchanged by that move: pack tooling (validatePackDirectory) validates the same metadata.json/template.yaml pair per problem.

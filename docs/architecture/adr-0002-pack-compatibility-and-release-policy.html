ADR-0002 — Problem Pack compatibility, deprecation, and release policy

The durable compatibility contract between TenkaCloud Core, the @tenkacloud/problem-sdk public API, Pack manifests, problem metadata, runtime capabilities, and test harnesses. It tells contributors what is stable, gives maintainers a safe way to evolve the platform, and gives any implementation an explicit rulebook instead of guessed compatibility behavior.

1. Context

A problem pack is a versioned collection of problem artifacts plus a manifest (tenkacloud-pack.json). External authors create, validate, version, publish, install, and remove packs without editing the platform core repository. The platform core owns lifecycle, validation, catalog composition, runtime capability checks, deployment, scoring, access, and audit. A pack owns problem metadata, infrastructure templates and assets, scoring declarations, documentation, and optional coordination plugins.

The foundation that this policy governs already exists in code:

  • The manifest schema (infrastructure/lib/problem-pack/manifest.ts) carries schemaVersion, a reverse-DNS id, an exact SemVer version, a SemVer-range core field, a list of requiredRuntimes ({provider, engine}), and optional dependencies. satisfiesCoreRange(version, range) is the pure, dependency-free function that answers whether a concrete core version falls inside a pack's declared range.
  • The snapshot store (snapshot.ts) makes a published revision immutable: a content digest (SHA-256 over a canonical, sorted file list and bytes) is recorded in a lock file, re-installing identical content is a no-op, and installing the same id@version with a different digest fails closed.
  • The catalog composer (effective-catalog.ts) merges core problems with installed pack snapshots, validates each manifest's core range and requiredRuntimes against the platform before merging, and fails closed on a duplicate problem id (packs cannot override core in v1). The lifecycle engine (lifecycle.ts) installs / lists / inspects / removes revisions and refuses to remove a revision that is pinned by an event, deployment, or activation.

These modules answer the mechanical questions (does this version satisfy this range? is this digest identical?). What they do not encode is the human-facing policy: what counts as a breaking change, how long a deprecated thing is supported, exactly when validation warns versus rejects, and what a release is allowed to alter. Without that policy, every author and maintainer reinvents the answer, and the answers drift. This ADR fixes the policy so the code has a single rulebook to implement against.

What this policy must guarantee. An unambiguous accept / reject result for any (core version, pack compatibility range) pair; an exact, predictable behavior when an installed pack becomes incompatible; a clear distinction between warning, deprecation, and rejection; and the set of fixture classes that must pass before any core release.

2. Decision

Adopt the following policy as the durable compatibility contract for problem packs.

  1. Five independent version axes evolve under SemVer with explicitly defined meaning (§3).
  2. A pack's core SemVer range is matched against the platform core version by satisfiesCoreRange; activation is refused when the installed core falls outside that range (§4).
  3. A pack revision is immutable once published; its content digest is its identity. New content always means a new version (§5).
  4. The @tenkacloud/problem-sdk public contract is additive in minor, breaking only in major, guarded by an API report and a contract fixture suite (§6, aligned with #2106).
  5. Metadata and manifest schema evolution follows additive-safe / breaking-needs-major rules (§7).
  6. A four-state status taxonomy — Preview Supported Deprecated Removed — with defined transitions and minimum notice windows (§8).
  7. A fixed set of validator diagnostic codes distinguishes compatibility failure from deprecation warning (§9).
  8. A machine-readable compatibility matrix is published for each core release (§10).
  9. Every release passes a fixed release checklist and fixture gate; a core release cannot change a supported fixture outcome without an explicit, recorded compatibility exception (§11).
  10. Installed pack snapshots are never silently auto-upgraded, and existing event and deployment snapshots keep their resolved metadata and provenance across any pack or core upgrade (§4.4).

3. Version axes

Five axes version independently. Conflating them is the root cause of brittle plugin systems, so each has one owner and one meaning.

The five independent version axes.
Axis Owner Format Meaning Where it lives
Core platform version Platform maintainers SemVer (exact) The running platform's capabilities and behavior. The value matched against a pack's core range. PlatformContext.coreVersion
Manifest schema version Platform maintainers Integer (major only) The shape of tenkacloud-pack.json. Bumped only on a breaking schema change. Currently 1. manifest.schemaVersion
Public SDK version Platform maintainers SemVer (exact) The @tenkacloud/problem-sdk API surface an author builds against. Additive in minor, breaking only in major. package.json of the SDK
Pack version Pack author SemVer (exact) One immutable revision of one pack's content. Classified breaking / additive / patch by §5. manifest.version
Runtime capability version Platform maintainers provider/engine identity; optional version suffix when a capability is revised A {provider, engine} capability the platform can satisfy. A capability's behavior is frozen for the identifier it advertises (§4.3). requiredRuntimes[] / platform capability set
Lock record. At validate / install time the lock entry pins, per revision: packId, version, contentDigest, sourceKind, sourceRef, installedAt, and the coreVersion the pack was installed against. The lock additionally records the manifest schemaVersion and the SDK version the pack validated against, so a later reader can reconstruct the exact compatibility context that was in force at install time — not the context that happens to be current.

4. Core compatibility model

4.1 Matching a pack against the platform

A pack declares the core versions it supports as a SemVer range in its core field (for example ^1.4.0, >=1.4 <2, or 1.4 - 1.9). The platform decides admissibility with the existing pure function: 

satisfiesCoreRange(platform.coreVersion, manifest.core) === true   // admissible
satisfiesCoreRange(platform.coreVersion, manifest.core) === false  // refused: CORE_RANGE_UNSATISFIED

This is the single source of truth for the accept / reject result. The composer (effective-catalog.ts) already calls it before merging a pack's problems and returns CORE_RANGE_UNSATISFIED on a miss. The result is total and deterministic: for any concrete coreVersion and any valid range there is exactly one answer, and an invalid version or range yields false (fail closed) rather than an exception.

4.2 Required runtimes

Beyond the core range, every requiredRuntimes entry — a {provider, engine} capability — must be present in the platform's available capability set, or activation is refused with RUNTIME_UNAVAILABLE. Providers are constrained to the declared set (aws, gcp, azure, sakura). Adding a new capability to the platform is additive and never breaks an existing pack; removing a capability is a breaking core change handled through the deprecation lifecycle (§8).

4.3 A capability's behavior is frozen for its identifier

No hidden behavior change. A runtime may be deprecated, but its provider/engine behavior must not silently change for an installed pack revision. If a capability's semantics need to change, it is published under a new identifier (or an explicit capability-version suffix), the old identifier is moved through Deprecated → Removed, and packs migrate by declaring the new identifier in a new pack version. The same provider/engine string never means two different things.

4.4 Installed snapshots are pinned, never auto-upgraded

When an installed pack becomes incompatible — because the platform core moved out of the pack's range, or a required capability was removed — the platform fails closed at install or activation time, surfacing CORE_RANGE_UNSATISFIED / RUNTIME_UNAVAILABLE. It never silently disables, mutates, or upgrades a snapshot, and it never breaks an active event without an explicit operator action.

Behavior when an installed pack becomes incompatible.
Situation Platform behavior Result
New install / fresh activation of an incompatible revision Reject before any catalog change; emit the matching diagnostic code. Fail closed
Already-pinned revision referenced by a live event / deployment Keep serving the pinned, resolved snapshot. The lock and deployment record retain the original contentDigest and provenance. No auto-upgrade. Preserved
Operator wants to move a live event to a compatible revision Requires an explicit operator action (install + re-activate the new revision). Operator-driven
Remove a pinned revision Refused (lifecycle.removePack returns PINNED) until the reference is gone. Refused

Existing event and deployment snapshots keep their resolved metadata and provenance after any pack or core upgrade. Provenance recorded at activation (packId, packVersion, contentDigest) is the durable record; later catalog state never rewrites it.

5. Pack versioning rules

A pack version is an exact SemVer string. Authors classify each release by its effect on consumers of the pack — operators who activate it and competitors who solve its problems — not by how much code changed.

What counts as breaking / additive / patch for a pack.
Bump Trigger Examples
MAJOR (breaking) Any change that can break an operator's expectations or an existing scoring outcome. Removing or renaming a problem id; changing a problem's scoring kind or its flag / phase semantics; tightening requiredRuntimes to a capability not previously needed; narrowing the core range so previously supported cores are excluded; removing a declared dependency that consumers relied on.
MINOR (additive) Backward-compatible additions: existing problems behave identically and existing activations remain valid. Adding a new problem; adding an optional portal slot; widening the core range to cover more cores; adding optional metadata fields that older readers ignore safely; adding a non-required runtime.
PATCH Fixes that change neither the catalog surface nor scoring outcomes. Wording / documentation fixes; a template typo with no behavioral effect; non-scoring asset corrections.

5.1 Immutability of a published revision

A published id@version is bound to exactly one content digest. The snapshot store enforces this: re-installing identical content is a no-op, and installing the same id@version with a different digest is rejected with DIGEST_CONFLICT. The remedy is always to bump the version; revisions are never edited in place. This is what lets a lock pin (packId, version, contentDigest) and have it mean the same bytes forever, and it is why deployment provenance can be trusted long after the pack moved on.

Pre-release identifiers (for example 2.0.0-rc.1) are permitted by the manifest's SemVer grammar and are how a Preview revision is published (§8). A pre-release is still immutable by digest; promoting it to a stable line means publishing the stable version (2.0.0), not mutating the pre-release.

6. SDK contract guarantees (aligns with #2106)

@tenkacloud/problem-sdk is the public surface an author builds a pack against (types, schema helpers, validation entry points). Its compatibility promise mirrors SemVer precisely:

SDK bump Promise Author impact
MAJOR Breaking changes are allowed: removing or renaming an exported symbol, changing a type's shape, or tightening a validation rule. Requires author action; covered by a migration guide (§12).
MINOR Additive only: new exports, new optional fields, looser validation. Nothing previously valid becomes invalid. Drop-in; no author action.
PATCH Bug fixes that do not change the documented contract. Drop-in.

The promise is mechanically guarded. Every SDK release produces a checked-in API report (the exported surface), and a diff that adds a breaking change without a major bump fails the release gate. A contract fixture suite of reference packs validates against the SDK; a fixture that passed under a minor or patch and fails afterward is a release blocker (§11).

7. Schema evolution rules (manifest and metadata)

The manifest is currently schemaVersion: 1 and .strict() — every unknown top-level field is rejected. Problem metadata is more permissive in its projection fields. Both evolve under one set of rules:

Change Allowed without major? Rule
Add an optional metadata field Yes Older readers ignore it safely — but only when the schema version explicitly permits forward-compatible reads. An additive field never changes the meaning of an existing field.
Add a required field No Breaks older packs that omit it; requires a new schema major or a migration path.
Remove a field No Requires a new schema major or a migration path.
Change a field's meaning, or give it a stricter interpretation No A semantic or stricter-meaning change to an existing field requires a new schema major or a migration path. Silent reinterpretation is prohibited.
Tighten validation on an existing field (e.g. new .strict() rejection) No Treated as breaking; needs a major or a deprecation window (warn, then error).
Forward compatibility is opt-in, not assumed. "Older readers ignore unknown fields safely" holds only where the schema version's rules explicitly allow it. The .strict() manifest does not ignore unknown top-level fields today, so a new manifest field is a schema change, classified by the same table. Metadata projections, which are designed to be extended, are where additive forward-compatible reads apply.

8. Deprecation lifecycle and status taxonomy

Every versioned, externally observable thing — a pack revision line, a runtime capability, an SDK API, a manifest schema version — carries one of four statuses. The taxonomy and its transitions are the same regardless of what is being versioned.

Status taxonomy and what each state means for install and activation.
Status Meaning Install / activation Validator output Minimum notice window
Preview Available for evaluation; the contract may change. Published as a SemVer pre-release. Allowed only with an explicit opt-in; never the default selection. Informational note that the surface is Preview. None — no stability promise is made.
Supported The full compatibility guarantee of this ADR applies. Allowed. No diagnostic. n/a
Deprecated Still works exactly as before, but slated for removal. The replacement is named in docs and in machine-readable output. Allowed; behavior unchanged. Warning diagnostic with the replacement and the planned removal version. At least 2 minor core releases (or one major), and never fewer than 90 days, between the deprecation announcement and removal.
Removed No longer available. Rejected. Fails closed at install / activation, never mid-event without explicit operator action. Error diagnostic naming the removal version and replacement. n/a (the window elapsed before this state)
Warn first, then error. A deprecated capability, field, or version emits a warning during its support window and only becomes an error at or after the declared removal version. An author therefore always sees the warning — in docs and in diagnostic output — before anything fails. When feasible, a deprecation ships with a codemod or migration validation so the fix can be applied and checked mechanically.

9. Validator diagnostic codes

Compatibility outcomes are reported with stable, machine-readable codes so tools and authors can switch on them. Failure codes reject; warning codes inform. The failure codes reuse the existing composer reasons so policy and code stay in lockstep.

Compatibility diagnostic codes.
Code Severity Raised when
CORE_RANGE_UNSATISFIED Error The platform core version is outside the pack's core range (satisfiesCoreRange returns false).
RUNTIME_UNAVAILABLE Error A declared requiredRuntimes capability is not in the platform set.
DUPLICATE_PROBLEM_ID Error A problem id collides across sources (packs cannot override core; no last-writer-wins).
DIGEST_CONFLICT Error The same id@version is installed with a different content digest — an immutable revision cannot change.
SCHEMA_VERSION_UNSUPPORTED Error The manifest schemaVersion is newer or older than the core supports.
SDK_MAJOR_INCOMPATIBLE Error The pack was built against an SDK major the current core no longer accepts.
RUNTIME_DEPRECATED Warning A required runtime capability is Deprecated; names the replacement and removal version.
FIELD_DEPRECATED Warning A manifest or metadata field in use is Deprecated; names the replacement.
SDK_API_DEPRECATED Warning An SDK export the pack uses is Deprecated; names the replacement and removal major.
PREVIEW_SURFACE_IN_USE Info The pack depends on a Preview capability, field, or API; no stability promise.

10. Machine-readable compatibility matrix

Each core release publishes a compatibility matrix so a tool — or an author's CI — can decide admissibility without running the platform. It is JSON, versioned by its own schemaVersion, and is the declarative companion to satisfiesCoreRange. 

{
  "schemaVersion": 1,
  "coreVersion": "1.6.0",
  "manifestSchemaVersions": { "supported": [1], "deprecated": [], "removed": [] },
  "sdk": { "current": "1.6.0", "minimumSupportedMajor": 1 },
  "runtimes": [
    { "provider": "aws",    "engine": "cloudformation", "status": "supported" },
    { "provider": "gcp",    "engine": "deployment-manager", "status": "supported" },
    { "provider": "azure",  "engine": "arm", "status": "supported" },
    { "provider": "sakura", "engine": "terraform", "status": "preview" },
    { "provider": "aws",    "engine": "cdk-legacy", "status": "deprecated",
      "replacement": "aws/cloudformation", "removeIn": "2.0.0" }
  ]
}

A consumer evaluates a pack as: the manifest schemaVersion is in supported; the core version satisfies the pack's core range; every requiredRuntimes entry maps to a non-Removed runtime (a Deprecated one warns). The same logic the composer runs in process is thus reproducible from the published artifact.

11. Release policy and gates

11.1 How a pack revision is published and pinned

  1. The author bumps manifest.version per §5 and commits.
  2. The platform resolves an exact, immutable revision (a Git commit / ref or a local directory), never a mutable branch.
  3. Install validates and snapshots the content, computing the content digest and writing a lock entry that pins (packId, version, contentDigest, coreVersion, schemaVersion, sdkVersion).
  4. Activation pins that digest to a tenant / event; deployment records carry the same provenance so the resolved identity survives later upgrades.

Because the digest is the identity, the platform signals incompatibility instead of silently breaking: a revision that no longer satisfies the current core range or runtime set is rejected at install / activation with the matching diagnostic code, while already-pinned revisions keep running untouched.

11.2 Core release gate

A core release cannot change a Supported fixture's outcome without an explicit, recorded compatibility exception (a one-line entry in the release notes naming the fixture, the old and new outcome, and the justification). Absent that exception, a changed Supported-fixture outcome blocks the release.

The following fixture classes must pass before any core release:

Fixture classes required before a core release.
Fixture class What it proves
SDK API report The exported SDK surface changed only in ways the version bump allows.
Manifest schema fixtures Known-good manifests still validate; known-bad ones still fail with the same diagnostic codes.
Compatibility-range fixtures A table of (core version, range) pairs yields the same accept / reject result — satisfiesCoreRange is characterized, not free to drift.
Reference packs One pack each for AWS, GCP, Azure, Sakura, plus a scoring pack, a portal-UI pack, and a composite pack, validate, snapshot, and compose unchanged.
Provenance preservation An event snapshot taken before the release keeps its resolved metadata, digest, and provenance after it.
11.3 Release checklist
  • Bump the affected version axes per their rules; no conflated bumps.
  • Regenerate and diff the SDK API report; reconcile any breaking diff against the bump.
  • Run all fixture classes in §11.2; investigate every changed Supported outcome.
  • Record any unavoidable Supported-outcome change as a compatibility exception in the release notes.
  • Publish the updated compatibility matrix (§10).
  • For any new deprecation: announce in docs and machine-readable output, set the removal version, and ship a codemod / migration validation where feasible.
  • Confirm no installed snapshot is auto-upgraded and no event snapshot is rewritten.

12. Migration guide template

Every breaking change (a pack major, an SDK major, a manifest schema major, or a runtime removal) ships a migration guide following this template, so an author can move forward mechanically.

Migration guide template 
Title: Migrating <thing> from <old> to <new>

1. What changed and why
   - One-paragraph summary of the breaking change.

2. Affected surface
   - Fields / exports / capabilities / problem ids that changed, with before → after.

3. Required actions (in order)
   - [ ] Step 1 ...
   - [ ] Step 2 ...

4. Automated migration
   - Codemod / validation command, if available, and how to run it.

5. Verification
   - The fixture(s) or validator command that confirm the migration is complete
     (expect no remaining FIELD_DEPRECATED / SDK_API_DEPRECATED / RUNTIME_DEPRECATED warnings).

6. Timeline
   - Deprecation announced in: <core version / date>
   - Removed in: <core version>
   - Minimum support window observed: <2 minor releases / 90 days, whichever is longer>

13. Consequences

Positive

  • Authors know exactly what is stable: Supported surfaces carry the full guarantee, Preview ones carry none, and the boundary is machine-readable.
  • Maintainers can evolve the platform safely: the fixture gate and API report make accidental breakage a failed release rather than a field incident.
  • Any implementation has an explicit rulebook — accept/reject is total and deterministic, and the diagnostic codes are fixed — instead of guessing compatibility behavior.
  • Operators are protected: incompatibility surfaces at install / activation, never mid-event, and provenance on existing snapshots is durable.

Costs and obligations

  • Maintaining the reference-pack fixtures (seven classes) and the API report is recurring work that gates every release.
  • Deprecations are slow on purpose: a minimum of two minor releases / 90 days means the platform carries deprecated surfaces for a while.
  • The compatibility matrix is another artifact to publish and keep in sync per core release.
Explicitly rejected behaviors. No blanket promise that every old pack works forever; no silent auto-upgrade of installed pack snapshots; no runtime behavior change hidden behind the same provider/engine identifier; and no breaking of existing event snapshots when a pack changes. Any of these would void the guarantees above.

14. Alternatives considered

Alternative Why rejected
One conflated version for core + SDK + manifest Forces a major bump of everything whenever any one surface breaks, and makes a pack's real requirement unexpressible. Independent axes (§3) keep each promise honest.
Auto-upgrade installed snapshots to the newest compatible revision Violates immutability and reproducibility; an event's behavior could change underneath competitors. Pinning + explicit operator action (§4.4) is required instead.
"Be liberal": ignore unknown fields everywhere, never reject Silently accepts manifests that mean something the core does not implement, turning author mistakes into runtime surprises. Forward compatibility is opt-in per schema version (§7); the manifest stays .strict().
Reinterpret a provider/engine identifier with new behavior in place Breaks the frozen-behavior guarantee — the same identifier would mean two things across releases. New behavior gets a new identifier (§4.3).
Hard-cut removals (no deprecation window) Leaves authors no warned path forward and risks breaking live events. The warn-first / minimum-window lifecycle (§8) is mandatory.

15. Rollout

This ADR is a policy, not a code change, so its adoption is incremental and rides on the existing problem-pack work items.

Until those follow-ups land, the policy still governs by review: the accept / reject result, immutability, and the no-auto-upgrade / no-snapshot-rewrite rules are already enforced in code today (satisfiesCoreRange, the digest lock, the pinned-removal refusal), so the platform is consistent with this ADR from day one.

ADR-017: Cloud Action Intent / Trust Bridge — cross-cloud authority transfer

credentials を移送せず、 signed intents を移送して provider-native の短命 authority と交換する protocol 層を packages/trust-bridge として持つ

Status:Accepted 2026-05-15
Tracking: #795
Related: ADR-002、 ADR-007、 ADR-010、 ADR-015、 ADR-016

Context

TenkaCloud は AWS 専用の SaaS から、 多 cloud 競技 (= AWS + GCP + Azure + Cloudflare 上で問題を deploy / scoring する形) へ広げる構想がある。 同時に、 AI agent から自動 deploy / destroy を呼ぶ場面でも認可境界が課題になる。

「multi-cloud で資源を扱う」 問題の hard part は provisioning ではなく authority transfer である。

あるクラウド上の workload が、 別 provider / 別 account でクラウド操作を実行する権限を、
**長寿命 credential を信頼境界を越えて移送せず** に、 どう安全に得るか?

既存 primitive は十分にある:

Primitive役割
OIDC / JWT / JWS標準的な signed token 表現
OAuth Token Exchange (RFC 8693)token → token の交換 protocol
AWS AssumeRole / AssumeRoleWithWebIdentity短命 STS credentials の発行
GCP Workload Identity Federation外部 IdP の token で GCP service account を引く
Azure Federated Identity Credential外部 OIDC で Azure AD app を引く
SPIFFE / SPIREworkload identity 配布の標準
OPA / Cedarpolicy engine

しかし TenkaCloud には これらより 1 段上 の cloud action authority transfer protocol 層が無い。 具体的には、 「誰が、 何の context で (tenant / event / team / problem / deployment)、 どの provider に、 どの action を、 どの scope で、 どれくらいの TTL でやろうとしているか」 を構造化して signed 化する protocol が欠けている。

なぜ既存 primitive 単体では足りないか

OIDC や AssumeRole は identity や credential の primitives であって、 action intent の primitive ではない。 「Team Alpha が Problem hello-world の deploy を AWS account 449... に実行しようとしている」 のような context-aware request を運ぶ data model が無い。

結果として、 多くの実装は次の anti-pattern に倒れる:

AWS runner が GCP service account key を保管する
AWS runner が Azure client secret を保管する
AWS runner が Cloudflare API token を保管する
Terraform runner が全 provider credential を持ちこむ

これは enterprise-grade cloud automation / AI agent governance / cloud competition infrastructure のいずれの観点でも受け入れがたい。 TenkaCloud は credentials を移送せず、 signed intents を移送する モデルを採る。

制約

制約影響
Custom cryptography 禁止JWS / JWT / OIDC など標準 library を再利用。 独自署名 algorithm を発明しない
既存 AWS flow を壊さないADR-002 で確立した CompetitorDeployRole + ExternalId の経路は protocol 層 (AwsAssumeRoleExchange) の入口として再利用する
Cost 0 原則Phase 1 では DDB / Lambda / IAM の追加リソースを最小に保つ。 token 検証は in-Lambda で完結する
OAuth / OIDC / SPIFFE の置換ではない本 library は higher-level protocol。 下位 primitive は既存 library に委譲
1 つの universal standard を最初から狙わないTenkaCloud 内部利用 → OSS 公開 → community feedback の順で熟す

Decision

Accepted: packages/trust-bridge という TenkaCloud 内部 library を新設し、 credentials を移送せず、 signed CloudActionIntent を移送して provider-native の短命 credential と交換する protocol 層を担わせる。 当初は AWS adapter 1 件で内部利用、 後続 phase で GCP / Azure / 外部公開を進める。

D1
CloudActionIntent schema
tenant / event / team / problem / deployment / target / action / constraints を構造化する claim shape。 Zod で type-safe に narrowing 可能
D2
JWS 署名 + 検証
canonical JSON を JWS (RFC 7515) で署名。 既存 library (= jose or panva/jose) を再利用、 custom crypto は書かない
D3
ProviderTokenExchange interface
provider 別の交換ロジックを pluggable に。 初版は AWS (AssumeRoleExchange)、 Phase 4 で GCP / Azure / Cloudflare adapter を追加
D4
PolicyEvaluator interface
policy decision は library に hard-code せず hook 化。 inline allowlist / OPA / Cedar / metadata constraints を後付け可能
D5
CloudActionAuditRecord
decision 1 件 = audit 1 件。 enterprise 監査 / incident investigation / AI agent governance / competition replay debug の起点
D6
5 phase rollout
Phase 1 内部 skeleton → Phase 2 AWS adapter → Phase 3 Deploy API 統合 → Phase 4 GCP / Azure experiment → Phase 5 protocol 文書化

D1: CloudActionIntent schema

TenkaCloud の domain model (= tenant → event → team → problem → deployment) を そのまま claim 化することで、 「context-aware authority bridge」 にする (= generic credential broker ではなく)。

export interface CloudActionIntent {
  readonly version: "tenkacloud.cloud-action-intent.v1";
  readonly requestId: string;       // ULID 形式
  readonly nonce: string;            // replay 防止
  readonly source: {
    readonly system: "tenkacloud";
    readonly tenantId: string;
    readonly eventId?: string;
    readonly teamId?: string;
    readonly problemId?: string;
    readonly deploymentId?: string;
    readonly targetId?: string;
    readonly workloadId: string;     // 発信元 workload の安定 ID
  };
  readonly target: {
    readonly provider: "aws" | "azure" | "gcp" | "cloudflare";
    readonly providerAccountRef: string;
    readonly region?: string;
    readonly resourceScope?: string;
  };
  readonly action: {
    readonly type: "deploy" | "destroy" | "inspect" | "collectOutputs" | "verifyTrust";
    readonly engine: "cloudformation" | "terraform" | "bicep" | "pulumi" | "script";
    readonly entry?: string;
    readonly requestedScopes: readonly string[];
  };
  readonly constraints: {
    readonly ttlSeconds: number;
    readonly notBefore?: string;
    readonly expiresAt: string;
    readonly maxEstimatedCostUsd?: number;
    readonly allowPrivilegeEscalation: boolean;
  };
}

schema 互換性は version field で扱う (= 将来 v2 を追加するときは破壊変更を避けつつ並走させる)。

D2: JWS 署名 + 検証

署名は JWS (RFC 7515) に閉じる。 canonical JSON は JSON.stringify + keys ソート方式を採用 (= canonical-json npm 等)。 鍵管理は AWS KMS asymmetric key (= 既に Free Tier 内で使える) を first-class にする。 私鍵を Lambda env に置かない。

library 出力:

export interface CloudActionToken {
  readonly format: "jws";
  readonly token: string;   // JWS compact serialization
}

D3: ProviderTokenExchange interface

provider 別の adapter を統一 interface に揃える。 既存 AWS の AssumeRole + ExternalId 経路を library の adapter として包み直す (= ADR-002 の経路を破壊せず、 library 経由でアクセスする形に変える)。

export interface ProviderTokenExchange {
  readonly provider: "aws" | "azure" | "gcp" | "cloudflare";
  exchange(
    token: CloudActionToken,
    context: ExchangeContext,
  ): Promise<ProviderCredential>;
}

Phase 4 で GcpWorkloadIdentityFederationExchange / AzureFederatedCredentialExchange / CloudflareScopedTokenExchange を追加する。 Cloudflare は OAuth Token Exchange 経路を採る。

D4: PolicyEvaluator interface

policy decision は library の責務外。 hook 経由で外注し、 implementation は組み合わせ自由にする (= inline allowlist / OPA / Cedar / tenant policy document / problem metadata constraints / Terraform plan / CFn template risk analysis)。

export interface PolicyEvaluator {
  evaluate(intent: CloudActionIntent): Promise<PolicyDecision>;
}

export interface PolicyDecision {
  readonly decision: "allow" | "deny" | "needs_approval";
  readonly reason?: string;
  readonly allowedScopes?: readonly string[];
  readonly maxTtlSeconds?: number;
  readonly policyVersion?: string;
}

D5: CloudActionAuditRecord

policy decision 1 件 = audit log 1 件。 「誰が、 いつ、 どの context で、 どの provider に、 何を要求して、 何が決定され、 何 TTL の token が発行されたか」 を構造化保存する。

export interface CloudActionAuditRecord {
  readonly requestId: string;
  readonly tenantId: string;
  readonly eventId?: string;
  readonly teamId?: string;
  readonly problemId?: string;
  readonly deploymentId?: string;
  readonly targetId?: string;
  readonly provider: string;
  readonly action: string;
  readonly decision: "allow" | "deny" | "needs_approval";
  readonly issuedCredentialExpiresAt?: string;
  readonly policyVersion?: string;
  readonly createdAt: string;
}

初版は CloudWatch Logs に structured JSON で出す (= ADR-015 で確立した trace-log と同じ format)。 後続で DDB / S3 archive へ落とす経路を検討する。

D6: 5 phase rollout

Phase内容独立 PR で merge 可能か
1packages/trust-bridge 新設、 schema / signing / verification / TTL / nonce / audit / unit testYes (= 内部 dormant library として独立価値)
2AwsAssumeRoleExchange 実装、 既存 competitor account / ExternalId 経路を adapter 経由でラップYes (= AWS 経路の挙動不変)
3Deploy API が CloudActionIntent を発行 → 検証 → exchange → AWS 操作 の経路を内部利用、 user-visible API は不変Yes (= 内部実装の置き換え)
4GCP / Azure adapter prototype、 1 つの cross-cloud demo targetYes (= 1 provider ずつ独立 PR)
5docs/architecture/cloud-action-intent.md で protocol 仕様を公開 (= claim model / threat model / provider mapping / OAuth/OIDC/SPIFFE との関係)Yes (= docs のみ)

各 phase は INVARIANT_PR_SHIPS_WORKING_INCREMENT に従う。 Phase 1 は dormant library で OK、 Phase 3 から既存 Deploy 経路が library 経由になる。

Consequences

Positive

  • cross-cloud authority の安全な経路を持つ: 私鍵を持ち回さず、 signed intent + provider-native short-lived credentials の組み合わせで cloud 操作を実行できる。 enterprise audit / AI agent governance / cloud competition の 3 ユースケースを同じ protocol で扱える
  • TenkaCloud domain model を活かす: tenant / event / team / problem / deployment が claim になっているので、 「Team Alpha の Problem hello-world の deploy 要求」 という形で意味を持った authority transfer が可能
  • policy hook で組織別の要件を吸収: OPA / Cedar / tenant 別 allowlist / 問題 metadata の上限額制限を後付けできる。 policy hard-code を避けることで library を再利用しやすくする
  • OSS 公開時の position が明確: 既存 primitive (= OIDC / SPIFFE / Token Exchange) の上位層であり、 universal standard を狙わずに TenkaCloud の domain knowledge を凝縮した library として出せる
  • AI agent からの cloud 操作を audit 可能にする: Claude Code / Codex CLI が自動 deploy を呼ぶ際、 全 decision が CloudActionAuditRecord として残るので 「AI が勝手に大規模 deploy した」 系の incident に対する追跡経路を提供する

Negative / Trade-off

  • library を 1 つ maintain する負担: packages/trust-bridge の API / behavior / breaking change policy を管理する必要がある。 internal 利用 → OSS 公開の moment まで API を頻繁に変える
  • 政治的合意形成のリスク: 「TenkaCloud 独自 protocol」 として始まるが、 業界標準にしたい場合は OAuth WG / IETF への提案が要る。 初版は標準化を狙わない (= 内部利用が成立してから議論)
  • provider adapter の脆さ: AWS / GCP / Azure / Cloudflare それぞれの federation API は仕様変更があり、 adapter ごとに maintenance burden が線形に積む
  • policy engine 選定の決定先送り: hook 化したことで OPA / Cedar / 独自 DSL の決定が後ろに送られる。 Phase 4-5 で 1 つに収束させないと policy 表現がバラバラになる

Risk

Risk影響緩和策
token replay古い token で意図しない deploy が走る短 TTL (= 1〜5 min) + nonce + audience binding の 3 段で防御。 nonce 保存は DDB 1 件 (= Free Tier 内)
confused deputylibrary が誤った tenant / team の claim で別 tenant の credential を発行tenant / event / team / target の cross-check を library 内で常時実施。 policy hook が deny する経路も用意
over-broad provider scoperequested scopes が広すぎて over-privilege な credential が出るpolicy hook で allowedScopes を絞る。 default は maxTtlSeconds: 300 + 最小 scope。 problem metadata の上限を constraint に
tenant boundary escapetenant A の signing key で tenant B の claim を作るtenant 別 KMS key 分離 (= ADR-002 と同じ思想)。 audience binding に tenant 別 endpoint を入れる
target account mismatchclaim の providerAccountRef と実 exchange 先の account がズレるadapter が claim 内 providerAccountRef と adapter 設定 (= AssumeRole RoleArn) の account ID を strict 比較 (= mismatch なら deny)
leaked signed tokentoken が log / network に漏れて再利用されるnonce で 1 度きりに制約 + TTL 5 min 以内 + audience binding (= 流出しても別 endpoint で使えない)
malicious problem package問題 template が過大権限を要求problem metadata に scope 上限を宣言、 policy hook が問題側 metadata と組織側 policy の AND で評価
destroy が context 不在で失敗deploy 時の context が消えて destroy が新規 intent を作れないdestroy は別 signed intent で発行 (= 独立 audit を残す)。 deploy 時の context を deployment metadata に保存し、 destroy intent が参照する

Alternatives considered

選択肢判定理由
A. credential を Lambda env / DDB に保管して直接使う却下各 provider の long-lived credential を 1 workload に集約する anti-pattern。 enterprise / AI agent / 競技 infra の 3 use case すべてで受け入れがたい
B. SPIFFE / SPIRE を直接採用却下workload identity 配布の標準ではあるが、 cloud action intent 層の primitive ではない。 SPIFFE は本 library の 1 段下に位置する (= 将来 workloadId 配布で利用検討余地はある)
C. OAuth Token Exchange (RFC 8693) を直接採用却下token → token 交換の標準 protocol だが、 TenkaCloud の context (= tenant / event / team / problem) を claim に乗せる規約が無い。 本 library が context-aware に拡張する立ち位置
D. provider 別 library 4 つを並走 (= AWS 用 / GCP 用 / Azure 用 / Cloudflare 用)却下共通の claim shape / signing / policy hook / audit を 4 倍 maintain する。 abstraction を 1 つの library に固める方が長期保守コストが低い
E. packages/trust-bridge 内部 library + provider adapter pattern採用既存 primitive を再利用しつつ、 TenkaCloud domain model を claim 化する higher-level layer を 1 個追加。 内部利用 → OSS 公開の順で熟す
F. 既存 AWS-only flow のまま multi-cloud を諦める却下戦略的 rationale に反する (= TenkaCloud Lite + Trust Bridge は adoption + 技術的 moat の 2 軸)。 Lite だけでは差別化が薄い

Open Questions

本 ADR では下記を Phase 1 着手時に再検討するものとして残す。

  1. CloudActionIntent は JWT claim 直接か、 canonical JSON を JWS で wrap するか: JWS で wrap する方が canonical 形が安定する。 ただし JWT 直接の方が外部 library 互換性が高い。 Phase 1 で benchmark + 既存 audit エコシステムとの相性を見て決める
  2. nonce 保存先: DDB 1 件 / Redis-like / caller 提供 のどれにするか。 TenkaCloud は DDB 1/1 PROVISIONED 制約があるため DDB を default にし、 nonce TTL 5 min で TTL 属性削除に任せる方針
  3. policy engine は library 同梱か hook のみか: hook のみで一旦リリースし、 利用パターンが固まったら built-in evaluator (= inline allowlist) を 1 つ加える方針
  4. パッケージ分割: 1 package or 4 package: 初版は packages/trust-bridge 1 個。 provider adapter が増えて bundle size が問題になったら @tenkacloud/trust-bridge-core + @tenkacloud/trust-bridge-aws 等に切り出す
  5. Terraform plan approval flow との対応: plan → human approval → apply の flow で、 plan 段階で intent を生成し approval 後に exchange する 2 段モデルが自然。 Phase 3 で実装するときに固める
  6. destroy は元 deploy context が必要か、 別 signed destroy intent か: 別 destroy intent を default にする。 deploy 時の deploymentId を destroy intent の source.deploymentId に書く形で audit chain を成立させる
  7. CloudActionIntent を Provider Engine に直接公開するか: Phase 3 では TenkaCloud 内部のみ。 Phase 5 (docs 公開) と同時に外部 Provider Engine への公開を検討
  8. 最小 demo の定義: 「AWS account A の Lambda が、 AWS account B の CFn stack を deploy する」 を最小 demo にする (= 既存 AWS competitor account flow が adapter 経由で動く)。 Phase 2 完了で測定可能

Relationship to other ADRs

  • ADR-002 (cross-account federation): 本 library の AWS adapter は ADR-002 で確立した CompetitorDeployRole + ExternalId 経路を内部利用する。 ADR-002 の wire 自体は変えない
  • ADR-016 (TenkaCloud Lite): 同時並行で進む adoption surface 改善。 Lite mode は本 library に依存しない (= Phase 4-5 で tenkacloud run CLI が内部利用するときに合流)
  • ADR-007 (outside-in architecture): 本 library は infrastructure 層に置き、 アプリ層に protocol 知識を漏らさない (= ADR-007 の規律に従う)
  • ADR-015 (ADR convention as harness): 本 ADR は ADR-015 の adr-self-contained rule に準拠 (= chat 痕跡 / 段階反映 metadata を残さない)

ADR-012: Problem plugin architecture — 4 アセット (resources / scoring / engine / portal) + generic dispatcher

Status:Proposed 2026-05-12
Trigger: PR-608 (#606 Phase 2 score engine) close
Related ADR: ADR-001、 ADR-005、 ADR-008 (#574 user WIP)
Related Issue: #572、 #606

欲しい姿 (= 一目で分かる version)

1 問題は 4 つのアセット を持つ。Platform は 4 つを generic に host するだけ。

problems/<id>/
├── metadata.json    # 宣言 (既存)
├── template.yaml    # ①リソース      = 競技者 AWS account に立つ CFn
├── scoring/         # ②採点          = 観測 → スコア計算
│   └── index.ts
├── engine/          # ③攻撃 / 仕組み = 時間駆動の active な変化 (Battle 主用途)
│   └── index.ts
└── portal/          # ④ダッシュボード = 競技者の画面
    └── index.tsx

新問題を足す = この dir を 1 個 git add するだけ。 platform は触らない。 差し替えも同 dir を更新するだけ。

ユーザー指摘 (2026-05-12): 「攻撃とかの仕組みは問題側のコードで作ればいい」 + 「Challenge は共通化できるが、Battle は柔軟性が必要」 = この ADR の根本方針。

Challenge と Battle のスタンス差

ChallengeBattle
性格 静的・個別演習。flag 提出 or 単純 uptime 動的・対戦型。時間駆動の攻撃 / 妨害 / 多段 phase
採点 (②) 宣言で十分 (= 80% case)。metadata.json の scoring.kind = "flag" or "uptime-flat" で platform 内蔵 evaluator が動く。scoring/index.ts は 不要 カスタム Lambda 推奨 (= 80% case)。scoring/index.ts を問題側で書き、phase / platform 分類 / 多段配点 / bonus を自由に表現
攻撃 / 仕組み (③) 原則無し。Challenge は時間駆動の active 攻撃を持たない 必須 (= 多くの Battle で)。engine/index.ts を schedule で invoke、競技者環境を能動的に変える (= EC2 latency 注入 / phase flag flip / 攻撃発動)
portal (④) generic で十分。flag 提出 form + score 表示は platform 内蔵 component を流用。portal/ は不要 カスタム推奨。Battle 固有 UX (= phase countdown / 攻撃 timeline / multi-slot 登録 form) を portal/index.tsx で書く
具体例 hello-world (flag) / hello-world-battle (uptime-flat 中身は実は Challenge 寄り) security-battle-royale / microservice-migration-battle

運用ルール: Challenge は metadata + template だけで完結 (= 雛形がほぼコピペ)。Battle は 4 つ揃える前提で書く (= 個別 build / test が必要)。Platform はどちらにも対応する generic dispatcher。

4 アセットの contract

① リソース (template.yaml) — 既存

CFn template。競技者 AWS account に deploy される。passive な仕掛け (= EC2 user-data 内の cron / EventBridge Scheduler rule 等で deploy 直後から自動進行する妨害) はここに同梱して良い。

例: microservice-migration-battle の passive 仕掛け 
Resources:
  Ec2Instance:
    Type: AWS::EC2::Instance
    Properties:
      UserData:
        Fn::Base64: !Sub |
          #!/bin/bash
          # 60 min 後に tc qdisc で 200ms latency 注入 (= EC2 劣化攻撃)
          echo "0 */60 * * * /usr/sbin/tc qdisc add dev eth0 root netem delay 200ms" | crontab -

UserData 内なので platform は知らない、ただ deploy するだけ。

endpoint = default + override 可能な slot (= 統一モデル)

全 endpoint は 1 つの統一モデル で扱う:

要素内容
slot問題が宣言する endpoint の役割名 (例: main / admin / users)
default URLCFn output から自動取得 or 固定値。deploy 直後はこれが使われる
override競技者が portal UI で別 URL に変更可能。 effective URL = override || default

なぜこの形か: Battle 問題では競技者が deploy 直後の構成を 変えていく ことが本質的:

  • security-battle-royale: default は S3 直 URL → 競技者が CloudFront を前段に置いたら新 URL で override
  • microservice-migration-battle: default は EC2 の 3 path → Lambda / ECS / App Runner に切り出したら slot ごとに override
  • hello-world-battle: default の EC2 URL のまま (= override 不要)、あるいは CDN を被せて override
// problems/<id>/metadata.json (= security-battle-royale 例)
{
  "endpoints": [
    {
      "slot": "main",
      "default": { "from": "cfn-output", "key": "EndpointUrl" },
      "overridable": true,
      "label": "メイン endpoint",
      "description": "deploy 直後は S3 直、CDN / WAF 等を被せて変更可能"
    },
    {
      "slot": "admin",
      "default": { "from": "cfn-output", "key": "AdminUrl" },
      "overridable": true
    }
  ]
}
// microservice-migration-battle 例 (= 3 slot、各 slot を別 hosting に切り出す)
{
  "endpoints": [
    { "slot": "users",   "default": { "from": "cfn-output", "key": "Ec2BaseUrl", "appendPath": "/users" },   "overridable": true },
    { "slot": "orders",  "default": { "from": "cfn-output", "key": "Ec2BaseUrl", "appendPath": "/orders" },  "overridable": true },
    { "slot": "catalog", "default": { "from": "cfn-output", "key": "Ec2BaseUrl", "appendPath": "/catalog" }, "overridable": true }
  ]
}

Platform は 3 機能の generic な endpoint registry を提供:

  1. deploy 直後に CFn output から default URL を抽出して各 slot に書き込む
  2. 競技者の override (POST /problems/:id/endpoints { slot, url }) を受け付ける
  3. effective URL (= override があれば override、無ければ default) を scoring / engine に渡す

scoring/index.ts / engine/index.ts には統一形で渡る:

event.endpoints = {
  users:   "https://d12345.cloudfront.net/users",     // ← competitor が CDN 被せて override
  orders:  "http://ec2-abc.amazonaws.com/orders",     // ← default のまま (未 override)
  catalog: "https://api-gw.execute-api.../catalog"    // ← Lambda + API GW に移して override
}

問題側は slot 名で endpoint を引いて probe するだけ。endpoint が 1 つでも N 個でも同じ contract。

Challenge (flag 系) は endpoint 概念を持たない (= 提出 form 経由)。metadata.json の endpoints 配列を省略するだけ。

② 採点 (scoring/index.ts) — Battle 主用途、Challenge は省略可

Platform から 1 分毎に invoke される Lambda。観測 → スコア delta を返す pure function。 副作用 (= state 書き換え / 攻撃発動) は ③ engine に分離。

// problems/<id>/scoring/index.ts
import type { ProblemScoringHandler } from "@tenkacloud/scoring-sdk";

export const score: ProblemScoringHandler = async (event) => {
  // event: { tenantId, teamId, deployedAt, registeredEndpoints, prevState, phaseElapsedMin }
  // 戻り値: { delta: number, source: string, emitEvent: boolean, newState?: object }

  // 例: microservice-migration の phase-aware 採点
  if (event.phaseElapsedMin > 90) {
    const ok = await probe(`${event.registeredEndpoints.users}/score?legacy=true`);
    return { delta: ok ? 1000 : -100, source: "users-legacy", emitEvent: true };
  }
  // ... 通常採点
};
項目仕様
signature固定 (@tenkacloud/scoring-sdk が型を export)
呼出し頻度1 min 間隔 (= ADR-005 の polling 統一)
状態prevState / newState 経由で per-team の小さな state を platform DDB に保管。問題は直接 DDB を触らない
IAMper-problem 専用 role。外部 HTTP allow (= 競技者 endpoint probe)、AWS SDK は限定 (cross-tenant 不可)
戻り値delta を ScoreEvent stream に乗せる。source は問題ごと unique にして集計を分離

③ 攻撃 / 仕組み (engine/index.ts) — Battle 主用途

Platform が schedule (cron / time-of-day) で invoke する Lambda。state を変える / 競技者環境を能動的に揺らす。 採点と分離する理由は (a) 副作用と純粋関数を分けたい (b) 1 min より粗い頻度で十分なことが多い (c) state 変更の権限が要る (= IAM scope を採点と分離)。

// problems/<id>/engine/index.ts
import type { ProblemEngineHandler, ProblemEngineSchedule } from "@tenkacloud/scoring-sdk";

export const schedule: ProblemEngineSchedule = [
  { name: "ec2-degradation", afterDeployMinutes: 60 },
  { name: "legacy-switch",   afterDeployMinutes: 90 },
];

export const tick: ProblemEngineHandler = async (event) => {
  // event: { tenantId, teamId, deployedAt, scheduleName, registeredEndpoints, prevState }
  if (event.scheduleName === "ec2-degradation") {
    // SSM RunCommand で competitor EC2 に tc qdisc を追加 (= 攻撃発動)
    await ssm.send(new SendCommandCommand({ ... }));
    return { newState: { ec2Degraded: true } };
  }
  if (event.scheduleName === "legacy-switch") {
    return { newState: { legacyMode: true } };  // scoring がこれを読んで挙動を変える
  }
};
項目仕様
signatureschedule 配列 (= いつ呼ぶか) + tick 関数 (= 何をやるか)
呼出しPlatform が EventBridge Scheduler で時刻指定 invoke (deploy 時刻 + offset)
権限per-problem role。SSM RunCommand / EC2 stop / Lambda invoke / DDB write 等を明示許可。cross-tenant 不可、自分が deploy した resources にのみ触れる
statescoring と共有 (prevState / newState per-team)

④ ダッシュボード (portal/index.tsx) — Battle 主用途、Challenge は generic flow 流用

participant-portal が 動的に load する React モジュール。問題固有 UI を提供。

// problems/<id>/portal/index.tsx
import type { ProblemPortalPlugin } from "@tenkacloud/portal-plugin-sdk";

export default {
  problemId: "microservice-migration-battle",
  slots: {
    // 既定 slot に問題固有 component を挿す
    StatusPanel:       ({ team, scores, phase }) => (...),  // 各 slot の現状 + phase countdown
    RegistrationPanel: ({ slots, onRegister })   => (...),  // 3 endpoint URL 登録 form
  },
  routes: [
    { path: "/migration-help", element: <MigrationGuide /> },
  ],
} satisfies ProblemPortalPlugin;
項目仕様
buildVite で plugin 単体を ESM bundle 化 (target ~50 KB)、S3 配信
loadportal が runtime-config の problems[].pluginUrl から React.lazy(() => import(url))
共有 design systemCloudscape は SDK 経由で peer-dep (= bundle 二重化を避ける)
CSPportal hosting で plugin URL を script-src 許可リスト化

Platform 側 = generic dispatcher

Platform はこの 4 つの contract を満たす generic な host だけ実装する。問題固有のことは 一切しない。

platform 機能役割新規 / 既存
Deploy template.yaml を競技者 account に CFn deploy 既存 (ADR-001 / ADR-002)
Scoring runtime (a) Challenge: metadata の scoring.kind を解釈する 内蔵 evaluator (= flag / uptime-flat)
(b) Battle: per-problem scoring/index.ts Lambda を 1 min 毎に invoke		 新規 (Phase 2-3)
Engine runtime per-problem engine/index.ts の schedule 宣言を読んで EventBridge Scheduler rule を立てる。時刻になったら invoke 新規 (Phase 4)
State store per-(problem, tenant, team) の小さな state を保管する generic DDB (= scoring / engine が prevState / newState で出し入れ) 新規 (Phase 3)
Portal mount portal が起動時に runtime-config から plugin URL 一覧を読み、 該当画面で React.lazy 動的 load 新規 (Phase 5)
IAM 発行 per-problem Lambda role を problem deploy 時に発行、最小権限 新規 (Phase 4)

具体例 — 既存 + 新規 問題のマッピング

問題カテゴリ①template②scoring③engine④portal
hello-worldChallenge flag を出力する CFn (=既存) 不要 (metadata kind: flag) 不要 不要 (generic flag form 流用)
hello-world-battleBattle (sample) endpoint を出す CFn (=既存) 不要 (metadata kind: uptime-flat) 不要 不要 (generic uptime widget 流用)
security-battle-royaleBattle 攻撃可能な web app CFn (=既存) 必要 (攻撃検知ロジック を問題側で) 必要 (攻撃 trigger / mitigation) 必要 (攻撃 timeline UI)
microservice-migration-battleBattle EC2 + docker compose (=PR-605) 必要 (phased-polling + platform 分類 + bonus) 必要 (60min EC2 劣化 / 90min legacy switch) 必要 (3-slot 登録 form + phase countdown)

SDK が定める contract

plugin 作者が import する型を @tenkacloud/scoring-sdk + @tenkacloud/portal-plugin-sdk として packages で公開。SDK が問題側コードと platform を decouple する唯一の接面。

SDKexport説明
@tenkacloud/scoring-sdk type ProblemScoringHandler ② signature
type ProblemEngineSchedule ③ schedule 宣言型
type ProblemEngineHandler ③ tick signature
@tenkacloud/portal-plugin-sdk type ProblemPortalPlugin ④ default export 型
type PortalSlotComponents portal 標準 slot 群 (= StatusPanel / RegistrationPanel / HelpDrawer 等)
type PortalRouteDef 問題固有 sub-route

段階的ロールアウト

Phasescope影響
1 (本 PR) 本 ADR 採択 + 4 アセットの contract + SDK 型定義の skeleton doc のみ
2 problems/SCHEMA.json 拡張 (= Challenge 用の declarative kind 5 種を formalize) + 既存 hello-world / hello-world-battle metadata を新 schema に rewrite (挙動 unchanged) 既存 Challenge 系を新 schema に乗せる、platform 既存 evaluator はそのまま
3 per-problem state 用 DDB ProblemPluginState + scoring runtime (= Battle 用の scoring/index.ts Lambda を invoke する dispatcher)。SDK package @tenkacloud/scoring-sdk 公開 新 DDB + 新 dispatcher Lambda。既存 health-check-handler を refactor して dispatcher に統合
4 engine runtime (= engine/index.ts schedule から EventBridge rule を生成し時刻 invoke)。 microservice-migration-battle を本 architecture で再実装 (= PR-608 の代替) #572 完結。security-battle-royale の platform-bleed を audit + migrate
5 portal plugin runtime (= participant-portal の動的 load + Cloudscape peer dep + CSP)。SDK package @tenkacloud/portal-plugin-sdk 公開。 microservice-migration の 3-slot 登録 UI を plugin で実装 portal hosting に plugin URL config 追加。 既存問題は generic flow 流用で UI 変更なし
6 ADR-008 (#574) 統合: plugin code (= scoring / engine / portal) を private repo の S3 経由 presigned URL で配信。public 同梱は dev / sample のみ 本格運用問題の答え漏れ防止 (= microservice-migration の slow endpoint コード等)

Consequences

positive

  • 新問題追加は dir 1 個 + git add。platform に手を入れる必要なし
  • 問題の差し替えが容易。同 problemId で 4 アセットを update するだけ
  • Battle の柔軟性 = 問題作者が好きに書ける。攻撃の発動タイミング / 採点ロジック / UI 全部 plugin で
  • Challenge の共通化 = 雛形で済む。metadata + template だけで動く、SDK 学習不要
  • ADR-008 と統合可能: plugin code が private repo + S3 + presigned URL に乗れば答え漏れ対策完了
  • Community contribution の準備: 第三者が問題を寄稿する場合、 SDK で contract が明確なので review が機械化しやすい

negative

  • SDK の ABI 安定が必要 (= 一度公開した signature を不用意に変えると全 problem PR が壊れる)
  • per-problem Lambda の cold start (1 min 毎 invoke、~1s × 60 = 60s/h を許容)
  • UI plugin の lazy load による初回 200ms 程度の表示遅延 (= preload で緩和可)
  • 初期 setup: Phase 2-5 で計 ~5 PR 規模
  • 既存 security-battle-royale の platform-bleed audit が必要 (= 隠れた問題固有 logic が platform にある可能性)

open questions

  • scoring Lambda の 言語: TypeScript 縛り or Python も許容 (Container Image 化)
  • engine の権限上限: SSM RunCommand まで許可するか / EC2 stop / Lambda invoke 等の暴れ枠
  • operator (= 競技運営) 側に問題固有 UI が要るか (= application-admin-console plugin slot を追加するか、本 ADR の scope 外)
  • scoring / engine の同 lambda 統合 vs 分離: 副作用の有無で物理 Lambda を分けるか、1 Lambda の export を 2 つにするか
  • ADR-008 確定との順序: 待たずに Phase 2-5 を進めて Phase 6 で後付け、で OK か
  • 同 problemId の versioning (= A/B 並走運用)

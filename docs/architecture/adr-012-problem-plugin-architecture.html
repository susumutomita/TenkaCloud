ゲームの本質 — Platform が提供すべき要素

ユーザー指摘 (2026-05-12): 「ゲームというものの本質を捉えていかないといかない」「Overcooked! 的に要素が積まれていて、マルチタスク・得点・妨害の要素が組み込めるようになっていればかなり面白くなる」

Overcooked! (= 協力料理アクション) の面白さは 同時に進行する複数 task を限られた時間で捌く ところにある。 TenkaCloud Battle が「ゲーム」として面白くなる要素を分解すると:

Overcooked! 要素TenkaCloud Battle に置換するとPlatform が提供する仕組み
マルチタスク (= 焼く + 切る + 配膳を同時) 複数 endpoint slot を同時管理 / 複数 phase 進行 / 複数 disruption に対処 metadata の endpoints[] N slot / phases[] 多段 / disruptions[] 複数。 portal が同時に複数 panel で状態を表示
Score (= リアルタイムにお皿が出る) 得点が動くのが視覚的に分かる ScoreEvent stream の live 表示 / per-event delta animation / leaderboard リアルタイム更新 / 1 分間隔 polling で sparkline
妨害 (= 床が動く / 火災 / 客の文句) 競技中の active 妨害 (S3 content swap / latency 注入 等) metadata disruptions[] で declarative 宣言、 platform が時刻 / 条件 で発動を orchestrate、 operator UI で予告 / 即発動
時間制限 + カオス累積 競技時間が進むほど妨害が重なる phase 多段 (= 60min 劣化 → 90min legacy → 120min 終了 等)、 segment ごとの累積効果
視覚的フィードバック (= "皿が割れた!") 状況を一目で把握できる UI portal の StatusPanel に "次フェーズまで残り XX:XX" / 妨害発動時 toast / score delta の色付け
チームプレイ 1 team 内で役割分担 team scope の portal (= 既存 ADR-005)、 同 team 内では同じ画面を共有

= これら 6 要素を組み合わせて 1 つの問題を構成できる platform にすれば、 problem author が「ゲームとしての面白さ」を design できる。 Authoring 体験がここに乗る:

  1. Author は metadata で「 N slot + N phase + N disruption」 を宣言
  2. Platform は各要素を generic に dispatch / 可視化
  3. 競技者は同時進行を捌く面白さを体感

Platform は building blocks を提供、problem author が組み立てる という構図 (= レゴブロック)。 1 つの block が無いと「ゲームらしさ」が落ちるので、 Phase 2-5 で 6 要素を漏れなく実装する。

設計の山場: developer-friendly + AI-friendly な problem authoring

ユーザー指摘 (2026-05-12): 「この仕組みを誰でも実装で組み込めるようにプラットフォームで ガイドしないと、問題が作れない / 誰も乗れないプラットフォームになってしまう」 「開発者フレンドリー / AI フレンドリーに作らないと全くダメ」 「ここが体験の見せ所、設計の山場」

本 ADR の 核心は問題作成体験。 3 アセット / 厚 metadata DSL / disruption 機構は すべて「人間 + AI agent が 1 時間以内に新問題を ship できる」 ことを目的とする。 platform がどれだけ強力でも、 problem を作る人が居なければ何も起きない。

Developer-friendly な要件

  1. 30 分 onboarding: 新規 problem author が初回 PR を出すまでの目標時間
  2. Scaffolding コマンド: tenkacloud problem create <id> --kind battle で雛形 dir 生成 (metadata.json + template.yaml + portal/ + tests)
  3. Local dev loop: tenkacloud problem dev <id> で localhost で問題を起動、 portal UI も local rendering、 metadata 変更で hot reload。AWS deploy 不要で iteration
  4. Validation: tenkacloud problem validate <id> が
    • metadata DSL を JSON Schema で lint
    • template.yaml を cfn-lint
    • required endpoint / CFn output / disruption Lambda の存在確認
    • 具体的なエラーメッセージ (= 「scoring.kind が unknown: 'phasing-pollign' (= 'phased-polling' の typo?)」)
  5. Sample 問題が教材: 既存 4 問題 (hello-world / hello-world-battle / security-battle-royale / microservice-migration) を 完成形 with rich コメント で配置。author は copy-paste-edit で済む
  6. Documentation: docs/problems/AUTHORING.html で step-by-step 30 分 onboarding guide

AI-friendly な要件

  1. JSON Schema に AI hint を埋める: 各 field に description / examples / aiContext (= "When in doubt about scoring.kind, default to uptime-flat for Challenge, phased-polling for Battle")
  2. /create-problem skill を AI 対話型に拡張: 「難易度は?」「想定時間?」「妨害種類?」「3rd party hosting?」 を AI に質問させ、 完成した metadata + template + portal を一気に生成
  3. AGENTS.md に "Problem Authoring" セクション: AI agent が問題を作る時の参照リソース。 ヒューマン向け AUTHORING.html と pair で整備
  4. 既存問題が training data: 4 sample 問題は code comment / metadata description / portal component を AI が読んで模倣しやすい よう冗長気味に書く (= imperative 命令文 + WHY コメント)

Pattern library: 既存 4 sample を copy 元として配置

「こういう問題作りたい」copy 元 sample
flag 提出だけの個別演習hello-world (Challenge)
1 endpoint uptime 監視hello-world-battle (Battle minimal)
複数 endpoint 監視 + 攻撃検知security-battle-royale
多段 phase + 妨害 + 3 hosting platform 分類microservice-migration-battle

ユーザー指摘 (2026-05-12): 「Claude Code の skill として問題作成を組み込んだりテンプレートを用意したりする必要がある」

component役割
.claude/skills/create-problem/ の拡張 既存 skill を新 metadata DSL 対応に拡張。 AI 対話で問題定義 (= category / kind / endpoints / disruptions) を聞き出し、 完成形 dir を生成。 既存問題を context として AI に渡し模倣を促す
.claude/templates/problems/<kind>/ 5 kind 各々の skeleton template。 tenkacloud problem create が copy 元として使う。 各 kind の完成形に近い metadata + template.yaml + portal/ + tests を含む
AGENTS.md "Problem Authoring" セクション AI agent が問題を作る時の context 集約: 「skill 呼び方 / template 場所 / 既存 4 sample の URL / metadata DSL の JSON Schema / よくある落とし穴」
JSON Schema の aiContext field 標準の description に加え AI 向け hint を埋める (= 「scoring.kind 選び方の判断軸: Challenge なら flag / uptime-flat、 Battle で時刻依存採点なら phased-polling」 等)
4 sample 問題の rich コメント code comment / metadata description / portal component を AI 模倣しやすい imperative + WHY コメント密度で書く (= existing 4 problems を training data 化)

CLI 一覧 (= ADR-010 #578 と統合)

この CLI + Claude Code skill + template + 4 sample が揃わなければ ADR-012 はどんなに綺麗でも実用化されない。 Phase 2 で必ず ship。

注: 「Battle」 は TenkaCloud 固有の用語 (= 対戦型問題カテゴリ)。 AWS GameDay 等の用語ではないので、外部資料と並べる時は明確に区別する。

1 枚で分かる構造

problems/<id>/

├── template.yaml    # ①リソース = 競技者 AWS account に立つ CFn。passive 仕掛け (= cron 等) 同梱可
└── portal/          # ②ダッシュボード = Battle 固有 UI (Challenge は不要、generic 流用)

ユーザー指摘 (= 設計の制約)

2026-05-12 順序付きで:
1.「採点 / リソース / ダッシュボードが欲しい機能」
2.「攻撃とかの仕組みは問題側のコード (= template / metadata) で作ればいい」
3.「Challenge は共通化できる、Battle は柔軟性が必要」
4.「endpoint は default を問題で指定、競技者が override 可能」
5.「採点 Lambda は platform 側に 1 個、問題ごとに立てない (= ぐちゃぐちゃ防止)」
6.「endpoint 数と default 値 (= deploy 時 CFn output から team ごと set) を指定できないといけない」
7.「だからかなり metadata の作り込みをしないといけない」

= 厚 metadata DSL で問題固有性を吸収し、platform は generic 1 個に保つ。

厚 metadata DSL (= 本 ADR の主役)

骨子

metadata.json で次を宣言できる必要がある:

領域宣言する内容例 (microservice-migration)
endpoint slotN 個の slot 名 / default URL の取得元 / override 可否3 slot (users / orders / catalog)、deploy 時 CFn output Ec2BaseUrl + appendPath で default を team ごとに set、競技者は override 可
採点 kind5 つの builtin から選択 (flag / uptime-flat / uptime-multi / phased-polling / attack-detection)phased-polling
採点 rulekind に応じた detail パラメータ (= 配点表 / platform 分類 / bonus 条件 等)下記 "phased-polling" の details
phase 進行deploy からの経過時間で switch する rule60 min: EC2 degradation 開始 / 90 min: scoring path を /score?legacy=true に切替
dashboard slotportal の標準 slot に対する custom component の有無 (= "RegistrationPanel" / "StatusPanel" 等)StatusPanel + RegistrationPanel に custom 指定

Platform 側 = 1 つの generic scoring Lambda + endpoint registry + portal loader

platform 機能役割備考
Deploytemplate.yaml を競技者 account に CFn deploy既存 (ADR-001 / ADR-002)
Endpoint registry(1) deploy 時に CFn output から default URL を抽出して per-team で書き込む (2) 競技者の override を受け付ける (3) effective URL (override || default) を scoring に渡す新規。1 つの DDB ProblemEndpoints
Generic scoring Lambda1 min 毎に全 (tenant × team × problem × slot) を iterate。各問題の metadata scoring.kind を読んで分岐 (= 5 kind の builtin handler)。phase 進行は metadata の phases 配列から経過時間で評価。ScoreEvent を発行新規・platform 1 つ・全問題で共有。 既存 health-check-handler を refactor して取り込む
Portal plugin loaderparticipant-portal が metadata.dashboard.slots を読んで該当 component を S3 から React.lazy 動的 load新規、Battle 用

Platform は 5 kind の builtin scoring を持つだけで全問題に対応。問題が 5 kind で表現できなければ ADR を 1 個増やす (= 6 つ目の kind を足す)。Lambda は増えない。

Disruption mechanism (= 妨害 / mid-contest 条件変更)

Battle 問題ではコンテスト中に「S3 コンテンツが攻撃後版に差し替わる」「EC2 に latency 注入」「IAM が剥奪される」などの 妨害 / 条件変更 を仕掛ける。 ユーザー指摘 (2026-05-12):

「application 管理用の画面で どこでどのような妨害をいれるか / 変えられるように しておかないといけない」
「問題アカウントに 遅延なく 展開できないといけない」

2 つの仕組み

① Operator UI② Cross-account event transport
場所 application-admin-console 内 "Disruption Planner" page (新規) Platform 中央 EventBridge bus → 競技者 account 内 rule + Lambda
役割 operator が妨害種類 / 時刻 / 強度を画面で edit、Trigger NOW で即発火 Platform から PutEvents → 競技者 account の Lambda が ~1 秒で実行
必要権限 Tenant Admin JWT EventBridge bus policy で competitor account を許可 (= AssumeRole 不要)

① Operator UI 要件

  • Disruption catalog 表示: metadata.disruptions[] で問題が宣言した妨害種類を一覧
  • Per-team / per-disruption の schedule 表: 「team-A の S3 swap → 14:00 予定 / team-B キャンセル」
  • Edit: trigger 時刻 / パラメータ (= 妨害強度 / target slot / コンテンツ variant 等) を画面で変更
  • Trigger NOW: schedule を待たず即発火
  • All-teams broadcast: 「全 team の S3 swap を 5 min 後に同時発動」
  • Cancel: 予定中の disruption を取消

② Cross-account event transport の配線

[application-admin-console (operator)]
        │
        ▼ "Trigger NOW" click
[Platform DisruptionApi Lambda] ──┐
                                   │
[Platform EventBridge Scheduler] ──┘  (scheduled fire も同経路)
        │
        ▼ PutEvents (= e.g. "disruption.s3-content-swap")
[Platform central EventBridge bus "tenkacloud-disruption"]
        │
        ├─→ team-A account ▶ EventBridge rule ▶ DisruptionHandler Lambda
        ├─→ team-B account ▶ EventBridge rule ▶ DisruptionHandler Lambda
        └─→ ... (= 全 team、 sub-second 配信)

EventBridge cross-account を選ぶ理由:

  • AssumeRole 不要 = ADR-009 (#459) の federation を read-only に保てる、 write 経路を別 IAM で発行する必要なし
  • Sub-second 配信 = ユーザー要件「遅延なく」を満たす
  • N team scaling 不要 = Platform は 1 回 PutEvents するだけ、各 team の rule subscription が独立に拾う
  • blast radius = 1 team account に閉じる = DisruptionHandler Lambda は自 team の resources にしか触れない

template.yaml の受信側

Resources:
  # 競技者 account 内、Platform からの event を受ける専用 bus
  DisruptionEventBus:
    Type: AWS::Events::EventBus
    Properties: { Name: !Sub "tenkacloud-disruption-${TeamId}" }

  # Platform account からの PutEvents を許可
  CrossAccountSource:
    Type: AWS::Events::EventBusPolicy
    Properties:
      EventBusName: !Ref DisruptionEventBus
      StatementId: tenkacloud-allow-platform
      Statement:
        Effect: Allow
        Principal: { AWS: !Sub "arn:aws:iam::${TenkaCloudAccountId}:root" }
        Action: events:PutEvents
        Resource: !GetAtt DisruptionEventBus.Arn

  # 妨害種別ごとに rule + Lambda (= metadata.disruptions[] と 1:1)
  ContentSwapRule:
    Type: AWS::Events::Rule
    Properties:
      EventBusName: !Ref DisruptionEventBus
      EventPattern:
        detail-type: ["disruption.content-swap"]
        detail: { teamId: [!Ref TeamId] }
      Targets:
        - Arn: !GetAtt ContentSwapLambda.Arn

  ContentSwapLambda:
    Type: AWS::Lambda::Function
    Properties:
      Code:
        ZipFile: |
          import boto3
          def handler(event, _):
              variant = event["detail"]["parameters"]["contentVariant"]
              boto3.client("s3").copy_object(
                Bucket="", Key="index.html",
                CopySource=f"/_staging/{variant}/index.html"
              )

Phasescope
1 (本 PR)ADR 採択。metadata DSL の schema 詳細を確定 (= JSON schema 草案 + 5 kind 各々の rule field)

Consequences

positive

  • 新問題追加が dir 1 個 git add で済む。platform に手を入れる必要なし
  • 採点 Lambda は 1 つ。IAM / CFn / lifecycle がぐちゃぐちゃにならない
  • metadata DSL が型 (JSON Schema) で固まるので、 PR review が機械化可
  • community contribution 時、寄稿者は問題 dir だけ理解すれば OK
  • Phase 3 で既存 health-check-handler / submit-flag handler を refactor 統合できる (= 同じ generic dispatcher に乗る)

negative

  • metadata DSL 作り込みコストが大きい (= ユーザー指摘 7)。5 kind 各々の rule field を精緻に設計しないと、後から breaking 拡張で全問題の metadata を直すことになる
  • 5 kind の builtin で表現できない問題が出たら、 新 kind を ADR 1 個増やして足す必要 (= 拡張コスト)
  • generic scoring Lambda が問題ごとの分岐を 1 つの Lambda に背負うので、 PR review で慎重さが要る (= regression risk が問題横断)

open questions

  • metadata DSL の 5 kind が真に MVP として十分か (= security-battle-royale 既存ロジックを uptime-multi + attack-detection 2 kind で全部表現できるか、 audit が必要)
  • phase 進行で expressible でない非定常な攻撃 (= 競技者の行動依存で trigger される攻撃) が要るか、 要るならどう宣言するか
  • operator (= 競技運営) 側にも problem 固有 UI が要るか (= application-admin-console plugin slot は本 ADR の scope 外)
  • ADR-008 確定との順序 (= 待たずに Phase 2-5 を進めて Phase 6 で後付け、で OK か)
  • 同 problemId の versioning (= 同 event で複数 version 並走可能性)

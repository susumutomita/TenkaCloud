ADR-012: Problem plugin architecture — 問題は self-contained plugin、platform は generic host

Status:Proposed 2026-05-12
Trigger: PR-608 (#606 Phase 2 score engine) close
Related ADR: ADR-001、 ADR-004、 ADR-005、 ADR-008 (#574 user WIP)
Related Issue: #572、 #606、 #574

Context

2026-05-12: PR-608 (= #572 Microservices Migration Battle Phase 2 score engine) を close。理由は 問題固有ロジック (DDB schema / endpoint registration API / polling Lambda / phase progression / +5,000 bonus) が platform 側 (infrastructure/lib/problem-deploy/) に書かれていたこと。これでは新問題を足すたびに platform を改造する設計になっており、 problem 追加が独立しない。

ユーザー指摘 (2026-05-12): 「問題側に評価関数や画面のコードがあったら追加できたり、差し替えたりできるようにできない」 = problem は self-contained な plugin で、platform は generic host であるべき。

本 ADR で plugin architecture を確定する。問題は problems/<id>/ 配下に scoring 宣言 + (任意) 評価関数 Lambda + (任意) Portal UI コンポーネント を同梱、platform は宣言を読んで dispatch する generic engine になる。

制約由来本 ADR への影響
polling over SSEmemory feedback_polling_over_sse plugin scoring は polling 駆動、subscription は作らない
cost 最小化 (DDB 1/1 PROVISIONED + Lambda only)repo 経済設計 plugin Lambda の cold start / per-invoke cost を試算し、宣言的 DSL で済む 80% は Lambda 不要に
secrets-manager-forbiddenharness rule plugin code 配信は SSM Parameter Store SecureString / S3 + presigned URL のいずれか
tenant 分離はインフラ層でINVARIANT_TENANT_ISOLATION_AT_INFRA_LAYER plugin Lambda は tenant 跨ぎできない IAM scope。DDB access は platform が proxy
HTML 設計ドキュメントmemory feedback_design_docs_html 本 ADR も HTML、plugin authoring guide も HTML
private repo 分離計画ADR-008 (#574 user WIP) plugin code (= scoring + UI) も ADR-008 の S3 配信路に乗せる、設計を統合する

現状 (= PR-608 で観測された設計違反)

  • infrastructure/lib/problem-deploy/handlers/microservice-migration-registration-handler/ — 問題名が platform ハンドラ名に出ている
  • MicroserviceMigrationScoresTable — 問題固有 DDB が platform stack に
  • POST /problems/microservice-migration-battle/endpoints — 問題名が route path に hard-coded
  • scripts/deploy-battles.sh + EC2 user-data の tc qdisc cron — phase 進行 logic が deploy script に
  • 同じ罠が既存 security-battle-royale にもある可能性大 (= 別 audit が要る)

D1. 宣言的 scoring DSL

metadata.json で 80% case を declarative に書ける DSL を定義する。Lambda 不要、JSON だけで済む。

kind用途schema 例
uptime-flat 固定 endpoint を probe、ok=+pt / fail=skip (= 既存 hello-world-battle 等) { kind: "uptime-flat", endpoints: [{ outputKey, path, expectStatus, pointsPerSuccess }] }
flag 1 回提出型 flag、StackOutput 比較 (= 既存 hello-world) { kind: "flag", flagOutputKey: "FlagValue", points: 100 }
phased-polling 時刻でフェーズが進む polling、platform 別配点、bonus (= #572 microservice-migration) 下記の details 参照
battle-attacks Battle 攻撃検知 (= 既存 security-battle-royale) { kind: "battle-attacks", attackedEndpoints: [...], pointsPerAttack: -50 }
custom D2 escape hatch を発動 (= per-problem Lambda) { kind: "custom", lambdaSource: "scoring/index.ts" }
D1: phased-polling の具体 schema (= #572 を表現する) 
{
  "kind": "phased-polling",
  "slots": ["users", "orders", "catalog"],
  "registrationApi": "platform.endpointRegistry",   // platform 側が generic endpoint registry を提供
  "metaPath": "/meta",
  "scorePath": "/score",
  "platformRules": {
    "ec2":       { "points": 100,  "degradedPoints": 10 },
    "lambda":    { "points": 1000 },
    "ecs":       { "points": 1000 },
    "apprunner": { "points": 1000 }
  },
  "phases": [
    { "name": "deploy",      "afterMinutes": 0  },
    { "name": "degraded",    "afterMinutes": 60, "switchPlatformDegraded": ["ec2"] },
    { "name": "legacy",      "afterMinutes": 90, "scorePathOverride": "/score?legacy=true" }
  ],
  "responsePenalties": [
    { "if": "responseTimeMs > 1500", "points": 10 }
  ],
  "bonuses": [
    { "kind": "all-slots-on-platforms", "platforms": ["lambda","ecs","apprunner"], "points": 5000 }
  ]
}

この schema を platform の phased-polling evaluator が 1 分毎の polling で解釈し、ScoreEvent を発行する。問題側コードは 0 行。

D2. escape hatch — custom scoring Lambda

DSL で書けない複雑な評価 (= 例: SQL injection 検出 / 解の正解判定が動的に変わる / 競技者の発信した値を集計) は 問題側に Lambda を同梱。

項目仕様
場所problems/<id>/scoring/ (TypeScript)、entry は scoring/index.ts の export async function score(event): Promise<ScoreResult>
buildPhase 1: platform CDK が NodejsFunction で個別 Lambda を立てる (= problemId が Function 名 prefix)。Phase 2 で ADR-008 と統合し S3 + Lambda Layers / RIE で per-problem 配信に
invocationgeneric polling Lambda が InvokeCommand で問題ごとの scoring Lambda を呼ぶ (= EventBridge 経由 fanout は overkill)
signature(event: { tenantId, slot, registeredUrl, phaseElapsedMin, prevState }) => Promise<{ delta, platform, emitEvent, newState }>
state必要なら prevState + newState で per-(tenant, slot) state を保持。platform が DDB に書き込む
限界scoring Lambda は tenant 跨ぎ access 不可 (= IAM が tenant scope に絞る)。外部 HTTP は許可 (= 競技者 endpoint probe)、AWS SDK は限定 IAM で許可

D3. Portal UI 拡張機構

案採否内容欠点
D3-A採用 動的 import + S3 配信。問題側 problems/<id>/portal/ を Vite で別 bundle にビルド (= ESM module、~50 KB target)、Cloudfront/S3 配信。participant-portal が React.lazy(() => import(/* @vite-ignore */ pluginUrl)) で runtime load build 1 段増 (= per-problem rollup)、CSP 設計が要る
D3-B却下 Module Federation (Webpack Federation) Vite ベースなので技術スタック分裂、SSR 想定なし
D3-C却下 iframe 埋め込み shared design system (Cloudscape) が使えない、cross-origin の状態同期が辛い
D3-D却下 宣言的 UI schema (JSON で描画指定) 複雑な UI が表現不能、escape hatch が要る → 結局 D3-A と二重実装
D3-A の plugin component contract 
// problems/<id>/portal/index.tsx
import type { ProblemPortalPlugin } from "@tenkacloud/portal-plugin-sdk";

const plugin: ProblemPortalPlugin = {
  problemId: "microservice-migration-battle",
  components: {
    RegistrationPanel: ({ slots, registered, onRegister }) => { /* JSX */ },
    StatusPanel:       ({ team, scores })                   => { /* JSX */ },
    HelpDrawer:        ({ language })                       => { /* JSX */ },
  },
  routes: [
    { path: "/migration-progress", element: <MigrationProgress /> },
  ],
};

export default plugin;

participant-portal は config.problems[].pluginUrl を runtime-config から読み、必要な component を slot に挿入する (= "RegistrationPanel" を Home に、"StatusPanel" を ScoreBoard に、等の slot 規約)。Cloudscape components は SDK 経由で共有 (= duplicate bundle を避ける)。

D4. plugin code 配信路 (= ADR-008 と統合)

scoring Lambda + UI bundle を以下の経路で配信する:

環境scoring LambdaUI bundle
dev (local) problems/<id>/scoring/ を直接 NodejsFunction で deploy vite dev で plugin 経路を inline serve
production (= public problem) CFn パイプラインが problems/<id>/scoring/ を S3 にアップロード → Lambda を s3 source から作る UI bundle も同じ S3 prefix にアップロード、CloudFront 配信
production (= private problem、ADR-008) private repo TenkaCloudChallenges の CI が S3 (= 運営 account の private bucket) に zip 配置、Worker が presigned URL でダウンロード UI bundle も同じ private bucket に置き、portal が **15 分 TTL presigned URL** で fetch (= 答え漏れ対策)

ADR-008 (#574 user WIP) が確定したら、本 ADR-012 の "production private" 経路を ADR-008 の S3 + presigned URL spec に合致させる。Phase 1 は public 経路のみで MVP 立ち上げ。

D5. trust boundary / 信頼境界

plugin code (= scoring Lambda + UI bundle) は 第三者寄稿の可能性 (将来) + 誤動作リスク を抱える。次の境界で隔離:

境界scoring LambdaUI bundle
IAM per-problem 専用 role、DDB は platform proxy table のみ Read/Write、 cross-tenant access 不可 (N/A、frontend)
network outbound HTTP は許可 (= 競技者 endpoint probe)。AWS API は IAM で絞る portal-host の origin に同梱 (= CORS は同 origin で問題なし)
memory / CPU Lambda 標準 sandbox。timeout 30s 上限 browser tab sandbox
secrets SSM Parameter Store SecureString は read 不可 (platform proxy のみ可能) tokenless (= portal の teamLoginKey は SDK が wrap)
code review PR ベースで人間 review (= ADR-008 community contribution review) 同上
CSP (N/A) portal の CSP で script-src 制限。Plugin URL は許可リストで明示

D6. backward compat / migration

既存 3 問題 (= hello-world-battle / security-battle-royale / hello-world) は本 ADR 採択後、段階的に新 plugin pattern に migrate する。

問題現状migration plan
hello-world-battle health-check-handler が metadata の endpoints を読んで polling (= ほぼ DSL) kind: "uptime-flat" declarative DSL に formalize、health-check-handler を generic evaluator として renaming
security-battle-royale battle-attacks handler が problem 固有の判定を含む可能性大 (= audit 必要) kind: "battle-attacks" として DSL 化、固有 logic は scoring Lambda escape hatch に移行
hello-world flag 提出型、submit-flag handler が generic kind: "flag" declarative DSL に formalize、submit-flag handler を generic evaluator として renaming
microservice-migration-battle Phase 1 ship 済 (problem files のみ)、Phase 2 (PR-608) は close kind: "phased-polling" DSL を実装 → metadata.json で declarative に書き直す。scoring Lambda は不要

D7. plugin author の開発体験

  • /create-problem skill が plugin pattern の雛形 (= metadata.json + scoring/index.ts stub + portal/index.tsx stub) を生成
  • local dev: bunx tenkacloud problem dev <problemId> で plugin を local serve、participant-portal の dev server に hot-reload で挿す
  • test: problems/<id>/scoring/index.test.ts で Lambda handler 単体テスト (= vitest + AWS SDK mock)。portal/<component>.test.tsx で UI render テスト
  • schema validation: make validate-problems が DSL を SCHEMA.json 拡張で型 check

段階的ロールアウト

Phasescope依存

Phase 3 platform に generic-scoring-engine Lambda を導入 (= 既存 health-check-handler / submit-flag handler を refactor して DSL 駆動に)。3 既存問題が新 engine で動くことを e2e 検証 Phase 2

Consequences

positive

  • 新問題を足すのに platform を改造不要 (= 問題ファイル + 任意 scoring/portal の追加だけ)
  • 問題の 差し替え が可能 (= 同 problemId で metadata + scoring/index.ts を更新するだけ)
  • community contribution (= ADR-008 が描く第三者寄稿) と整合: 寄稿者が repo 構造を理解する範囲は problems/<id>/ だけで済む
  • 既存 security-battle-royale も同じ枠組みに乗せられる (= 現在の隠れた platform-bleed を解消)
  • plugin author に 明示 SDK (= @tenkacloud/scoring-sdk + @tenkacloud/portal-plugin-sdk) を提供することで、 platform-side ABI が安定し PR review が機械化できる

negative

  • 初期 setup 工数大: 4 phase (= 5 PR 程度) の段階移行。dogfood 中の 0 user 環境を考えるとペイする
  • per-problem scoring Lambda の cold start: 1 min 間隔 polling では invoke 頻度低いので worst-case 1 invoke/min × ~1s = 60s cold start hit / hour、許容
  • UI plugin の lazy load による初回表示遅延: ~50 KB plugin bundle + CSS、~200ms 想定。preload で緩和可
  • plugin author に SDK + dev workflow を学習させる必要 — ドキュメント整備コスト
  • schema migration: 既存 metadata.json に scoring.kind 等の field を追加する breaking change。Phase 2 で一度に migrate

open questions (= follow-up)

  • scoring Lambda の 言語: TypeScript 縛りで良いか / Python も許容するか (= NodejsFunction vs Function + Container Image)
  • scoring Lambda の versioning: 同 problemId で複数 version 並存 (= A/B 競技開催) を許可するか
  • portal plugin の i18n: ADR-008 / #583 i18n と整合する design / API surface
  • plugin の circuit breaker: scoring Lambda が連続失敗したときの platform 側 fallback (= 0 点 vs skip vs operator alert)
  • ADR-008 確定との 順序: ADR-008 を待たずに本 ADR の Phase 2-5 を進められるか (= public 同梱で MVP 立ち上げて、Phase 6 で private 配信を後付け)

ADR-012: Problem plugin architecture

3-asset model + thick metadata DSL + platform-side generic scoring dispatcher

Status: Proposed 2026-05-12
Related: ADR-001、 ADR-005、 ADR-008、 ADR-010

Context

TenkaCloud は AWS マルチテナント SaaS の cloud competition platform。 競技問題は problems/<category>/<id>/ ディレクトリに格納され、 platform の Worker Lambda が CloudFormation template を競技者 AWS account に deploy する (ADR-001)。

本 ADR 起草時点で 4 問題が repo 内に存在する:

  • hello-world (Challenge) — flag 提出型
  • hello-world-battle (Battle minimal) — uptime probe 型
  • security-battle-royale (Battle) — 攻撃検知 + 複数 endpoint 監視
  • microservice-migration-battle (Battle) — 多段 phase + 妨害 + 3 hosting platform 分類

「Battle」 「Challenge」 は TenkaCloud 固有のカテゴリ用語 (= 対戦型 / 個別演習型) で、 AWS GameDay 等の業界標準用語ではない。

現状の課題

初期実装では、 個別問題の scoring logic / mid-contest disruption mechanism / dashboard を infrastructure/lib/problem-deploy/ 配下の platform Lambda にハードコードする方向で進めた。 結果として:

  1. 新問題追加が platform 改修を伴う: 例えば microservice-migration-battle の score engine は handlers/microservice-migration-registration-handler/ という問題名付き Lambda を platform に追加する必要があった
  2. 問題固有 logic が複数 Lambda に散在: scoring / disruption / endpoint registration が別々の handler に分かれ、 問題ごとに platform を改造
  3. 第三者寄稿が困難: 問題を寄稿するために platform stack の改修が要るので、 contribution boundary が明確でない

= 問題が self-contained でなく、 platform を伴走改修する設計 になっていた。

Goals

軸目標
責務分離問題固有 logic は problems/<id>/ 内で完結。 platform は generic dispatcher
表現力既存 4 問題 (flag / uptime / 多段 phase / 攻撃検知) を全カバー
Authoring30 分 onboarding 目標。 human + AI agent どちらも新問題を作れる
Game designマルチタスク / 得点 / 妨害 / 時間制限 を組み合わせやすい building blocks
拡張第三者寄稿 + ADR-008 private repo separation と整合

Decision

3-asset model

problems/<id>/
├── metadata.json    # 厚 DSL: endpoint slot / scoring rule / phase / disruption / dashboard slot 宣言
├── template.yaml    # ① Resources: 競技者 AWS account に立つ CFn (passive 仕掛けはここに同梱可)
└── portal/          # ② Dashboard: Battle 固有 UI (Challenge は generic 流用、 dir 自体省略可)

「採点 Lambda」 や「engine Lambda」 を problems/<id>/ 内に持たせない。 problem authors は コード 0 行 (= metadata + CFn template + 任意 portal component) で新問題を作れることを目標とする。 採点 logic は metadata DSL で declarative に表現し、 platform 側に 1 つの generic scoring Lambda が dispatcher として動く。

Platform-side runtime

Component役割
Deploy worker (既存)template.yaml を競技者 account に CFn deploy
Endpoint registry(1) deploy 時に CFn output から default URL を team ごと set (2) 競技者の override を受付 (3) effective URL (= override || default) を scoring に渡す
Generic scoring Lambda1 分間隔で全 (tenant × team × problem × slot) を iterate。 metadata.scoring.kind を読んで 5 種の builtin handler に dispatch。 ScoreEvent stream に emit
Portal plugin loaderparticipant-portal が metadata.dashboard.slots を読んで該当 component を S3 から React.lazy で動的 load

5 種の builtin scoring kind:

kind用途例
flag1 回提出型、 StackOutput と比較hello-world
uptime-flat固定 endpoint 群を polling、 ok=+pt / fail=skiphello-world-battle
uptime-multiN 個 endpoint を全 probe、 全 OK で配点security-battle-royale (= main + admin 同時生存)
phased-polling時刻で score rule が変わる、 platform 分類 / bonus 対応microservice-migration-battle
attack-detectionCloudWatch Logs / StackOutput の counter から攻撃数で配点security-battle-royale の攻撃検知部

5 種で表現できない問題が出た時は本 ADR の拡張で kind を増やす。 「問題ごとに Lambda を立てる」 ことはしない。

Endpoint model: default + override の slot

各 endpoint は metadata.endpoints[] で slot として宣言する。

要素説明
slot問題が宣言する endpoint の役割名 (例: main / admin / users)
default URLCFn output から team ごとに deploy 時 set (= 固定値も可)
override競技者が portal UI で別 URL に変更可能。 effective URL = override ?? default

この model は次のケースを 1 contract で吸収する:

  • 1 endpoint (例: hello-world-battle) — slot 1 個、 CFn output から default、 競技者は通常 override しない
  • N endpoint (例: security-battle-royale) — slot N 個、 default は CFn output、 競技者が WAF / CDN を被せたら override
  • N slot を競技者が後追い登録 (例: microservice-migration-battle) — default は EC2 path、 Lambda / ECS / App Runner に切り出したら slot ごとに override
metadata.json 例 (microservice-migration-battle) 
{
  "id": "microservice-migration-battle",
  "category": "Battle",
  "difficulty": 4,
  "estimatedMinutes": 120,

  "endpoints": [
    { "slot": "users",   "default": { "from": "cfn-output", "key": "Ec2BaseUrl", "appendPath": "/users" },   "overridable": true },
    { "slot": "orders",  "default": { "from": "cfn-output", "key": "Ec2BaseUrl", "appendPath": "/orders" },  "overridable": true },
    { "slot": "catalog", "default": { "from": "cfn-output", "key": "Ec2BaseUrl", "appendPath": "/catalog" }, "overridable": true }
  ],

  "scoring": {
    "kind": "phased-polling",
    "intervalMinutes": 1,
    "probe": { "metaPath": "/meta", "scorePath": "/score" },
    "platformRules": {
      "ec2":       { "points": 100,  "degradedPoints": 10 },
      "lambda":    { "points": 1000 },
      "ecs":       { "points": 1000 },
      "apprunner": { "points": 1000 }
    },
    "failurePenalty": -100,
    "responsePenalties": [ { "if": "responseTimeMs > 1500", "points": 10 } ],
    "bonuses": [
      { "kind": "all-slots-on-platforms", "platforms": ["lambda","ecs","apprunner"], "points": 5000, "once": true }
    ]
  },

  "phases": [
    { "name": "degraded", "afterMinutes": 60, "effect": { "switchPlatformToDegraded": ["ec2"] } },
    { "name": "legacy",   "afterMinutes": 90, "effect": { "scorePathOverride": "/score?legacy=true" } }
  ],

  "dashboard": {
    "slots": {
      "RegistrationPanel": "portal/RegistrationPanel.tsx",
      "StatusPanel":       "portal/StatusPanel.tsx"
    }
  }
}

Disruption model

Battle problem で要求される mid-contest 条件変更 (= S3 静的コンテンツ swap / EC2 latency 注入 / IAM 剥奪等) は 2 phase で実装する。

Disruption Phase 1 (本 ADR): Self-triggered via template.yaml-bundled Scheduler

template.yaml に EventBridge Scheduler + Disruption Lambda を bake する。 deploy 時刻 + offset で self-fire。 platform は cross-account write 権限を持たず、 全ロジックが競技者 account 内で完結する。

  • operator UI: problem deploy 前に application-admin-console で disruption parameters / timing を設定。 値は CFn parameter として template.yaml の Scheduler に注入される
  • blast radius: 1 team 1 deploy に閉じる
  • 制約: deploy 後に動的変更不可 (= 変更には CFn update が必要)
template.yaml 例 (= S3 content swap disruption) 
Parameters:
  ContentSwapAfterMinutes: { Type: Number, Default: 60 }

Resources:
  ContentBucket: { Type: AWS::S3::Bucket, ... }

  SwapContentFunction:
    Type: AWS::Lambda::Function
    Properties:
      Code:
        ZipFile: |
          import boto3
          def handler(event, _):
              boto3.client("s3").copy_object(
                Bucket="", Key="index.html",
                CopySource="/_staging/post-attack/index.html"
              )

  Phase2Schedule:
    Type: AWS::Scheduler::Schedule
    Properties:
      ScheduleExpression: !Sub "rate(${ContentSwapAfterMinutes} minutes)"
      Target: { Arn: !GetAtt SwapContentFunction.Arn }

Disruption Phase 2 (Future, separate ADR): Condition-triggered by platform

scoring Lambda が観測条件 (= 競技者 score / 経過時間 / 任意 metric) を検知し、 cross-account EventBridge 経由で sub-second に disruption を trigger する。 operator は runtime に強度 / timing を動的調整できる。 詳細は別 ADR で扱う。

Consequences

Positive

  • 新問題追加 = problem dir 1 個 git add で済む。 platform 改修不要
  • 採点 Lambda は 1 つに集約。 IAM / CFn / lifecycle 管理が一元化
  • community contribution / AI agent authoring に対応可能な API surface
  • game design building blocks (= 6 要素) が明示され、 problem author が「面白さ」 を設計しやすい

Negative

  • metadata DSL の初期設計コストが大きい (= 5 kind の rule field を精緻に設計しないと、 後の breaking 拡張で全 problem の metadata を直すことになる)
  • 5 kind で表現できない問題が出たら ADR を追加して kind を増やす拡張作業が必要
  • Generic scoring Lambda が問題横断の責務を持つため、 PR review で慎重さが要る (= regression risk が問題横断)
  • Disruption の runtime 動的変更が Phase 1 では不可 (= CFn redeploy が要る)。 動的需要は Disruption Phase 2 (= 別 ADR) で対応

Risk: Hidden platform-bleed in existing code

既存 security-battle-royale の scoring / attack detection logic にも platform-bleed が残っている可能性がある。 Phase 4 で audit し、 新 DSL に移行できないものは本 ADR の拡張で扱う。

Open questions

  • metadata DSL の 5 kind が真に MVP として十分か (= security-battle-royale の既存ロジックを uptime-multi + attack-detection 2 kind で表現できるか、 audit が必要)
  • 非定常な攻撃 (= 競技者の行動依存で trigger される攻撃) を Disruption Phase 1 (= self-triggered Scheduler) でカバーできない場合の暫定対応
  • operator (= 競技運営) 側の application-admin-console に問題固有 UI plugin slot を追加する必要性
  • ADR-008 採択との順序: Phase 2-6 を本 ADR 単独で進めて Phase 7 で後付け、 で問題ないか
  • 同 problemId の versioning (= 同 event で複数 version 並走運用)

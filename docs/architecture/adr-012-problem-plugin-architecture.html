ADR-012: Problem plugin architecture — 3 アセット + 厚 metadata DSL + platform 1 つの generic scoring Lambda

Status:Proposed 2026-05-12
Trigger: PR-608 (#606 Phase 2 score engine) close
Related ADR: ADR-001、 ADR-005、 ADR-008 (#574 user WIP)
Related Issue: #572、 #606

1 枚で分かる構造

problems/<id>/
├── metadata.json    # 厚 DSL    = endpoint slot / 採点 rule / phase / 攻撃 / dashboard slot を全部宣言
├── template.yaml    # ①リソース = 競技者 AWS account に立つ CFn。passive 仕掛け (= cron 等) 同梱可
└── portal/          # ②ダッシュボード = Battle 固有 UI (Challenge は不要、generic 流用)
採点 (= 観測 → score)攻撃 (= 時間駆動の状態変化)
誰が宣言問題側 metadata.json問題側 (template.yaml or metadata.json)
誰が実行platform 内 1 つの generic scoring Lambdapassive: 競技者 account 内の cron/Lambda (= template.yaml 同梱) / active: platform scoring Lambda が metadata phase 宣言に従って分岐
問題側の Lambda コードなし (= 問題ごとに Lambda 立てるとぐちゃぐちゃになる、ユーザー指摘 5 / 2026-05-12)なし

新問題追加 = この dir 1 個 git add するだけ。platform は触らない。 metadata DSL が表現できる範囲なら code 0 行で新問題が動く。

ユーザー指摘 (= 設計の制約)

2026-05-12 順序付きで:
1.「採点 / リソース / ダッシュボードが欲しい機能」
2.「攻撃とかの仕組みは問題側のコード (= template / metadata) で作ればいい」
3.「Challenge は共通化できる、Battle は柔軟性が必要」
4.「endpoint は default を問題で指定、競技者が override 可能」
5.「採点 Lambda は platform 側に 1 個、問題ごとに立てない (= ぐちゃぐちゃ防止)」
6.「endpoint 数と default 値 (= deploy 時 CFn output から team ごと set) を指定できないといけない」
7.「だからかなり metadata の作り込みをしないといけない」

= 厚 metadata DSL で問題固有性を吸収し、platform は generic 1 個に保つ。

厚 metadata DSL (= 本 ADR の主役)

骨子

metadata.json で次を宣言できる必要がある:

領域宣言する内容例 (microservice-migration)
endpoint slotN 個の slot 名 / default URL の取得元 / override 可否3 slot (users / orders / catalog)、deploy 時 CFn output Ec2BaseUrl + appendPath で default を team ごとに set、競技者は override 可
採点 kind5 つの builtin から選択 (flag / uptime-flat / uptime-multi / phased-polling / attack-detection)phased-polling
採点 rulekind に応じた detail パラメータ (= 配点表 / platform 分類 / bonus 条件 等)下記 "phased-polling" の details
phase 進行deploy からの経過時間で switch する rule60 min: EC2 degradation 開始 / 90 min: scoring path を /score?legacy=true に切替
dashboard slotportal の標準 slot に対する custom component の有無 (= "RegistrationPanel" / "StatusPanel" 等)StatusPanel + RegistrationPanel に custom 指定

採点 kind の 5 つ (= MVP set、必要なら拡張)

kind用途例
flag1 回提出型、StackOutput 値と比較hello-world
uptime-flat固定 endpoint 群を polling、ok=+pt / fail=skiphello-world-battle
uptime-multiN 個の endpoint を全部 probe、 全 OK で配点security-battle-royale (= main + admin の両方が生きてないと点取れない)
phased-polling時間で score 計算 rule が変わる、platform 分類 / bonus 対応microservice-migration-battle
attack-detectionCloudWatch Logs / stack output の counter を読んで攻撃数で配点security-battle-royale の attack 検知部分

Platform 側 = 1 つの generic scoring Lambda + endpoint registry + portal loader

platform 機能役割備考
Deploytemplate.yaml を競技者 account に CFn deploy既存 (ADR-001 / ADR-002)
Endpoint registry(1) deploy 時に CFn output から default URL を抽出して per-team で書き込む (2) 競技者の override を受け付ける (3) effective URL (override || default) を scoring に渡す新規。1 つの DDB ProblemEndpoints
Generic scoring Lambda1 min 毎に全 (tenant × team × problem × slot) を iterate。各問題の metadata scoring.kind を読んで分岐 (= 5 kind の builtin handler)。phase 進行は metadata の phases 配列から経過時間で評価。ScoreEvent を発行新規・platform 1 つ・全問題で共有。 既存 health-check-handler を refactor して取り込む
Portal plugin loaderparticipant-portal が metadata.dashboard.slots を読んで該当 component を S3 から React.lazy 動的 load新規、Battle 用

Platform は 5 kind の builtin scoring を持つだけで全問題に対応。問題が 5 kind で表現できなければ ADR を 1 個増やす (= 6 つ目の kind を足す)。Lambda は増えない。

ChallengeBattle
性格 静的・個別演習 動的・対戦型、時間駆動の攻撃 / phase / 多段
metadata の厚さ 薄い (= kind: flag + flagOutputKey 等の数 field) 厚い (= endpoint slot 多段 / phase / platform 分類 / bonus / dashboard slot を詰める)
template.yaml flag を出す CFn のみ CFn + passive 仕掛け cron 同梱可

新問題追加コスト metadata + template ほぼコピペ metadata 厚く書く + portal component 数本 + template の仕掛け設計

portal plugin contract (= ② asset の中身)

participant-portal が runtime で動的 load する React module。metadata の dashboard.slots で「どの標準 slot に custom component を挿すか」を宣言。

// problems/<id>/portal/StatusPanel.tsx (= 例)
import type { PortalSlotProps } from "@tenkacloud/portal-plugin-sdk";

export default function StatusPanel({ team, endpoints, scores, phase, nextPhaseAt }: PortalSlotProps) {
  return (
    <Container>
      <Header>3 slot 状態</Header>
      {Object.entries(endpoints).map(([slot, url]) => (
        <Box key={slot}>{slot}: {url} / score {scores[slot]}</Box>
      ))}
      <Box>次フェーズまで残り {formatCountdown(nextPhaseAt)}</Box>
    </Container>
  );
}

段階的ロールアウト

Phasescope
1 (本 PR)ADR 採択。metadata DSL の schema 詳細を確定 (= JSON schema 草案 + 5 kind 各々の rule field)
2problems/SCHEMA.json を拡張。既存 3 問題 (hello-world / hello-world-battle / security-battle-royale) の metadata を新 DSL に書き直す (= 既存挙動 unchanged)

5portal plugin loader 実装 (= React.lazy + CSP + SDK package @tenkacloud/portal-plugin-sdk 公開)

Consequences

positive

  • 新問題追加が dir 1 個 git add で済む。platform に手を入れる必要なし
  • 採点 Lambda は 1 つ。IAM / CFn / lifecycle がぐちゃぐちゃにならない
  • metadata DSL が型 (JSON Schema) で固まるので、 PR review が機械化可
  • community contribution 時、寄稿者は問題 dir だけ理解すれば OK
  • Phase 3 で既存 health-check-handler / submit-flag handler を refactor 統合できる (= 同じ generic dispatcher に乗る)

negative

  • metadata DSL 作り込みコストが大きい (= ユーザー指摘 7)。5 kind 各々の rule field を精緻に設計しないと、後から breaking 拡張で全問題の metadata を直すことになる
  • 5 kind の builtin で表現できない問題が出たら、 新 kind を ADR 1 個増やして足す必要 (= 拡張コスト)
  • generic scoring Lambda が問題ごとの分岐を 1 つの Lambda に背負うので、 PR review で慎重さが要る (= regression risk が問題横断)

open questions

  • metadata DSL の 5 kind が真に MVP として十分か (= security-battle-royale 既存ロジックを uptime-multi + attack-detection 2 kind で全部表現できるか、 audit が必要)
  • phase 進行で expressible でない非定常な攻撃 (= 競技者の行動依存で trigger される攻撃) が要るか、 要るならどう宣言するか
  • operator (= 競技運営) 側にも problem 固有 UI が要るか (= application-admin-console plugin slot は本 ADR の scope 外)
  • ADR-008 確定との順序 (= 待たずに Phase 2-5 を進めて Phase 6 で後付け、で OK か)
  • 同 problemId の versioning (= 同 event で複数 version 並走可能性)

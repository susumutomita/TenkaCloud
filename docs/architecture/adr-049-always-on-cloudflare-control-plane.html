ADR-049 — Always-On Control Plane on Cloudflare, On-Demand AWS Event Runtime

Status: Proposed Date: 2026-07-02 Epic: Always-on Control Plane (#2279) Supersedes: none (adds a third deployment mode next to ADR-016 Lite mode)

TenkaCloud should be hostable 24/7 at (near-)zero fixed cost. Today even Lite mode keeps a full AWS application footprint between events. This ADR adopts a third deployment mode — Always-On mode — in which the permanently available surface (event definitions, team roster, score summaries, organizer console, participant portal, public pages) runs on Cloudflare Workers + static assets with Auth0 as the organizer IdP, while AWS is confined to the event runtime: problem deployment into competitor accounts, live scoring probes, disruption injection, and one-time AWS Console federation. The two clouds are linked without long-lived credentials — signed action intents (the trust-bridge pattern from ADR-039) from Cloudflare into AWS, and GitHub Actions OIDC for stack lifecycle. Migration is strangler-fig: control-plane data moves first behind a new repository seam (SQLite contract, hosted on Turso, reachable from both AWS Lambda and Workers), compute second, command paths third. Lite mode and SaaS mode are unchanged.

1. Context

Lite mode (ADR-016, make deploy) deploys two CloudFormation stacks — tenkacloud-lite and tenkacloud-lite-problem-deploy — comprising Lambda, Cognito, DynamoDB, S3, CloudFront, API Gateway, Step Functions, EventBridge, and CodeBuild. The footprint is engineered toward $0 idle (the DynamoDbLowCapacity aspect pins every table and GSI to provisioned 1 RCU/1 WCU; log retention is capped; SBT's per-project KMS keys are stripped), but three structural burdens remain between events:

  • The 25/25 RCU/WCU ceiling. Lite mode's 8 tables plus ~8 GSIs consume roughly 16 of the 25 always-free RCU/WCU pairs. Every new table eats the remaining headroom, and live-event scoring (~1.7 writes/s at 50 deployments, per the write-rate analysis in #1196) already rides on DynamoDB burst credits above the provisioned 1 WCU.
  • A permanent per-minute tick. GenericScoringLambda fires every minute (≈43,200 invocations/month) even when no event is running, because it conflates control-plane reconciliation (event status transitions, scheduled deploy/teardown per ADR-047) with event-runtime work (uptime probes, disruption effects).
  • Free-tier fragility. The design leans on AWS always-free allowances that no longer apply uniformly (accounts created after July 2025 are on a credits-based free plan), and API Gateway's free tier expires 12 months after account creation.

Meanwhile the public surface has already drifted off AWS: landing/ is served from GitHub Pages and is configured for Cloudflare Pages (root wrangler.toml, project tenkacloud-www), the demo mode (#1954) ships on the same Pages project, and the developer portal (ADR-0003) is a fully static export. Cloudflare is therefore not a new vendor for this repository; #1973 additionally established Workers trust-boundary patterns on the problem side.

Two further cost findings motivate scope beyond the original hypothesis in #2279:

  • CodeBuild is a sleep tax. Each problem deploy runs one CodeBuild build (scripts/deploy-battles.sh) whose 5–15 minutes are almost entirely aws cloudformation deploy waiting for stack completion. At the #538 design target (25 teams × 30 problems = 750 create builds per wave) that is ≈$37 per wave at general1.small rates — paid for idling on a CloudFormation waiter.
  • The control-plane store can be made pluggable. Handlers currently pass a DynamoDBDocumentClient around (57 files under infrastructure/lib/problem-deploy/handlers/ import the DynamoDB SDK), so a repository seam is prerequisite work for any store migration — and once it exists, the store choice becomes reversible.

2. Decision

Adopt the always-on/on-demand split as a new deployment mode ("Always-On mode"), implemented incrementally behind seams so that each phase is independently shippable and reversible. Lite mode remains the default single-tenant AWS path; SaaS mode remains the multi-tenant AWS path.

2.1 Decision constraints (binding)

  • ExternalId is always required for AssumeRole into competitor accounts, and the secret material stays in AWS SSM SecureString — it is never replicated to Cloudflare, Turso, or GitHub.
  • No long-lived cross-cloud credentials anywhere: GitHub→AWS via OIDC, Cloudflare→AWS via signed intents verified AWS-side (nonce + expiry + audience), AWS→control-store via a scoped DB token.
  • Frontend freshness model is unchanged: polling per ADR-014; the SSE/WebSocket prohibition stands.
  • The SPAs stay build-identical across modes; per-mode differences flow only through runtime-config.json (the existing invariant).
  • Architecture invariant INVARIANT_CONTROL_PLANE_USES_SBT is scoped to SaaS mode; it does not apply to Always-On mode (or to Lite mode, which already has no SBT). The harness rule is amended accordingly in Phase 0.
  • Every phase must leave make deploy (Lite) and make deploy-saas behavior-identical; Always-On mode is additive.

4. Identity: Auth0 for organizers, hashed team keys for participants

The project has prior Auth0 operating experience (#253, pre-Cognito era).

5. Control-plane data: a SQLite contract behind a repository seam

5.1 The seam

There is no swappable data layer today: handlers receive a DynamoDBDocumentClient (e.g. EventSharedResources.ddb) and build commands inline. The seam introduces aggregate-scoped repository interfaces — domain methods, not a generic key-value shim — so each backend implements them idiomatically: 

// packages/control-data (new workspace package)
export interface EventsRepository {
  getEvent(tenantId: string, eventId: string): Promise<EventRecord | null>;
  listEvents(tenantId: string, cursor?: string): Promise<Page<EventRecord>>;
  putEvent(record: EventRecord): Promise<void>;
  transitionStatus(eventId: string, from: EventStatus, to: EventStatus): Promise<boolean>;
}
export interface TeamsRepository {
  putTeam(record: TeamRecord): Promise<void>;                 // stores loginKeyHash, never plaintext
  findTeamByLoginKeyHash(hash: string): Promise<TeamRecord | null>;
  listTeams(eventId: string): Promise<readonly TeamRecord[]>;
}
// implementations:
//   DynamoDbEventsRepository / DynamoDbTeamsRepository  — extraction of today's code, default
//   SqlEventsRepository / SqlTeamsRepository            — one SQL layer, SQLite dialect
//     driver: @libsql/client (Turso; also self-hosted sqld)  |  D1 binding (Workers only)
// selection at cold start: CONTROL_DATA_BACKEND=dynamodb|turso (feature flag, ADR-035 mechanism)

Phase 1 scopes the seam to the Events and Teams aggregates in Lite mode — small enough for one PR wave, load-bearing enough to prove the model (team lookup is on the participant hot path). Deployments, ProblemEndpoints, and Disruptions are explicitly not abstracted: they are event-runtime data and stay DynamoDB (Table 4).

5.2 Why SQLite as the contract, and why Turso first

Cloudflare D1 and Turso both speak the SQLite dialect, so a single SQL schema and a single SqlXxxRepository implementation cover both; switching hosts is a driver swap plus a .dump-and-import, not a rewrite. That turns "D1 vs Turso" from an architecture bet into a hosting decision taken per phase:

Choice: Turso first, precisely because it is the only candidate reachable from both compute planes — control data can leave DynamoDB while the handlers are still Lambdas, and later serve Workers without a second migration. Turso's vendor risk is real and is mitigated structurally: the seam keeps DynamoDB as a one-flag rollback, the schema is plain SQLite with a verified dump/export path, and sqld is MIT-licensed and self-hostable. D1 is re-evaluated at the Phase-3 gate (§13) once compute lands on Workers; with the leaderboard read fixed (below), D1's daily free quotas also fit, making it a viable endgame host via the same seam.

5.3 Leaderboard and score summary

Today a leaderboard request drains the full tenant partition (GSI1) per poll — with 300 clients polling every 30 s that is ~29M row reads per event day at SQL granularity, which would exceed D1's free daily read quota and waste Turso's monthly one. The control store therefore keeps a materialized score summary (one row per team per event, upserted by the runtime's summary feed, plus a per-event JSON leaderboard snapshot regenerated at most once per polling interval). Raw score events (the per-tick audit timeline) never leave the event-runtime DynamoDB table; they are exported to flat storage at event archive time. This drops event-day control-store reads to <1M rows and makes both hosts comfortable.

6. One-time AWS Console access: keep the existing AWS-side issuer, drop Cognito

#2279 hypothesized that Cognito must remain "for AWS Console federation". Code inspection shows the shipped federation flow (handlers/participant-handler/sso.ts, #1931/#1919 lineage) never touches Cognito: it resolves the team's deployment, performs the two-stage sts:AssumeRole (tenant CompetitorDeployRole with the SSM-stored ExternalId, then the per-problem ParticipantViewerRole with ExternalId=jobId, 1 h), and exchanges the session for a sign-in token at signin.aws.amazon.com/federation. The sibling getCliCredentials() (#1197) returns raw short-lived credentials over the same chain.

Decision: this Lambda is exactly the "minimal AWS-side BFF" the issue asked to evaluate — it is kept unchanged as an event-runtime component, and the Workers portal API proxies to it with a signed intent. Cognito is therefore not needed anywhere in Always-On mode. Operational constraints already encoded in the flow (omit SessionDuration for AssumeRole-derived sessions per #747/#1003; no sensitive material in URLs/logs per #864; capability gating for non-AWS targets per ADR-048) carry over untouched.

7. Cloudflare → AWS command seam: signed intents, no shared credentials

Today the control→runtime seam is an in-account EventBridge PutEvents (DeployCreateRequested / DeployDeleteRequested / BulkDeployCreateRequested). In Always-On mode the publisher is a Worker outside AWS, so the seam becomes: Workers sign a CloudActionIntent (JWS; the schema and signer already exist in packages/trust-bridge, ADR-039/#795) and POST it to a minimal AWS ingress (Lambda Function URL). The ingress verifies signature, audience, expiry, and a nonce (replay prevention, same pattern as the customer-execution plane's nonce table), authorizes the tenantId/eventId scope, then re-publishes the event onto the bus — the state machines downstream are untouched. AWS-originated feedback (deploy status, score summaries) flows back by the runtime calling the control store directly with a scoped DB token, keeping the frontend polling model intact.

  • The JWS signing key lives in Workers secrets; its public key is pinned AWS-side via the runtime stack config. Rotation is a redeploy of both halves.
  • Intent payloads carry identifiers only — never ExternalId or any credential. The AWS side resolves secrets from SSM exactly as today.
  • The event contract (source: tenkacloud.deploy, detail types, field shapes) is frozen; the ingress is a transport adapter, not a new API.

8. Event-runtime lifecycle: GitHub Actions OIDC, tags, and enforced cleanup

The event-runtime CDK stacks are deployed per event and destroyed after it, from GitHub Actions using OIDC federation — no long-lived AWS keys in CI. Verified terms: standard GitHub-hosted runners are free and unlimited for public repositories, and both the GitHub OIDC token and sts:AssumeRoleWithWebIdentity are free. This usage (deploying the repository's own infrastructure) is squarely within GitHub's Actions terms; per-problem deploy jobs are not moved here (§9).

9. Build execution: retiring CodeBuild from the problem-deploy path

The per-problem CodeBuild build is a two-line buildspec around scripts/deploy-battles.sh: no compilation, no Docker, no VPC — just aws-cli, jq, and a blocking aws cloudformation deploy. The blocking wait is the entire reason Lambda's 15-minute cap was ever a constraint. Splitting create from wait removes it: the repository already contains every needed precedent (describe-stack-lambda polls cross-account CFn from Lambda; the trust-bridge CloudFormationExecutor runs deploy/destroy from an SQS-driven Lambda without inline waits; ADR-014 makes polling the house style).

Contracts preserved by the replacement (these are the regression surface): the EventBridge detail shapes; the Deployments status transitions (PENDING→IN_PROGRESS→COMPLETE/FAILED, DELETING→DELETED); stackOutputs/stackId fields; tc-{problemSlug}-{teamSlug} naming; the TenkaCloud:* stack tags; retry semantics; and participant log streaming. The last one changes mechanically: deploy-logs.ts currently resolves CloudWatch streams via codebuild:BatchGetBuilds and the stored buildId. The deploy Lambda instead writes progress lines to a deterministic log stream named by jobId, and the endpoint resolves streams by that convention — the portal contract (DeploymentLogEntry) keeps its shape, with source: "codebuild" retired in favor of a runtime source value. Server-side redaction is unchanged. Derivative consumers to update in the same phase: the CloudWatch dashboard's CodeBuild widget, the system-audit-writer CodeBuild-failure rule, and the CDK tests asserting the CodeBuild project.

SaaS-mode CodeBuild consumers (SBT provisioning ScriptJobs, the tenant-update pipeline) are out of scope: low-frequency, SBT-coupled, and SaaS mode is not this ADR's subject. The tenant-update rollout is a natural future GitHub Actions CD workflow, noted as backlog.

10. Scoring and the evergreen Challenge category

"AWS only during events" has one honest exception: the Challenge category is self-paced and evergreen. The split that preserves it with zero standing AWS compute:

  • flag / multi-flag — always-on, on Workers. Flag submission is a pure data operation (hash-compare + conditional score update + score event append). It moves to the Workers portal API against the control store, so evergreen Challenges accept submissions 24/7 with no AWS involvement. Single-statement UPDATE … SET score = score + ? is atomic on the SQLite hosts, matching today's conditional-write race safety.
  • uptime-flat / uptime-multi / phased-polling / attack-detection — event-runtime only. These require probing deployed problem endpoints and reading AWS-side state; the per-minute scoring tick ships inside the runtime stack and therefore exists only while a runtime is deployed. Its write-back target stays the runtime Deployments table; a summary upsert feeds the control store per tick (§5.3).
  • Reconciliation and scheduling (event status transitions, ADR-047 scheduled deploy/teardown) move to a Workers Cron against the control store — this is what finally deletes the 24/7 AWS tick.

DNS flip back to CloudFront/API Gateway (kept warm during the compat window); control store is shared, so no data migration on rollback.
4 — Command seam + runtime lifecycle Signed-intent ingress; GitHub Actions OIDC deploy/destroy workflows; tagging contract; nightly sweeper. Runtime stack remains deployable by hand (make target) throughout.
5 — Scoring split + Always-On GA Flag kinds on Workers; reconciliation to Workers Cron; runtime tick scoped to the runtime stack; audit/usage flows into the control store; mode documentation (make deploy-always-on or equivalent entry point). Kinds are dispatched per problem metadata — reverting a kind's executor is a dispatch-table change.

Compatibility window: during Phases 3–5, Lite mode remains fully supported and the Always-On deployment runs against the same control store, so an organizer can fall back to Lite for a given event without data loss. The strangler direction is one-way by choice, not by necessity.

14. Open validation items

  • Auth0 free-plan MAU: official sources say 25,000; multiple 2026 trackers say 7,500. Re-verify on the live pricing page before Phase 3 commits. Either figure covers organizer-only usage.
  • Cloudflare free-plan commercial-use terms: conclusion (allowed for the developer platform) rests on the Service-Specific Terms; re-read the live terms once before GA.
  • Turso p95 latency from Lambda ap-northeast-1 and from Workers (post-2025 diskless architecture has no trustworthy public benchmark) — Phase 1 measures it.
  • Validated in Phase 1: Events/Teams repository operations are single SQL statements, and idempotent schema bootstrap uses one atomic client.batch(statements, "write"). The production adapter never opens an interactive transaction, so Turso's 5 s interactive window is not on these paths. Unit tests pin the write-batch contract; re-evaluate if a future aggregate operation spans multiple statements.
  • Step Functions transition count under the 750-deploy bulk path after CodeBuild removal — validate the ≈$0.7/wave estimate in Phase 2.
  • GitHub Actions runtime-deploy duration (CDK deploy of the runtime stack) and whether the 20-concurrent free plan ever queues lifecycle workflows behind CI.
  • AWS account free-plan type (pre/post-July-2025) of the target deployment account — affects Table 8's "$0 within free tier" cells.

15. Consequences

Positive: fixed cost drops to $0 idle / $5 event months with hard spend ceilings on every always-on component; the 25/25 RCU/WCU ceiling and the permanent per-minute tick disappear; per-event deploy cost drops ~50×; the platform gains a genuinely public, always-available surface (evergreen Challenges, portal, docs) independent of any AWS account state; secrets and cross-account trust remain entirely inside AWS; each phase is independently valuable (seam, CodeBuild removal). Negative / cost: a third deployment mode raises the documentation and test matrix; the stack becomes multi-vendor (Cloudflare + Auth0 + Turso + GitHub + AWS), each with its own failure modes and terms drift; Workers/Lambda dual-targeting of shared handler code demands discipline (Hono helps but SDK-touching code must stay behind the seam); the control store loses DynamoDB-native TTL and conditional-write idioms, replaced by cron sweeps and SQL constraints; Turso adds a seed-stage vendor to the critical path until the D1/self-host decision at the Phase-3 gate; and the signed-intent ingress is new security-critical code that must be reviewed like the trust-bridge itself.

16. Alternatives considered

Stay fully on AWS, optimize Lite mode further

Rejected as the target state: the idle burdens are structural (provisioned-capacity ceiling, API Gateway free-tier expiry, per-minute tick), and the 2025 AWS free-plan changes make "free forever on AWS" unreliable for new accounts. However, Phases 1–2 are exactly this alternative's best ideas, adopted regardless.

Cloudflare D1 as the first control store

Rejected for sequencing, not capability: D1 is unreachable (as a first-class client) from the Lambda handlers that own control data today, so choosing it first forces compute and data to move simultaneously — the opposite of strangler-fig. It remains the natural endgame host once compute is on Workers, via the same SQLite schema and seam.

DynamoDB behind the seam for Always-On mode (Workers → DynamoDB over HTTP)

Rejected: Workers-side SigV4 signing against DynamoDB is possible but keeps the AWS account and its capacity model on the always-on path, defeating the fixed-cost goal; and cross-cloud per-request latency applies to every control read.

Auth0 alternatives (keep Cognito; or Clerk/WorkOS/Keycloak)

Keeping Cognito contradicts the goal (it is the always-on AWS anchor) and its post-2024 pricing tiers are MAU-billed anyway. Self-hosted Keycloak violates the zero-standing-compute constraint. Clerk/WorkOS are viable but Auth0 has prior operating history in this project (#253), Organizations on the free plan, and enterprise-connection parity for the #1293 multi-IdP requirement. The Auth0 choice is confined behind standard OIDC, so swapping IdPs later is low-cost.

GitHub Actions as the per-problem deploy executor

Rejected on four independent grounds: GitHub's Additional Product Terms prohibit hosted runners as an application job-execution backend; free-plan concurrency (20) is under the 60-job burst; dispatch returns no run id (correlation hacks required) and secondary rate limits cap sustained dispatching; and public-repo workflow logs would publish competitor-account deploy output.

Buildkite for deploy jobs

Rejected: the OSS grant covers the control plane but agents are self-hosted, so the compute cost and operational surface stay ours — a standing agent fleet is precisely the always-on burden this ADR removes. No capability the Lambda+SFN path lacks.

Durable Objects / Queues for scoring instead of a SQL store

Deferred, not rejected: DO would serialize leaderboard updates elegantly, but raw scoring stays AWS-side in this design, and the materialized-summary model keeps SQL volumes trivial. Revisit only if flag-submission concurrency on Workers shows contention.

WebSockets/SSE for live scoreboards while "modernizing" the frontend path

Rejected: ADR-014's polling-first policy stands; Workers static assets + polling reproduce today's freshness contract without new protocol surface.

17. Non-goals

  • No immediate implementation of the Cloudflare migration in this change — this ADR plus the Phase-0 invariant amendment only.
  • No port of full SaaS multi-tenancy (SBT tiers, silo pipelines, per-tenant Cognito pools) to Cloudflare; SaaS mode continues as-is on AWS.
  • No move of problem environments themselves to Cloudflare — competitor-account CloudFormation stays the deployment target (the #1973 Cloudflare problem kind is unaffected).
  • No change to Lite mode's default behavior; the repository seam defaults to DynamoDB there.
  • No replacement of SaaS-mode CodeBuild consumers (SBT ScriptJobs, tenant-update pipeline) in this ADR's phases.

ADR-034: Real attack realization (security-battle-royale)

operator が撃つ「攻撃」を、 実際に競技者アプリへ作用させて採点に反映するための実現パターンと、 攻撃ごとの実装レシピ・検証手順

Status: Proposed 2026-06-03
Related: ADR-031 (cross-account 配送 / action), ADR-033 (scoring-side effect), ADR-029 (revert / 永続禁止), ADR-012 (scoring kind = plugin)
Issue: #1666 (#1417 の子)

背景 — なぜ stackstack と同じ手では実現できないか

ADR-033 で stackstack の disruption は「採点上の効果 (penalty)」として実装し、 fire→減点 を logic で完全検証できた (実クラウド不要)。 しかし security-battle-royale の 3 攻撃 (sqli-auth-bypass / sqli-data-exfil / availability-flood) は本質的に異なる: 「競技者の防御が実際に持ちこたえるか」をテストする。 これは点を引くだけでは表現できない —

  • SQLi: 防御済 (parameterized query) のチームは 突破されない、 脆弱なチームは 突破される。 結果は 実アプリへ撃ってみないと分からない。 一律 penalty では「防御したのに減点」になり競技として破綻する。
  • availability-flood: rate-limit / 水平スケールで守ったチームは 生き残る、 単一 Flask のままのチームは 飽和する。 これも実負荷をかけて初めて分かる。

よって攻撃の実現は、 (1) 実際に作用させる配送機構 (ADR-031 の cross-account action) と (2) その結果を採点へ戻す経路 の 2 つを要する。 配送は ADR-031 で既存。 本 ADR は 「結果→採点」をどう繋ぐかを攻撃の型ごとに決め、 security-battle-royale の 3 攻撃の実装レシピと検証手順を確定する。

決定 — 2 つの実現パターン

パターン結果→採点の経路該当攻撃
A. 可用性劣化型
(degrade → 既存 uptime が拾う)		 攻撃 action (ADR-031) が実アプリを劣化させる (= プロセス飽和 / 接続枯渇)。 新しい採点経路は不要 — 既存の uptime-multi probe が slot 不通を検知し、 そのサイクルの加点を失う (failurePenalty も適用可)。 復旧は ADR-029 の revert で必ず止める。 availability-flood (= microservice-migration-battle の ec2-latency-injection と同型。 違いは netem 遅延ではなく負荷)。
B. 防御テスト型
(self-report → attack-detection が読む)		 攻撃 action が probe を撃ち、 競技者アプリ自身が「ブロックしたか/突破されたか」を CFn Output の counter に self-report する (= アプリが攻撃検知を実装している前提)。 採点は attack-detection kind (ADR-012) が counter 増分を読み、 ブロックできたチームを加点する。 突破は減点しない (= 防御できた事実を評価)。 sqli-auth-bypass / sqli-data-exfil。

パターン A は「攻撃が刺されば既存 uptime が勝手に下がる」ので最小。 パターン B は「防御の成否」という uptime では測れない性質を、 アプリの self-report + attack-detection scoring で測る (platform は防御の中身を知らない — 問題が所有する、 ADR-012)。

security-battle-royale 実装レシピ

availability-flood (パターン A)

disruption に action を追加。 template の InstanceId Output を targetRef に、 EC2 上で時間制限付きの HTTP 負荷を localhost のアプリ (frontend :80 / api :8080) にかける。 守り (nginx limit_req / 水平スケール) があれば uptime probe は通り続け、 無ければ飽和して落ちる。 revert で負荷を確実に止める (ADR-029)。 

// metadata.disruptions[availability-flood].action (ADR-031)
{
  "kind": "ssm-run-command",
  "targetRef": "InstanceId",
  "documentName": "AWS-RunShellScript",
  "paramTemplate": { "commands": [
    "END=$(( $(date +%s) + {{durationSeconds}} ))",
    "while [ $(date +%s) -lt $END ]; do for i in $(seq 1 {{concurrency}}); do curl -s -o /dev/null --max-time 2 http://localhost:8080/api/v1/apistatus & done; wait; done || true"
  ] },
  "revert": { "afterSeconds": {{durationSeconds}}+30, "documentName": "AWS-RunShellScript",
              "paramTemplate": { "commands": ["pkill -f 'curl -s -o /dev/null' || true"] } }
}
// parameters: { "durationSeconds": 30, "concurrency": 50 } ; operatorEditable: ["afterMinutes","concurrency"]

⚠ 負荷の強さ (concurrency) は EC2 インスタンスサイズと「単一 Flask が飽和するが OS は落ちない」境界に依存する。 これは 実機で 1 度 tune する必要がある (= 後述の検証手順)。 ec2-latency-injection の tc netem が決定的なのに対し、 負荷は環境依存。

sqli-auth-bypass / sqli-data-exfil (パターン B)

2 段構え。 (B-1) アプリ側: security-battle-royale の reference アプリが /api/v1/auth で SQLi をブロックしたら blocked counter を、 突破されたら bypassed counter を増やし、 CFn Output (AttackBlockedCount) に露出する。 (B-2) action: operator fire が ssm-run-command で localhost へ SQLi payload を撃つ (parameterized query なら失敗 = blocked)。 (B-3) scoring: kind を attack-detection に切替/併用し、 AttackBlockedCount の増分を加点する (ADR-012 の attack-detection は既存)。 突破 (bypassed) は減点せず 0 加点に留める (= 防御を評価、 失格にしない、 ADR-029 と整合)。

これにより「防御できたチームだけが攻撃イベントで加点される」= 防御の成否が採点に正しく反映される。 platform は SQLi の中身を知らず、 counter を読むだけ (= 問題所有、 ADR-012)。

代替案と却下理由

案却下理由
3 攻撃すべてを ADR-033 の penalty effect で実現却下。 防御の成否を測れない。 守ったチームも一律減点になり「攻撃を防ぐ」競技性が消える (= ハリボテ)。
availability-flood を CPU/メモリ stress で実現却下。 飽和はするが「rate-limit / scale で守る」という教育的意図 (= リクエスト洪水) をテストしない。 HTTP 負荷で撃つ。
SQLi の成否を platform 側 probe の戻り値で判定却下。 executor (ADR-031) は inject + revert を投げるだけで戻り値を採点へ運ぶ経路を持たない。 アプリ self-report + attack-detection counter が ADR-012 の既存機構に乗る。

影響 / 実装順序

  1. availability-flood (パターン A): submodule に action 宣言追加 + durationSeconds/concurrency parameters。 validate-problems が action/targetRef/placeholder を検証 (account 不要)。 配送は既存 executor (#1419)。
  2. SQLi (パターン B): reference アプリに attack-detection counter (AttackBlockedCount Output) + scoring kind を attack-detection 併用に。 action で probe 配送。
  3. 実機 tune + 検証 (account 律速): 1 アカウントに脆弱版/防御版アプリをデプロイし、 各攻撃を fire して — flood は「防御版は uptime 維持・脆弱版は失点」、 SQLi は「防御版は AttackBlockedCount 増 = 加点・脆弱版は加点無し」 — を目視。 concurrency を飽和境界に tune。

完了の定義は「防御したチームは攻撃を凌いで有利になり、 怠ったチームは不利になる」が実機で観測できること。 これは 実クラウドアカウントを要する (stackstack の純採点圧力と違い、 防御の物理的成否を測るため)。 本 ADR は account 入手前に実装を最大限進めるための設計を確定する。

Resolved: scoring kind の衝突 (B-3)

当初の懸念: security-battle-royale は uptime-multi で可用性を採点しており、 ADR-012 は 1 問題 1 scoring kind なので attack-detection へ切替えると可用性採点が消える。

決定 (option a、 ただし live probe で実装): uptime-multi に任意の attackBlocked: { slot, path, pointsPerBlock } を追加 (#1666)。 採点 tick は宣言時、 その slot の base URL + path を live probe し (= 走行中アプリの counter endpoint を読む)、 応答 body をブロック回数として parse、 前回からの増分に pointsPerBlock を掛けて加点する (差分 cap + baseline 追従は attack-counter.ts の共通ロジックで attack-detection と共有)。 可用性採点はそのまま、 防御の加点を 1 kind 内に重ねる。

⚠ 重要な落とし穴: counter は 必ず live probe で読む。 初期実装で deployment.stackOutputs (= deploy 時 1 回 capture の static な CFn output) から読もうとしたが、 runtime の counter 増分を追えず実 event で永遠に発火しない hollow だった (既存の attack-detection kind も同じ static-read の罠で、 どの問題も使っていない)。 採点時に endpoint を probe して初めて live な防御成否を測れる。

Open questions (残)

  • reference アプリの attack-counter 自己申告 (B-1): security-battle-royale の api/api.py が SQLi をブロックした回数を counter endpoint (例 /attack-stats) に露出する実装。 endpoint ロジック (SQLi を弾いたら +1) は unit-test 可能だが、 「実 SQLi で正しく弾くか」は実アプリへ撃つ live 検証を要する (account)。
  • 既存 attack-detection kind 自体の static-read を live probe に寄せる移行 (= 同じ罠の是正)。

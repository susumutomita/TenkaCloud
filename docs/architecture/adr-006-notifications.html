ADR-006: 運営 → 競技者 Notifications を Events table 同居 + 60 秒 polling で配信する

Status:Proposed 2026-05-10
Issue: #499
Related ADR: ADR-004 (Event/Team)、 ADR-005 (polling 60s 統一)

Context

Participant Portal の /notifications route は現状 PlaceholderPage が貼ってある状態で、運営から競技者への通知 (例: 「14:00 に競技開始します」「メンテナンスで 5 分停止します」「scoring 再開しました」) を出す機能が無い。本 ADR は (a) 通知データの保存 場所、(b) 配信経路 (push vs pull)、(c) 既読管理、(d) 運営 UI、(e) 参加者 UI の 5 軸を確定する。

制約由来本 ADR への影響
polling over SSEmemory feedback_polling_over_sse Web Push / WebSocket / SSE は使わない
polling 60s 統一ADR-005 D4 notifications 専用 polling も 60s で統一
DDB は 1 RCU/1 WCU PROVISIONEDDynamoDbLowCapacity Aspect 新テーブル増設は避ける
tenant 分離はインフラ層でINVARIANT_TENANT_ISOLATION_AT_INFRA_LAYER notifications は EVENT# (tenant scope) で閉じる
運営は tenant API + Cognito JWT、参加者は teamLoginKey bearer 既存 ADR-004 / ADR-005 同じ 2 経路に乗せる

現状

  • frontend: apps/participant-portal/src/App.tsx で /notifications → PlaceholderPage (「運営からの通知をここに表示します」)
  • backend: 該当 API なし
  • 運営側: 通知を出す手段なし (= Slack 等の外部チャネル運用)

解くべき設計判断

D1. データの保存先

案採否内容欠点
D1-A採用 既存 Events table に同 partition で乗せる: PK=EVENT#<eventId>、SK=NOTIFICATION#<isoTimestamp>#<ulid> 1 partition 内に META と Notification 行が混在 (= sparse single-table design)、Events Query に begins_with 必要
D1-B却下 新 DDB NotificationsTable 新テーブル増設で DynamoDbLowCapacity Aspect 影響範囲が広がる、運用コストも 1 段階増
D1-C却下 Deployments table に PK=NOTIFICATION#<eventId> Deployments table の責務 (= 1 deployment 単位) を超えて混乱、ParticipantPortalLambda が DDB Read 権限を別 partition へ拡張する必要
D1-A の詳細 schema
属性型説明
PKStringEVENT#<eventId> (既存と同じ)
SKStringNOTIFICATION#<occurredAt>#<ulid> (時系列で sort 可能)
tenantIdStringtenant 跨ぎ防止 check 用
eventIdString解析しやすさのため復元
notificationIdStringULID (= SK 内の ulid と同じ)
titleString1 行サマリ、120 chars max
bodyString本文、2000 chars max
severityString"info" | "warning" (D4)
createdByStringoperator の Cognito sub (監査用)
occurredAtStringISO 8601 UTC、SK 内と同じ値を attribute にも
expiresAtNumberDDB TTL、event の expiresAt と同じ

D2. 既読管理

既読 (read state) を server-side で管理しない。理由:

  • 1 team = 複数競技者でログインキー共有運用 (Phase 2c) なので「user 単位の既読」概念が そもそも曖昧 (= 同 team の別ブラウザで読んだら既読扱い? それとも全員別?)
  • per-user read tracking を始めると DDB row が爆発 (= notifications × users)、 DynamoDbLowCapacity Aspect の 1 WCU では捌けない
  • shared 運用では「最後に表示した notification の occurredAt」を browser localStorage に保存し、それより新しいものを「unread」と扱うのが UX として十分

→ Decision 2: localStorage に lastSeenAt を保存、それより新しい notification 数を unread として TopNav に表示。サーバー API には read endpoint を作らない。

D3. 配信経路 (push vs pull)

Web Push / SSE / WebSocket は feedback_polling_over_sse + ADR-005 D4 と 整合させて使わない。polling 60 秒 で統一する (ADR-005 と同じ tick)。

層tick備考
backend (運営の write)operator が手動 trigger 頻度低 (1 イベント数件想定)、batch / scheduler 不要
frontend (TopNav 未読 badge)60 秒 TeamViewProvider と同じ tick に乗せて 1 系統に集約 (= 別 polling は立てない)
frontend (/notifications page)page open 時 + 60 秒 page を見ている間だけ更新、closing 時に lastSeenAt を localStorage に commit

D4. severity

初期 release では 2 段階 のみ。後で必要になれば追加。

severity意図UI 表現
info普通の通知 (例: 「scoring 再開しました」) 青い pill-status info badge、TopNav badge は普通色
warning注意喚起 (例: 「30 分後にメンテで 5 分停止」) 黄色い pill-status warning badge、TopNav badge は強調色

(参考: 案として urgent / error もあり得るが、Battle のゲーム性に 通知 spam で影響を与えるリスクがあるので 導入しない。本当に urgent なら Slack 等で別配信)

D5. ライフタイム / TTL

Notification 行の expiresAt は event 行の expiresAt と同じ値 を使う。理由:

  • event 終了後に古い notification を残す意味が薄い (= 競技者は次 event の通知を見る)
  • DDB TTL に乗せて自動削除 (= 運用 op 不要)
  • event archive (= ARCHIVED) しても TTL までは見える (= 競技者の振り返り猶予)

D6. 運営 UI 配置

運営側の通知作成 UI は EventDetail 画面の中に modal で組み込む。理由:

  • 「event 単位で通知を打つ」が自然 (= cross-event の通知は要求されていない)
  • 新 page を立てると navigation 増、既存 EventDetail に「通知」 section と modal を貼れば 1 画面で完結
  • operator の workflow: 競技開始時刻設定 → Bulk Deploy → 通知発信、と同じ画面で完結

D7. Web Push / Browser Notification API

本 ADR では扱わない (= Phase 4+ 以降)。理由:

  • Web Push は Service Worker + VAPID key + browser permission 必要 (= 実装規模大)
  • polling 60s で「2 分以内に届けば十分」が満たせるので、push の必要性は低い
  • 競技者は Portal を開いて競技中なので、画面内 TopNav badge で十分視認できる

Migration

Phase 4.1 (本 ADR 実装の最初の PR、scope 中)
  1. Events table の write 権限を持つ event-handler Lambda が NOTIFICATION#<ts>#<ulid> SK で行を書けることを CDK レベルで確認 (= 既存権限で OK と想定、不足なら追加)
  2. POST /events/:id/notifications handler 実装 (validation + DDB PutItem)
  3. tenant API GW route 追加 (user 担当)
  4. ParticipantPortalLambda の IAM に events table Query 追加 (user 担当)
  5. GET /portal/me/notifications handler 実装 (auth → eventId 解決 → DDB Query)

Consequences

Positive

  • 運営が Slack 等の外部チャネルに依存せず Portal 内で完結して通知できる
  • 新 DDB を立てない (D1-A) ので運用コスト 0、DynamoDbLowCapacity Aspect の影響範囲不変
  • polling 60 秒で 2 分以内に届くので Battle のゲーム性に十分
  • localStorage 既読管理 (D2) で per-user read tracking の DDB 爆発を回避

Negative

  • shared teamLoginKey 運用なので「同 team の別 user が既読にした」を別 user は知らない (= 各人 localStorage、別 device は別管理)
  • Web Push が無いので Portal を閉じている人には届かない (= 競技中は Portal 開きっぱなし前提)
  • Events table の partition に異種 row (META + NOTIFICATION) が混在し、Query 時の begins_with 必須

Capacity 見積もり

項目値根拠
1 event の通知件数5 〜 20 件運用想定 (開始 / 中盤 / 終了 + メンテ通知)
1 行サイズ~2 KB (title + body 含む)body 最大 2000 chars + meta
Query (1 event 全件) のサイズ~40 KB (20 行 × 2KB)begins_with で notification のみ
必要 RCU (eventually consistent)~5 RCU40KB / 8KB = 5 RCU/req、25 teams × 60s polling = 25/min = 0.4 req/s
burst capacityOKDDB 標準 burst 5 分で十分吸収可

結論: DynamoDbLowCapacity Aspect の 1 RCU PROVISIONED でも burst capacity で吸収可。継続的に 25 teams 同時 polling する場合の peak は ~10 RCU 相当だが、毎分の spike なので burst credit (= 300 RCU/min 相当) で十分。実測でスロットルが起きたら Phase 4 の follow-up で limit 既定値を 50 に下げるか auto-scaling 検討。

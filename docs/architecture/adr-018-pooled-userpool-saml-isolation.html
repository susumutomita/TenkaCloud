ADR-018: pooled tenant の UserPool 分離問題 — SAML SSO は PLATINUM 限定で短期 mitigation、 long-term は per-tenant UserPool 化を保留

Status:Accepted 2026-05-17
Supersedes: (なし)
Superseded-by: (なし)

1. Context

TenkaCloud は SBT (@cdklabs/sbt-aws) ベースの multi-tenant SaaS。 tier 設計:

  • BASIC / ADVANCED (= pooled tier): serverless-saas-ref-arch-tenant-template-pooled stack を **全 pooled tenant が共有**。 内部の Cognito UserPool / API Gateway / Lambda が共有リソース。 tenant 分離は DDB の partition key + JWT claim (custom:tenantId) で実現
  • PLATINUM (= silo tier): provision-tenant.sh が CodeBuild 経由で per-tenant に serverless-saas-ref-arch-tenant-template-<tenantId> stack を立て、 Cognito UserPool / API Gateway / Lambda がすべて tenant 専用

この設計のもとで、 application-admin-console から SAML IdP federation を tenant 別に設定できる機能を加えた (Issue #839)。 pooled tier の operator が \"うちの会社 SSO で sign-in を統一したい\" と requirement を出したのが背景。 当該機能は cognito-idp:CreateIdentityProvider / UpdateIdentityProvider / UpdateUserPoolClient を call し、 当該 tenant の (= pooled なら共有) UserPool に SAML IdP を attach する。

問題: pooled tier の tenant が SAML を有効化すると、 **同 UserPool 上の全 pooled tenant の Cognito Hosted UI に追加 IdP が表示される**。 1 tenant の SAML 設定が他 tenant の sign-in 経路に副作用する。 SaaS isolation 観点で受け入れ不可。

Issue #897 で短期 mitigation (= Application Admin Console から SAML SSO page を隠して PLATINUM 限定にする) は実装済 (PR #904)。 しかし long-term の architecture 判断 (= pooled UserPool 分離そのものをどう扱うか) が未決のまま Issue #898 として残っていた。

2. Decision

本 ADR で次の 2 件を decide する。

decision本 ADR の結論根拠
D1. 短期 SAML SSO 機能は PLATINUM (silo) tier 限定。 pooled (BASIC / ADVANCED) tenant の Application Admin Console からは menu / route ともに hide。 既に Issue #897 / PR #904 で実装済 (= 本 ADR では \"採用判断の正本\" として明文化) per-tenant UserPool 分離は cost / 構造影響が大きい (D2 参照)。 SAML は \"あれば嬉しい\" 機能で、 \"無いとサービス成立しない\" 機能ではない。 PLATINUM upgrade promo に倒すことで価値訴求にも転用
D2. 長期 pooled tenant の UserPool を per-tenant 化 (= 全 tenant silo 化) は 採用しない。 当面は D1 の機能 gate で十分。 ただし条件が変われば本 ADR を re-evaluate する trigger (D3) を明示 SBT の tenant-template-pooled は \"pooled tier = 共有リソース\" を前提に設計されており、 per-tenant UserPool 化は SBT 構造から大幅に逸脱する。 cost 試算 (= 後述 §3) でも Free Tier 範囲を超え、 BASIC / ADVANCED の price point に合わない
D3. re-evaluate trigger 次のいずれかが起きたら本 ADR を見直し:
(a) PLATINUM tier の採用率が pooled tier を超え、 pooled の存在意義 (= cost optimization) が薄れたとき
(b) Application Admin から SAML 以外にも UserPool に副作用する機能要求が複数 issue 化されたとき (= SAML を hide するだけで対応できない multi-tenant 競合が増えたとき)
(c) SBT が pooled 内 sub-isolation (= 1 UserPool 内 multiple-IdP per-tenant-attribute filter) のような mechanism を支援したとき 		(a) は cost meta から自然に判断材料が出る、 (b) (c) は手動 review

3. なぜ per-tenant UserPool 化を採用しないか (= D2 の根拠)

3.1 cost 試算

Cognito 料金は MAU (monthly active users) per UserPool ベース。 50,000 MAU まで無料、 超過後は MAU 単価。 ただし UserPool は無料、 課金は user / MAU。

一見 \"UserPool を分けても課金は user 数に依存するので cost は変わらない\" に見える。 しかし real cost は:

  • operational cost: per-tenant に UserPool を作ると tenant 数 × Hosted UI domain × callback / logout URL × IdP / Client 設定の管理対象が線形に増える。 SBT pipeline / deploy 時間も伸びる
  • CloudFormation 制約: AWS account あたり UserPool は 1,000 件 / region (= service quota)。 pooled tier の tenant が 1,000 を超えたら quota 引き上げ申請が必要
  • CFn deploy 時間: per-tenant UserPool は CodeBuild 経由で個別 stack を立てるため、 1 tenant あたり 5-15 分の deploy 時間 (= 現状 PLATINUM tier の所要時間)。 全 pooled tenant を silo 化すると onboarding が線形に slow になる

3.2 SBT 構造との不整合

SBT の tenant-template-pooled は明示的に \"複数 tenant が共有する stack\" を意図している (= ref-arch の前提)。 per-tenant UserPool 化は事実上 \"全 tenant silo 化\" であり、 pooled tier を廃止することと等価。 既存 tier 区分 (basic / standard / premium / platinum) のうち pooled 3 つを silo に統合すると pricing model も整理が必要になり、 影響範囲が architecture を超えて business model に及ぶ。

3.3 isolation の現状評価

pooled UserPool 共有が generate する isolation hole は次の 3 種類:

hole現状本 ADR での扱い
SAML IdP 表示 1 tenant の SAML 設定が同 UserPool の他 tenant の Hosted UI に IdP button を表示 D1 で機能 gate (= pooled では SAML disable)
UserPool email 設定 1 tenant が UserPool の SES sender / email template を変えると他 tenant の招待メールも変わる 当該機能は Application Admin に開放していない (= System Admin only)。 影響なし
UserPool 削除 / 再構成 SBT の pooled stack delete は全 pooled tenant を同時 deprovision する System Admin のみ可。 Application Admin 経路無し。 影響なし

= UserPool 共有が generate する cross-tenant 副作用は SAML だけ。 D1 で塞げば D2 (UserPool 分離) は不要。

4. Implications

4.1 Application Admin Console

  • pooled tenant の Application Admin は SAML SSO menu / route が見えない (= PR #904 で実装済)
  • PLATINUM tenant の Application Admin は従来通り SAML 設定可能
  • SAML を使いたい pooled tenant への messaging は \"upgrade to PLATINUM\" promo に倒す (= UI strings は \`platinum_only_*\` keys、 4 locale 完備)

4.2 System Admin (= サービス提供元) の責務

  • pooled UserPool の email template / SES sender / IdP 設定は System Admin のみ。 Application Admin に露出させない
  • pooled tenant から SAML 設定の手動依頼があった場合、 サービス提供元としては \"PLATINUM tier への upgrade をご案内\" 一本で対応。 個別の SAML 仲介はしない (= 1 tenant の都合で他 tenant に副作用させない)

4.3 SBT migration / 将来の SBT version 上げ

  • SBT 0.3.9 → 0.4.x の upgrade で pooled stack の構成が変わる場合、 本 ADR の D2 を再評価する。 SBT 側が pooled 内 sub-isolation を支援したら D3 (c) trigger で path 変更

4.4 cost / SLA

  • cost: 現状の pooled stack 1 つ運用は維持。 per-tenant UserPool 化による cost 増は発生しない
  • SLA: pooled tenant の SAML 不可は SLA / 契約書 / tier comparison page に明記 (= 後述 §7 follow-up)

5. Alternatives considered

Alt-A: 全 tenant silo 化 (= pooled tier 廃止)

  • cost / SBT structural impact が大きい (§3)
  • BASIC tier の price point を維持できなくなる (= silo cost が basic price を上回る)
  • Rejected: business model / SBT 整合性で受け入れ不可

Alt-B: pooled UserPool 内で provider 名に tenantId prefix を付けて分離

  • provider 名は UserPool 内 unique なので、 tenant-acme-saml / tenant-beta-saml のように prefix を付ければ衝突回避可能
  • しかし Cognito Hosted UI の sign-in button は UserPool 内 provider を全件表示する。 別 tenant の user が別 tenant の IdP を選択する経路は残る
  • API 側で IdP-initiated SSO の identityProviderName を tenant claim と check しても、 user-initiated 経路は防げない
  • Rejected: Hosted UI の表示制御が UserPool 単位のため、 prefix だけでは isolation 保証にならない

Alt-C: Application Admin に SAML を見せつつ \"co-tenant impact\" warning を出す (= 旧実装)

  • UI で \"shared UserPool warning\" を表示し、 ユーザに risk を transparent に伝える
  • しかし Application Admin は SaaS の customer 側 admin であり、 service provider の infrastructure 事情を判断する立場にない。 risk 通知は責任 punt
  • 1 tenant の Application Admin が UI を操作したら他 tenant の sign-in を壊せる経路を service provider が 残してはいけない
  • Rejected: 責務設計の誤り (= Issue #897 で議論済)

Alt-D: System Admin が pooled tenant の SAML を代理設定する

  • pooled tenant が SAML 希望時、 Application Admin から System Admin に ticket を切ってもらい System Admin が pooled UserPool に provider 名 = tenantId prefix で設定
  • = Alt-B + ticket 運用。 Hosted UI 表示の問題 (= 別 tenant の user が別 tenant の IdP button を見る) は残る
  • service provider 側 operational burden が増え、 Alt-B の根本問題 (Hosted UI 単位の表示制御) も解消しない
  • Rejected: cost と効果が見合わない

Alt-E: pooled UserPool を \"per-tier UserPool\" に分割 (= BASIC = pool-A、 ADVANCED = pool-B 等)

  • tenant 数より tier 数 (3 個) は少ないので per-tenant 分割より cost が控えめ
  • しかし同 tier 内では tenant 共有は変わらず、 SAML 影響範囲は \"同 tier の全 tenant\" になるだけで isolation はまだ不完全
  • Rejected: 中間解で根本問題が解けていない

# Platform architecture <MaturityBadge level="stable" />

Read the platform through its users, responsibilities, components, and operation sequences.
These diagrams describe the implementation, not an inventory of deployed AWS resources.

<h2 id="reading-order">Reading order</h2>

Start with **05 System context → 04 Use cases** in the
[Draw.io source](https://github.com/susumutomita/TenkaCloud/blob/main/docs/architecture/diagrams/system-architecture.drawio).
Then read the views below. Use **01 SaaS / 02 Lite / 03 Local** for physical placement and wiring.

The [developer architecture guide](https://github.com/susumutomita/TenkaCloud/blob/main/docs/architecture/README.md)
links each operation to its source files, completion criteria, and failure diagnostics.
The shared diagrams use Japanese labels alongside implementation names.

<h2 id="cloud-responsibilities">Cloud responsibilities</h2>

[![Logical architecture](/docs/assets/architecture/logical.svg)](/docs/assets/architecture/logical.svg)

SaaS uses SBT to manage tenants. Lite omits that tenant-management layer.
Pooled and silo describe where organizer applications are placed, not additional logical responsibilities.
The boxes do not correspond one-to-one to CDK stacks or AWS accounts.

<h2 id="cloud-components">Cloud components</h2>

[![Cloud components](/docs/assets/architecture/cloud-components.svg)](/docs/assets/architecture/cloud-components.svg)

Event APIs, deployment workflows, participant APIs, the coordination dispatcher, and scheduled scoring have different owners.
Tenant isolation combines request authentication and scope checks with storage keys and stack boundaries.
Supported Turso configurations update deployment state through the StatusWriter Lambda; Step Functions does not connect directly to SQL.

<h2 id="local-play-and-docker">Local play and Docker</h2>

[![Local Docker components](/docs/assets/architecture/local-components.svg)](/docs/assets/architecture/local-components.svg)

`make local` is a personal-practice path with a fixed local event and team.
The control container and problem containers run under the same Docker daemon.
Problem correctness is checked through HTTP `/verify`, progress is saved in SQLite,
and containers are started and stopped through the Docker socket.
A read-only socket mount does not make Docker API operations read-only.

The in-development multi-team local host and the crypto-battle development harness are separate paths.
The `make local-dev` Simulator is enabled only by explicit opt-in; Docker problems do not require it.

<h2 id="saas-tenant-onboarding">SaaS tenant onboarding</h2>

[![Tenant onboarding sequence](/docs/assets/architecture/tenant-onboarding.svg)](/docs/assets/architecture/tenant-onboarding.svg)

Registration acceptance is separate from tenant readiness. Check the SBT lifecycle result.
PLATINUM deploys a dedicated stack; other tiers use the existing pooled stack.

<h2 id="problem-deployment">Problem deployment</h2>

[![Cloud problem deployment sequence](/docs/assets/architecture/problem-deployment.svg)](/docs/assets/architecture/problem-deployment.svg)

This shows the AWS Lambda deployment path. HTTP acceptance counts are not successful deployment counts.
Check each deployment job's COMPLETE or FAILED result.
For cross-account deployment and status polling, each worker invocation retrieves the mandatory ExternalId from SSM SecureString and calls STS AssumeRole for the competitor role before calling CloudFormation with temporary credentials.
The same-account development path may omit both role and ExternalId parameter; configuring only one is an error.
The guide describes the Distributed Map alternative and the omitted CodeBuild path.

<h2 id="cloud-answers-and-scoring">Cloud answers and scoring</h2>

[![Cloud participant scoring sequence](/docs/assets/architecture/participant-scoring.svg)](/docs/assets/architecture/participant-scoring.svg)

Flag submission and coordination operations use separate paths.
Coordination state persistence and score delivery are also separate: pending scores are saved and delivery is retried.
Scheduled scoring is triggered independently of participant submissions.

<h2 id="local-play-startup-and-scoring">Local play startup and scoring</h2>

[![Local startup and scoring sequence](/docs/assets/architecture/local-play-sequence.svg)](/docs/assets/architecture/local-play-sequence.svg)

Starting a problem returns 202 before the actual Docker startup completes.
Answers are checked by the problem verifier, then progress is persisted before the response.
Verifier connection failures remain errors; they are not converted to incorrect answers or success.

# Platform architecture <MaturityBadge level="preview" />

<h2 id="reading-order">Reading order</h2>

Read the responsibilities and trust boundaries before selecting an execution environment. This unpublished candidate runs one community competition process; it does not include SaaS tenant provisioning.

<h2 id="local-play-and-docker">Local competition and Docker</h2>

`make local` serves organizer and participant applications from one Bun process. Organizer roles and event/team keys authorize separate HTTP surfaces. SQLite and private key files retain competition state and runtime ownership. `make down` stops owned local runtimes while preserving data; explicit teardown is separate.

New Docker events prepare up to 512 dormant jobs, then participants Start / resume and Stop (keep data). Defaults are team 3 / host 12 active environments and 4096 MiB summed memory caps. The 40 gateway slots are active-only; runtime ports persist while stopped. Writable layers and volumes survive, not RAM. There is no automatic eviction or reset. Existing events keep their legacy lifecycle. Generic Docker catalog/workbench restoration is in progress. The target is all 106 former local problems as Challenge competitions. Terminal support and real Docker/browser verification remain incomplete. Verifiers must remain separate from public challenge surfaces and other teams.

<h2 id="cloud-components">AWS exercises and cloud platform</h2>

The reviewed AWS adapters deploy owned CloudFormation stacks in verified competitor accounts. The deployment role requires the host ExternalId; participant access assumes a separate saved viewer role with the deployment ExternalId. Operator credentials never become participant credentials.

Cloud Turso integration and platform placement are in progress. `make deploy` and `make destroy` currently fail explicitly without resource changes. A long-running process, its schedulers and persistent identity need an actual deployment contract before cloud claims can be made.

<h2 id="problem-deployment">Problem deployment and scoring</h2>

An authenticated organizer requests an event operation. Ownership is saved before external creation. Status, errors and recovery remain durable. Participant requests recheck team, event, problem and time; verified scores, progression and retry receipts commit together before success is returned. A failed verifier or uncertain cloud operation is not a success.

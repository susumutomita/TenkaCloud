# Run an event end to end <MaturityBadge level="preview" />

This is the operator walkthrough: from a freshly deployed platform to a competitor
solving a problem in their own cloud account. It is the prose form of the
single-pass flow the platform guarantees (tenant creation → application console →
problem deploy → participant join).

## Create a tenant

In SaaS mode, a System Admin creates a tenant from the `admin-console` (the control
plane front end). Tenant creation emits `onboardingRequest`; the tenant is
provisioned as pooled by default, or as a dedicated silo stack for the PLATINUM
tier. The tenant admin then receives the `application-admin-console` URL for their
plane. In Lite mode there is a single local tenant and you go straight to the
application console.

## Connect a competitor account

Each competing team deploys a one-time CloudFormation template
(`infrastructure/templates/competitor-bootstrap.yaml`) into their own AWS account.
It creates a least-privilege IAM role whose trust policy is pinned to the
TenkaCloud control-plane account id **and** the tenant's **ExternalId**, so only
TenkaCloud — and only for that tenant — can assume it. The team shares the
resulting role ARN back to the operator. The full competitor-side steps live in the
[competitor setup guide](https://github.com/susumutomita/TenkaCloud/blob/main/infrastructure/templates/README.md).

## Deploy a problem

In the `application-admin-console`, create an event, pick problems from the catalog
(the picker only offers cloud-deployable problems — local-only container problems
are excluded, and non-AWS problems appear once multi-cloud is enabled), assign each
team's account and region, and deploy. Each deploy assumes the team's role with the
ExternalId and runs CloudFormation in their account. Watch status by polling the
deployment until it reaches a terminal state, then tear it down from the same
console when the event ends.

## Enable multi-cloud

To run Sakura / Azure / GCP problems, set `features: { "nonAwsRuntime": true }` in
`runtime-config.json`. A Team Cloud Credentials panel then appears on the Competitor
Accounts page; register each team's provider credentials there (the panel writes
them to SSM SecureString via the API — operators never touch SSM directly). Once a
provider's credentials are registered, that provider's problems become selectable in
the event picker. The provider-by-provider credential steps and which fields go in
the panel are in the [competitor setup guide](https://github.com/susumutomita/TenkaCloud/blob/main/infrastructure/templates/README.md),
and the support state of each runtime is the
[runtime capability matrix](/developers/docs/reference/runtime-matrix/).

and the [platform architecture](/developers/docs/concepts/architecture/).

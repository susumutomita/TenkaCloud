# イベントをエンドツーエンドで運営する <MaturityBadge level="preview" />

これは運営者向けのウォークスルーです。現在開催手順として案内するのはLiteです。
SaaSのテナント作成とマルチクラウドは末尾に分離し、コード構成の参考として説明します。

## 開催までの道のり

「開催したい人はいるが、運営経験がない」状態から使える準備表です。まず、責任者と協力者で開催計画を1枚にまとめます。以下の時期と作業時間は**初回開催の見積り**です。会場の予約期限や社内承認に合わせて前倒しし、開催後に実績で更新してください。

**企画 → 人と場所 → 環境 → リハーサル → 開催 → 撤収・振り返り**

[問題として練習する：はじめての開催責任者](https://github.com/susumutomita/TenkaCloudChallenge/tree/main/challenges/event-host-rehearsal)。Dockerを使うローカル専用の問題です。AWS上の問題ピッカーには表示されません。仮想の開催計画を作り、4つのチェックポイントで確認します。合格は本番環境の準備完了を意味しません。

### いつまでに、何を用意する？

| 時期の目安 | 担当と作業時間の見積り | 用意するもの・数量 | 完了条件・間に合わないとき |
| --- | --- | --- | --- |
| 4週間前 | 責任者＋協力者、60分 | 目的・参加者属性・日時・予算上限を記入した企画書1枚 | 責任者と開催目的が決まる。担当がいなければ募集前に協力者を探す |
| 3週間前 | 会場担当＋募集担当、各60〜120分 | 会場またはオンライン接続先1つ、定員、電源・通信の確認記録、募集文1本 | 場所と定員を確定して募集する。未確保なら日程・規模を変更する |
| 2週間前 | 技術担当＋進行担当、各60〜120分 | チーム案、問題一覧、使うバージョン、必要機材表、当日役割表 | 対象者に合う問題と担当が決まる。難しければ出題数を減らす |
| 1週間前 | 当日担当全員、競技時間＋60分 | テストチーム、当日と同じ設定、司会台本、障害連絡表 | ログイン→練習→回答→得点→終了→撤収を通す。採点・接続が未確認なら本番開始を約束しない |
| 前日 | 技術担当＋受付担当、30〜60分 | 確定名簿、チーム別配布物、予備機材、連絡先、固定したコミット番号 | 全担当が配布先と手順を確認。欠席時の代役を決める |
| 当日60分前 | 技術担当＋会場担当、30分 | 接続・電源・画面・問い合わせ先の確認 | 不調を切り分ける。再開条件を責任者が判断する |
| 当日30分前 | 受付担当＋司会、30分 | 受付、チーム別ログイン情報、練習時間 | 全チームの接続を確認して開始時刻を案内。未接続なら原因を確認し開始を調整する |
| 競技中 | 司会＋質問担当＋技術担当、競技時間 | 残り時間案内、質問・障害の記録 | 公平な同一案内を全員へ出す。停止・再開の判断者を一本化する |
| 終了後 | 責任者＋技術担当、30〜60分 | 得点確認、結果、アンケート、撤収記録 | 得点を確定し、不要環境の削除結果と費用を確認する。削除要求だけで完了としない |
| 翌週 | 担当全員、30分 | 実績時間・困りごと・改善案1枚 | 次回テンプレートの担当・数量・見積りを更新する |

### 開催計画と協力者を1枚にする

この表をコピーして主催者の管理場所に保存します。氏名・連絡先・ログイン鍵を公開Issueや公開資料に貼らないでください。

| 記入欄 | 今回の計画 |
| --- | --- |
| 目的・対象者 | 何を体験してほしいか／暗号・AWSの経験／必要な配慮 |
| 日時・形式・会場 | 受付・練習・競技・発表・撤収の時間／対面またはオンライン |
| 人数・定員・チーム | 参加人数／1チームの人数／チーム数／欠席時の組み替え |
| 責任者・代役 | 開始・中断・再開・得点確定を判断する担当 |
| 募集・会場・受付 | 担当／対応可能時間／代役／内部の連絡方法 |
| 司会・質問対応・技術 | 担当／対応可能時間／代役／競技中に同時対応できるか |
| 予算・環境 | 上限／使用環境／費用確認担当／撤収担当・期限 |
| 教材・バージョン | 問題一覧／競技時間／問題設定／リハーサル済みコミット番号 |

兼任は可能ですが、受付中の障害対応など、同時に起こる仕事を一人へ集中させないようにします。必要人数は運営規模とリハーサル結果で決めます。

### 数量を決める：23人・1チーム4人の例

チーム数は、人数を4で割って端数を切り上げます。23人なら6チームです。これは準備計算であり、システムの最大収容人数の保証ではありません。

| 品目 | 数え方 | 23人の例 |
| --- | --- | --- |
| チーム別ログイン情報・配布先 | チーム数分。鍵の一覧を公開せず、再配布担当を決める | 6組 |
| PC | 全員で操作するなら参加人数＋予備数。チーム共有なら事前に共有方式を告知 | 23台＋予備2台＝25台（この例の方針） |
| 電源・通信 | 参加PC＋運営PC。会場の口数・回線・利用規約を実地確認 | 必要台数を会場担当へ渡して確認 |
| 紙・筆記具 | 手計算する参加人数分＋予備 | 23組＋予備 |
| 進行表・障害連絡表 | 各担当が参照できる共通の最新版 | 1つの正本を共有 |

AWSアカウントの必要数や構成は選ぶ問題と開催方式によります。チーム数だけで決めず、下のデプロイ手順と問題READMEを確認してください。

### 当日の司会台本

1. **受付**：「自分のチーム名とログイン先を確認してください。鍵は他チームに共有しません。接続できない方は受付へお知らせください。」
2. **練習**：「最初の1問で、回答する場所と得点の表示を確認します。練習と本番の得点・時間の扱いは今回の設定で説明します。」
3. **開始前**：「正解・不正解・期限切れの扱いを確認します。困ったらこちらの窓口へ。全チームの準備を確認してから開始します。」
4. **競技中**：「残り時間は画面で確認できます。共通の変更や障害案内はこちらから全チームへお伝えします。」
5. **終了**：「回答受付を終了します。記録を確認してから得点と順位を確定します。結果に疑問がある場合は窓口へお知らせください。」

### 困ったときの判断表

| 状況 | 最初の確認 | 判断者と次の行動 |
| --- | --- | --- |
| 主担当が欠席 | 代役の連絡・権限・手順の所持 | 責任者が役割を再配置。対応できなければ規模・開始を変更 |
| 1チームだけ未接続 | URL、チーム別ログイン情報、端末、回線 | 受付→技術担当へ。鍵を全員向けに貼って解決しない |
| 全チームが接続不可 | 共通の回線・Portal・環境状態 | 技術担当が切り分け、責任者が開始延期と次回案内時刻を通知 |
| 回答したのに得点が合わない | オーダー番号、時刻、画面、採点記録 | 技術担当が照合。確認前に再送を繰り返させたり点数を書き換えたりしない |
| 中断が必要 | 影響範囲、記録、現在の時間・得点 | 責任者が全員へ案内。一時停止できるとは仮定せず、使うモードで確認済みの手順を使う |
| 撤収に失敗 | 残ったリソースと削除失敗の理由 | 技術担当が残件と期限を記録し引き継ぐ。費用確認を継続する |

## Liteで競技を運営する

1. LiteのApplication Admin Consoleへログインする。
2. イベント、テストチーム、問題を作る。
3. 下記の手順でテスト競技者AWSアカウントを接続する。
4. 問題を起動し、接続先を開く。
5. 問題を解いて本物の`TC{...}`を提出し、得点を確認する。
6. リセットして再起動できることを確認する。
7. 停止し、競技者AWSの問題スタックが削除されたことを確認する。
8. Participant PortalのURL、team key、開始時刻を参加者へ渡す。

## 管理者SSOを企業IdPに接続する

管理者SSOはParticipant Portalのチームログイン鍵とは別の認証経路です。TenkaCloudではCognito User PoolをSAML Service Providerとして使い、Microsoft Entra ID、Google Workspace、AWS IAM Identity CenterなどのSAML 2.0 IdPと接続できます。

Application Admin ConsoleのSAML SSOは実験的機能で、デフォルトでは無効です。tenant単位のIdP設定はLiteまたはsilo tierの専用User Poolで使い、pooled tenantでは使用しません。本番イベントの前に非本番環境で一連のログインを確認してください。

1. Application Admin Consoleの「ID プロバイダ」画面を開き、表示されたACS URL、SPエンティティID、email attribute mappingを取得する。ドキュメント中の例ではなく、画面に表示された値を正本にする。
2. IdP側でSAML 2.0アプリケーションを作成し、ACS URLとSPエンティティIDを設定する。`NameID`は同一ユーザーで安定した値にし、通常はemailを使う。
3. IdP側でテストユーザーまたはテストグループをアプリケーションへ割り当て、IdP metadata XMLを取得する。AWS IAM Identity Centerは汎用SAMLとして設定する。
4. TenkaCloudへmetadata XMLを登録し、email attribute mappingを確認する。最初はgroup-to-role mappingを空にし、基本ログインが成功してから認可設定を追加する。
5. private browsing windowからTenkaCloudのログインを開始し、IdP認証、Cognito callback、Application Admin Consoleへの復帰までを確認する。IdPのポータルから直接開くだけではなく、TenkaCloudから開始するSP-initiated loginを確認する。
6. 通常ログインでも同じIdPへルーティングされること、ログイン後のemail、tenant、roleが期待どおりであることを確認する。IdP登録と通常ログインのルーティングは別の設定経路なので、登録だけで完了と判断しない。
7. SSO障害時に備え、既存のCognito local administratorを少なくとも1名維持する。SAML assertion、ID token、metadata XMLは組織情報を含むため、Issueやチャットへ無加工で貼らない。

証明書更新、障害切り分け、IdPの撤去を含む詳細手順は[管理者向けCognito / SAML IdP接続プレイブック](https://github.com/susumutomita/TenkaCloud/blob/main/docs/operations/cognito-saml-idp-playbook.md)を参照してください。

## SaaSでテナントを作成する（構成参考）

SaaS モードでは、System Admin が `admin-console`からテナントを作成するコードがあります。
しかし、最近の新規AWS環境でテナント作成から採点・削除までを通した記録はありません。
本番手順として使用せず、専用環境で再検証してください。

## 競技者アカウントを接続する

参加する各チームは、CloudFormationテンプレート
`infrastructure/templates/competitor-bootstrap.yaml`を自分のAWSアカウントへ
1回デプロイします。`ExternalId`は開催者が設定した値と同じ、16〜128文字の半角英数字と
`_ = , . @ : / -`を使います。作成されたロールARNを開催者へ共有します。秘密鍵や
AWS管理者認証情報は共有しません。詳細は[競技者セットアップガイド](https://github.com/susumutomita/TenkaCloud/blob/main/infrastructure/templates/README.md)にあります。

## 問題をデプロイする

`application-admin-console` でイベントを作成し、カタログから問題を選び（ピッカーに表示されるのはクラウドにデプロイ可能な問題だけです。ローカル専用のコンテナ問題は除外され、非 AWS の問題はマルチクラウドを有効にすると表示されます）、各チームのアカウントとリージョンを割り当てて、デプロイします。各デプロイは ExternalId を使ってチームのロールを AssumeRole し、チームのアカウントで CloudFormation を実行します。デプロイメントが終了状態に達するまでポーリングでステータスを見守り、イベントが終わったら同じコンソールから撤収します。

## マルチクラウドを有効にする（構成参考）

Sakura / Azure / GCPは一律に実行可能とは限りません。先に
[ランタイム対応マトリクス](/developers/docs/reference/runtime-matrix/)で対象問題の
状態を確認し、実行可能と記載されたruntimeだけを専用のテストイベントで検証します。

# 問題カタログの選択 <MaturityBadge level="preview" />

起動は[開催のクイックスタート](/developers/docs/getting-started/#local-start)、作成は[問題作成マニュアル](/developers/docs/manual/problem-author/)から始めます。このページは、この checkout の取得元設定の仕様です。ローカルパス対応は main に実装済みですが、該当 revision がリリースされるまでは開発版の機能です。公開サイトや古い checkout に同じ機能があるとは限りません。

<h2 id="catalog-source-schema">カタログ取得元の正式 schema</h2>

機械可読な正本は [`catalog-read.ts` の `SelectionSchema` と `SourceSchema`](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/problem-pack/catalog-read.ts)です。起動に使う checkout の定義を確認してください。[`downloaded-catalog.ts`](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/problem-pack/downloaded-catalog.ts) と `git-source.ts` の取得処理で、パス・通信方式・内容も検証します。`scripts/problem-pack/catalog-schema.json` は**問題の metadata** の schema であり、取得元設定の schema ではありません。

| フィールド | 契約 |
| --- | --- |
| `schemaVersion` | 必須。数値の `1` |
| `sources` | 必須。1 件以上の配列。各要素は下記どちらか一方の形 |
| Git 取得元 | 必須の文字列 `url`、空でない文字列 `ref`、任意の文字列 `subdir` |
| ローカル取得元 | `path` だけ。前後の空白を除いて空でない文字列 |

設定全体と各要素は未知のフィールドを拒否します。`type`、`kind`、`branch` はありません。`path` と `url`・`ref`・`subdir` は混在できません。Git 取得は認証なしの HTTPS に限定し、URL 内の認証情報・query・fragment を拒否します。`ref` は branch・tag・`HEAD`・完全な commit を指定し、取得時に不変 commit へ解決します。`subdir` は repository 内の相対パスに限り、絶対パスや `..` は使えません。

ローカルの相対パスは、シェルの作業ディレクトリではなく**設定ファイルのあるディレクトリ基準**です。絶対パスも使えます。`path` はカタログまたは Pack のルートを直接指定し、`subdir` は付けません。private repository は利用者が権限のある方法で事前に clone / checkout し、そのディレクトリを選びます。Git の直接認証取得は未対応です。GitHub Actions やカタログ更新 PR は不要です。

<h2 id="mixed-sources">Git とローカルの混在例</h2>

`config/my-catalogs.json` に保存します。2 つのローカルディレクトリには、公開カタログとも互いにも重複しない問題 ID を用意してください。

```json
{
  "schemaVersion": 1,
  "sources": [
    { "url": "https://github.com/susumutomita/TenkaCloudChallenge.git", "ref": "main" },
    { "path": "../../private-event-problems" },
    { "path": "../../uncommitted-workshop-problems" }
  ]
}
```

TenkaCloud のルートから、まず host 起動・deploy をせずに取得と生成を確認します。

```sh
make catalog-download CATALOG_SOURCES=./config/my-catalogs.json
make catalog-prepare
```

開催準備ができたら起動します。

```sh
CATALOG_SOURCES=./config/my-catalogs.json make local
```

`CATALOG_SOURCES=./config/my-catalogs.json make deploy ENV=development` も同じ snapshot 準備を行い、その後に実際の deploy を行います。実行前に対象・権限・費用を別途確認してください。稼働中の host は自動で切り替わりません。再起動は開催者と調整します。

起動時と `make catalog-download` は取得開始を表示し、全取得元の検証と選択の保存が終わると、取得元ごとに URL または解決済みローカルパス、snapshot digest、問題数を表示します。Git は指定した `ref` と解決済み commit も表示します。URL の認証情報・query・fragment や通信エラーの生データは出しません。最後に選択中の取得元数と合計問題数を表示します。保持済みの過去版はこの合計に含めません。失敗時は明示的に停止を表示し、途中までの取得を成功として案内しません。これらは起動用カタログの取得結果であり、保存済み大会の問題が移行したことを表しません。

<h2 id="metadata-and-snapshots">metadata と不変 snapshot</h2>

既存の `challenges/<id>/metadata.json`、`battles/<id>/metadata.json` の配置、または `tenkacloud-pack.json` に `problemsRoot` を宣言した検証済み SDK Pack を使います。[問題 metadata](/developers/docs/reference/problem-metadata/)と [Pack manifest](/developers/docs/reference/pack-manifest/)の仕様に従ってください。問題リストは既存の探索処理が category/problem ディレクトリの metadata から生成します。`sources` は取得元を選ぶ設定で、問題一覧を手書きするものではありません。生成物の `problems/` に問題を作成しないでください。

取得時に未 commit の編集・追加問題もコピー・検証し、`.tenkacloud/catalog-store/snapshots/<digest>` に保存します。Local と Cloud は選択済みの不変 snapshot を使い、`problems/` は build 用の生成ビューです。ファイル監視や hot reload はありません。ID 重複、必須 metadata・ファイルの欠落や不正、ディレクトリ以外の指定、コピー対象の symbolic link は以前の選択を置き換える前に拒否します。取得元ルート自身の symbolic link も拒否します。

問題専用のディレクトリを使ってください。dot file / directory、`node_modules`・`dist`・`coverage`、credential / secret 名や一般的な秘密鍵ファイルはコピーから除外します。これはファイル名フィルターであり、**内容中の秘密情報を検出する機能ではありません**。必要な hidden asset も除外されるため、名前変更や分離を行って結果を検証します。取得前に全ファイルを確認し、home directory や private repository 全体の無害化には使わないでください。

`selected.json` は digest と解決済み取得元を記録します。ローカル revision の互換用 `commit` は digest の先頭 40 文字で、Git commit ではありません。取得するのは設定した取得元だけで、旧版の自動再取得や別の固定版取得コマンドはありません。既存大会の過去版表示・再開には保存済みの snapshot を使います。環境を移す場合も必要な snapshot store を保持してください。失われた旧版を自動復元する機能はありません。

<h2 id="replace-catalog">問題を追加・入れ替える</h2>

1. 追加なら既存と重複しない問題 ID を使い、取得元の `challenges/<id>/metadata.json` または `battles/<id>/metadata.json` と必要なファイルを用意します。入れ替えなら取得元の URL / `ref` / `path` またはその中の問題定義を変更します。別の取得元を末尾に足しても同じ ID の上書きにはならず、重複として拒否します。
2. `CATALOG_SOURCES` で選ぶ設定を保存します。Git の版を固定するには `ref` を確認済みの完全な commit にします。ローカル編集は `path` から取得し直すまで反映されません。既存大会に必要な retained snapshot は削除しません。
3. 別の確認用 checkout で、前述の `make catalog-download` と `make catalog-prepare` を実行します。metadata・runtime の対応範囲と取得エラーを確認してから、開催者と反映時刻を決めます。ダウンロード成功だけで新しい問題の起動・採点まで完了したとは判断しません。
4. Local は同じ非公開データディレクトリを使って `make down` 後に、同じ `CATALOG_SOURCES` と必要な `LOCAL_ARGS` で `make local` を実行します。独自の `--data` を使う場合は、停止側にも `make down LOCAL_ARGS="--data <同じディレクトリ>"` と指定します。変更を取り込む build を省略しません。新しい大会を作り、その問題を選択して起動・解答・採点・撤収を確認します。保存済みの大会は再起動後も元の snapshot と得点を使い、新しい問題へ自動移行しません。

Cloud は選択後の `make deploy` が別途必要です。これは実 AWS の変更なので、対象・権限・費用を確認し、通常の deploy 手順に従います。既存大会の pin を書き換えたり、問題の入れ替えのために全データを初期化したりしません。取得と保持の根拠は [`downloaded-catalog.ts`](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/problem-pack/downloaded-catalog.ts)、旧大会と新大会の分離は [`downloaded-catalog-http.test.ts`](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/local-host/tests/downloaded-catalog-http.test.ts)で確認できます。別端末から参加させる場合は [Tailscale の前提と接続確認](/developers/docs/getting-started/#tailscale-first-connection)、IP が変わった場合は [待受と URL の更新](/developers/docs/getting-started/#changed-host-ip)も確認します。

<h2 id="runtime-boundary">実行制限と Pack CLI の境界</h2>

カタログとして受理されても、すべての runtime を実行できるわけではありません。Local の native 問題は既存のレビュー済み allowlist を維持し、リモート Docker 問題には対応 Linux の隔離機構が必要です。CloudFormation 問題は Cloud 開催専用で、既存のレビュー済み対応範囲を維持します。Cloud は Docker / Compose を除外します。開催前に対応する問題の解答・採点・撤収を確認してください。metadata の発見だけでは、これらの実行結果を証明しません。

SDK Pack は `make pack-validate ARGS="./my-pack"` で検証します。Pack CLI の `install` / `activate` は別の `.tenkacloud/pack-store` を管理し、現在の `make local` / `make deploy` はその有効化記録を入力に使いません。検証した元ディレクトリを `sources` で指定します。[最初の Pack チュートリアル](/developers/docs/tutorials/first-pack/)も参照してください。

<h2 id="verify-contract">仕様の検証コマンド</h2>

repository の指定ツールと依存関係を用意して実行します。

```sh
bun test scripts/problem-pack/test/local-catalog.test.ts scripts/problem-pack/test/downloaded-catalog.test.ts scripts/problem-pack/test/discover-problems-catalog.test.ts
bun run generate:landing-docs
bun run scripts/landing/generate-landing-docs.ts --check
```

取得テストは Git / local の混在、設定ファイル基準のパス、metadata 探索、不変 revision の保持、不正入力時の選択保持を検証します。AWS deploy や全チームでの大会完遂を実証するものではありません。

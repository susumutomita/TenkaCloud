# Select a problem catalog <MaturityBadge level="preview" />

Start with the [hosting quickstart](/developers/docs/getting-started/#local-start) or [problem author manual](/developers/docs/manual/problem-author/). This page defines the catalog source contract for this checkout. Local-path support is implemented on main and remains a development feature until its revision is released; a deployed site or older checkout may use an earlier contract.

<h2 id="catalog-source-schema">Catalog source schema</h2>

The machine-readable source of truth is [`SelectionSchema` and `SourceSchema` in catalog-read.ts](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/problem-pack/catalog-read.ts). Check these definitions in the same checkout as your launcher. The acquisition checks in [`downloaded-catalog.ts`](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/problem-pack/downloaded-catalog.ts) and `git-source.ts` also validate paths, transport and content. `scripts/problem-pack/catalog-schema.json` describes **problem metadata**, not source selection; do not use it to validate this configuration.

| Field | Contract |
| --- | --- |
| `schemaVersion` | Required number `1` |
| `sources` | Required nonempty array; each entry is exactly one of the two shapes below |
| Git source | Required string `url`, nonempty string `ref`; optional string `subdir` |
| Local source | Only `path`: a nonempty string after trimming whitespace |

Unknown fields are rejected at both the configuration and entry level. There is no `type`, `kind` or `branch` field. Do not combine `path` with `url`, `ref` or `subdir`. Git acquisition accepts unauthenticated HTTPS without embedded credentials, query or fragment; `ref` selects a branch, tag, `HEAD` or full commit and is resolved to an immutable commit. `subdir` must stay inside the repository without an absolute path or `..`.

A local path is resolved from the **configuration file's directory**, not the shell working directory. Absolute paths are accepted. Point `path` directly at the catalog or pack root; a local entry has no `subdir`. Private repositories require an authorized checkout by the user before selecting its directory. Direct authenticated Git acquisition is unsupported. No GitHub Actions or catalog update PR is required.

<h2 id="mixed-sources">Mix Git and local sources</h2>

Save this as `config/my-catalogs.json`. The two local directories must contain distinct problem IDs, also distinct from the public catalog.

```json
{
  "schemaVersion": 1,
  "sources": [
    { "url": "https://github.com/susumutomita/TenkaCloudChallenge.git", "ref": "main" },
    { "path": "../../private-event-problems" },
    { "path": "../../uncommitted-workshop-problems" }
  ]
}
```

From the TenkaCloud root, first validate acquisition and materialization without starting a host or deploying:

```sh
make catalog-download CATALOG_SOURCES=./config/my-catalogs.json
make catalog-prepare
```

Then start a host when ready:

```sh
CATALOG_SOURCES=./config/my-catalogs.json make local
```

`CATALOG_SOURCES=./config/my-catalogs.json make deploy ENV=development` uses the same snapshot preparation and then performs a real deployment. Review the target, permissions and costs separately before running it. These commands do not change the selection of an already running host; coordinate any restart with the organizer.

<h2 id="metadata-and-snapshots">Metadata and immutable snapshots</h2>

Use the existing `challenges/<id>/metadata.json` and `battles/<id>/metadata.json` layout, or a validated SDK pack with `tenkacloud-pack.json` declaring `problemsRoot`. Follow the [problem metadata reference](/developers/docs/reference/problem-metadata/) and [pack manifest](/developers/docs/reference/pack-manifest/). The existing discovery code generates the problem list from metadata in category/problem directories. `sources` selects acquisition roots; it is not a manually maintained problem list. Do not author in generated `problems/`.

At acquisition, local content, including uncommitted edits and added problems, is copied and validated into `.tenkacloud/catalog-store/snapshots/<digest>`. Local and Cloud consume selected immutable snapshots; `problems/` is a generated build view. There is no file watcher or hot reload. Duplicate IDs, invalid/missing required metadata or files, non-directories and included symbolic links fail before replacing the previous selection. The local source root itself must not be a symbolic link.

Use a dedicated problem directory. Copying excludes dot files/directories, `node_modules`, `dist`, `coverage`, credential/secret filenames and common private-key files. This is a filename filter, **not a secret-content detector**. Required hidden assets are also excluded: rename or separate them and validate the result. Review all files before acquisition; do not rely on this filter to sanitize a home directory or private repository.

`selected.json` records a digest and resolved source. For local revisions its compatibility `commit` value is the first 40 digest characters, not a Git commit. Acquisition fetches only configured sources; there is no automatic historical download or separate fixed-edition acquisition command. Existing events read their already stored snapshots. Preserve the required snapshot store when moving an installation; missing history is not automatically restored.

<h2 id="replace-catalog">Add or replace problems</h2>

1. For an addition, use a unique problem ID and provide `challenges/<id>/metadata.json` or `battles/<id>/metadata.json` plus its required files in the source. For a replacement, change the source URL / `ref` / `path` or the problem definition inside it. Appending another source with the same ID fails as a duplicate; it does not override the earlier source.
2. Save the configuration selected by `CATALOG_SOURCES`. Use a reviewed full commit in Git `ref` to pin an edition. Local edits take effect only after reacquiring their `path`. Preserve retained snapshots needed by existing events.
3. In a separate verification checkout, run the `make catalog-download` and `make catalog-prepare` commands above. Check metadata, runtime support and acquisition errors before agreeing an adoption window with the organizer. Successful acquisition does not prove the new problem starts or scores correctly.
4. For Local, preserve the same private data directory, run `make down`, then `make local` with the same `CATALOG_SOURCES` and required `LOCAL_ARGS`. For a custom `--data`, also stop with `make down LOCAL_ARGS="--data <same-directory>"`. Keep the build enabled to incorporate the change. Create a new event, select the problem, and check startup, answers, scoring and teardown. Saved events retain their original snapshots and scores after restart; they do not migrate to the new problem automatically.

Cloud requires a separate `make deploy` after selection. It changes real AWS resources: review the target, permissions and costs and follow the normal deployment procedure. Do not rewrite existing event pins or reset all data to replace a problem. See [`downloaded-catalog.ts`](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/problem-pack/downloaded-catalog.ts) for acquisition/retention and [`downloaded-catalog-http.test.ts`](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/local-host/tests/downloaded-catalog-http.test.ts) for old/new event separation. For remote participation, also check [Tailscale prerequisites and connectivity](/developers/docs/getting-started/#tailscale-first-connection) and [binding/URL updates after an IP change](/developers/docs/getting-started/#changed-host-ip). That Tailscale section requires client and local `tailscaled` 1.104.4 or newer, with SSH forwarding disabled on the event host.

<h2 id="runtime-boundary">Execution and Pack CLI boundaries</h2>

Catalog acceptance does not enable every runtime. Local native execution retains its reviewed problem allowlist; remote Docker exercises require supported Linux isolation. CloudFormation problems require Cloud hosting and retain their existing reviewed support boundary. Cloud excludes Docker/Compose. Validate participant solving, scoring and teardown for each supported problem before an event; metadata discovery alone proves none of those runtime outcomes.

`make pack-validate ARGS="./my-pack"` validates an SDK pack. Pack CLI `install` and `activate` manage a separate `.tenkacloud/pack-store`; those activation records are not the input to current `make local` or `make deploy`. Select the original validated directory through `sources` instead. See the [first pack tutorial](/developers/docs/tutorials/first-pack/).

<h2 id="verify-contract">Verify this contract</h2>

With the repository's pinned tools and installed dependencies, run:

```sh
bun test scripts/problem-pack/test/local-catalog.test.ts scripts/problem-pack/test/downloaded-catalog.test.ts scripts/problem-pack/test/discover-problems-catalog.test.ts
bun run generate:landing-docs
bun run scripts/landing/generate-landing-docs.ts --check
```

The source tests cover mixed Git/local acquisition, configuration-relative paths, metadata discovery, immutable retention and invalid-input rollback. They do not perform an AWS deployment or prove a complete multi-team event.

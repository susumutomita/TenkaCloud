# Competition organizer manual <MaturityBadge level="preview" />

This documents the unpublished integration candidate. Local event/team operation is implemented; cloud platform deployment and complete catalog playability are not verified release claims.

<h2 id="prepare-local-host">Prepare the local host</h2>

Follow [getting started](/developers/docs/getting-started/) with `make local`. Keep one process per private data directory. Bootstrap a local Admin; Operator can run events and Viewer can inspect them. Keep a local password Admin available when using optional SAML.

<h2 id="run-the-event">Run the event</h2>

Create teams and select problems, prepare dormant Docker jobs, inspect failures, then start the schedule. Participants start each Docker environment when needed; AWS deployment remains a separate operation. Distribute each team's invitation only to that team. Rehearse correct and incorrect submissions, hints, scores, one team's failure, restart and teardown. End Event stops scoring; it does not prove resources were removed.

All 106 former local problems are intended to become Challenge competitions. Generic catalog/workbench work is in progress; terminal access and complete real Docker/browser verification remain incomplete. Use the actual selected problem's evidence, not its presence in a picker, to decide event readiness.

<h2 id="aws-problems">Optional AWS problems</h2>

`make local LOCAL_ARGS="--aws-region ap-northeast-1"` enables the reviewed AWS adapters. Obtain approval for credentials, target accounts, resources and cleanup before live use. Register each competitor account, download `templates/competitor-bootstrap.yaml` from the console, use the displayed operator account, exact role name and persisted ExternalId, then verify the account. The bootstrap AdministratorAccess exception must not spread to participant roles.

`hello-world` uses flag scoring. `hello-world-battle` requires both endpoint registrations and readiness before uptime scoring. Both healthy means +100 per cycle; either failing means -100. Disruptions need their own revert and health check. Existing AWS sessions may outlive event end.

<h2 id="storage-and-shutdown">Storage and shutdown</h2>

The local database is SQLite. Back up the complete private data directory consistently, including key files. `make down` preserves event data and stopped Docker state; use the same data directory on restart. New on-demand Docker environments stay stopped after `make local` until a participant resumes them. It does not delete AWS resources or reset the event clock. Never delete state that still owns environments.

Cloud Turso is in progress; `make deploy` and `make destroy` currently fail without changing resources. A zero-fixed-cost cloud platform has not been established. AWS exercise charges are separate.

Historical SaaS/Lite and individual-practice instructions are available in the [pinned legacy source](https://github.com/susumutomita/TenkaCloud/tree/825415fcda5075ad723daf9e4514eac47d7b8bb9). Do not use them against this candidate or assume data migrates automatically.

New Docker events prepare dormant team/problem jobs, up to 512 per event. Participants use **Start / resume** and **Stop (keep data)**. Stop retains the existing writable layer and volumes, not RAM; there is no automatic eviction or reset. Existing events retain their legacy lifecycle.

Defaults allow 3 active environments per team, 12 across the host and a 4096 MiB sum of configured container-memory caps. These are admission limits, not measured usage or machine-size guarantees. New Compose plans preserve authored caps and add 512 MiB memory, 1 CPU and 256 PIDs where missing. Override admission limits with `make local LOCAL_ARGS="--max-active-per-team 3 --max-active-environments 12 --container-memory-mib 4096"` after reviewing the workload.

The 40 gateway slots apply only to active environments. Dense runtime-port assignments survive Stop. A synthetic 20-problem × 5-team plan allocated 100 jobs using 105 runtime ports; this proves allocation and lifecycle behavior, not concurrent Docker performance. See `docs/local-play-requirements.md` for measurement guidance.

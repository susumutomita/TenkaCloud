# Competition organizer manual <MaturityBadge level="preview" />

Use this manual when you deploy TenkaCloud, prepare an event, invite people, or
change an environment setting. You do not need to understand the platform's
source code or write a problem pack.

## Your goal

An organizer can open the Admin Console, each participant can open the correct
Participant Portal, and every problem can be started, scored, and stopped.

## Choose the operating mode first

| Mode | Choose it when… | Command |
| --- | --- | --- |
| Lite | One organizer runs one TenkaCloud environment | `make deploy ENV=<environment>` |
| SaaS | A platform operator serves multiple tenant organizations | `make deploy-saas ENV=<environment>` |

Start with Lite unless you are deliberately operating a multi-tenant service.
For the complete deployment paths, read
[Deploy modes and launch paths](/developers/docs/operate/deploy-paths/).

## The event checklist

1. Choose a dedicated AWS account and region.
2. Create `infrastructure/environments/<environment>/.env` from that
   environment's `.env.example`.
3. Fill the required account and administrator values.
4. Choose the control-data database before the first real event.
5. Deploy, open the Admin Console, and confirm the invited organizer account.
6. Create the event, teams, and problem selection.
7. Rehearse start, endpoint access, flag scoring, reset, and stop with a test
   team.
8. Send participants only the Participant Portal URL, team key, start time, and
   [participant manual](/developers/docs/manual/participant/).

The complete console workflow is in
[Run an event end to end](/developers/docs/operate/run-an-event/).

## Where settings live

Environment settings live in:

```text
infrastructure/environments/<environment>/.env
```

The selected environment comes from `ENV`. For example:

```bash
make deploy ENV=development
make deploy ENV=production
```

Changing `.env` does not update a running environment by itself. Review the
change, then run the appropriate deploy command. Keep credentials and tokens
out of Git.

### Required identity settings

| Setting | Meaning | When to set it |
| --- | --- | --- |
| `TENANT_ADMIN_EMAIL` | First Lite organizer invitation | Lite; falls back to `SYSTEM_ADMIN_EMAIL` |
| `SYSTEM_ADMIN_EMAIL` | SaaS system administrator invitation | SaaS |
| `AWS_ACCOUNT_ID` | Guard against deploying to the wrong AWS account | Recommended for every environment |
| `AWS_REGION` | AWS region for the deployment | Set when the AWS CLI default is not the intended region |

## Choose the control-data database

Control data means event definitions, teams, deployments, endpoints, competitor
accounts, disruptions, audit logs, and SAML identity-provider records. It is not
the participant's problem environment.

| Value | Storage | Choose it when… |
| --- | --- | --- |
| unset or `dynamodb` | AWS DynamoDB | You want the default AWS-native path |
| `turso` | Turso/libSQL | You explicitly want the zero-DynamoDB Lite profile |

Set the backend with:

```dotenv
CDK_PARAM_CONTROL_DATA_BACKEND=dynamodb
```

For Turso, all three settings are required:

```dotenv
CDK_PARAM_CONTROL_DATA_BACKEND=turso
CDK_PARAM_TURSO_DATABASE_URL=https://<database>-<organization>.turso.io
CDK_PARAM_TURSO_AUTH_TOKEN_PARAMETER_NAME=/TenkaCloud/<environment>/turso/auth-token
```

The token itself must be stored as an AWS Systems Manager Parameter Store
`SecureString`. Never paste it into `.env`. The guided setup is:

```bash
make turso-live ENV=development
```

### Do not treat switching as a checkbox

- DynamoDB and Turso do not synchronize data.
- Choose the backend before the first real event whenever possible.
- Switching an existing stack from DynamoDB to Turso starts from the data
  available in the Turso database.
- The existing DynamoDB tables use `RETAIN`. CloudFormation can remove them
  from the stack without deleting them, so they can continue to incur cost.
- Export and verify required data before switching. Review retained tables
  manually only after the new environment is confirmed.
- Switching back to DynamoDB cannot recover writes that existed only in Turso.

The Turso path is implemented and covered by unit and CDK synth tests, but it
has **not yet been live-verified** against a real Turso database, fresh AWS
deployment, and resulting bill. Read [Running costs](https://github.com/susumutomita/TenkaCloud/blob/main/docs/running-costs.md)
before relying on it for an event.

## Common parameters

Leave a setting unset unless you can explain the operational result.

| Setting | Default | What it changes |
| --- | --- | --- |
| `DYNAMODB_BILLING_MODE` | `PROVISIONED` | DynamoDB billing mode; `PAY_PER_REQUEST` is also supported |
| `DYNAMODB_READ_CAPACITY` / `DYNAMODB_WRITE_CAPACITY` | `1` / `1` | Provisioned capacity; only used with `PROVISIONED` |
| `CDK_PARAM_LOG_RETENTION_DAYS` | `1` | CloudWatch Logs retention; only AWS-supported values are accepted |
| `CDK_PARAM_OPS_ALERT_EMAIL` | unset | Creates operations alert resources when an address is provided |
| `CDK_PARAM_OPS_MONTHLY_COST_LIMIT_USD` | unset | Monthly cost threshold used with operations alerts |
| `CDK_PARAM_SOURCE_BUCKET_VERSIONING` | `false` | Enables or suspends source bucket versioning |
| `CDK_PARAM_DEPLOY_QUOTA_BY_TIER` | unset | Per-tier concurrent deploy limits as JSON |
| `CDK_PARAM_DEPLOY_ALLOWED_CIDRS` | unset | Comma-separated ingress allowlist for compatible problems |
| `CDK_PARAM_DEPLOY_VIA_LAMBDA` | `true` | Uses Lambda for problem deploys; `false` selects the legacy CodeBuild path |
| `CDK_PARAM_FEATURES` | unset | Boolean feature map as JSON |
| `CDK_PARAM_AUDIT_LOG_ENABLED` | `true` | Enables the admin audit log |

The environment's `.env.example` is the parameter catalog. It documents
accepted values and interactions next to each setting; copy only the settings
you intend to override.

## Before participants arrive

- Use a test team with the same permissions and region as participants.
- Confirm every endpoint opens from the expected network.
- Submit one real flag and confirm the score changes.
- Reset and stop a problem, then confirm resources are gone.
- Check the event clock, team key delivery, support contact, and incident path.
- Do not send AWS administrator credentials, `.env`, or database tokens to
  participants.

If you need to change how a parameter works in the source code, switch roles
and use the [developer manual](/developers/docs/manual/developer/).

# はじめに <MaturityBadge level="preview" />

未公開の統合 candidate の手順です。ローカルの大会・チーム運用は実装されていますが、クラウド基盤の配置や全カタログのプレイ確認が完了した公開版ではありません。

<h2 id="local-start">ローカル競技を起動する</h2>

Git、Make、Bun 1.4.4 と確認対象の checkout を用意します。macOS または Linux（WSL2 を含む）が対象です。Docker 問題には Docker Engine と Compose が必要です。リポジトリのルートで実行します。

```sh
git clone https://github.com/susumutomita/TenkaCloud.git
cd TenkaCloud
make install
make local
```

`make local` は起動前に `catalog-sources.json` の Git 取得元（URL と `ref`）またはローカル取得元（`path`）から問題を取得します。既定は TenkaCloudChallenge の `main` で、この Git 取得にはネットワーク接続が必要です。取得に失敗すると起動を中止します。`make deploy` も同じ選択を使います。保存済みの大会は取得時の不変 snapshot を使い続けます。`problems/` は生成される build 用ビューで、Git submodule ではありません。作問用 branch を使う場合は設定の `ref` を変更します。設定と取得処理は [catalog-sources.json](https://github.com/susumutomita/TenkaCloud/blob/main/catalog-sources.json) と [downloaded-catalog.ts](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/problem-pack/downloaded-catalog.ts) で確認できます。

既定の開催者 URL は `http://127.0.0.1:5174`、参加者 URL は `http://127.0.0.1:5175` です。実際にはプロセスが表示した URL を使います。主催者キーだけでログインし、ユーザー名・パスワードは使いません。対話ターミナルで `make local` を起動するたびに新しいキーを一度だけ表示し、以前の主催者キーとログインを失効させます。起動中の再発行は、別の対話ターミナルで同じデータディレクトリを指定して `make local-reset` を実行します。大会・得点・参加者キー・問題のデータを保持します。非対話起動と public/container 起動では既存のキーを保持し、ログにキーを出力しません。

<h2 id="connect-from-another-device">別の端末から参加する</h2>

既定の loopback URL は同じ PC でだけ開けます。信頼できる隔離ネットワーク上で参加者へ接続させる場合は、host に割り当て済みの IPv4 を明示します。以下の `100.96.12.34` は説明用なので、実際のアドレスへ置き換えてください。Tailscale の `100.64.0.0/10` 内の IPv4 も受け付けます。VPN や権限をこのコマンドで設定することはありません。

```sh
make local LOCAL_ARGS="--lan 100.96.12.34 --unsafe-lan"
```

開催者は host 自身の `http://127.0.0.1:5174` を開きます。参加者へは `http://100.96.12.34:5175` と、そのチームのキーを渡します。参加者側で `127.0.0.1` を開くと参加者自身の端末へ接続するため、host には届きません。主催者キーは参加者へ渡さないでください。

`--unsafe-lan` は HTTP での待受への同意です。アプリ自身が TLS を提供するわけではありません。上の LAN 起動では、Docker を使わない native 問題（例: Crypto Battle）を利用できます。Docker / Compose 問題の開始・再開・復旧は、専用の隔離モードがないと `network_isolation_required` で拒否します。Mac / Docker Desktop はこの隔離モードに未対応です。同じ PC の loopback 演習は従来どおり利用できますが、専用 guard による隔離の保証はありません。

別端末から Docker 問題を使うには、対応する native Linux 上で `--competition-network` と、LAN / VPN の経路と重ならない `--docker-network-pool` を明示する必要があります。Docker 28.4.x、rootful のローカル daemon、firewall / nsenter の権限などの前提を満たさなければ拒否します。[guard の前提](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/local-host/linux-network-guard.ts)を先に確認してください。単に LAN の待受 IP を指定しても、firewall や VPN の設定を自動で変更しません。

Mac や隔離モードを使えない環境で、全員を信頼できる仲間内の開催に限り、`--unsafe-docker-lan` を足すと別端末から Docker 問題を使えます。

```sh
make local LOCAL_ARGS="--lan 100.96.12.34 --unsafe-lan --unsafe-docker-lan"
```

このフラグは `--lan <ip> --unsafe-lan` と一緒にしか指定できません。`--competition-network`、`--vpn-peers`、公開 origin とは組み合わせられず、起動前に拒否します。このときの Docker 演習にはチーム間のネットワーク隔離がありません。ほかのチームの演習、host、LAN に到達できるため、信頼できる参加者だけで使ってください。認証とチームごとのデータ分離は変わりません。分離ありで準備した大会はこのフラグでも分離なしに開始・再開・復旧せず、`network_isolation_required` で拒否します。新しい大会を作ってください。起動時には、この警告を `LAN HTTP is unencrypted` の警告に続けて表示します。

非隔離の Docker unit が保存されている場合は、停止状態でも LAN host の起動を listener 開始前に拒否します。既存 job / unit を自動停止・移行することはありません。`--unsafe-docker-lan` を付けて起動した場合は、非隔離の unit があっても起動できます。そうでなければ、主催者と保守時間を決め、元の loopback host で必要なデータを保存して対象環境を停止・削除してから、隔離環境を新規作成します。稼働中の host をそのまま更新・再起動しないでください。

この制約は演習コンテナの境界です。Tailscale 接続だけで参加者端末全体の通信や端末間アクセスを制限することはありません。HTTPS 構成、VM からの実通信、多人数での競技開催は、この手順で検証済みとは扱いません。

初回は build を省略しません。すでに同じコードと選択カタログで build 済みの場合だけ `--no-build` を追加できます。未 build またはカタログ不一致で起動を拒否されたら、次の起動で省略せずに build します。稼働中の host を変更する場合は、開催者と停止・再開の時刻を決めてから進めます。

<h2 id="tailscale-first-connection">Tailscale 未接続の端末から参加する</h2>

専用開催端末だけを共有する手順です。参加者を会社の tailnet 全体へ加入させる前提ではありません。会社所属の PC や既存サービスを、所有者・管理者の承認なしに共有しないでください。以下は承認後に行う確認用手順で、共有経路を含む実機リハーサルは未完了です。Docker の別端末利用には、前述の native Linux 隔離条件も必要です。

**主催者の準備**

1. 共有を許可された専用端末を用意し、[公式ダウンロード](https://tailscale.com/download)から Tailscale 1.104.4 以降を導入します。開催用に承認されたアカウントでログインし、選択中の tailnet、開催端末名、自 IPv4 を記録します。端末では `tailscale ip -4` と `tailscale status` で照合できます。`tailscale version --daemon` でクライアントと手元の `tailscaled` が 1.104.4 以降であることを確認します。VM なら VM 自身の IP を使います。
2. 参加者と、共有を受けるログイン方法・アカウント・参加者自身の tailnet を事前に確認します。共有の発行・承認には、それぞれの tailnet の Owner / Admin / IT admin 権限が必要です。個人用と会社用がある場合、同じ名前でも選択先を確認します。
3. 開催側と参加側の管理者が [grants](https://tailscale.com/docs/features/access-control/grants) / [ACL](https://tailscale.com/docs/features/access-control/acls) の有効な許可をレビューします。共有先ユーザーから専用開催端末への TCP 5175 を対象にし、Docker の演習 gateway を使う場合だけ、設定した `--gateway-ports` の TCP 範囲も対象にします。既定は 5200–5239 です。5174、SSH、不要なサービスや生のコンテナ port は許可しません。既存の広い許可が残っていれば、狭い許可を追加するだけでは制限できません。招待ユーザーを含む allow-all は、[Tailscale 1.104.4、転送の無効化とポリシー](#tailscale-client-security) に従って置き換えます。
4. 管理画面の Machines で開催端末の名前と IP を確認し、Share → Copy invite link → Copy share link から、参加者ごとに単発の招待を発行します。再利用リンクは選びません。招待リンクは接続権を与えるため、本人にだけ渡します。共有は端末へのアクセスを渡す仕組みで、単一 port の公開保証ではありません。[共有の公式仕様](https://tailscale.com/docs/features/sharing)を確認してください。

**初参加者の準備と接続**

1. 自分の端末へ公式アプリを導入します。iPhone は [公式 iOS 手順](https://tailscale.com/docs/install/ios)に従い、VPN 構成を許可して、事前に決めた自分のアカウントでログインします。会社のログイン情報を主催者から受け取る必要はありません。
2. 主催者から受け取った招待を開き、ブラウザのログイン方法・アカウント・承認先 tailnet を確認して承認します。アプリでも、その共有を受けた同じアカウント / tailnet を選び、Connected を確認します。別の tailnet に切り替わっている場合は続行せず、選択先を照合します。
3. 一覧から主催者が伝えた開催端末名を探し、共有された IP を確認します。自分のスマホの IP、別の Mac、古い登録を接続先にしないでください。共有端末は別 tailnet にあっても表示されるため、単に IP が見えるだけで所属が同じとは判断できません。
4. その IP と host の起動ログに出た参加者 URL を照合し、`http://<開催端末のIPv4>:5175/` を開きます。この LAN 手順は IP による Host / Origin 検査を使うため、MagicDNS 名の URL に置き換えません。共有時の IP 競合で受信側に別 IP が割り当てられた場合も、そのまま進めず主催者へ確認します。

**共有後の確認と競技終了**

主催者は Host Console を `127.0.0.1:5174` のままにし、参加者用に forward / proxy しません。参加者にはチームキーだけを渡します。大会開始前は参加端末で 5175 の画面とログインまでを確認します。gateway は使用中のものだけ listen するため、範囲全体に常時応答するわけではありません。

管理者は有効な policy の検査・テストで、5175 と使用する gateway の許可、5174 と不要なサービスの不許可を確認します。native 問題だけなら gateway の許可は不要です。ポートの許可、Tailscale の端末共有、演習コンテナの Linux guard、アプリのチームキー認証は別の境界です。共有しただけで演習や参加者 PC 全体が隔離されるとは扱いません。

PC の参加端末では、承認済みの開催端末だけを次のように確認できます。例の IP は実際の開催端末へ置き換えます。

```sh
EVENT_HOST_IP=100.96.12.34
curl --fail "http://${EVENT_HOST_IP}:5175/healthz"
nc -vz -w 3 "$EVENT_HOST_IP" 5175
nc -vz -w 3 "$EVENT_HOST_IP" 5174
```

health は `status: ok` / `role: participant`、5175 は接続成功、5174 は接続不可を確認します。スマホでは同じ `/healthz` をブラウザで開けます。5174 の接続失敗だけでは ACL の証明にならないため、管理者は policy テストも確認します。gateway は実際に発行された URL と使用中の port を確認し、未起動の port の無応答を障害と扱いません。

全員の接続を確認してから大会を開始します。native 問題は操作と得点、Docker 問題はポータルが発行した gateway URL から自チームの演習への接続を確認します。正答・誤答・ヒントは対応する問題で確認します。終了時は End Event で採点を止め、必要な結果を保存します。環境を残すなら Stop (keep data) で停止し、主催者が保守手順に沿って host を停止します。削除を選ぶ場合は Teardown の対象とデータ消去を先に確認します。

最後に主催者が対象端末の Share 画面から対象者の Revoke invite を実行し、未使用の招待も取り消します。Share 画面で対象者と未使用招待が失効したことを確認します。参加者の再接続失敗は補助確認です。host 停止による接続失敗だけでは共有失効の証明になりません。これは共有の失効で、他人の端末本体を削除する操作ではありません。再参加には新しい招待と承認が必要です。受信側の解除メニューは実画面の対象・影響を確認してから使い、一般の Remove machine と混同しません。

<h2 id="tailscale-client-security">Tailscale 1.104.4、転送の無効化とポリシー</h2>

TenkaCloud は Tailscale を導入しません。このリポジトリのコンテナーイメージ、導入スクリプト、IaC でも版を固定しません。開催端末と参加者の端末へ [1.104.4 以降](https://tailscale.com/changelog)を入れてください。`tailscale version` はクライアントを表示します。`tailscale version --daemon` は手元の `tailscaled` も表示します。両方を 1.104.4 以降にします。この版で [TS-2026-014](https://tailscale.com/security-bulletins)、[TS-2026-015](https://tailscale.com/security-bulletins)、[TS-2026-016](https://tailscale.com/security-bulletins)、[TS-2026-017](https://tailscale.com/security-bulletins) が修正されています。Tailscale の説明は [Tailscale SSH: Findings and fixes](https://tailscale.com/blog/tailscale-ssh-findings-fixes) です。

文書どおりの参加経路は TCP 5175 の HTTP です。設定した gateway の範囲は、Docker 演習の使用中だけ追加します。Tailscale SSH は無効のままにします。`tailscale set --ssh` の既定は無効です。有効になっている場合は `tailscale set --ssh=false` を実行します。開催端末では、`tailscaled` のサービス環境に `TS_SSH_DISABLE_FORWARDING=1` を設定し、参加者を接続させる前に `tailscaled` を再起動します。[TS-2026-014](https://tailscale.com/security-bulletins) は、Unix ソケットの転送が root で実行され、許可された対向が Docker ソケットや `tailscaled` の local API など root 専用ソケットへ到達できた、と報告しています。この環境変数は Tailscale SSH 自体を止めずに転送を止めます。再起動の間は tailnet が切れます。復帰後に `tailscale ip -4` を再度照合します。`tailscale serve` を Docker ソケットや local API ソケットへ向けず、`TS_SERVE_ALLOW_ALL_INTERFACES` は未設定のままにします。

文書どおりの手順は Tailscale SSH も Tailscale Serve も有効にしません。上の 4 件の対象は、名前のある機能を有効にしたノードです。開催端末が Docker ソケットを持つことはあり、後から SSH を有効にすると TS-2026-014 の条件に入ります。大会の前に版と転送の環境変数を揃えます。

転送を止めると、Tailscale SSH の `ssh -L`、`ssh -R`、Unix ソケット転送、エージェント転送は使えなくなります。この手順はそれらを使いません。開催者が自分の管理作業で転送を使っている場合は、変数を外すまで使えません。

systemd では drop-in に変数を書き、再読み込みして再起動します。他の導入方法では、`tailscaled` を起動する環境に同じ変数を入れて、そのサービスを再起動します。

```ini
# /etc/systemd/system/tailscaled.service.d/50-disable-ssh-forwarding.conf
[Service]
Environment=TS_SSH_DISABLE_FORWARDING=1
```

```sh
sudo systemctl daemon-reload
sudo systemctl restart tailscaled
```

共有は、相手に見せる端末を共有した端末に限る仕組みです。その端末のどの port が応答するかは tailnet の policy が決めます。既定の policy は全 port を許可します。狭い grant を足すだけでは、残っている広い許可は消えません。専用の開催 tailnet では allow-all を置き換え、`autogroup:shared` には TCP 5175 だけを渡します。Docker の gateway を使うときだけ TCP 5200–5239 も足します。開催者自身の通信は `autogroup:admin` のような別の grant に残します。参加者向け、および開催端末の tag 向けの `ssh` 規則は足しません。Tailscale は、共有された tag 付き端末へ、SSH 規則と port 22 の両方が許すときに SSH できる、と説明しています。既定の SSH の宛先 `autogroup:self` は変えないでください。

```json
{
  "grants": [
    {
      "src": ["autogroup:admin"],
      "dst": ["*"],
      "ip": ["*"]
    },
    {
      "src": ["autogroup:shared"],
      "dst": ["*"],
      "ip": ["5175"]
    }
  ]
}
```

`ip` にポート番号だけを書くと TCP です。書き方は [共有の公式例](https://tailscale.com/docs/features/sharing) に合わせています。Docker gateway を使うときだけ、共有側の `ip` に `"5200-5239"` を足します。この断片は完全な policy ではありません。既定の `ssh` 規則の `dst` は `autogroup:self` のままにし、招待ユーザーを含む `*` や `*:*` の許可を消し、[policy test](https://tailscale.com/docs/reference/syntax/policy-file) で招待ユーザーの `:22` と `:5174` が拒否され `:5175` が許可されることを確認します。`autogroup:member` は、宛先端末がそのユーザーへ共有されているとき、招待ユーザーも含みます。

このリポジトリは headscale を導入も設定もしません。大会の制御プレーンには Tailscale を使います。上記の bulletin は、修正済み headscale の版を示していません。[headscale 0.29.6 の changelog](https://github.com/juanfont/headscale/blob/main/CHANGELOG.md)（2026-10-24）は、Tailscale の Go 依存を v1.102.0 へ上げた記録があり、TS-2026-014 から TS-2026-017 には触れていません。この依存は制御サーバーのライブラリです。ノードは自分の Tailscale クライアントで動作します。公開されている [Tailworm の報告](https://tailworm.com/) は Tailscale の bulletin ではありません。報告は、headscale 0.29.5 では受理した SSH セッションに転送が付き、policy で転送を切れないと述べ、そのサーバーの認証前の可用性の問題も記述しています。headscale 側が修正を出すまで、headscale 上で Tailscale SSH を許可しないでください。Tailscale 1.104.4 以降のノードでも、クライアントの更新と `TS_SSH_DISABLE_FORWARDING=1` は必要です。

<h2 id="changed-host-ip">開催端末の IP が変わったとき</h2>

`--lan` は起動時に指定した IPv4 に固定され、Tailscale の端末登録や tailnet を変えても自動追従しません。主催者は開催端末自身の `tailscale ip -4`、選択中の tailnet、共有先で見える端末名と IP を再照合します。参加者自身の IP や、共有時の競合で割り当てられた別 IP を bind 先に使いません。共有先だけ別 IP の場合は、この IP ベースの手順の対応範囲外として接続を止め、管理者と経路を確認します。

保守時間を決め、データを保持する `make down` の後、正しい IPv4 を `--lan` に指定して `make local` を起動します。`--data`、`CATALOG_SOURCES`、隔離・gateway の必要なオプションは元の設定を確認して引き継ぎ、build は省略しません。独自の `--data` を使う場合は、停止側にも `make down LOCAL_ARGS="--data <同じディレクトリ>"` と指定します。これらは主催者が確認して実行する操作です。IP のために `local-clear` やデータ削除を行う必要はありません。

起動ログの新しい `http://<開催端末のIPv4>:5175/` を参加者へ再配布し、`/healthz`、ログイン、使用する gateway を再確認します。主催者は引き続き `http://127.0.0.1:5174` を使います。IP に依存する共有・許可の有効範囲は管理者が別途レビューし、Tailscale や OS の設定を起動コマンドが修正するとは扱いません。待受と URL の根拠は [`options.ts`](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/local-host/options.ts) と [`server.ts`](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/local-host/server.ts)です。

<h2 id="check-local-connection">起動と接続を確認する</h2>

host 上で開催者画面、参加者の端末で参加者画面の HTTP 応答を確認します。別端末の例の IP は実際の host の IP へ置き換えます。

```sh
# host 上で実行
curl --fail --silent --output /dev/null --write-out '%{http_code}\n' http://127.0.0.1:5174/
# 参加者の端末で実行
curl --fail --silent --output /dev/null --write-out '%{http_code}\n' http://100.96.12.34:5175/
```

どちらも `200` を確認してから、ブラウザでログイン画面を開きます。応答がない場合は、起動ログの URL、指定 IP が host にあること、端末間の既存の接続経路を確認します。HTTP 応答だけではログイン・採点・問題環境への接続は確認できません。次の大会手順で正答・誤答と得点も確認してください。

この説明の実装根拠は [options.ts](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/local-host/options.ts) 、[server.ts](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/local-host/server.ts)、[LAN の engine 構成](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/local-host/application.ts)、[Docker の拒否条件](https://github.com/susumutomita/TenkaCloud/blob/main/scripts/local-host/docker-engine.ts) です。開発時の回帰確認は次を実行します。待受アドレスと origin、隔離なしの LAN 演習の拒否、取得失敗・snapshot と build の整合性のテストであり、実際のネットワーク隔離の証明ではありません。

```sh
make catalog-download catalog-prepare
bun test scripts/local-host/tests/public-mode.test.ts scripts/local-host/tests/catalog-startup.test.ts scripts/local-host/tests/lan-isolation.test.ts
```

<h2 id="first-event">大会を作成して参加する</h2>

1. 開催者コンソールで大会、チーム、出題する問題を選びます。
2. jobs を準備し、チームごとの結果を確認します。新しい Docker jobs は参加者が起動するまで停止状態です。AWS 問題は配置手順を使います。
3. Schedule から大会を開始し、各チームへ参加者 URL とチームキーを渡します。
4. 参加者ポータルへそのキーで入ります。Docker は **Start / resume** で起動し、問題文、操作、得点まで確認します。使い終えた環境は **Stop (keep data)** で停止します。

開催者と参加者が使う一つの競技システムです。個人練習専用のログインはありません。Docker カタログと workbench の復旧は進行中です。現行 26 問が一覧に出ることと、terminal や実 Docker のブラウザ操作まで全問確認済みであることは別です。

<h2 id="stop-and-resume">データを消さず停止・再開する</h2>

同じ checkout の別端末で実行します。

```sh
make down
make local
```

`make down` は管理対象のローカルプロセスと所有する Docker 環境を止め、DB、得点、キー、Docker のデータを保持します。大会の終了や AWS 問題 stack の削除は行いません。`make local` 後も、新しいオンデマンドの Docker jobs は参加者が再開するまで停止したままです。書き込みレイヤーと volume は保持しますが、RAM は保持しません。再起動しても大会の時刻はリセットされません。End Event は採点を止め、環境の teardown は所有する環境を削除します。削除が完了するまでデータディレクトリを消さないでください。

起動オプションは `LOCAL_ARGS` へ渡します。例は `make local LOCAL_ARGS="--no-build"` です。`--data` を指定した場合、`make down` にも同じディレクトリを指定します。

`make local-clear` は host を停止してから、確認後に競技データと所有する Docker 問題データを消去します。主催者キーと host 設定は保持します。`make down` はデータを保持して停止し、`make local-reset` は主催者アクセスを再発行します。

<h2 id="cloud-setup">クラウド開催を設定する</h2>

使う AWS CLI のプロファイルを選び、`aws sts get-caller-identity` で確認します。`make env-init ENV=development` を実行して、開催者のメールアドレス・配置先アカウント ID・リージョンを入力します。選択した `.env` がなければ作成します。既存ファイルの設定を変える場合は編集してください。

Turso は `make turso-live ENV=development` で CLI の導入・ログイン・DB の作成・SSM へのトークン保存・認証検証を進め、配置前に確認します。DynamoDB は `env-init` の後で `make deploy ENV=development` を実行します。`make turso-live-guide` で手順を表示でき、`make turso-token-rotate ENV=development` でトークンを表示せずに再発行できます。期限を設定する場合は `ROTATE_ARGS="--expiration 30d"` を指定し、期限前に更新してください。前提条件・プロファイルの選択・各確認事項は、checkout の `infrastructure/README.md` に記載しています。

<h2 id="cloud-status">クラウド配置の状態</h2>

`make deploy` と `make destroy` は権限設定を確認したうえで、この版の Lambda + Turso/DynamoDB CLI を実行します。クラウド開催は Lambda・Cognito と選択した Turso / DynamoDB で、汎用 CloudFormation 配置、flag / multi-flag・定期採点、参加者の Console / CLI アクセス、Cryptography Battle などの組み込み coordination を実行します。撤収時に対象を確認し、基盤の所有データはデフォルトで削除します。通常の `make destroy` は外部 Turso の行を残し、`make destroy-all` で明示的にリセットします。問題環境の撤収は別操作です。Lambda + Turso/DynamoDB によるクラウド開催は検証中で、費用ゼロを保証していません。AWS サービスの問題はクラウド開催専用です。Docker / Compose 問題はローカル開催専用で、クラウドのカタログには表示しません。実 AWS・hosted Turso での大会性能は未検証です。cloud pipeline は現行 CLI を既定で使います。build を始める前にソース設定と配置 role を確認してください。

<h2 id="codespaces-native">Codespaces の転送 URL で native 問題を試す</h2>

Codespaces 内の `make local` は、`CODESPACES=true`、端末名 `CODESPACE_NAME`、転送ドメイン `GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN=app.github.dev` を検証し、指定した各 port から完全一致の HTTPS origin を作ります。既定は `https://<端末名>-5174.app.github.dev` と `https://<端末名>-5175.app.github.dev` です。起動ログの URL を使います。明示した `--public-admin-origin` / `--public-participant-origin` は優先し、片方だけの指定や不正な環境値は拒否します。明示 LAN・VPN・console appliance の経路は切り替えません。通常の Mac / Linux は従来どおり主催者画面を loopback に保ちます。

これは既存の native public mode を使い、Codespace 内では両 listener が `0.0.0.0` になります。Ports の 5174 は Private のまま、主催者本人の GitHub 認証と TenkaCloud 主催者キーで開きます。public 起動のログにはキーを出しません。キーを取得する場合は別の非共有対話ターミナルで `make local-reset` を実行し、独自 `--data` なら同じディレクトリを指定します。この操作は主催者キーを再発行し、古い主催者セッションを失効させます。参加者には 5175 とチームキーを使います。port visibility は自動変更せず、共有や公開の判断は別途必要です。`--behind-proxy` の X-Forwarded-For 信頼も自動では有効にしません。

public mode では Docker / Compose 問題を提供しません。初期化の Bun 導入は [README](https://github.com/susumutomita/TenkaCloud/blob/main/README.ja.md)を参照してください。転送 origin・認証拒否・URL 配信はローカル fixture で検証しましたが、実 Codespaces の proxy、browser、再起動、多人数開催は未検証です。Codespace の停止・保存制限も確認してください。[公式 port 転送](https://docs.github.com/en/codespaces/developing-in-a-codespace/forwarding-ports-in-your-codespace)と [lifecycle](https://docs.github.com/en/codespaces/about-codespaces/understanding-the-codespace-lifecycle)を参照します。

次は[開催者マニュアル](/developers/docs/manual/organizer/)、[参加者マニュアル](/developers/docs/manual/participant/)、[配置の境界](/developers/docs/operate/deploy-paths/)です。


### ローカルの問題ディレクトリを使う

`catalog-sources.json` の `sources` には、Git の `{ "url": "https://…", "ref": "main" }` とローカルの `{ "path": "../TenkaCloudChallenge" }` を混在できます。複数のローカルディレクトリも指定できます。相対 path はこの設定ファイルが置かれたディレクトリを基準に解決し、絶対 path も受け付けます。private Git は、利用者が通常の方法で取得した checkout を path に指定します。TenkaCloud に credential を設定する必要はありません。Git の直接取得は従来どおり認証なしの HTTPS です。

```json
{
  "schemaVersion": 1,
  "sources": [
    { "path": "../TenkaCloudChallenge" },
    { "path": "../private-event-problems" }
  ]
}
```

問題ごとの `metadata.json` が一覧の正本です。独立した問題一覧は編集しません。既存の `challenges/<id>/metadata.json` と `battles/<id>/metadata.json` の構造、または `tenkacloud-pack.json` の `problemsRoot` を使います。README などの通常ファイルは問題として列挙しません。必要なメタデータ・ファイルの欠損、無効値、ディレクトリ名と ID の不一致、source 間を含む ID 重複はエラーです。別 repository の同じ ID を上書きする用途には使えません。

`make local` と `make deploy` の準備は、編集・追加した未コミットのファイルも含めて検証済み snapshot を作り、その固定版を使います。元の作問ディレクトリは変更しません。取得・検証に失敗したら以前の選択を保持し、起動・build を中止します。保存済み大会の定義を途中で更新せず、稼働中 host の自動更新・再起動もしません。変更を取り込む次回起動は build を省略しないでください。

問題専用のディレクトリを指定し、実 credential を教材へ置かないでください。取得時は `.git` を含む dot entry（`.dockerignore` や `.htaccess` も対象）、`node_modules`、`dist`、`coverage`、`credentials` / `secret` 系のファイル名、秘密鍵の一般的な拡張子を除外します。これは任意の名前・本文に含まれる秘密の検出ではありません。教材に必要なファイルまで除外される場合は、秘密と分離した名前・構成に直して検証します。source 自身と含まれる symlink、特殊ファイルは拒否し、外部へたどりません。retained snapshot は作問元を再読込せず検証します。local の `commit` 欄は content digest の先頭40桁による内部 ID で、Git commit ではありません。snapshot store を移さず local の lock だけ別環境へコピーして復元することはできません。

別の設定ファイルを使う場合は `CATALOG_SOURCES=./config/my-catalogs.json make local`、deploy 準備は `CATALOG_SOURCES=./config/my-catalogs.json make deploy ENV=development` の形式です。後者は通常の実 deploy を含むので、対象・費用・権限を確認して実行します。取得だけの確認には `make catalog-download CATALOG_SOURCES=./config/my-catalogs.json`、続いて `make catalog-prepare` を使います。保存済みの Git snapshot を補うため、local のみの選択でも既存 lock に Git の retained revision があればネットワーク取得が必要です。

新規クラウド環境の stack 名は `tenkacloud-cloud` 系です。既存の `tenkacloud-lite` 系 stack は名前を維持します。CLI は Lite / cloud の既存 stack を検出し、両方ある場合は `TENKACLOUD_STACK_LAYOUT=lite` または `cloud` の明示指定が必要です。旧 Lite の更新は所有情報と永続 resource ID を検証します。 catalog pin のない旧 Lite 環境は、resource / schema の検査後、bootstrap・source upload・配置の前に、進行中の大会がないことを初回だけ明示確認します。開催中の大会は完了まで配置済みの版で継続してください。大会が残っていないことを運用者が確認してから対話で承認し、非対話の更新には `CLOUD_ARGS="--confirm-no-active-events"` を使います。通常の `--yes` ではこの確認を省略できません。legacy catalog key だけでは安全な更新を証明できず、過去のデータも自動移行しません。新規環境と復旧済み環境は通常の `make deploy` で自動配置します。公開 cloud-v1 の resource / DB schema への上書き更新は拒否し、データは自動移行しません。`--drain-events` は使えません。問題環境を大会の Teardown で撤収してから基盤を削除してください。

両 DB とも 99 チーム、SQL coordination は旧 4 MiB 上限です。現行 catalog の 8 template はすべて `TemplateBody` の 51,200 bytes 以内で、`TemplateURL` は未実装です。全 AWS 問題の配置確認済みを意味しません。
